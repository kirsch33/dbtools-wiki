Sandbox Integration Guide

The Sandbox previews tool windows and validates a staged product candidate without starting Revit. It runs one fresh process per candidate year.

Candidate loading

The BCL-only Sandbox entry validates a year directory before Core-backed logging, Presentation, or WPF startup:

DBTools.addin
DBTools.dll
DBTools.Core.dll
DBTools.Presentation.dll
DBTools.HandyControl.dll
Tools/DBTools.<Tool>.dll

It checks the .addin, exact file set, PE identities, assembly locations, and supported year. It then loads the candidate's top-level product images and manifest-declared tool images from their actual paths in the default context. The entry uses a non-inlined boundary to start WPF after candidate loading and exits after validation. Do not add a Loader, Bootstrap, embedded payload, runtime manifest, or DBTools-owned load context to make Sandbox work.

Register a window

Declare the window in the tool's manifest.yml:

sandboxWindows:
  - id: DBTools.MyTool.Main
    displayName: "My Tool"
    group: "Common"
    xamlResource: "DBTools.ToolViews.MyTool.MyToolView.xaml"
    windowKind: Modal
    designTimeViewModelType: "DBTools.MyTool.App.DesignTime.MyToolDesignTimeViewModel"
    designTimeViewModelAssembly: "DBTools.MyTool"
    designTimeViewModelVisibility: Public

The xamlResource value must match the owning project's embedded logical name:

<EmbeddedResource Include="App\Views\MyToolView.xaml">
  <LogicalName>DBTools.ToolViews.MyTool.MyToolView.xaml</LogicalName>
</EmbeddedResource>

The required fields are `id`, `displayName`, `group`, `xamlResource`,
`windowKind`, `designTimeViewModelType`, `designTimeViewModelAssembly`, and
`designTimeViewModelVisibility`. Optional fields include width, height, minimum sizes,
taskbar visibility, startup location, and tool-specific grouping metadata. Keep the
manifest as the single owner of these values; do not infer a window type from a filename.

For example, a tool with two raw views can declare separate stable ids while sharing one
design-time state type:

```yaml
sandboxWindows:
  - id: DBTools.MyTool.Main
    displayName: "My Tool"
    group: "Common"
    xamlResource: "DBTools.ToolViews.MyTool.MainView.xaml"
    windowKind: Modal
    width: 1200
    height: 700
    minWidth: 900
    minHeight: 500
    startupLocation: CenterScreen
    designTimeViewModelType: "DBTools.MyTool.App.DesignTime.MyToolDesignTimeViewModel"
    designTimeViewModelAssembly: "DBTools.MyTool"
    designTimeViewModelVisibility: Public


Sandbox copies manifest values into local specifications and opens the raw view
through `DBTools.Presentation.ToolWindows.ToolWindowHost`. It does not activate
a candidate `Window` type by reflection. Raw views have no `x:Class`,
code-behind, payload pack URI, event attribute, payload BAML, or implicit
payload template. Use explicit templates, selectors, and display paths for
bound content.

## Runtime ownership

Presentation owns stable WPF shells, themes, resources, and
`ToolWindowCallbackScope`. Core and tool assemblies remain candidate-owned and
are loaded from the year tree. Sandbox does not invoke App's Revit startup and
does not load Revit reference DLLs as executable product files.

## Archive and validation

Distribution archives are year-keyed even though both years target the same TFM:

```text
.artifacts/sandbox/<configuration>/<year>/<tfm>/
sandbox/<year>/<sanitized-tfm>/

Portable checks validate raw XAML, manifest ownership, metadata, and recursive file fingerprints. Native WPF layout, binding, theme, and window cleanup require the Windows acceptance process. A live daemon Dev Mode inject/reload remains a separate operational proof.

Design-time ViewModels

The manifest's designTimeViewModelType and designTimeViewModelAssembly are validated against the candidate tool image. The type must be public, concrete, and have a public parameterless constructor. Keep design-time construction independent of Revit documents, external events, network services, and production settings.

public sealed class MyWindowDesignTimeViewModel
{
    public MyWindowDesignTimeViewModel()
    {
        Rows = [new MyRow("Example", "Preview")];
    }

    public IReadOnlyList<MyRow> Rows { get; }
}

Use explicit state and commands in the design-time graph. A small NoOpCommand is appropriate for a display-only action whose behavior is outside the validation surface; do not hide a production command failure behind a design-time double. If a design-time fixture needs an analyzer suppression, keep it on the narrow declaration and explain the actual WPF or generated-code reason.

Raw XAML is the stable boundary. It must use the exact logical resource name, avoid x:Class, code-behind event attributes, payload CLR namespaces, inferred columns, and implicit payload templates. Bind visible text, headers, items, and tooltips explicitly. The stable Presentation host owns themes, resources, window lifecycle, and the callback scope; a tool owns its candidate view resource and design-time ViewModel.

Local commands

Build the candidate before running the Sandbox:

./build.sh AssembleDistributionCandidate -y 2026
./build.sh AssembleDistributionCandidate -y 2027

Without --dist-dir, interactive validation opens the published Release tree. Pass --dist-dir to select a candidate:

dotnet run --project src/DBTools.Sandbox/DBTools.Sandbox.csproj \
  -- --dist-dir .artifacts/dist/candidate/2026

Headless validation avoids creating windows while preserving candidate checks:

dotnet run --project src/DBTools.Sandbox/DBTools.Sandbox.csproj -- \
  --headless --dist-dir .artifacts/dist/candidate/2026 \
  --revit-reference-dir /path/to/Revit2026

The supported options are --dist-dir (or --dist-dir=<path>), --revit-reference-dir (required with --headless, rejected without it), and --headless. Blank values are rejected. An absent or ambiguous year directory fails before Core, Presentation, or WPF loads. Run one fresh process per candidate year; do not reuse a process after changing the candidate tree.

Validation checks and troubleshooting

The validation sequence is deliberately ordered:

  1. Parse the year and candidate directory.
  2. Validate .addin, required top-level files, recursive Tools/ files, PE identities, and supported target framework.
  3. Load candidate App/Core/Presentation/HandyControl and declared tool images from their actual default-context paths.
  4. Validate embedded manifests, raw XAML logical names, design-time ViewModels, and stable resource ownership.
  5. Construct native windows, exercise layout and interactions, capture binding errors, close windows, and verify Dispatcher cleanup.

Common failures have direct owners:

Failure Check
Tool window resource missing Match xamlResource to the owning project's LogicalName.
ViewModel cannot be created Make the declared type public, concrete, and parameterless.
Binding errors Inspect the binding listener output and bind display state explicitly.
Candidate file mismatch Rebuild the selected year and compare the recursive product listing.
Revit reference mismatch Pass the matching installed year directory; reference files are metadata evidence.
Window cleanup failure Close the window and allow its Dispatcher cleanup to complete before process exit.

The Sandbox process does not prove Revit startup, daemon ProductLoadContext sharing, or Dev Mode reload behavior. Those remain separate coordinator-owned Windows/daemon proofs.

Tool examples

GM uses multiple sandboxWindows entries that point to raw logical resources and tool-owned design-time ViewModels. SGT follows the same pattern for its raw views. A new tool should copy the manifest shape, add explicit raw resources and ViewModels, and add the owning Pure validation fixture before requesting native evidence.
