Modularity

Tools use Core for execution, transactions, settings, logging, and window lifecycle. Presentation owns stable WPF shells, controls, resources, and themes. Tool assemblies own feature behavior, raw views, and ViewModels.

Use constructor injection inside services. Resolve the first workflow from ICommandContext at the command boundary. Creating New Tools describes assembly ownership and module registration.

Service lifetimes

The application service root lasts for one runtime generation. A command or modeless session owns a run scope for Revit-dependent services.

Service Lifetime Purpose
ISafeExecutor Singleton Error policy, logging, and notifications at entrypoints.
IAlertService Singleton Alert and selection dialogs.
ISettingsProvider Singleton Fresh typed reads and atomic batch commits.
ToolRegistry Application runtime Command and hook registrations.
IRevitRunScope Scoped Current Revit application and document access.
IRevitCallGate Scoped Synchronous API callbacks in a valid Revit context.
ITransactionRunner Scoped Transactions for model changes.
ITransactionGroupService Scoped Group health and commit/rollback.

Use ILogger<T> through injection and context.Logger at command boundaries. The application logging host owns logger lifetime.

Keep Document, UIDocument, and run-scope references within their command or session lifetime. Pass operation-specific document inputs or obtain verified current state from the run scope. Dispose the command/session scope only after its owned work and cleanup finish.

Safe execution

DBTools.Core.SafeExecution.Domain.ISafeExecutor defines two boundaries:

Task RunAsync(
    Func<Task> action, ILogger logger, IErrorNotifier? notifier,
    SafeExecutionOptions opts, CancellationToken ct = default);

Task<SafeExecutionResult> RunWithoutThrowingAsync(
    Func<Task> action, ILogger logger, IErrorNotifier? notifier,
    SafeExecutionOptions opts, CancellationToken ct = default);

RunAsync propagates failures. RunWithoutThrowingAsync records an explicit outcome for a caller that must contain failure, such as a Revit event callback. Both provide correlation IDs, timing, cancellation admission, exception logging, and configured notifications. ToolCommand already owns this boundary. Let workflow failures reach it.

SafeExecutionOptions requires an operation name:

var options = new SafeExecutionOptions("Inspect Model")
{
    BannerMode = SafeExecutionOptions.Mode.ErrorOnly
};
await executor.RunAsync(InspectAsync, logger, notifier, options, ct);
Option Default Effect
LogStart true Log entry.
LogCompletion true Log completion.
LogFailure true Log a failed operation.
BannerMode SuccessAndError Show success/error banners, errors only, or neither.
FailureSurface Surface Surface fatal errors through the configured failure surface.
CorrelationId Unspecified Supply an existing execution correlation ID.

ErrorBanner(name, logStart, logCompletion) selects error-only banners. SuppressFailurePresentation(name) suppresses banners, fatal presentation, and routine start/completion logs while retaining failure logging. Disable LogFailure only when an already-published lifecycle owner observes and logs that same fault. Preserve the failed Task.

App composition adapts the UI-owned log surface to ISafeExecutionFailureSurface. Window error boundaries use IWindowErrorLogSurface and WindowErrorPresenter. Consumers depend on these contracts rather than constructing concrete logger or notification windows.

Use structured log fields:

logger.LogInformation("Processing {Count} elements in {Document}", count, document.Title);
logger.LogError(exception, "Inspection failed for {Document}", document.Title);

Use IAlertService for user decisions and IErrorNotifier for banners. Propagate failures through the safe-execution boundary with their context.

Revit run scopes and call gates

IRevitRunScope exposes UIApplication, CallGate, GetActiveUiDocument(), GetActiveDocument(), and GetVerifiedActiveDocument(expectedDocument, context). The verification method checks validity and DocumentSessionKey equality before returning the active document. Use the verification method before operating on a retained document.

Run profile Gate Use
InlineUi InlineRevitCallGate Commands already executing in a valid Revit API callback.
QueuedModeless QueuedRevitCallGate Modeless work through the App-owned ExternalEvent host.

The gate accepts synchronous callbacks:

Task RunAsync(Action<UIApplication> work,
    CancellationToken ct = default, RevitCallGateMode mode = RevitCallGateMode.Auto);
Task<T> RunAsync<T>(Func<UIApplication, T> work,
    CancellationToken ct = default, RevitCallGateMode mode = RevitCallGateMode.Auto);

Await the returned Task outside the callback. Do not pass async lambdas into the gate. Async-state-machine Actions and known Task/ValueTask result shapes are rejected before execution. An awaitable hidden in object or an interface is rejected after the callback runs. Side effects remain. Custom awaiters are outside this check.

A Revit API callback's context applies to its synchronous prefix. An async continuation must acquire a valid gate again before using the Revit API. InGate reports execution within a gate callback. It does not make arbitrary background work safe.

On normal host retirement, pending queued work is dropped and its Tasks remain pending, even if cancellation arrives later. Shutdown must not await these Tasks. Failed-startup cleanup cancels pending work instead. See Revit execution for the full callback and shutdown contract.

Transactions

ITransactionRunner wraps synchronous model modifications:

Task RunInActiveDocumentAsync(string name,
    Action<RevitTransactionContext> action, CancellationToken ct = default);
Task<T> RunInActiveDocumentAsync<T>(string name,
    Func<RevitTransactionContext, T> action, CancellationToken ct = default);
Task RunInDocumentAsync(Document doc, string name,
    Action<RevitTransactionContext> action, CancellationToken ct = default);
Task<T> RunInDocumentAsync<T>(Document doc, string name,
    Func<RevitTransactionContext, T> action, CancellationToken ct = default);

Use transaction.Document inside the callback:

await transactions.RunInDocumentAsync(document, "DB Tools - Set Mark", transaction =>
{
    var element = transaction.Document.GetElement(elementId);
    element.LookupParameter("Mark").Set(mark);
}, ct);

The runner selects a SubTransaction when the document is modifiable and a new Transaction otherwise. It enforces document context and applies TransactionFailurePreprocessor. The callback rules match the call gate: no async Actions or Task/ValueTask results. Give each transaction a descriptive undo name.

Transaction groups

ITransactionGroupService groups several transactions into one undo operation:

bool IsActive { get; }
Task BeginAsync(string name, CancellationToken ct = default);
Task FinalizeAsync(TransactionGroupFinalization finalization,
    CancellationToken ct = default);
Task<bool> IsGroupHealthyAsync(CancellationToken ct = default);

Finalize with TransactionGroupFinalization.Commit to assimilate the group or Rollback to discard it. IsGroupHealthyAsync returns true when no group exists and false when an active group has lost its healthy started state.

The session/workflow owner must finalize on success, failure, and cancellation. Use a separate cancellation token for cleanup when the operation is canceled. Attempt all owned cleanup and retain both the operation and finalization errors. Do not use an unguarded finally exception that hides the operation's failure. Long-lived tool sessions also own the ordering of persistence, window closure, group finalization, and scope disposal.

Alerts and selection

IAlertService exposes request-based dialogs:

AlertResult Show(AlertRequest request);
bool Confirm(string message, IWindowOwnerHandleProvider ownerHandleProvider,
    string title = "DB Tools");
T? SelectSingle<T>(AlertSelectionRequest<T> request) where T : class;
IReadOnlyList<T> SelectMultiple<T>(AlertSelectionRequest<T> request) where T : class;

Confirmation requires an owner provider. In a command:

var alerts = context.Resolve<IAlertService>();
if (!alerts.Confirm("Delete the selected elements?", context.OwnerHandleProvider))
    return;

Selection requests supply choices, a display function, window title, header, and owned window options. For example:

var selected = alerts.SelectSingle(new AlertSelectionRequest<Level>(
    levels, level => level.Name, "Select Level", "Target Level",
    new AlertWindowOptions(context.OwnerHandleProvider))
{
    Message = "Choose the target level."
});

Core owns selection policy, body construction, and typed result extraction.

Settings

Inject ISettingsProvider and the typed SettingsSection<T>. Call Get(section) at the operation boundary for a fresh snapshot. Reads layer appsettings.json and the current per-year user file. Commit one or more section writes as a batch:

var options = settings.Get(section);
options.AutoUpdateEnabled = true;
await settings.CommitAsync(new[] { section.CreateWrite(options) }, ct);

Do not retain a settings snapshot in a singleton when subsequent operations need saved changes. Settings Packs owns DTO restrictions, source-generated metadata, file locking, save timing, and post-commit errors.

Shared UI resources

DBTools.Presentation.ThemeBrushKeys exposes ComponentResourceKey values. Use dynamic resources so the window's theme supplies each brush:

<Border xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:theme="clr-namespace:DBTools.Presentation;assembly=DBTools.Presentation"
        Background="{DynamicResource {x:Static theme:ThemeBrushKeys.Surface}}">
    <TextBlock Text="Inspection"
               Foreground="{DynamicResource {x:Static theme:ThemeBrushKeys.Body}}" />
</Border>

Keys cover brand, surface, text, status, and DataGrid brushes. Use the actual members in ThemeBrushKeys.cs and tokens in Resources/Tokens.xaml. Do not invent string keys or duplicate color values. Window-scoped resources avoid changing another add-in's theme. See the Theme System.

Merge the stable Presentation theme into a raw view through ResourceUri:

<Grid xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
      xmlns:resources="clr-namespace:DBTools.Presentation.Resources;assembly=DBTools.Presentation">
    <Grid.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <ResourceDictionary Source="{resources:ResourceUri Resources/Theme.xaml}" />
            </ResourceDictionary.MergedDictionaries>
        </ResourceDictionary>
    </Grid.Resources>
</Grid>

ResourceUri selects the loaded Presentation assembly's versioned resource URI. Keep raw views on stable resources rather than constructing payload pack URIs.

Design tokens

Resources/Tokens.xaml defines spacing, padding, corner radius, and typography. Use the token with the property type it expects:

Token Type and value
Spacing4, Spacing8, Spacing16 Thickness values of 4, 8, and 16.
Spacing4.Value, Spacing8.Value, Spacing16.Value Double values for scalar properties.
Pad8, Card.Padding Thickness values of 8 and 16,12.
ButtonGap Thickness 8,0,0,0: space before each button after the first in a row.
MinHeight.Button Double value of 36: the height of action buttons and the controls in their row.
Radius4, Radius8 CornerRadius values of 4 and 8.
FontSize.Body, FontSize.Title, FontSize.Header Double values of 13, 16, and 20.

Tool-window sessions

A raw tool view uses framework or stable Presentation types. It has no Window root, x:Class, code-behind event attributes, tool CLR namespaces, payload BAML, or implicit templates for tool types. Bind display values explicitly.

Core's ToolWindowFactory installs the theme, owner, icon, error boundary, and progress lifecycle before parsing. It registers the session for normal closure and runtime-generation retirement:

using var xaml = new MemoryStream(ToolWindowXaml.ReadEmbeddedResource(
    typeof(MyToolWindowViewModel).Assembly,
    "DBTools.ToolViews.MyTool.MyToolWindow.xaml"));
var session = factory.Create(ToolWindowKind.Modal, xaml, viewModel,
    new ToolWindowOptions { Title = "My Tool", Width = 800, Height = 600 });
_ = session.ShowDialog();

Use ToolWindowKind.Modeless and session.Show() for a modeless surface. Register payload handlers and owned cleanup through the session. A custom initializeShell callback owns the initializer it creates and must register its disposal through session.AddCleanup.

Normal close dispatches payload Closed handlers before releasing owned state. Retirement of an open session also clears its view graph. Keep the application run scope alive through failure-bearing session completion. Window.Close() alone does not establish that asynchronous cleanup finished.

Presentation owns shells and ToolWindowCallbackScope. Core and tool assemblies can belong to a replaceable product generation. Stable controls and resources must not retain a retired ViewModel, callback, or tool type. This contract also applies to Settings, alerts, logger windows, banners, and progress UI.

Sandbox Integration covers previews and native WPF validation. Hooks covers subscriptions that also need generation-safe shutdown.
