Leveraging DBTools Modularity

DBTools is designed as a modular Revit add-in platform where tools share common infrastructure while maintaining clear boundaries. This guide explains how to use DBTools.Core services and DBTools.Presentation WPF resources without crossing the stable/collectible boundary.

Philosophy

DBTools follows these modularity principles:

  1. Shared Infrastructure, Independent Tools - Core services are centralized; tools are self-contained
  2. Dependency Injection First - All services are resolved through DI, enabling testing and flexibility
  3. Contract-Driven - Interfaces define contracts; implementations can vary per context
  4. Error Handling at Boundaries - All entrypoints run inside ISafeExecutor
  5. Window-Scoped Theming - Each window owns its theme resources to avoid cross-add-in conflicts
  6. Composition Owns Concrete UI Services - Core window initialization attaches shared contracts, while App startup supplies concrete notification features such as WindowErrorNotifier; UI window error boundaries and logger-window error relay sinks depend on the UI-owned IWindowErrorLogSurface contract rather than the full logger-window shell implementation, WindowErrorBoundaryPresenter owns handled-error banner/log-surface presentation outside the dispatcher boundary host, and view-activated hooks consume IErrorNotifier from DI instead of constructing concrete notification feature types inside Core hook gates

Two-Tier DI Architecture

DBTools uses a two-tier dependency injection model:

Tier Lifetime Purpose Examples
Singleton Application lifetime Infrastructure services ISafeExecutor, IAlertService, ISettingsProvider, ToolRegistry
Scoped Per-command lifetime Revit context services ITransactionRunner, IRevitCallGate, IRevitRunScope

Shared Services from DBTools.Core

ISafeExecutor

The central error handling service. All tool entrypoints must execute within ISafeExecutor.

public interface ISafeExecutor
{
    Task RunAsync(Func<Task> action, ILogger logger, IErrorNotifier? notifier,
        SafeExecuteOptions opts, CancellationToken ct = default);
    Task<SafeExecutionResult> RunWithoutThrowingAsync(Func<Task> action, ILogger logger,
        IErrorNotifier? notifier, SafeExecuteOptions opts, CancellationToken ct = default);
}

What it provides:

  • Correlation IDs for log tracing
  • Execution timing
  • Exception logging with full stack traces and inner exceptions
  • Cancellation admission immediately before caller work, inside the existing cancellation boundary
  • Diagnostic formatting through the internal SafeExecution/Runtime/ExceptionDiagnosticsLogger; SafeExecutor retains policy, notification, and propagation decisions
  • User notification via banners
  • Fatal-error surfacing through the execution-owned ISafeExecutionFailureSurface; App composition adapts the UI-owned log surface's show action without making Logging depend on SafeExecution
  • Banner success/error presentation and notifier-failure logging inside the retained SafeExecutor execution boundary
  • Explicit failure-policy split: RunAsync(...) rethrows, while RunWithoutThrowingAsync(...) is the named opt-in path for callers that intentionally suppress propagation after logging/notifying

Source: src/DBTools.Core/SafeExecution/Runtime/SafeExecutor.cs:59-103 Source: src/DBTools.Core/SafeExecution/Runtime/ExceptionDiagnosticsLogger.cs:11-211

Usage in a command:

// Commands automatically use ISafeExecutor via ToolCommand base class
[Transaction(TransactionMode.Manual)]
public sealed class GmCommand : ToolCommand
{
    protected override Task RunAsync(ICommandContext context)
    {
        Guard.NotNull(context, nameof(context));
        var uiapp = context.UIApplication
                    ?? throw new InvalidOperationException("[SpecFail/GM/UIAppMissing] UIApplication is required.");
        var logger = context.Resolve<ILogger<GmCommand>>();
        var loggerWindowManager = context.Resolve<ILoggerWindowHost>();

        // Build a lightweight document fingerprint for resume staleness checks
        string? docKey = null;
        try
        {
            var doc = uiapp.ActiveUIDocument?.Document;
            if (doc != null)
            {
                var path = doc.PathName;
                var title = doc.Title;
                docKey = !string.IsNullOrWhiteSpace(path) ? path : title;
            }
        }
        catch (System.Exception ex)
        {
            logger.LogWarning("[GM] Failed to compute DocumentKey: {Message}", ex.Message);
        }

        // Launch GM UI
        ShellLauncher.Launch(context, docKey);

        loggerWindowManager.ShowIfDebugModeOrEnableForPendingError();
        return Task.CompletedTask;
    }

    protected override SafeExecuteOptions CreateExecuteOptions(Autodesk.Revit.UI.ExternalCommandData commandData)
    {
        return new SafeExecuteOptions
        {
            Name = "Global Mapper",
            // Launching the GM window is not a "user-completed" operation; avoid a success banner on open.
            BannerMode = SafeExecuteOptions.Mode.ErrorOnly
        };
    }
}

ITransactionRunner

Unified API for executing Revit model modifications with automatic transaction management.

public interface ITransactionRunner
{
    Task RunInActiveDocumentAsync(string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInActiveDocumentAsync<T>(string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
    Task RunInDocumentAsync(Document doc, string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInDocumentAsync<T>(Document doc, string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
}

Key behaviors:

  • Auto-selects transaction type: SubTransaction if doc.IsModifiable, otherwise new Transaction
  • Cross-document protection
  • Failure handling with TransactionFailurePreprocessor

Usage example:

public class FoundationTypeOrganizer
{
    private readonly ITransactionRunner _tx;
    
    public FoundationTypeOrganizer(ITransactionRunner tx, Document doc, ILogger logger)
    {
        _tx = tx;
        // ...
    }
    
    public async Task OrganizeAsync()
    {
        await _tx.RunInDocumentAsync(_doc, "Organize Foundation Types", tx =>
        {
            var doc = tx.Document;
            // Modify document - transaction is automatic
        });
    }
}

ITransactionGroupService

Manages transaction groups for operations requiring multiple transactions to appear as a single undo item.

public interface ITransactionGroupService
{
    bool IsActive { get; }
    Task BeginAsync(string name, CancellationToken ct = default);
    Task FinalizeAsync(TransactionGroupFinalization finalization, CancellationToken ct = default);
    Task<bool> IsGroupHealthyAsync(CancellationToken ct = default);
}

Usage for batch operations:

public class TdvService
{
    private readonly ITransactionRunner _tx;
    private readonly ITransactionGroupService _group;
    
    public TdvService(IRevitCallGate gate, ITransactionRunner tx, 
        ITransactionGroupService group, ILogger<TdvService> logger)
    {
        _tx = tx;
        _group = group;
        // ...
    }
    
    public async Task ApplyMultipleChangesAsync()
    {
        var commitGroup = true;
        await _group.BeginAsync("Batch Apply");
        try
        {
            // Multiple transactions appear as one undo item
            await _tx.RunInActiveDocumentAsync("Step 1", tx => { /* ... */ });
            await _tx.RunInActiveDocumentAsync("Step 2", tx => { /* ... */ });
            await _tx.RunInActiveDocumentAsync("Step 3", tx => { /* ... */ });
        }
        catch
        {
            commitGroup = false;
            throw;
        }
        finally
        {
            await _group.FinalizeAsync(commitGroup, CancellationToken.None);
        }
    }
}

IAlertService

Service for showing alert dialogs with various body types.

public interface IAlertService
{
    AlertResult Show(AlertRequest request);
    bool Confirm(string message, string title = "DB Tools");
    T? SelectSingle<T>(AlertSelectionRequest<T> request) where T : class;
    IReadOnlyList<T> SelectMultiple<T>(AlertSelectionRequest<T> request) where T : class;
}

Usage examples:

// Simple confirmation
var alerts = context.Resolve<IAlertService>();
if (alerts.Confirm("Delete 15 elements?", "Confirm Delete"))
{
    // Proceed
}

// Single selection
var selectedLevel = alerts.SelectSingle(new AlertSelectionRequest<Level>(
    levels,
    level => level.Name,
    "Select Level",
    "Target Level")
{
    Message = "Choose the level to place elements on"
});

// Multiple selection
var selectedTypes = alerts.SelectMultiple(new AlertSelectionRequest<FamilySymbol>(
    familyTypes,
    t => t.Name,
    "Select Types",
    "Types to Process"));

Selection dialog request construction and typed result extraction live behind the Core-owned selection dialog policy; concrete selection-list body composition is a Core alert-body factory responsibility, and consumers still use the IAlertService request-object API.

ILogger

DBTools uses Microsoft.Extensions.Logging with Serilog as the provider.

// Resolve from DI
var logger = context.Resolve<ILogger<MyService>>();

// Or use the context's logger
var logger = context.Logger;

// Structured logging
logger.LogInformation("Processing {Count} elements in {Document}", 
    elements.Count, doc.Title);

logger.LogWarning("[GM] Failed to compute DocumentKey: {Message}", ex.Message);

logger.LogError(ex, "[{Command}] execution failed.", GetType().Name);

Important: Always use structured logging with named placeholders, not string interpolation.

IRevitRunScope

Represents a single Revit run scope (command, modeless session, or test). Owns UIApplication, the call gate, document access, and disposal; scoped transaction services are resolved from IAppRunScope or ICommandContext with Resolve<T>().

public interface IRevitRunScope : IDisposable
{
    UIApplication UIApplication { get; }
    IRevitCallGate CallGate { get; }
    UIDocument GetActiveUiDocument();
    Document GetActiveDocument();
    Document GetVerifiedActiveDocument(Document expectedDocument, string? context = null);
}

The verification operation is current-state based: callers retain an expected document only as a session identity and receive the active document only after validity and DocumentSessionKey equality are established.

Run Scope Profiles:

Profile Use Case Description
InlineUi Modal commands, daemon-hosted Revit automation Executes directly on Revit UI thread
QueuedModeless Long-running/modeless tools Uses the App-owned ExternalEvent host

ISettingsProvider

Typed settings access with persistence. Each read combines application defaults and the current per-year file.

public interface ISettingsProvider
{
    TSettings Get<TSettings>(SettingsSection<TSettings> section)
        where TSettings : class, new();
    Task CommitAsync(IReadOnlyCollection<SettingsSectionWrite> writes,
        CancellationToken ct = default);
}

Use SettingsSection<T>.CreateWrite(value) to build a typed batch. The provider commits the complete batch with one file swap, so consumers never observe a partially saved settings-window operation.

Usage:

// Via ISettingsProvider (singleton)
var settings = context.Resolve<ISettingsProvider>();
var section = context.Resolve<SettingsSection<GmSettings>>();
var gmSettings = settings.Get(section);

Tool-window sessions

Tool UI uses raw embedded XAML without x:Class or code-behind. Its root is a stable view element such as Grid; ToolWindowHost supplies the modal or modeless shell. Core's ToolWindowFactory installs the theme, owner, icon, error boundary and progress lifecycle before parsing, then registers the session for normal close and generation retirement.

using var xaml = new MemoryStream(ToolWindowXaml.ReadEmbeddedResource(
    typeof(MyToolWindowViewModel).Assembly, "DBTools.ToolViews.MyTool.MyToolWindow.xaml"));
var session = factory.Create(ToolWindowKind.Modal, xaml, viewModel,
    new ToolWindowOptions { Title = "My Tool", Width = 800, Height = 600 });
_ = session.ShowDialog();

Use ToolWindowKind.Modeless and session.Show() for a modeless surface. Register payload event handlers and owned cleanup through the session. A custom shell initializer owns its cleanup handle and must register it with session.AddCleanup.

DI Patterns

Creating a Tool Module

Every tool implements ToolModule to register its services:

public sealed class GmToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        Guard.NotNull(services, nameof(services));
        Guard.NotNull(manifest, nameof(manifest));
        services.AddGm();  // Extension method for cleaner registration
    }
}

ToolModule Base Class

public abstract class ToolModule
{
    public virtual void RegisterSettings(IServiceCollection services, 
        ToolManifest manifest) { }
    
    public virtual void RegisterServices(IServiceCollection services, 
        ToolManifest manifest) { }
    
    public virtual void RegisterSettingsPacks(IServiceCollection services, 
        ToolManifest manifest) { }
    
    public virtual void RegisterHooks(ToolRegistry registry, 
        ToolManifest manifest) { }
}

After a module registers settings, services, settings packs, and hooks into temporary startup surfaces, Core validates that the manifest owns at least one concrete responsibility: ribbon tools, settings, settings packs, or hooks. Ribbon registration construction also belongs to Core once App startup resolves the concrete Revit command and availability types.

Best Practices

1. Always Use ISafeExecutor at Entrypoints

// DO: Inherit from ToolCommand (uses ISafeExecutor internally)
public sealed class MyCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        // ISafeExecutor wraps this automatically
    }
}

// DON'T: Create IExternalCommand without error handling
public class BadCommand : IExternalCommand
{
    public Result Execute(...) 
    {
        // No error handling - will crash Revit
    }
}

2. Prefer Scoped Services for Revit-Dependent Code

// DO: Scoped registration for services that need Revit context
services.AddScoped<IElementNameQuery, ElementNameQuery>();
services.AddScoped<FamilyScanner, FamilyScanner>();

// DON'T: Singleton for services that capture Document references
services.AddSingleton<IBadService, ServiceThatHoldsDocument>();  // Memory leak!

3. Use Transaction Services, Not Raw Transactions

// DO: Use ITransactionRunner
await _tx.RunInActiveDocumentAsync("Create Wall", tx =>
{
    Wall.Create(tx.Document, curve, levelId, false);
});

// DON'T: Create raw Transaction objects
using var tx = new Transaction(doc, "Create Wall");
tx.Start();
Wall.Create(doc, curve, levelId, false);
tx.Commit();  // Manual error handling required

4. Reference Theme Brushes via BrushKeys

<!-- DO: Use BrushKeys for reliable resolution -->
<Border Background="{DynamicResource {x:Static theme:BrushKeys.Surface}}"/>

<!-- DON'T: Use string keys (fragile) -->
<Border Background="{DynamicResource Brush.Surface}"/>

5. Use the shared window lifecycle

Compose raw views through ToolWindowFactory. Use session.ShowDialog() or session.Show() for presentation and session.AddCleanup for owned state. Settings, Alert, Logger and banners follow this lifecycle. Payload code supplies view models and raw resources; Presentation owns every shell and teardown.

Anti-Patterns to Avoid

1. Service Locator Pattern

// DON'T: Use AppRuntimeAccessor.Resolve outside of command constructors
public class BadService
{
    public void DoWork()
    {
        var alerts = AppRuntimeAccessor.Resolve<IAlertService>();  // Hidden dependency
    }
}

// DO: Inject via constructor
public class GoodService
{
    private readonly IAlertService _alerts;
    
    public GoodService(IAlertService alerts)
    {
        _alerts = alerts;
    }
}

2. Silent Failures

// DON'T: Swallow exceptions
try { DoWork(); }
catch { /* silent failure */ }

// DON'T: Return defaults pretending success
catch (Exception) { return new List<Element>(); }

// DO: Let ISafeExecutor handle errors
await executor.RunAsync(async () =>
{
    DoWork();  // Exception propagates to error handling
}, logger, notifier);

3. Capturing Document References

// DON'T: Hold Document references in singleton services
public class BadService
{
    private readonly Document _doc;  // Will become stale!
    
    public BadService(Document doc) => _doc = doc;
}

// DO: Accept Document per-call
public class GoodService
{
    public void DoWork(Document doc)
    {
        // Fresh reference each call
    }
}

4. Raw Console/MessageBox Output

// DON'T: Use Console or MessageBox
Console.WriteLine("Debug info");
MessageBox.Show("Error occurred");

// DO: Use logging and IAlertService
_logger.LogDebug("Debug info");
_alerts.Show(new AlertRequest("Error", new MessageBodyViewModel("Error occurred")));

5. Bypassing Theme System

// DON'T: Use hard-coded colors
<Border Background="#222228"/>

// DO: Use theme brushes
<Border Background="{DynamicResource {x:Static theme:BrushKeys.Surface}}"/>
