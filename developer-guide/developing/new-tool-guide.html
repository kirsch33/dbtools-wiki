Creating New Tools

A DB Tools tool owns its source, manifest, resources, production assembly, and tests. App discovers embedded manifests, registers services, and composes ribbon controls. Each tool assembly ships under the product year's Tools/ directory. Service and settings modules follow the same assembly contract as ribbon tools.

Use this page to create the tool boundary. See Modularity for runtime services, Settings Packs for configuration, Hooks for events, and Testing Tools for validation.

Prerequisites

Run commands from the repository root. Desktop builds support Revit 2026 (2026.5 or later) and Revit 2027. Both use net10.0-windows. The selected year chooses API references and output directories. APS Design Automation uses a separate Revit 2026/.NET 8 contract.

Check the build entrypoint before adding a tool:

./build.sh --help
./build.sh BuildApp -y 2026

On native Windows, use the PowerShell entrypoint:

pwsh -NoProfile -File build.ps1 BuildApp -y 2026

build.sh supports Linux and WSL. It refuses native Windows shells. The wrappers acquire the SDK pinned in global.json and initialize the HandyControl submodule when needed. Build and validation commands explains the targets, defaults, logs, and source gates.

1. Choose the owner and names

Place a tool under src/Tools/<Category>/<Tool>/. Categories such as Common, Structural, Experimental, and Services organize source. They do not enter CLR namespaces. A tool's namespace root is DBTools.<Tool>.

Follow the repository's .agents/canon/CANON.md naming contract:

  • Mirror folders in namespaces beneath the component root.
  • Give each C# identity its own file with the same name. Partial companions may use dotted suffixes, such as Workflow.Validation.cs.
  • Put manifest-facing commands and modules under App/Composition/.
  • Put whole-tool composition, windows, navigation, and session lifetime under App/.
  • Put user capabilities under Features/<Concept>/ and shared tool language under Domain/.
  • Put Revit adapters beneath the nearest owning concept's Revit/ folder.
  • Create only populated owners. CANON bans Shell and Shared as production owners and treats Models as a generic kind bucket.

For example:

src/Tools/Common/MyTool/
├── App/
│   ├── Composition/
│   │   ├── MyToolCommand.cs
│   │   └── MyToolToolModule.cs
│   ├── DesignTime/
│   │   └── MyToolWindowDesignTimeViewModel.cs
│   ├── ViewModels/
│   │   └── MyToolWindowViewModel.cs
│   └── Views/
│       └── MyToolWindow.xaml
├── Assets/
│   └── my_tool.png
├── Features/
│   └── Inspection/
│       └── InspectionWorkflow.cs
├── Settings/
├── Tests/
├── DBTools.MyTool.csproj
└── manifest.yml

The optional Settings/ and Tests/ entries represent actual content, not placeholder directories. Short tool prefixes use Pascal-compressed forms such as Gm, Sgt, and Tdv. Window names pair with their runtime and design-time ViewModels, for example GmWindow, GmWindowViewModel, and GmWindowDesignTimeViewModel.

2. Create the production project

Every tool manifest root needs a production project with DBT_IsToolAssembly=true, including a module with no ribbon commands. Add production and test projects to DBTools.sln under the owning solution folder.

This project is a starting point for the example tool's DBTools.MyTool.csproj:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>$(DBT_RevitTargetFramework)</TargetFramework>
    <DBT_RevitHostIdentity>$(DBT_DesktopRevitHostIdentity)</DBT_RevitHostIdentity>
    <DBT_IsToolAssembly>true</DBT_IsToolAssembly>
    <RootNamespace>DBTools.MyTool</RootNamespace>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
  <ItemGroup>
    <Compile Remove="Tests\**\*.cs" />
    <ProjectReference Include="..\..\..\DBTools.Core\DBTools.Core.csproj" />
    <PackageReference Include="Microsoft.Extensions.Logging.Abstractions" />
    <EmbeddedResource Include="Assets\*.png">
      <Link>Resources\Icons\%(Filename)%(Extension)</Link>
    </EmbeddedResource>
  </ItemGroup>
</Project>

The repository supplies year-specific Revit API metadata packages through Directory.Build.targets. Do not copy installed Revit DLLs into the product. Declare a direct, versionless package reference when source uses that package's API. Prefer the smallest package that supplies the API.

When tests need internal production types, declare visibility in the tool project for the exact consuming assembly names:

<ItemGroup>
  <InternalsVisibleTo Include="DBTools.MyTool.Pure.Tests" />
  <InternalsVisibleTo Include="DBTools.MyTool.Local.Tests" />
</ItemGroup>

Content-derived assembly identity applies by default to tool assemblies through build/MSBuild/ContentVersion.targets. This includes non-WPF tools.

For WPF, add UseWPF=true, reference Presentation where used, and add CommunityToolkit.Mvvm when using its generators. Tool views are raw embedded XAML. Disable automatic Page compilation and give each raw resource an explicit logical name:

<PropertyGroup>
  <UseWPF>true</UseWPF>
  <EnableDefaultPageItems>false</EnableDefaultPageItems>
</PropertyGroup>
<ItemGroup>
  <ProjectReference Include="..\..\..\DBTools.Presentation\DBTools.Presentation.csproj" />
  <PackageReference Include="CommunityToolkit.Mvvm" />
  <EmbeddedResource Include="App\Views\MyToolWindow.xaml"
                    LogicalName="DBTools.ToolViews.MyTool.MyToolWindow.xaml" />
</ItemGroup>

Tools with Revit-dependent designer source can exclude **\Revit\**\*.cs when DesignTimeBuild=true. Keep designer-only resource dictionaries separate from runtime raw views. If a project compiles Properties\DesignTimeResources.xaml, its Page metadata can declare SubType=Designer, Generator=MSBuild:Compile, and ContainsDesignTimeResources=true.

3. Declare the manifest

A ribbon module can use this manifest:

id: DBTools.MyTool
assembly: DBTools.MyTool
moduleType: DBTools.MyTool.App.Composition.MyToolToolModule
order: 0
panel: Common
tool:
  ribbonTools:
    - internalName: DBTools.MyTool
      commandType: DBTools.MyTool.App.Composition.MyToolCommand
      runProfile: InlineUi
      displayText: "My Tool"
      iconBaseKey: my_tool
      tooltip: "Inspect the active model"
      controlKind: PushButton
      order: 50

assembly is the actual simple assembly name. It does not end with .dll in any case and contains no /, \, , or :; the same rule applies to sandboxWindows assembly fields. App embeds manifests centrally, but compiles no tool source, XAML, or assets. The product build discovers declared tool projects and stages their assemblies under <year>/Tools/. build/MSBuild/ProductOutput.proj builds and stages those owners. ToolAssemblyResolver loads the declared file in the root assembly's owning context. Runtime resolves modules, commands, icons, and raw views from that owner.

Manifest fields

Field Requirement and meaning
id Required unique tool identifier.
assembly Required simple assembly name.
moduleType Optional fully qualified ToolModule type.
order Required load order, lower first. Use 0 without an ordering requirement.
panel Required for every ribbon manifest and by settings-pack registration. Accepted values: Settings, Common, Structural, Testing, Services.
tool.settings.configSection Optional single JSON property name in settings.<year>.json.
tool.settingsPacks Optional pack definitions with required key and title.
tool.ribbonTools Ribbon command definitions. May be absent for a service/settings/hook module.
sandboxWindows Optional raw-view previews. See Sandbox Integration.

A module must own at least one responsibility: ribbon tools, settings, settings packs, or registered lifecycle hooks. A moduleless manifest requires panel and at least one ribbon tool. It cannot declare settings or settings packs.

For a service module, retain the project and declare its actual owner:

id: DBTools.DialogSuppression
assembly: DBTools.DialogSuppression
moduleType: DBTools.DialogSuppression.App.Composition.DialogSuppressionToolModule
order: -1
panel: Services
tool:
  settings:
    configSection: Tools.DialogSuppression
  settingsPacks:
    - key: services.dialog_suppression
      title: "Dialog Suppression"

Ribbon fields

Field Requirement and meaning
internalName Required unique control identity, also used by warning definitions.
commandType Required fully qualified concrete ToolCommand type.
availabilityType Optional separate type implementing IExternalCommandAvailability. Omit for command-owned availability.
runProfile InlineUi by default, or QueuedModeless.
displayText Required label. YAML double-quoted strings support \n line breaks.
iconBaseKey Required embedded icon key without extension.
tooltip Required tooltip text.
controlKind PushButton by default, or SplitButtonItem, PulldownButtonItem, StackedButtonItem.
group Required nonblank group for grouped controls. Invalid for a push button.
order Required order within the panel/group.
groupDisplayText Optional group header text.
groupTooltip Optional group header tooltip.
groupIconBaseKey Optional group header icon key.

Optional values cannot be blank. Push buttons cannot carry grouped-control metadata. Entries in one panel with the same controlKind and group form one split button, pulldown button or stack, ordered by order. The lowest-order split entry is the primary command. The remaining entries are its dropdown commands. App planning and Revit construction use that sequence.

Use a 32×32 main icon such as my_tool.png. An optional 16×16 companion is my_tool_16.png. Match the base filename to iconBaseKey.

4. Register services

ToolModule lives in DBTools.Core.Tools.Modules.Composition. Its registration methods receive the manifest from DBTools.Core.Tools.Manifest:

Method Contribution
RegisterSettings Typed persistence sections.
RegisterServices Tool services and dependency injection registrations.
RegisterSettingsPacks Settings catalog definitions and context/view factories.
RegisterHooks Lifecycle hook registrations in ToolRegistry.

Startup calls RegisterSettings, RegisterServices, RegisterSettingsPacks, and RegisterHooks in that order for each module before validating and merging its registrations. Keep modules limited to composition. Put behavior with the feature that owns it. For example, a module can register a feature workflow:

using DBTools.Core.Tools.Manifest;
using DBTools.Core.Tools.Modules.Composition;
using DBTools.MyTool.Features.Inspection;
using Microsoft.Extensions.DependencyInjection;

namespace DBTools.MyTool.App.Composition;

public sealed class MyToolToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        ArgumentNullException.ThrowIfNull(services);
        ArgumentNullException.ThrowIfNull(manifest);
        services.AddScoped<InspectionWorkflow>();
    }
}

A simple moduleless command may declare [CommandService(typeof(Workflow))] on the command. Framing Joins uses this pattern for FramingJoinsWorkflow. Do not reconstruct ribbon registrations in a module. App resolves concrete command and availability types. Core constructs their shared registrations.

5. Implement the command

Use ToolCommand from DBTools.Core.Tools.Commands for ribbon commands. It supplies safe execution, contextual logging, command preflight, and scope creation/disposal. Revit constructs the command with an inert parameterless constructor. Resolve services inside RunAsync:

using Autodesk.Revit.Attributes;
using DBTools.Core.Tools.Commands;
using DBTools.Core.Tools.Commands.Context;
using DBTools.MyTool.Features.Inspection;

namespace DBTools.MyTool.App.Composition;

[Transaction(TransactionMode.Manual)]
public sealed class MyToolCommand : ToolCommand
{
    protected override Task RunAsync(ICommandContext context)
    {
        ArgumentNullException.ThrowIfNull(context);
        return context.Resolve<InspectionWorkflow>().ExecuteAsync(context.Document);
    }
}

This example assumes the feature defines InspectionWorkflow.ExecuteAsync(Document). The context exposes UIApplication, UIDocument, Document, Logger, OwnerHandleProvider, ShowErrorBanner, ShowWarningBanner, and inherited Resolve<T>(). Use the error banner for a failure and the warning banner for an expected refusal or a partial result. A documentless command overrides RequiresActiveDocument=false. Accessing its Document or UIDocument throws.

Every ToolCommand implements IExternalCommandAvailability. Omit availabilityType to infer the concrete command. An explicit type equal to the command is rejected. A separate availability class uses an explicit type. The default predicate requires an open document unless RequiresActiveDocument is false. Override IsCommandAvailableCore for other predicates and use CommandAvailability methods such as HasActiveView, HasSelection, or HasStructuralFramingSelection.

Use the scoped ITransactionRunner for model changes. Its callbacks are synchronous, even though the entrypoint returns a Task. A modeless command uses the queued run profile and an owned session. See Modularity for call-gate, transaction, logging, and session contracts.

6. Add views, settings, and hooks

A tool view embeds a stable element such as Grid. It has no x:Class, code-behind, tool CLR namespace, or event attributes. Presentation supplies the window shell. Core's ToolWindowFactory installs runtime services and registers its session. See Tool-window sessions.

Use ObservableObject, [ObservableProperty], and [RelayCommand] from CommunityToolkit.Mvvm for bindable state and commands. Match the ViewModel's folder and namespace. Keep design-time ViewModels independent of Revit and production services. Sandbox Integration describes resource names, manifest declarations, visibility, and preview construction.

For persisted options, define a DTO and a source-generated JSON context. Register one SettingsSection<T> and read it through ISettingsProvider. A settings pack adds the editor context and view. Settings Packs contains the complete registration and persistence sequence.

For view-change work, register an IViewActivationTask service. For owned event subscriptions, implement IHookLifecycle and register the concrete service and its lifecycle registration. Hooks describes admission, failure handling, rollback, and synchronous shutdown. Feature Warnings describes configuration failures that disable commands.

7. Add tests and validate

Tests live under the owning Tests/ directory and mirror production ownership:

Tests/
├── Features/Inspection/InspectionWorkflowTests.cs
├── Integration/Revit/Features/Inspection/InspectionWorkflowHostedTests.cs
├── Support/
├── DBTools.MyTool.Pure.Tests.csproj
└── DBTools.MyTool.Local.Tests.csproj

Pure projects compile plain NUnit tests against the tool project. Local projects use explicit positive compile membership for [RevitLocal] fixtures and their support. A DA project claims coverage only through real APS WorkItem tests. Optional *.Portable.Pure.Tests projects exercise portable production targets on Linux. Keep the execution projects separate.

Use focused commands during development:

./test.sh list --tool GM --scope pure --fixture DuplicateDetectionEngineTests
./test.sh test --tool GM --scope pure --fixture DuplicateDetectionEngineTests
./build.sh BuildSelectedLocalTests --TestProjects DBTools.GM.Local.Tests -y 2026

Replace GM with the new tool's directory key after its test projects exist. See Testing Tools for execution hosts and routing.

Run the new tool's Pure fixtures through test.sh. Use Revit-hosted tests for ribbon composition and commands that need the Revit API. Use Windows Pure fixtures for WPF bindings, themes, and window cleanup. See Testing Tools for selection and execution commands.
