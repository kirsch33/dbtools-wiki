Creating New Tools in DBTools

This guide covers the complete process of creating a new tool for the DBTools Revit add-in platform. By the end, you'll understand the tool module system, manifest configuration, command implementation, and UI patterns.

Overview

DBTools uses a manifest-driven plugin architecture. Each tool:

  1. Lives in its own folder under src/Tools/
  2. Declares metadata via manifest.yml
  3. Implements a ToolModule subclass for DI registration
  4. Provides one or more ToolCommand implementations when it exposes ribbon commands
  5. May instead be a service/settings module with settings packs or hooks and no ribbon command
  6. Optionally includes WPF UI, settings, and hooks

Tool Module Lifecycle

Assembly ownership: Every manifest root under src/Tools/ owns a project that declares <DBT_IsToolAssembly>true</DBT_IsToolAssembly> and ships as its own file-backed assembly beneath the product year's Tools/ directory, including service and settings modules without ribbon buttons.

Manifests name the actual owning assembly, such as DBTools.TDV, DBTools.SGT, or DBTools.Settings; tool IDs are not assembly aliases. App discovers every manifest centrally and resolves its declared owner from <product>/Tools/<assembly>.dll in the active owning context.

Prerequisites

Before creating a new tool:

  1. Ensure you can build the solution: bash build.sh
  2. Use the singular desktop target map: net10.0-windows for Revit 2026.5+ and Revit 2027
  3. Decide on a tool category: Common, Structural, Testing, Services, or new category
  4. Choose a unique tool ID (e.g., DBTools.MyTool)

Step 1: Directory Structure

Create your tool folder under the appropriate category:

src/Tools/
  Common/           # General-purpose tools
    GM/             # Global Mapper (complex example)
    ElevationTags/  # Simple example
  Structural/       # Structural engineering tools
    SGT/            # Super Girt Tool (complex example)
    FramingJoins/   # Simple example
  Services/         # Cross-tool services/settings modules
    DialogSuppression/
    Experimental/     # In-development / not-yet-production tools

Minimal Ribbon Tool Structure

src/Tools/<Category>/<ToolName>/
  Assets/
    my_tool.png              # 32x32 icon for ribbon (required)
    my_tool_16.png           # 16x16 small icon (optional)
  Features/
    MyToolCommand.cs         # ToolCommand implementation
  manifest.yml               # Tool metadata and ribbon config
  <ToolName>ToolModule.cs    # DI registration
  DBTools.<ToolName>.csproj  # Project file (for IDE/tests)

Use this shape when the manifest declares tool.ribbonTools. The command type named by each ribbon tool must extend ToolCommand; the icons named by iconBaseKey live under Assets/; and the project file provides IDE navigation and command/test isolation.

Minimal Service/Settings Module Structure

src/Tools/Services/<ServiceName>/
  manifest.yml                    # Tool metadata plus settings/settingsPacks or hooks
  <ServiceName>ToolModule.cs      # DI, settings pack, and hook registration

Use this shape for modules that register shared services, hooks, settings, or settings packs without adding a ribbon button. These modules omit tool.ribbonTools, ToolCommand implementations, and ribbon icons. Add Settings/, Hooks/, or other source folders only when the module owns those concerns; add a .csproj only when the module needs independent IDE/test isolation.

Step 2: Project File (.csproj)

Create a project file for a tool that owns an assembly. It participates in the product-output build and also enables:

  • IntelliSense and navigation
  • Per-tool test projects
  • Design-time XAML preview

Service/settings modules without ribbon commands may omit the project file unless they need independent IDE or test coverage boundaries.

Step 3: manifest.yml (Complete Schema)

The manifest file declares your tool's metadata, ribbon configuration, and optional settings.

Complete Schema Reference

# Required: Unique tool identifier
id: DBTools.MyTool

# Required: Actual owning assembly name (without .dll)
assembly: DBTools.MyTool

# Required: Fully-qualified type name of ToolModule subclass
moduleType: DBTools.MyTool.MyToolToolModule

# Required: Load order (lower = earlier). Use 0 unless you need ordering.
order: 0

# Optional: Sandbox windows for design-time preview
sandboxWindows:
  - id: DBTools.MyTool.Main
    displayName: "My Tool"
    group: "Common"               # or "Structural", "Testing", "Services"
    xamlResource: "DBTools.ToolViews.MyTool.MyToolWindow.xaml"
    designTimeViewModelType: "DBTools.MyTool.App.DesignTime.MyToolWindowDesignTimeViewModel"
    designTimeViewModelAssembly: "DBTools.MyTool"
    designTimeViewModelVisibility: Public

# Required: Tool configuration. A command-bearing ribbon module declares ribbonTools;
# a service/settings module may provide only settings and settingsPacks.
tool:
  # Optional: Settings configuration
  settings:
    configSection: Tools.MyTool   # Section in settings.{YEAR}.json

  # Optional: Settings packs for Settings window
  settingsPacks:
    - key: common.my_tool
      title: "My Tool"
      warnings:
        - id: core.my_tool.warning
          title: "My Tool Disabled"
          message: "Tool is disabled due to a configuration issue."
          disableTools:
            - DBTools.MyToolCommand

  # Required for ribbon modules; omit for service/settings modules with no ribbon button.
  ribbonTools:
    - internalName: DBTools.MyToolCommand
      commandType: DBTools.MyTool.Features.MyToolCommand
      availabilityType: DBTools.MyTool.Features.MyToolCommand
      runProfile: InlineUi
      displayText: "My Tool"
      iconBaseKey: my_tool
      tooltip: "Launch My Tool"
      controlKind: PushButton
      order: 50

Manifest Properties Reference

Property Required Description
id Yes Unique identifier (e.g., DBTools.MyTool)
assembly Yes Actual assembly name without .dll; every tool owner uses DBTools.<Tool>
moduleType No Full type name of ToolModule subclass when the tool has module-owned services, settings, settings packs, or hooks
order Yes Load order (0 for most tools)
panel Yes for moduleless ribbon tools Ribbon panel for manifests without moduleType
sandboxWindows No Design-time preview windows
tool.settings.configSection No settings.{YEAR}.json section for typed JSON settings
tool.settingsPacks No Settings window configuration
tool.ribbonTools No Ribbon button definitions. Required only for command-bearing ribbon modules; service/settings modules may omit it.

Every manifest tool section must have at least one concrete responsibility: ribbon tools, settings, settings packs, or hooks registered by the module. Moduleless manifests must declare panel and at least one tool.ribbonTools entry, and cannot declare settings or settings packs. Hook-only modules may keep tool.ribbonTools empty, but they must register at least one hook during RegisterHooks(...).

Ribbon Tool Properties

Property Required Description
internalName Yes Unique button identifier
commandType Yes Full type name of command class
availabilityType No Full type name of the concrete command, which also implements IExternalCommandAvailability
runProfile No InlineUi (default) or QueuedModeless
displayText Yes Button label (use \n for line breaks)
iconBaseKey Yes Icon filename without extension
tooltip Yes Button tooltip text
controlKind Yes PushButton, SplitButtonItem, PulldownButtonItem, StackedButtonItem
splitGroup No Group name for split/pulldown/stacked buttons
order Yes Button order within panel
groupDisplayText No Header text for pulldown groups
groupTooltip No Tooltip for pulldown header
groupIconBaseKey No Icon for pulldown header

Entries that share a split or pulldown group form one ordered command sequence. The lowest-order entry is the split primary command and later entries are the dropdown commands. App planning and Revit construction consume that exact sequence; there is no second primary/dropdown list to keep synchronized.

Step 4: ToolModule Class

The ToolModule subclass is the manifest entry point. Keep it thin: validate inputs, bind settings/settings packs, and delegate feature or shell DI to Shell/<ToolName>ServiceCollectionExtensions.cs.

Do not manually map manifest ribbon fields inside tool modules. App startup resolves the manifest command and optional availability types, then delegates registration construction to Core so panel mapping, execution defaults, control-kind mapping, and grouped-button metadata stay in the shared registry/ribbon contracts.

Minimal Command Workflow Registration

Simple inline command tools can register their command workflow dependency on the command itself. Framing Joins uses this path instead of a tool module:

[Transaction(TransactionMode.Manual)]
[CommandService(typeof(FramingJoinsWorkflow))]
public sealed class AllowJoinSelectedCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        Guard.NotNull(context, nameof(context));

        var workflow = context.Resolve<FramingJoinsWorkflow>();
        await workflow.ExecuteAsync(...).ConfigureAwait(false);
    }
}

With Service Registration

using DBTools.Core.Tools;
using DBTools.Core.Guarding.Domain;
using DBTools.MyTool.Shell;
using Microsoft.Extensions.DependencyInjection;

namespace DBTools.MyTool;

public sealed class MyToolToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        Guard.NotNull(services, nameof(services));
        Guard.NotNull(manifest, nameof(manifest));
        
        services.AddMyTool();
    }
}

With Hooks

using DBTools.Core.Tools;
using DBTools.Core.Guarding.Domain;
using Microsoft.Extensions.DependencyInjection;

namespace DBTools.SGT;

public sealed class SgtToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        Guard.NotNull(services, nameof(services));
        Guard.NotNull(manifest, nameof(manifest));
        
        services.AddSgt();
        services.AddSingleton<ContextualRibbonInjector, ContextualRibbonInjector>();
    }

    public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
    {
        Guard.NotNull(registry, nameof(registry));
        Guard.NotNull(manifest, nameof(manifest));

        registry.RegisterHook<IHookLifecycle, ContextualRibbonInjector>();
    }
}

Step 5: Command Implementation

Command-bearing ribbon modules implement commands with ToolCommand (not IExternalCommand directly) to get automatic error handling, logging, and run scope management. Service/settings modules with no ribbon tools skip this step.

Basic Command Structure

using System;
using System.Threading.Tasks;
using Autodesk.Revit.Attributes;
using DBTools.Core.Guarding.Domain;
using DBTools.Core.Revit.Execution.Commands;
using Microsoft.Extensions.Logging;

namespace DBTools.MyTool.Features;

[Transaction(TransactionMode.Manual)]
public sealed class MyToolCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        Guard.EnsureNotNull(context, nameof(context));
        
        var logger = context.Logger;
        var doc = context.Document;
        var uidoc = context.UIDocument;
        
        logger.LogDebug("[MyTool] Starting execution");
        
        // Your tool logic here
        
        await Task.CompletedTask.ConfigureAwait(false);
    }
    
}

With Transaction

[Transaction(TransactionMode.Manual)]
[CommandService(typeof(FramingJoinsWorkflow))]
public sealed class AllowJoinSelectedCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        Guard.NotNull(context, nameof(context));

        var workflow = context.Resolve<FramingJoinsWorkflow>();
        await workflow.ExecuteAsync(
            FramingJoinOperation.Allow,
            context.UIDocument,
            context.Document).ConfigureAwait(false);
    }
}

The workflow receives the scoped transaction runner, owner provider, and typed logger through constructor injection. The selected command profile has already created either InlineRevitCallGate or QueuedRevitCallGate for that scope, while the command passes only operation-specific inputs:

public FramingJoinsWorkflow(
    ILoggerWindowHost loggerWindow,
    ITransactionRunner transactions,
    IWindowOwnerHandleProvider ownerHandleProvider,
    ILogger<FramingJoinsWorkflow> logger)
{
    _loggerWindow = loggerWindow;
    _transactions = transactions;
    _ownerHandleProvider = ownerHandleProvider;
    _logger = logger;
}

await _transactions.RunInDocumentAsync(doc, $"DB Tools - {operationName} Join Selected", d =>
{
    modified = ExecuteCore(operation, framingTargets, _logger);
}).ConfigureAwait(false);

Step 6: UI Implementation (MVVM Pattern)

For tools with UI, follow the MVVM pattern with DBTools conventions.

Raw XAML view template

<Grid xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
      xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
      xmlns:resources="clr-namespace:DBTools.Presentation.Resources;assembly=DBTools.Presentation">
    <Grid.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <ResourceDictionary Source="{resources:ResourceUri Resources/Theme.xaml}" />
            </ResourceDictionary.MergedDictionaries>
        </ResourceDictionary>
    </Grid.Resources>
    <!-- Stable controls bound to the runtime or design-time view model. -->
</Grid>

Embed the file with an explicit logical name such as DBTools.ToolViews.MyTool.MyToolWindow.xaml. It declares no tool CLR namespace, Window root, x:Class or event attribute. The manifest supplies its design-time model.

Tool-window sessions

Tool UI uses raw embedded XAML without x:Class or code-behind. Its root is a stable view element such as Grid; ToolWindowHost supplies the modal or modeless shell. Core's ToolWindowFactory installs the theme, owner, icon, error boundary and progress lifecycle before parsing, then registers the session for normal close and generation retirement.

using var xaml = new MemoryStream(ToolWindowXaml.ReadEmbeddedResource(
    typeof(MyToolWindowViewModel).Assembly, "DBTools.ToolViews.MyTool.MyToolWindow.xaml"));
var session = factory.Create(ToolWindowKind.Modal, xaml, viewModel,
    new ToolWindowOptions { Title = "My Tool", Width = 800, Height = 600 });
_ = session.ShowDialog();

Use ToolWindowKind.Modeless and session.Show() for a modeless surface. Register payload event handlers and owned cleanup through the session. A custom shell initializer owns its cleanup handle and must register it with session.AddCleanup.

Step 8: Hooks (Optional)

Available Hook Contracts

Contract Purpose
ViewActivationHook Core-owned view-change dispatcher; tools plug in via IViewActivationTask

ViewActivated Hook

For view-activated behavior, register an IViewActivationTask. The singleton ViewActivationHook is already provided by the app layer.

using System;
using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;
using DBTools.Core.Tools.Hooks.ViewActivation;
using Autodesk.Revit.DB;
using Autodesk.Revit.UI;
using Autodesk.Revit.UI.Events;

namespace DBTools.MyTool.Features.Hooks;

public sealed class MyViewActivatedTask : IViewActivationTask
{
    public string TaskId => "mytool.view-activated";
    public string DisplayName => "My Tool View Activated";
    public IReadOnlyCollection<string> WarningIdsToSetOnFailure => Array.Empty<string>();

    // A non-null admission runs this attempt once; it captures the state its execution uses
    public Task<ViewActivationAdmission?> AdmitAsync(UIApplication application, ViewActivatedEventArgs args, CancellationToken ct)
    {
        var view = args.CurrentActiveView;
        return Task.FromResult<ViewActivationAdmission?>(
            view == null ? null : new ViewActivationAdmission(executionCt => ReactAsync(view, executionCt)));
    }

    private static Task ReactAsync(View view, CancellationToken ct)
    {
        // React to the admitted view
        return Task.CompletedTask;
    }
}

Register from your shell service collection extension:

public static IServiceCollection AddMyTool(this IServiceCollection services, ToolManifest manifest)
{
    services.AddSingleton<IViewActivationTask, MyViewActivatedTask>();
    return services;
}

Step 9: Command-owned Availability

Every ToolCommand implements IExternalCommandAvailability; its default predicate requires an open document. Set availabilityType to the same concrete command as commandType. Commands with another requirement override IsCommandAvailableCore and call CommandAvailability.HasActiveView, HasSelection, or HasStructuralFramingSelection.

Step 10: Declare Assembly Ownership

  1. Set <DBT_IsToolAssembly>true</DBT_IsToolAssembly> in the tool's production .csproj under src/Tools/<Category>/<Tool>/. Projects without WPF also set <DBT_ContentDerivedIdentity>true</DBT_ContentDerivedIdentity> to retain the existing content-version policy.
  2. Set manifest.yml's assembly and each design-time ViewModel assembly to the actual owner, such as DBTools.TDV.
  3. Embed icons, policies and raw XAML in that project. Preserve their logical resource names. Remove explicit App resource entries for the migrated tool.
  4. Reference the production project from Pure tests, Local tests and real consumers. Move required InternalsVisibleTo declarations to the tool project.

ProductOutput.proj restores declared tool owners, builds their final images, and stages them beneath the selected year directory's Tools/ folder. App manifests remain embedded centrally, while ToolAssemblyResolver loads each declared owner by explicit path in the active owning context. The final tree contains the four top-level product DLLs plus the fourteen tool DLLs beneath Tools/.

App embeds tool manifests for central discovery but compiles no source, XAML, or assets from src/Tools/. Runtime modules, commands, icons, settings, and raw XAML resolve from the manifest-declared owner. Tool XAML must continue to use framework and stable Presentation types.

Every tool declares its own assembly, resources, and test references. No tool-specific product-output, Core, or App runtime logic is required. SGT, Settings, and DialogSuppression use assembly: DBTools.SGT, DBTools.Settings, and DBTools.DialogSuppression respectively.

Step 11: Testing Setup

Test Project Structure

src/Tools/<Category>/<ToolName>/Tests/
  DBTools.<ToolName>.Pure.Tests.csproj   # plain [Test] fixtures; no Revit host
  DBTools.<ToolName>.Local.Tests.csproj  # [RevitLocal] fixtures
  PureBehaviorTests.cs
  RevitHostedBehaviorTests.cs
  Support/

Do not create a consolidated unsuffixed tool test project. Owner tests follow the taxonomy in Test Pipeline: .Pure.Tests compiles plain off-Revit fixtures against a plain ProjectReference to the tool, .Local.Tests compiles local Revit-hosted fixtures, and DA coverage requires a separate WorkItem-backed [RevitDA] project. Its WorkItem tests run like the DA Sentinel: on the operator's host as an HTTP client with dotnet test, with APS_CLIENT_ID and APS_CLIENT_SECRET set, for 5–12 minutes of APS processing time per WorkItem (the account includes 300 free minutes a month). Sub-agents and the daemon never run them; see APS Design Automation Sentinel. A tool whose inward code should also run on Linux adopts the optional portable target described in the Test Pipeline and adds DBTools.<ToolName>.Portable.Pure.Tests.

Running Tests

# Run a tool's pure lane through the repository wrapper
./test.sh test --tool MYTOOL --scope pure

# Run a specific fixture through the repository wrapper
./test.sh test --tool MYTOOL --scope pure --fixture MyTestName

Common Patterns and Best Practices

1. Service Extension Pattern

Centralize DI registration in an extension method:

// Shell/MyToolServiceCollectionExtensions.cs
namespace DBTools.MyTool.Shell;

public static class MyToolServiceCollectionExtensions
{
    public static IServiceCollection AddMyTool(this IServiceCollection services)
    {
        Guard.NotNull(services, nameof(services));
        
        services.AddScoped<IMyService, MyService>();
        services.AddScoped<MyOtherService>();
        
        return services;
    }
}

Then in ToolModule:

services.AddMyTool();

2. Error Handling

Never swallow exceptions. Use ISafeExecutor for top-level error handling (provided by ToolCommand):

// DON'T do this:
try { DoWork(); } catch { } // Silent failure

// DO this:
// Exceptions propagate to ToolCommand's ISafeExecutor
DoWork(); // Let exceptions propagate

3. Logging

Use the injected logger, not Console.WriteLine:

var logger = context.Logger;
logger.LogDebug("[MyTool] Processing {Count} elements", count);
logger.LogWarning("[MyTool] Skipped invalid element {Id}", elementId);
logger.LogError(ex, "[MyTool] Failed to process");

4. Transactions

Always name transactions descriptively:

await tx.RunAsync(doc, "DB Tools - My Tool Operation", d =>
{
    // Modifications here
}).ConfigureAwait(false);

5. Icon Naming

  • Main icon: my_tool.png (32x32)
  • Small icon: my_tool_16.png (16x16, optional)
  • Match the iconBaseKey in manifest (without extension)

6. Namespace Conventions

Choose the namespace root from the live tool family instead of flattening every tool to the same prefix. Common and Testing tools currently use DBTools.<ToolName> roots such as DBTools.GM, DBTools.TDV, and DBTools.VTC; Structural tools use DBTools.Structural.<ToolName> roots such as DBTools.Structural.FramingJoins. Established tools keep their current root unless a deliberate source migration changes every project, manifest, and callsite together.

<NamespaceRoot>                    # Root namespace
<NamespaceRoot>.Features           # Command entrypoints and feature-level APIs
<NamespaceRoot>.Features.<Slice>   # Feature-slice services/models (Transfer, Library, Preview, etc.)
<NamespaceRoot>.Shell              # Shell wiring and DI extensions
<NamespaceRoot>.Shell.Services     # Optional shell-only coordinators/factories
<NamespaceRoot>.Shell.Views        # WPF windows and controls
<NamespaceRoot>.Shell.ViewModels   # Runtime ViewModels
<NamespaceRoot>.Shell.DesignTime   # Design-time ViewModels
<NamespaceRoot>.Shared             # Cross-feature shared types
<NamespaceRoot>.Shared.Domain      # Shared domain/value objects
<NamespaceRoot>.Shared.Models      # Shared DTOs/view models
<NamespaceRoot>.Shared.State       # Optional cross-feature state stores
<NamespaceRoot>.Revit.Services     # Optional Revit-facing adapters/services
<NamespaceRoot>.Settings           # Optional settings/options

Avoid introducing retired namespace shapes in new scaffolds: Bootstrap, Features.Commands, Features.Logic, Shell.DI, and Shell.UI.
