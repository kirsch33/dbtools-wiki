Feature Warnings

A feature warning reports an actionable configuration or prerequisite problem. Active warnings block the commands named by their definitions and publish ribbon enablement updates. Warning state lasts for the current runtime session. It is not persisted to settings.

The Settings window displays warning cards. The Settings button shows a warning icon, and the DB Tools tab receives a highlight when warnings exist. Command preflight and contextual edit flows use the same registered warning policy as ribbon controls.

Defining warnings in manifest.yml

Declare warnings under a settings pack:

tool:
  settingsPacks:
    - key: structural.foundation_tags
      title: "Combined Foundation Tags"
      warnings:
        - id: core.structural.combined_tags
          title: "Combined Foundation Tags Disabled"
          message: "Use Settings -> Combined Foundation Tags -> Install/Repair. A successful repair clears the warning and re-enables the commands."
          disableTools:
            - DBTools.UpdateCombinedFoundationTags
            - DBTools.MoveCombinedFoundationTags
            - DBTools.OrganizeFoundationTypes
Property Requirement and meaning
id Required globally unique warning identity.
title Required warning-card title.
message Required description and corrective action.
disableTools Optional list of registered ribbon internalName values.

Use stable IDs such as core.library.invalid, core.structural.elevation_tags, and core.structural.joist_girder. List only commands that depend on the prerequisite. Name the problem, the affected operation, and the correction in the warning message.

ToolWarningManifest carries the ID, title, message, and disabled-tool list. The manifest is metadata. It does not activate the warning by itself.

Registering warning definitions

Register a warning as the Warning member of SettingsPackRegistration<TOptions,TContext> in ToolModule.RegisterSettingsPacks. Settings Packs contains the full registration, including the required typed SettingsSection.

Warning = new SettingsPackWarningRegistration<SettingsPackContext>
{
    Id = warning.Id,
    Title = warning.Title,
    Message = warning.Message,
    ToolInternalNamesToDisable = warning.DisableTools,
    FlagGetter = context => context.HasWarning,
    FlagSetter = (context, active) => context.HasWarning = active
}

SettingsPackWarningRegistration<TContext> exposes these members:

Member Type Required
Id, Title, Message string Yes
ToolInternalNamesToDisable IReadOnlyCollection<string>? No
FlagGetter Func<TContext, bool> Yes
FlagSetter Action<TContext, bool> Yes

The registration extension validates required values at runtime. The bound runtime warning retains the exact context created by its pack. Callers cannot supply another context to its getter or setter.

The context owns HasWarning for presentation and editing. The settings DTO owns persisted preferences such as AutoUpdateEnabled. IAutoUpdateSettings requires only that preference. Do not serialize a warning flag or derive command blocking from a saved flag.

Triggering warnings

Tools use DBTools.Core.Settings.Warnings.ISettingsWarningService:

IReadOnlyCollection<ISettingsWarningDefinition> Definitions { get; }
bool IsWarningActive(string warningId);
SettingsWarningStateChange SetWarning(string warningId, bool active);

warnings.SetWarning("core.structural.combined_tags", true);
if (warnings.IsWarningActive("core.structural.combined_tags"))
    return;

Blank or unknown IDs fail. Definitions must exist in the validated settings catalog before a tool uses them. Warning lookup is ordinal and case-sensitive. SetWarning updates session state and publishes the warning and aggregate visual state. SettingsWarningStateChange reports the prior and current state.

The concrete SettingsWarningService owns active-ID enumeration and replay. SettingsWarningPublicationPolicy publishes individual warning changes, full replay, and aggregate HasWarnings. Tools receive the narrowed public interface, not internal publication operations.

Validation and activation

A warning-aware editor implements ISettingsWarningContext.WarningId and returns an invalid SettingsValidationResult for a configuration problem. The ID must belong to that pack. Use the actual result API:

public Task<SettingsValidationResult> ValidateAsync(CancellationToken ct = default)
{
    ct.ThrowIfCancellationRequested();
    return Task.FromResult(string.IsNullOrWhiteSpace(LibraryPath)
        ? SettingsValidationResult.FromErrors("Select a library path.")
        : SettingsValidationResult.Success);
}

This excerpt checks an editor-owned LibraryPath. A real library validator must also check its required file/directory conditions. Conditional features can return Success when disabled if their configuration is unnecessary then. Do not report an unexpected I/O or programming exception as invalid settings.

Validation has distinct publication rules:

Operation Warning behavior
Startup Load saved options into fresh runtimes without views. Activate invalid warning-aware packs. Do not proactively clear warnings.
Open Settings Validate loaded options and publish warning state.
Validate button Evaluate unsaved drafts and editor flags. Do not change shared command blocking.
Save before commit Evaluate drafts and reject blocking invalid values. Do not publish draft decisions.
Save after commit Validate saved values in fresh runtimes, project decisions, and replay published state.
Reset Commit defaults, apply them, validate, and publish.

ISettingsPackSaveValidation.BlockSaveOnInvalid determines whether an invalid draft blocks Save. Invalid settings and a validation exception are different outcomes. Startup logs a validation exception without activating its feature warning. Settings-window failures propagate through the normal error path.

Startup disposes every runtime it creates. It retries a failed disposal once, logs persistent failures with the pack identity, and preserves cancellation when cleanup also fails. The warning evaluator uses the same validated SettingsCatalog as the Settings window.

Auto-update task integration

ViewActivationTask<TSettings> reads the current settings once during admission. It returns no admission when AutoUpdateEnabled is false or any configured warning is active. Otherwise it evaluates the tool predicate and returns an admission that captures that settings snapshot.

The hook distinguishes two failures:

  • An admission failure records a document-session failure and activates WarningIdsToSetOnFailure. A settings-read failure occurs at this boundary.
  • A failure while executing an admitted operation shows the canonical auto-update failure banner and suppresses further runs for that document session. It does not activate feature warnings automatically.

Tool-owned prerequisite checks can activate a warning explicitly, for example when required shared parameters are missing. Unexpected runtime exceptions must propagate to the hook's safe-execution boundary. See Hooks for admission, document-session identity, and failure handling.

An active warning can disable the editor's toggle through ToggleEnabled. Changing the persisted AutoUpdateEnabled preference is a separate tool policy. It is not a required side effect of SetWarning.

Warning UI and command blocking

SettingsWarningViewModel wraps an ISettingsPackRuntimeWarning. It exposes WarningId, Title, Message, IsActive, Clear and Fix commands, and Fix availability. The warning card binds to that row state.

Publication reaches ribbon controls in this order:

  1. The warning service publishes a WarningChangedEventArgs.
  2. RibbonSettingsObserver receives the published change.
  3. RibbonVisualUpdater applies its per-command enabled state.
  4. RibbonCompositionState updates registered buttons.

RibbonComposer registers controls before subscribing to settings changes. RibbonVisualUpdater also applies aggregate Settings-icon and tab-highlight updates. RibbonSettingsObserver owns subscription lifetime and dispatcher delivery. RibbonCompositionState owns the registered controls and panel state.

Command preflight checks every applicable active warning. Ribbon enablement instead applies each warning's latest update directly. If several warnings name one command, clearing one can visually enable its button while another still blocks execution. Give each disabled command one warning definition when its ribbon state must match command preflight.

WarningChangedEventArgs carries WarningId, PackKey, IsActive, and ToolInternalNamesToDisable. WarningSetChangedEventArgs carries aggregate HasWarnings. Treat these as published state, not persistence requests.

Clearing and fixing warnings

Clear sets the bound context warning false and calls ISettingsWarningService.SetWarning(id, false). It does not repair prerequisites or save settings. A later validation or prerequisite check can activate the warning again.

A tool can clear a warning programmatically after its prerequisite check succeeds:

warnings.SetWarning("core.structural.combined_tags", false);

Changing only a context property does not publish command availability. Use the service or the Settings validation workflow to synchronize published state.

A context that implements IWarningFixProvider can add a Fix action:

string FixWarningId { get; }
string FixLabel { get; }
Task FixWarningAsync(CancellationToken ct = default);

The provider's warning ID must match the card. Blank IDs or labels fail construction. SettingsWarningViewModel invokes the provider, updates command state when the context changes, and logs action failures. Its ActionFailed event passes failures to Settings feedback. Disposal unsubscribes the context observer.

Combined Foundation Tags uses Fix for Install/Repair and explicit refresh for shared parameter checks. Its constructor only prepares editor state. See Settings Packs for host context and persistence ordering.

Examples

Combined Foundation Tags uses core.structural.combined_tags for Update Combined Foundation Tags, Move Combined Tags, and Organize Foundation Types. Transfer Drafting Views (TDV) uses core.library.invalid for Import From Library and Export To Library. Joist Girder Weights uses core.structural.joist_girder for its update command. Their manifests under src/Tools/ define the IDs and messages.
