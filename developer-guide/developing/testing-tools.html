Selection and results

Use --list-tests to discover tests. Use --filter with FullyQualifiedName, DisplayName, or TestCategory. Omit the filter to run the full project. Use dotnet build on the Entry project to compile without submitting a job. Use --no-build after building the current source with the same configuration and properties.

TreatNoTestsAsError fails the run when discovery or execution reports zero tests. The adapter also fails a run whose daemon job selected tests but ran none, with "no selected test ran"; a run in which every selected test is skipped fails this way.

The adapter reports failures to VSTest. To find the daemon jobs for a run, set DBTOOLS_DAEMON_LABEL to a unique value before running dotnet test, or set <Label> under <dbtools-daemon> in the run settings. Every job carries the label. List the jobs with dbtools-daemon-cli jobs --json and find those with that label.

Revit call budgets

CountingRevitCallGate counts each IRevitCallGate.RunAsync request. RevitReadCounters counts each wrapped collector, EditFamily call, temporary transaction and regeneration. Counters advance once per wrapped operation, independent of the number of returned elements. Tests must wrap the Revit API operation they measure; unwrapped calls do not affect the count.

QueuedRevitTurnJourney.RunAsync starts a supplied action from dispatcher work and runs its gate calls through a real ExternalEvent turn. The result includes the gate request count and the native turn summaries. Use it for hosted tests of modeless user actions that ordinary hosted callbacks would run inline. Mark its fixture with [Category("RevitHostedTurns")] so the daemon releases the current API callback at an incomplete await. Compile these fixtures in a *.HostedTurns.Local.Tests project so shared assembly setup owns fixtures with one turn mode.

RevitCallGateModelInspectionTests inspects the staged project and a small project created for the test in one native queued turn. Each inspection uses five collectors, one family edit, one temporary transaction and one regeneration.

FramingTypeProbeBudgetTests loads 160 editable framing families with four types each into the staged project. The test measures analysis through the real Revit gate and rolls back the families and target wall.

Model paths

TestPathResolver reads DBTOOLS_DAEMON_REVIT_MODELS_DIR on every call. The daemon supplies the staged root. Relative paths retain their directory segments. Rooted paths and . or .. traversal segments fail.

var project = TestPathResolver.ResolveTestProjectPath("2026");

The host project resides at <year>/dbtools_test_model.rvt. Its relative link resides beside it at _LinkedModels/sgt_test_linked_model.rvt. Use CopyTestProject when a fixture needs both files in a temporary directory.

RevitFamilyTemplateResolver searches only requested template names beneath CommonApplicationData/Autodesk/RVT <running-year>/Family Templates. It orders English-Imperial candidates first, then paths deterministically. BasicFileInfo.Extract(...).Format must equal the running Revit year. No matching installed template yields Inconclusive with observed formats/errors. Repository-controlled models and assets are different: missing staged files must fail the test.

Hosted context and cleanup

Set DBT_StartHostedAppRuntime in a Local test project that uses App composition or needs App's Revit hooks. Elevation Tags and Joist Girder Weight enable the flag for their view-activation hooks. Profile setup calls RevitHost.EnsureRuntime(app) with the daemon-provided UIApplication. RevitLocalApplication creates the UIControlledApplication wrapper when App starts. Profile teardown shuts down the App lifecycle before releasing the assembly's test profile. The next assembly in the same Revit process starts its own App lifecycle with a fresh profile. If a job leaves a hosted lifecycle active, App replaces it when the profile path changes. Startup validates the theme, configures window capabilities, composes an isolated ribbon, attaches ViewActivated and contextual ribbon hooks, and completes deferred UI startup. The test profile sets AutoUpdateEnabled to false for Elevation Tags, Combined Foundation Tags and Joist Girder Weights. Tests of those updates enable the relevant setting with the production settings provider and restore it during cleanup. Use RevitHost.RunAsync(...) with the daemon-provided UIApplication to enter an explicit Revit API scope. A fixture can resolve RevitCallGateTask from the App service root to construct a QueuedRevitCallGate. App owns that task through shutdown. A fixture that builds its own App container uses AppHostedComposition.CreateLoggingRuntime() and AppHostedComposition.BuildServiceProvider(logging, isolationName, configure). The optional configure callback runs after App registrations. The fixture disposes its provider and logging runtime. WPF name-only product loads resolve with the active App assembly. The API scope ends when the synchronous test body returns its task. A fixture without the App runtime opens the same scope around its synchronous product call. After an incomplete await, enter a scope again only if the driver still owns the native callback on the Revit dispatcher. Use a queued gate after the callback returns.

DBT_TEST_RUN_ID keeps App startup failures headless. Hosted App composition captures startup failure messages. Fixtures release their windows, static state, documents and overlays. A hosted fixture that needs a sandbox window runtime passes DispatcherOperationRegistry.IsRetired and DispatcherOperationRegistry.Start to WindowStaticRuntimeTestScope. The scope releases the configuration, retires dispatcher work, and restores the incoming dispatcher registry state. An assembly that sets DBT_StartHostedAppRuntime starts and shuts down its own App runtime. Its fixtures can verify WindowStaticRuntime.IsConfigured inside RevitHost.RunAsync(...). The shared after-test action checks the App registry for retained tool windows. The daemon terminal owns final release of its active Autodesk document. Use document leases for fixture documents.

When work and cleanup fail, preserve both. Attempt every owned document close, UIDocument disposal, logging shutdown, transaction-group finalization, and window/session disposal. A production launch smoke must use the production session owner and await its exact startup and failure-bearing completion. Await session completion to observe Closed handlers, ViewModel cleanup, and scope disposal.

Add or move a fixture

  1. Identify the production operation and the result to assert.
  2. Select Pure tests for behavior without Revit, Revit-hosted tests for real API/document/session behavior, or Design Automation tests for APS execution.
  3. Mirror the production path beneath Tests/, or Tests/Integration/Revit/ for Revit-hosted fixtures. Include the fixture and support in the matching project.
  4. Use real product workflows, matchers, planners, and persistence. Supply doubles for external inputs such as Revit, network, filesystem, and time.
  5. List the selection, run the focused fixture, and run the affected Pure suites. Compile Revit-hosted fixtures separately when a Revit worker is unavailable.

Windows Pure tests can load Revit types and use their constants and enum values. Use production registrations and pass incidental Revit data through existing product boundaries. A Revit stub method throws NotSupportedException with the message <assembly> is a test stub. Its API calls require the host. This includes calls from type initializers and calls that construct a Revit attribute through GetCustomAttribute<TransactionAttribute>(). Use GetCustomAttributesData() to read attribute metadata. An NUnit action fails the case even if a catch block handles the stub exception. Apply [AllowRevitStubCalls] to a test method that checks this failure. Use Windows Pure tests for actual WPF behavior. Use Revit-hosted tests for document changes and other behavior that calls Revit. Local, Both, and DA NUnit categories are invalid routing metadata. Use [RevitLocal] and [RevitDA] for those execution hosts. Other categories can describe properties independent of the host.

Tests never send OS input or depend on the OS foreground; see User interface input.

Example: native duplicate detection

DuplicateDetectionEngineTests.DetectAsync_HigherScore_WithParameterOverlap uses real duplicate matchers and asserts their returned pairs. The fixture's setup supplies _svc and the external element-name query _names. SetFamilyParameterDiscovery constructs the native discovery state:

[Test]
public async Task DetectAsync_HigherScore_WithParameterOverlap()
{
    var projectState = new ProjectState
    {
        Families = new Dictionary<long, ProjectStateFamilyRecord>
        {
            [100] = new ProjectStateFamilyRecord { ElementId = 100, Name = "Door Type" },
            [101] = new ProjectStateFamilyRecord { ElementId = 101, Name = "Door Type 1" }
        }
    };
    SetFamilyParameterDiscovery(projectState.Families[100], "Width", "Height", "Frame Depth");
    SetFamilyParameterDiscovery(projectState.Families[101], "Width", "Height", "Frame Depth");
    _names.AddName(100, "Door Type");
    _names.AddName(101, "Door Type 1");

    var result = await _svc.DetectAsync(projectState);
    var pairs = result.Groups
        .Where(group => group.Kind == DuplicateKind.Families)
        .SelectMany(group => group.Pairs)
        .Where(pair => (pair.FromId == 100 && pair.ToId == 101) ||
                       (pair.FromId == 101 && pair.ToId == 100))
        .ToList();

    Assert.That(pairs, Is.Not.Empty);
    Assert.That(pairs.All(pair => pair.Score >= 90), Is.True);
}

View Template Comparer (VTC) supplies CategoryTabClassifierTests, which opens the staged project and classifies real Revit categories. That fixture uses [RevitLocal] to exercise the category adapter.

Hosted UI restrictions

Revit-hosted tests cannot display blocking modals. The daemon rejects modal dialogs, disabled native owners, and Revit unhandled-exception windows. This restriction also applies to short-lived dialogs.

Show hosted sessions modelessly with Show and bounded DispatcherDrain or DispatcherFaultScope helpers. Keep API, assembly-context, theme, and real Revit owner checks hosted. Test ShowDialog results, modal-loop exit, native owner disable/restore, and modal-child refusal in Windows Pure tests with real WPF windows and stand-in owners. Audit indirect alert and file-picker calls too.

ToolWindowDialog rejects Revit processes/routing categories before using the session. Its bounded watchdog supports Windows Pure tests, including a beforeShow callback. Hosted assembly setup also installs a modal tripwire on Revit's UI dispatcher: it records WPF ShowDialog entry and posts a Send-priority close of that exact dialog. The test fails even after Pass, Ignore, or Inconclusive. The daemon can detect a modal before the tripwire runs.

CommonDialog may raise the event without a WPF Window. The tripwire records it without closing an unrelated window. Native message boxes, TaskDialog, disabled owners, and separate STA dispatchers remain outside that backstop. The daemon's window probe is authoritative.

Exceptional closure tests use Core's per-window error boundary. Assert that only the exact attached window receives a classified handled-error signal, foreign failures remain unhandled, and unsubscribe/detach remove the observer. Hosted sessions consume that signal through a bounded modeless pump, finalize, and surface the original error before cleanup/lifetime assertions. Modal-frame behavior remains Windows Pure coverage.

Test settings and warnings

Use isolated files with the real settings reader and writer. Cover defaults, layering, case-insensitive keys, generated serialization, invalid values, atomic batches, competing writes, cancellation, and corrupt files. Exercise pending changes and post-commit failures through the real context and persistence workflow. Use Windows Pure tests for WPF bindings and owner handles. Use Revit-hosted tests for prerequisite actions that modify a document.

With real warning, catalog, and context services, check these outcomes:

  • Invalid saved configuration activates a warning during startup.
  • An unsaved invalid draft leaves shared command blocking unchanged.
  • Save and Reset publish decisions for committed values.
  • Clear and Fix act on the matching context and report failures.
  • Command preflight checks every applicable active warning. Ribbon enabled state follows the latest individual warning update.
  • A runtime execution exception suppresses the task for its document session.
  • A startup validation exception is logged without activating a feature warning.

APS Design Automation engine tests

testing/dbtools.DesignAutomation.Engine.DA.Tests contains DB-only NUnit tests for the Revit 2027 Design Automation engine. The dbtools-daemon Design Automation host loads the test assembly in the engine, supplies RevitAPI and NUnit, and passes the engine's Application to a test method that declares one Application parameter. The project targets net10.0-windows, references RevitAPI for compilation only and references no product project. The host rejects an assembly that is or references RevitAPIUI, AdWindows, UIFramework, WPF or Windows Forms. It does not run [Apartment], [RequiresThread] or async test, setup or teardown methods. The tests create a project document in the engine and need no model input.

dotnet build testing/dbtools.DesignAutomation.Engine.DA.Tests/dbtools.DesignAutomation.Engine.DA.Tests.csproj -p:RevitYear=2027
dbtools-daemon-cli submit \
  --assembly .artifacts/bin/dbtools.DesignAutomation.Engine.DA.Tests/debug_2027/dbtools.DesignAutomation.Engine.DA.Tests.dll \
  --design-automation "<deployment>" --year 2027

Register the repository once as a relay project with dbtools-daemon-cli project-create --dir <repository root> --name <name>, and have the deployment allow that project. The CLI matches the --assembly path to the one project whose inventory lists it and uses that project as the source. --project instead submits the project's whole inventory, which holds Local and Pure assemblies that the Design Automation host rejects.

The daemon owns the deployment's APS credentials and enforces its spend cap. --model adds .rvt inputs. A test opens a model by its staged path relative to the working directory.

Results and troubleshooting

VSTest reports executed, passed, failed and skipped counts. Use --logger trx to write a TRX file and --results-directory to choose its location. Find daemon jobs by their run label.

Failure Action
Missing model or parameters Check the project-declared model closure and the daemon-staged paths.
Stale or missing test output Run dotnet test without --no-build to build and test the current source.
Relay or host initialization Check the relay URL and the daemon's worker configuration.
Hidden desktop refusal Find visible_desktop_violation or private_desktop_unavailable in the daemon result.
Batch-only failure Isolate shared state in setup and teardown and inspect cleanup errors.
Missing product artifact Build the Release distribution from a clean checkout and compile the test graph.

BUILD fixtures in the ProductArtifacts category require a source-current dotnet build build/Build.proj and compiled hosted test outputs. See Artifact tests. DistributionContractTests inspect real output references and reject bundled Revit host DLLs. Revit supplies those DLLs at runtime.

DevModeCollectibleUnloadTests (in dbtools.Distribution.Tests) checks on Linux that a Dev Mode generation unloads. For each of 2026 and 2027 it loads the BuildAll output into a collectible AssemblyLoadContext, composes it, unloads it and requires the context to be collected:

  • Tool_module_composition_releases_the_collectible_generation runs AppToolModuleRegistrar.RegisterModules and builds and disposes the provider.
  • Retiring_gm_mapping_work_releases_the_collectible_generation retires GM's operation gate from its busy notification and while work is in flight. It checks that cancellation settles without the window dispatcher and the generation collects.
  • Resolved_app_singletons_release_the_collectible_generation builds the App provider from AppServiceProviderFactory.RegisterServices and resolves every closed singleton that is not a WPF type. A singleton whose resolution runs a WPF or Revit UI static initializer that fails on Linux is left out; the test lists these singletons and fails when the list changes.

A host context stands in for the Revit process. It holds dbtools.Presentation, the Windows Desktop runtime pack rewritten as IL-only images, and the year's Revit API reference packages rewritten as IL-only images whose methods throw. The test project restores the runtime pack selected by the SDK. BuildAll restores the Revit packages. No window opens and no Revit call runs, so Revit-side caches, Revit events and WPF resource lookups after a reload are outside this test.

Inspect %APPDATA%/dbtools/Logs/ first for reported application failures. Hosted job output returns application logs. Use the selected Revit year's journal for a crash only when those logs are inconclusive.
