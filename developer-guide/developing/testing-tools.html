Testing Tools for DBTools Development

This guide covers the complete testing infrastructure for DBTools, including test categories, running tests, writing effective tests, and using the TestSupport library.

Overview: Testing Philosophy

DBTools follows a production-first testing philosophy:

  1. Fix production code before changing tests - When a test fails, investigate production code first
  2. Assert outcomes, not interactions - Tests must verify real results, not just that mocks were called
  3. Stub only true externals - Mock the Revit API, filesystem, and network; never mock your own services
  4. No fake tests - If a test passes regardless of production correctness, delete it

What Makes a Test Legitimate

Legitimate (KEEP) Illegitimate (DELETE)
Revit API stubs Your own service mocks
File system stubs PlacementExecutionService/handler mocks
Network stubs Test doubles with domain behavior
Time/Random stubs for determinism "Mock was called" assertions only

Test Categories

DBTools has pure, local Revit, and a Revit 2026 Design Automation Sentinel lane. The Sentinel is an HTTP client of Autodesk's cloud. test.sh --scope da runs it on the invoking host with dotnet test, never through the daemon. See APS Design Automation Sentinel.

1. Non-Revit Project Tests

Tests that run without Revit. Use plain dotnet test for daemon-backed Pure entries; test.sh remains the coordinator route and Linux-native BUILD/DIST route:

  • Build Tests - Linux-native BUILD suites verify DBTools build output structure and metadata; run them on Linux, not the Windows broker
  • App Tests - Verify DBTools.App host queue and resource-contract behavior without launching Revit; this lane still needs the Windows Desktop runtime because it references the WPF app assembly
  • Core Tests - Verify DBTools.Core runtime behavior without launching Revit
  • Owner Pure Tests - Tool-owned pure logic tests in .Pure.Tests projects
  • DA Sentinel Tests - One real APS Design Automation WorkItem test that only the operator runs, plus network-free unit tests of its client
# Run build validation tests
./test.sh test --tool BUILD

# Run app host tests
./test.sh test --tool APP

# Run core runtime tests
./test.sh test --tool CORE

# Run the DA Sentinel's network-free tests; the WorkItem test itself is operator-only
./test.sh test --tool DA-SENTINEL --scope da -f 'TestCategory!=RevitDA'

# Run GM pure owner tests without launching Revit
./test.sh test --tool GM --scope pure

# Scope to one tool (pure runs in-process; Revit-hosted dispatches to the fleet)
./test.sh test --tool GM --scope pure

GM pure tests are for production behavior that can run over native DTOs, filesystem/cache contracts, and explicit true-external stubs. StatePersistenceTests, UIStateCacheTests, and UIStateLifecycleTests are pure because they exercise UI-state and saved-mapping persistence directly; MappingIntentStoreTests, SharedParameterTreeProjectorTests, SavedMappingRestoreWorkflowTests, FamilyMappingSelectionNavigationWorkflowTests, OperationRowProjectorTests, SessionOperationGateTests, and ProjectStateStoreTests are pure because they exercise native services directly, including persisted mapping-intent restoration, shared-parameter tree projection, saved-mapping restore, family-details navigation, commit-review operation and error rows, the session operation gate and overlay lifecycle, and project-state replacement. StatePersistenceRegistrationTests remain [RevitLocal] because AddGm validates the production service graph.

2. Revit Integration Tests

Tests that require a running Revit instance. Plain dotnet test on a daemon Hosted entry submits [RevitLocal] fixtures through the VSTest adapter. The coordinator continues to use test.sh, which submits through the daemon CLI. Both routes execute on the daemon fleet (the daemon boots Revit + NUnit + the add-in there):

  • UI Tests - ViewModel integration tests
  • Document Tests - Tests requiring Revit documents with elements
  • Adapter Tests - Tests verifying Revit API interactions

Test Host Markers

Revit-hosted tests must never display a blocking modal. The daemon probes visible Revit-process windows every second and rejects the whole run for a #32770 dialog, a disabled window anywhere in the native owner chain, or a Revit Unhandled Exception window. A short-lived dialog is still a violation.

Show real sessions modelessly with Show and use the shared bounded DispatcherDrain or DispatcherFaultScope pump. Keep Revit API, runtime ALC, theme, and real main-window owner identity checks hosted. Move ShowDialog results, modal-loop exit, native owner disable/restore, and modal-child refusal checks to Windows-VSTest Pure tests using real WPF windows and stand-in owners. Audit indirect calls, including owner-disabling presenters and alert/file-picker paths. ToolWindowDialog rejects the Revit process and Revit routing categories before it touches the session. Ad-hoc NUnit metadata cannot bypass the process check. Its watchdog remains available to Windows Pure tests, including a beforeShow callback for sessions deliberately closed before their modal loop.

The shared hosted assembly setup installs the runtime modal tripwire on Revit's UI dispatcher. It records an entering WPF ShowDialog and posts a Send-priority close of that exact dialog. The assembly action fails the test even if the body later calls Pass, Ignore or Inconclusive. The tripwire does not permit a modal: the daemon can still detect it before the close executes.

CommonDialog can raise the same event without a WPF Window; the tripwire records the violation and does not guess which unrelated window to close. Native message boxes, TaskDialog, disabled owners and tests with their own STA dispatcher remain outside that backstop. The daemon's visible-window probe is the final authority.

The current implementation uses explicit attributes for execution routing:

using DBTools.Tests.Shared;

[TestFixture]
[RevitLocal]
public class MyLocalRevitTests
{
    [Test]
    public void Test_LocalRevitBehavior()

    }
}
  • plain [Test] for pure/off-Revit tests
  • [RevitLocal] for local Revit-hosted tests
  • [RevitDA] for true APS Design Automation WorkItem tests

[RevitDA] marks a test that runs a real APS WorkItem. [RevitLocal] marks a test that runs in the Revit daemon; neither category implies support for the other host.

Owner test projects stay under the owning tool's Tests/ directory. Pure and local execution are separated by project membership, but project compile items separate Pure and hosted source sets. A plain [Test] fixture belongs in the owner pure project. [RevitLocal] fixtures belong in the owner local project. [RevitDA] fixtures belong in a DA project with a real WorkItem execution route before they claim DA coverage.

Host selection follows each test's own metadata rather than a flag: a plain [Test] runs in-process and a [RevitLocal] fixture runs Revit-hosted on the fleet. A [RevitDA] fixture is an APS WorkItem test. It runs on the invoking host as an HTTP client; the daemon never runs it.

Revit-hosted tests classify every missing prerequisite before deciding whether a skip is honest:

  • Repository-controlled inputs and expected production behavior are required. A missing staged model or asset, canonical element/view/style/material/link baseline, failed production outcome, or failed rollback/cleanup step must fail with the requested and observed state, resolved path, and running Revit year where relevant.
  • A skip is valid only when the current supported Revit runtime actually lacks a required API capability. The test must probe the current API and report the exact missing member or capability plus the running year; an owner-declared year range is not evidence.
  • Arbitrary exceptions remain failures. Tests must not catch and relabel them as inconclusive, search alternate models, repair fixture data dynamically, or swallow cleanup failures.

When both test work and owned cleanup fail, preserve both exceptions. Teardown must attempt every owned document close, UIDocument disposal, logging shutdown, transaction-group finalization, and window/session disposal step before reporting the aggregate failure. For production window-composition smokes, calling Window.Close() is not closure proof. The test must use the same production session owner as the command and await its failure-bearing completion through actual Closed, command/view-model cleanup, and scope disposal before closing the host document. Every session must likewise await its exact startup task and its attempts to persist UI state, release preview/Helix/effects, finalize the transaction group, close the window, detach handlers, and dispose the view model before disposing the App run scope; actual Closed is asserted separately from the cleanup-attempt marker. Startup Failed, Cancelled, or absent outcomes always select rollback. Once startup succeeds, persistence or cosmetic cleanup failures do not change the requested model outcome; failed transaction-group health still selects rollback. Exceptional dispatcher closure must exercise the Core-owned per-window error boundary rather than attach a tool-specific dispatcher handler. Contracts must prove that a classified failure notifies only the exact attached window after Core presentation and is marked handled, while a foreign failure is neither notified nor handled. They must also prove explicit unsubscribe and boundary detach remove the observer. The hosted session consumes that exact handled-error signal through a bounded modeless pump, surfaces the original primary failure after finalization, and orders cleanup and broken-lifetime assertions after it. Modal-frame behavior belongs to Windows Pure coverage. Hosted launch smokes must prove rollback and actual closure through the production session owner.

UI-state persistence logs and propagates its contextual failure to the session owner without invoking a window-affine notification from its background continuation. An incomplete dispatcher-affine task is not awaited after its window/pump lifetime is known to be gone; the broken-lifetime assertion is retained and the model outcome is downgraded to rollback while safe cleanup continues. The session still aggregates every persistence, preview, window, handler, view-model, transaction-finalization, notification, and logging failure, and the command's safe-execution boundary owns user-facing reporting.

The old Local, Both, and DA execution categories are invalid. The taxonomy guard fails if they reappear. A true DA test must execute through APS WorkItem infrastructure and assert real output/log/model artifacts. Attribute blocks may combine NUnit and routing metadata, such as [Test, RevitLocal]; discovery treats that the same as separate [Test] and [RevitLocal] attributes. Non-routing categories such as [Category("Integration")] remain allowed only as orthogonal facets like external service dependency markers.

  • DBTools.App.Pure.Tests links the BCL-only idle gate and routes Windows Pure execution through the daemon relay
  • DBTools.App.Local.Tests is reachable through ./test.sh test --tool APP --scope local, runs Revit-hosted on the fleet, and receives the staged product root with Tools/

Tool test suites stay fully contained under their owner Tests/ directory, but execution hosts stay split by project. Do not consolidate pure, local Revit, and true DA tests into one project unless the build can preserve all three host contracts without pulling the Revit add-in host or APS dependencies into plain [Test] execution. Today the accepted shape is:

  • owner .Pure.Tests.csproj for plain [Test] fixtures
  • owner .Local.Tests.csproj for [RevitLocal] fixtures
  • WorkItem-backed DA project/manifest ownership only when [RevitDA] tests exist for that owner

Directory organization rules:

  • keep test files beside the owning tool/project under Tests/
  • split directories before they grow past roughly 12 test/support files
  • remove empty test directories
  • do not create placeholder folders with no files
  • place shared or test-only collaborators under Support/, and only when they stub true externals or construct native DTO state

Setting Up a New Test Project

  1. Create the test class in the appropriate Tests/ directory
  2. Add NUnit attributes: [TestFixture] and [Test]
  3. Reference TestSupport: Add using DBTools.Tests.Shared
  4. Add [RevitLocal] or [RevitDA] only when the test needs that execution host

TestSupport Library

The TestSupport library provides shared utilities for all tests.

  • Execution/ owns the Revit execution attributes: [RevitLocal] routes daemon jobs, and [RevitDA] marks the Sentinel's APS WorkItem test.
  • Paths/ owns repository-root and Revit test-model path resolution.
  • Logging/ owns the shared bridge from NUnit output to DBTools logging. The bridge explicitly initializes shared App paths, then passes the side-effect-free AppPaths.LogsDir value to standalone logging.
  • TestDoubles/ owns behavior-neutral shared doubles used by multiple tool suites.
  • TestHost/ owns local Revit context helpers.

Test Path Resolution

Resolves test model paths from the test runner environment:

  • daemon-hosted Revit runs use DBTOOLS_DAEMON_REVIT_MODELS_DIR, which points at the daemon-staged model directory for the current job; the resolver evaluates this override on every call and does not cache it in the test process
  • the submitted model tree keeps its relative paths below that staged root; ResolveTestModelPath(...) validates the requested relative path and preserves its year, tool, shared-directory, and file-name segments
  • a model below <year>/Regression/ is an operator's working copy whose linked models are not staged; DocumentLease sets the staged copy's Revit links not to load before it opens one, and refuses a regression path outside the staged root
  • Pure fixtures use DBT_TEST_REPO_ROOT; hosted tests use the daemon-staged model root
  • there is no Windows-accessible repo-root metadata path and no %APPDATA% model cache
  • Revit-local tests that create transient fixture families use RevitFamilyTemplateResolver; it derives the exact current-year root from CommonApplicationData/Autodesk/RVT <Application.VersionNumber>/Family Templates, considers only the requested template file names, and orders English-Imperial candidates first with a deterministic path tiebreaker
  • each candidate is accepted only when BasicFileInfo.Extract(...).Format exactly matches the running Revit version; if none match, the fixture is inconclusive with every observed candidate format or extraction error reported

The family-template resolver is a capability probe because the template installation is owned by the current Revit host. In contrast, files requested below testing/RevitTestModels are repository-controlled staged inputs and their absence is a failed fixture, not an inconclusive case.

// Get base test models directory
var modelsDir = TestPathResolver.ResolveTestModelsDir();

// Get specific model path
var gmModel = TestPathResolver.ResolveTestModelPath("2026", "GM", "gm_test_model.rvt");

Writing Pure and Revit-Hosted Tests

Plain [Test] is the target marker for pure/off-Revit tests. A pure test should run in a normal NUnit/VSTest process without Revit API references, WPF/window behavior, the Revit add-in host, or APS Design Automation infrastructure.

Use [RevitLocal] only when the test genuinely requires local Revit-hosted execution. Use [RevitDA] only when the test executes through a real APS WorkItem path and asserts real WorkItem output, report, model, or sentinel artifacts.

The old phrase "DA-compatible" is no longer precise enough for new work. DA coverage requires actual WorkItem execution and output validation.

Example: Unit Test for Service Logic

Excerpt from src/Tools/Common/GM/Tests/Features/Duplicates/Detection/DuplicateDetectionEngineTests.cs:

[TestFixture]
public sealed class DuplicateDetectionEngineTests
{
    [Test]
    public async Task DetectAsync_DetectsFamilyDuplicates_WithSameStemAndParameterOverlap()
    {
        // Arrange: real project state with 64-bit element ids
        var projectState = new ProjectState
        {
            Families = new Dictionary<long, ProjectStateFamilyRecord>
            {
                [100] = new ProjectStateFamilyRecord { ElementId = 100, Name = "Plate" },
                [101] = new ProjectStateFamilyRecord { ElementId = 101, Name = "Plate1" }
            }
        };
        SetFamilyParameterDiscovery(projectState.Families[100], "Width", "Height");
        SetFamilyParameterDiscovery(projectState.Families[101], "Width", "Height");

        // Real matchers; only the Revit name query is a stub for the true external
        var names = new StubElementQuery(new Dictionary<long, string> { { 100, "Plate" }, { 101, "Plate1" } });
        var svc = CreateService(names);

        // Act
        var res = await svc.DetectAsync(projectState);

        // Assert: real outcome
        var famGroups = res.Groups.Where(g => g.Kind == DuplicateKind.Families).ToList();
        Assert.That(famGroups.Count, Is.GreaterThanOrEqualTo(1));
        var anyPair = famGroups.SelectMany(g => g.Pairs).Any(p => p.FromId == 100 && p.ToId == 101 && p.Score >= 90.0);
        Assert.That(anyPair, Is.True, "Expected high-score pair between 100→101.");
    }

    private static DuplicateDetectionEngine CreateService(
        IElementNameQuery names,
        IMaterialCatalog? materials = null,
        IGraphicsStyleCatalog? styles = null)
    {
        var naming = new NamingSimilarity();
        return new DuplicateDetectionEngine(
            new FamilyDuplicateMatcher(naming, new DuplicateParameterSimilarityEvaluator()),
            new StyleDuplicateMatcher(styles ?? new StubStyleService()),
            new MaterialDuplicateMatcher(materials ?? new StubMaterialService(), naming),
            new SharedParameterDuplicateMatcher(naming),
            names,
            NullLogger.Instance);
    }
}

Example: Build Test

DistributionContractTests is a [Category("Build")] fixture over the assembled distribution candidate; SupportedYears comes from the candidate's build metadata:

[TestCaseSource(nameof(SupportedYears))]
public void DBTools_DoesNotBundleHostAssemblies(int year)
{
    RequireArtifacts(year);

    var yearPath = GetYearPath(year);
    var bundledHostAssemblies = Directory
        .GetFiles(yearPath, "*.dll", SearchOption.AllDirectories)
        .Select(Path.GetFileName)
        .Where(fileName => fileName != null)
        .Select(fileName => fileName!)
        .Where(fileName => ForbiddenHostAssemblyFiles.Any(forbidden =>
            forbidden.Equals(fileName, StringComparison.OrdinalIgnoreCase)))
        .Distinct(StringComparer.OrdinalIgnoreCase)
        .OrderBy(fileName => fileName, StringComparer.OrdinalIgnoreCase)
        .ToArray();

    Assert.That(bundledHostAssemblies, Is.Empty,
        $"Year {year}: dist output must not bundle Revit host assemblies ({string.Join(", ", bundledHostAssemblies)})");
}

DBTools.dll is expected to reference Revit host assemblies; Revit supplies them at runtime. The artifact contract rejects copying those host DLL files into the shipping distribution.

Using RevitHost for Context

For tests requiring Revit context:

[Test]
[RevitLocal]
public async Task MyTest_WithRevitContext(UIApplication app)
{
    await RevitHost.RunAsync(app, async () =>
    {
        // Code runs within Revit context
        var doc = app.ActiveUIDocument?.Document;
        Assert.That(doc, Is.Not.Null);
    });
}

RevitHost is the shared local-test contract for Revit-hosted execution. It now does more than just queue into the host:

  • initializes the Revit year from UIApplication.Application.VersionNumber
  • enters the ambient call-gate scope used by daemon-hosted local tests
  • initializes the owned App host through AppRuntimeHostLifecycle.InitializeHost
  • installs the test-host runtime assembly context so WPF name-only DBTools.* loads resolve in the same ALC as DBTools.dll
  • carries the daemon-provided UIApplication as data; DBTools-owned native callback entries use a short main-thread RevitCallGateApiContext scope for their synchronous prefix, while continuations after an await use the product probe or queue and never retain that scope
  • enters RevitAmbientScope for both inline and queued execution; that scope is the sole owner that publishes and restores the ambient UIApplication

That means local fixtures should use RevitHost.RunAsync(...) instead of duplicating their own host/add-in/gate checks. Revit-hosted tests that bypass RevitHost can end up depending on ambient driver or desktop startup side effects rather than the shared test-host contract. A fixture releases only the runtime, task host, window owner, static runtime, and exact window overlay host it created; the daemon terminal owns the active Autodesk document's final release.

For Revit-hosted runs on the fleet, the dbtools-daemon test driver provides a DBT_TEST_RUN_ID. DBTools uses that test-run identity to keep startup failures headless in automation instead of blocking the job behind a modal DBTools error dialog.

Anti-patterns to Avoid

// BAD: Mocking your own service to make test pass
var mockEngine = new Mock<IDuplicateDetectionEngine>();
mockEngine.Setup(e => e.DetectAsync(
        It.IsAny<ProjectState>(), It.IsAny<IProgress<DuplicateKind>?>(), It.IsAny<CancellationToken>()))
    .ReturnsAsync(new DuplicateDetectionResult());

// BAD: Asserting only mock interactions
mockService.Verify(s => s.DoSomething(), Times.Once);
// Missing: actual outcome assertion!

// BAD: Test double that adds domain behavior

Running Tests

Available route: plain dotnet test

Daemon entry projects use the vendored 0.20.9 adapter. Hosted entries generate per-year Sources with their matching Models and Includes. The runsettings set RequiresInteractiveDesktop from the selected Pure source assemblies; the daemon always runs test code on its private hidden desktop. This route is validated for hosted and Pure. A true value routes UI rendering to a worker with an interactive private desktop; it never permits a test on the user's visible desktop. Hosted sources build as plain NUnit libraries, because Revit runs NUnit in-process. Pure sources keep Microsoft.NET.Test.Sdk, because the daemon runs each Pure source in its own VSTest testhost. The DBTOOLS_DAEMON_REQUIRES_INTERACTIVE_DESKTOP environment variable overrides the generated value. The package pin (DBT_DaemonTestAdapterSha256) is checked by dotnet test only; IDE runners and vstest.console do not run it.

Set DBTOOLS_DAEMON_RELAY_URL to the configured relay URL. test.sh reads the same environment variable (or accepts --relay); credentials remain daemon-owned. DBTOOLS_DAEMON_MACHINE_ID pins a machine in either route. Leave it unset for daemon AUTO selection.

Coordinator route: test.sh

test.sh is the coordinator's repository test route. Its current submission path uses the published dbtools-daemon-cli 0.20.9. It resolves the requested project lane, runs pure [Test] fixtures locally when the host supports them, and submits daemon-routed Pure and Revit-hosted [RevitLocal] fixtures as a job to the dbtools-daemon relay; the daemon boots Revit + NUnit + the add-in on the fleet. Auth is daemon-owned; the repo entrypoint does not accept or persist relay tokens.

The wrapper resolves project ownership before building. It builds each selected lane/year as one graph and finishes all requested graphs before the first submission. Each graph produces daemon input metadata and a prepared-artifact receipt containing source content identity, the selected project set, and output hashes. The receipt uses repository-relative paths and is keyed by lane, year, and project set. Compiling one tool does not overwrite another tool's receipt. A second edit to an already-dirty file invalidates the receipt. A source edit during compilation refuses the receipt. Normal test builds the current selection; --no-build is an explicit strict consumer for matching prepared artifacts and fails before routing when source, selection, or output bytes differ. Git's configured filters preserve source identity across tracked LFS model hydration. Receipt hashes still verify the selected model payload bytes.

Use repeatable --project PATH[,PATH...] with test, validate-request or list to intersect tool, scope and fixture selectors with repository-relative test project paths. Use forward slashes. Unknown paths and paths outside the requested tool/scope fail with exit 2. For Linux CI acceptance without Sandbox's Windows runtime, use:

./test.sh test --tool BUILD --scope pure --project testing/DBTools.Build.Tests/DBTools.Build.Tests.csproj,testing/DBTools.Distribution.Tests/DBTools.Distribution.Tests.csproj

./test.sh list --projects <selectors> prints only sorted scope<TAB>project.csproj rows. Paths are repository-relative with forward slashes. Every resolved project appears, even when static discovery finds no methods. This mode cannot be combined with --summary. An empty selection fails with exit 2. CI consumes these rows directly and rejects an explicitly requested scope absent from the listing.

After the product-only BuildAll step, CI invokes test --compile-only per Windows scope, building each selected test graph itself and using that scope's --project CSV and the original selectors. It saves the exact list --projects rows used for the producer selection and writes a schema-2 prepared-artifact receipt after the selected assembly, dependency, model, and include closure is built and hash-matched. Pure is year-free. Local receives the selected year; DA is always 2026. Transfer each selection's build-record-*.json and the union of its recorded output files, models, and includes to the same relative paths in a clean checkout. Windows CI consumes its prepared artifacts with test --no-build and the same scope, project set, selectors and hosted year. Receipts require the exact project set. A source or output mismatch fails without rebuilding. Linux native CI uses the ordinary test route and builds its selected graph. validate-request accepts the consumer's --no-build argv without reading test results and validates model metadata without copying model payloads.

The wrapper stores verified output bytes in the hash-addressed ${TMPDIR:-/tmp}/dbtools-test-inputs/<worktree-sha256>/objects/<sha256> cache and stages them into a private run directory on that filesystem before any submission. It rechecks the hash before reuse and uses a hard link or copy fallback, so later builds cannot change the frozen bytes. Local execution and daemon upload use that frozen copy. Local Pure runs execute the frozen assembly through dotnet vstest. For Pure fixtures, the wrapper exports DBT_TEST_REPO_ROOT for repository and restore-graph lookup in relocated outputs. Direct Pure callers can use embedded DBTools.RepoRoot metadata. The testhost working directory does not select restore inputs. Local jobs use the daemon-staged model root and temporary work directories without requiring a worker checkout. On Windows, the two Linux-native BUILD projects are skipped before compilation with a notice; the separate closed DIST acceptance suite remains daemon-routed. Explicit --project selection of only native projects fails before building on Windows. A changed selection with no runnable Windows projects and no explicit projects skips with a notice.

Repeat --fixture to select several exact classes. Attribute lists, separate attribute lines, qualified NUnit attributes and implicit fixtures are supported. Local filters end the fixture FQN with a dot, so similarly named fixtures are not included. Daemon submissions use repeatable --fixture-fqn arguments restricted to the submitted project. SGT Pure selects both projects.

The Local scope submits one request per selected year with the existing selected assembly and model contract. Two selected years remain separate requests so their reports and model closures stay independent. Pure daemon execution submits one request per selected project; each request carries only its own fixture selectors. All selected projects run even when one fails, and the aggregate returns a nonzero exit if any failed. DBT_PURE_CONCURRENCY sets the maximum number of concurrent daemon Pure submissions; it defaults to 2. Native Linux Pure suites execute serially. Signal and EXIT cleanup terminates in-flight submit process groups on Linux. TERM also stops graph builds and local test processes there. Windows waits for command status without Bash job control. Independent scopes continue after a failed execution. A fixture selects only requested scopes that own it. DBT_MSBUILD_MAX_CPU_COUNT controls graph build parallelism and defaults to 2.

./test.sh rerun --request REQUEST_ID reruns failures from previously submitted bytes. It does not compile or test edited source. Use a normal test invocation for new bytes.

Parallel Agent Safety

build.sh and test.sh take no lock. Run one build or test command per worktree at a time; agents run heavy commands through .agents/work/worktree_guard.sh, which holds a per-worktree lock. The wrapper does not take a local Revit process lock: pure tests run in-process, and Revit-hosted tests dispatch to the dbtools-daemon fleet, which serializes and provisions Revit hosts on its side. There is no longer a user-global add-in config to quarantine.

CI

CI runs the same test.sh entrypoint so semantics stay identical between local and CI:

# Build / app / core suites
./test.sh test --tool BUILD
./test.sh test --tool APP
./test.sh test --tool CORE

The CI workflow validates its dispatch inputs on an Ubuntu preflight job, then runs the same test.sh request on the self-hosted runner. CI holds no APS credentials, so a CI request that selects --scope da fails at the Sentinel.

Source: test.sh (run_da_scope) Source: testing/DBTools.DesignAutomation.Sentinel.DA.Tests/

LightweightSentinel_ExecutesRealDesignAutomationWorkItem is the one real APS Design Automation test. It zips the Sentinel appbundle, uploads it and the seed model, and runs a Revit 2026 WorkItem in Autodesk's cloud. The test project targets plain net8.0 and loads no Revit or Windows API, so it runs on Linux or Windows with dotnet test. The daemon never runs it.

Only the operator, or the coordinator agent with the operator's standing permission, runs it. Sub-agents, CI and the daemon hold no APS credentials. Run it from the repository root with the APS app credentials in the shell:

APS_CLIENT_ID='<client id>' APS_CLIENT_SECRET='<client secret>' ./test.sh test --tool DA-SENTINEL --scope da
  • APS_CLIENT_ID and APS_CLIENT_SECRET are required. When either is missing, the test fails with a message that names both variables. It never skips.
  • APS_BUCKET optionally selects the OSS bucket (default dbtools-tests).
  • The WorkItem part takes 5–12 minutes. The test stops waiting after 12 minutes.
  • Each run spends APS processing time for one Revit 2026 WorkItem.
  • Monthly allowance: the operator's Autodesk account includes 300 free APS processing minutes per month (APS product details, noted 2026-11-05). Billing counts compute time, not the wall-clock wait. The first two Sentinel runs (2026-11-05) used 30,540 compute milliseconds together, about 15 s each. Use the allowance to keep APS support working, and spend it carefully: run the smallest test that answers the question, and do not repeat a run whose result is already known.
  • test.sh builds the Revit 2026 DA graph and runs the frozen test assembly on this host. It writes result.trx and the NUnit work files (the uploaded bundle zip and the downloaded WorkItem output) to .artifacts/test-results/<run>/DBTools.DesignAutomation.Sentinel.DA.Tests/. For --scope da it rejects submit, rerun, --result-json and daemon options. A da-only request rejects every year other than 2026; a request that also selects pure or local must include 2026.

Each run creates its own appbundle version and activity version, binds a new run alias (run<32 hex digits>) to each, and writes to an output object named with the same id. The activity loads the appbundle version that this run uploaded. The test asserts the RevitVersion that Revit reports from inside the WorkItem.

After the run, pass or fail, the test deletes all but the newest two versions of the Sentinel activity and of the Sentinel appbundle, and the aliases that point at them, at most 25 versions of each resource per run:

  • Activities go first. An appbundle alias that a remaining activity version loads is kept, with its version, even when the two resources have different version counts.
  • An activity or appbundle that does not exist yet has nothing to prune; each resource is pruned even when the other fails. When the activities' references cannot be read, every appbundle alias is kept and only versions that no alias names are deleted.
  • A version or alias that is already gone counts as deleted.
  • A cleanup failure is reported together with the run's own failure.

Text from APS (error bodies, SDK exception messages and the WorkItem report) is redacted before it reaches a log line, an exception or the TRX: the client id and secret, every issued token, bearer tokens, Authorization/Cookie headers and credential fields are replaced, and long text is truncated.

The other tests in the project need no credentials and make no network calls: a fake HTTP handler covers version binding, pagination, token renewal, redaction, pruning and cleanup, run identity, the bundle layout and the credential failure. Agents run only these:

./test.sh test --tool DA-SENTINEL --scope da -f 'TestCategory!=RevitDA'

Debugging Test Failures

Common Issues

1. "Missing required test params file"

Cause: Running a fixture without its declared model input. Both the adapter entry and the coordinator route stage model inputs declared by the test project.

Fix: Use the primary adapter entry or the coordinator route:

DBTOOLS_DAEMON_REVIT_YEARS=2026 dotnet test testing/Daemon/Hosted/GM.Hosted.Entry.csproj \
  --filter "FullyQualifiedName~FamilyDeepScanTests.GM_DeepScan_Smoke"
./test.sh test --tool GM --scope local -y 2026

2. "Source files appear newer than build artifacts"

Cause: Source code was modified since the last build.

Fix: Run the selected suite through the wrapper; it rebuilds the exact current test project and required runtime before submission:

./test.sh test --tool GM --scope local -y 2026

Note: Hosted submission no longer consumes a pre-existing assembly opportunistically. The selected build and artifact resolution are one required wrapper workflow.

3. Revit host issues

Cause: Revit-hosted ([RevitLocal]) tests no longer launch Revit locally; the dbtools-daemon fleet owns the Revit host.

Fix: Run through the adapter entry or coordinator route and let the job dispatch to the fleet:

DBTOOLS_DAEMON_REVIT_YEARS=2026 dotnet test testing/Daemon/Hosted/GM.Hosted.Entry.csproj \
  --filter "FullyQualifiedName~FamilyDeepScanTests.GM_DeepScan_Smoke"
./test.sh test --tool GM --scope local -y 2026

4. Test passes in isolation but fails in batch

Cause: Shared state pollution between tests

Fix: Ensure [SetUp] and [TearDown] properly isolate state:

[SetUp]
public void SetUp()
{
    _notifier = new RecordingErrorNotifier();
    _overlay = new RecordingProgressOverlay();
    // Reset any shared state
}

[TearDown]
public void TearDown()
{
    _notifier.Reset();
    _overlay.Reset();
}

5. BUILD artifact prerequisite failure

Cause: Required build outputs are missing. Artifact tests fail instead of silently creating prerequisites or reporting an inconclusive result.

Fix: Build the required years explicitly. On the shared Linux host, prefix each command with host-gate:

./build.sh BuildTests -y 2026
./build.sh BuildTests -y 2027
./test.sh test --tool BUILD --scope pure --fixture ResourceAssemblyVersionContractTests

Candidate-consuming fixtures additionally require AssembleDistributionCandidate on a clean, committed source tree. The wrapper does not infer that prerequisite from a test filter.
