Settings Packs

A settings pack supplies a tool's editor in the DB Tools Settings window. It binds a typed settings section, an editor context, a WPF view, and optional warnings. Packs appear as cards grouped by their registered ribbon panel.

ISettingsProvider reads current settings and commits section batches. SettingsWindowViewModel owns Save and Reset through SettingsPersistenceWorkflow. Pack contexts edit state and validate it. They do not save independently.

Files and typed sections

The default user file is %APPDATA%/DBTools/settings.<year>.json. AppPaths.SettingsFile requires an initialized Revit year. The process can relocate its base directory through the DBTools.AppPaths.BaseDir AppContext value.

SettingsSectionReader reads appsettings.json from its base directory, then overlays the user file. An absolute user path is used directly. A relative one resolves against the base directory. The reader validates files at construction and reads both layers again on every Get. It retains no file watchers or open handles.

A section is one JSON property, such as Tools.FoundationTags. Its name must be nonblank and cannot contain :. It is not a nested configuration path. Section and property lookup is case-insensitive.

{
  "Tools.MyTool": {
    "AutoUpdateEnabled": true,
    "FamilyPattern": "^Example$"
  }
}

Register generated System.Text.Json metadata with the section as JsonTypeInfo<T>. The same metadata reads options and serializes writes:

using System.Text.Json.Serialization;
using DBTools.Core.Settings.Domain;

namespace DBTools.MyTool.Settings;

public sealed class MyToolSettings : IAutoUpdateSettings
{
    public bool AutoUpdateEnabled { get; set; } = true;
    public string FamilyPattern { get; set; } = "^Example$";
}

Place its JSON context in a separate matching file:

using System.Text.Json.Serialization;

namespace DBTools.MyTool.Settings;

[JsonSerializable(typeof(MyToolSettings))]
internal partial class MyToolSettingsJsonContext : JsonSerializerContext
{
}

IAutoUpdateSettings requires only AutoUpdateEnabled. HasWarning belongs to editor/session state and must not be added as a persisted warning flag.

Keep DTO graphs independent of Revit and UI state. The allowed leaf types are bool, string, and double. Nullable values, collections, dictionaries, and nested DTOs must resolve to those leaf types. Add-in enums and custom TypeConverter/JsonConverter implementations are not supported settings types. Use settable properties with initialized defaults so missing keys retain those defaults. Pure and Revit-hosted test executables disable reflection-based JSON serialization.

Read semantics and failures

The reader recursively overlays objects and merges arrays by index. A shorter override array retains the default array's remaining elements. A later scalar or null does not replace an earlier object or array. A different container kind replaces the earlier container.

Normalization preserves scalar conversions for strings, Booleans, and doubles. String nulls become empty strings. Boolean and double values parse from scalar text. Doubles use invariant culture. Invalid values fail the section read. Missing sections return a new settings instance.

Only a missing file or parent directory means absent configuration. Invalid JSON, a non-object root, access faults, and a directory at a file path remain errors. Comments and trailing commas are accepted. Commits preserve unrelated sections but do not retain comments.

Manifest declaration

Declare the persistence key and pack metadata in manifest.yml:

id: DBTools.MyTool
assembly: DBTools.MyTool
moduleType: DBTools.MyTool.App.Composition.MyToolToolModule
order: 0
panel: Common
tool:
  settings:
    configSection: Tools.MyTool
  settingsPacks:
    - key: common.my_tool
      title: "My Tool"
      warnings:
        - id: core.my_tool.configuration
          title: "My Tool Configuration Invalid"
          message: "Correct the family pattern and save settings."
          disableTools:
            - DBTools.MyTool

configSection names the JSON property. Pack key and warning id are unique catalog identities. They do not have to equal that property. Existing keys use forms such as structural.foundation_tags and core.structural.combined_tags. Each warning requires id, title, and message. disableTools is optional. See Feature Warnings for activation and command blocking.

Registration

Register the typed section in ToolModule.RegisterSettings:

public override void RegisterSettings(IServiceCollection services, ToolManifest manifest)
{
    services.AddSingleton(new SettingsSection<MyToolSettings>(
        manifest.GetRequiredConfigSection(),
        MyToolSettingsJsonContext.Default.MyToolSettings));
}

Register the editor in RegisterSettingsPacks. The following excerpt assumes SettingsPackContext implements ISettingsPackContext<MyToolSettings>, accepts a warning ID, and exposes HasWarning. MyToolSettingsView is the tool-owned pack view:

public override void RegisterSettingsPacks(IServiceCollection services, ToolManifest manifest)
{
    var section = new SettingsSection<MyToolSettings>(
        manifest.GetRequiredConfigSection(),
        MyToolSettingsJsonContext.Default.MyToolSettings);
    var pack = manifest.GetSingleSettingsPack();
    var warning = pack.GetSingleWarning(manifest.Id);

    services.AddDbtSettingsPackDefinition<MyToolSettings, SettingsPackContext>(
        new SettingsPackRegistration<MyToolSettings, SettingsPackContext>
        {
            SettingsSection = section,
            PackKey = pack.Key,
            PackTitle = pack.Title,
            RibbonPanel = manifest.GetRequiredPanel(),
            ApplyBehavior = SettingsPackApplyBehavior.NextToolRun,
            ContextFactory = (_, input) => new SettingsPackContext(input.RequireWarningId()),
            ViewFactory = context => new MyToolSettingsView { DataContext = context },
            Warning = new SettingsPackWarningRegistration<SettingsPackContext>
            {
                Id = warning.Id,
                Title = warning.Title,
                Message = warning.Message,
                ToolInternalNamesToDisable = warning.DisableTools,
                FlagGetter = context => context.HasWarning,
                FlagSetter = (context, active) => context.HasWarning = active
            }
        });
}

These APIs live under DBTools.Core.Settings.Composition, .Persistence, .SettingsPack, and .Warnings. Manifest extension methods live under DBTools.Core.Tools.Manifest. Use the tool's real namespaces for its context, view, and DTO.

SettingsSection, pack key/title/panel, and context/view factories are required registration members. When present, a warning requires its ID, title, message, and flag getter/setter. AddDbtSettingsPackDefinition also checks strings and delegates at runtime. ApplyBehavior defaults to Immediate. Set it explicitly when values apply at the next tool run or require a restart.

Apply timing

Value Meaning
Immediate Saved values apply immediately, such as ribbon visibility flags.
NextToolRun Commands or view-activation tasks read saved values on their next run.
RequiresRestart The pack documents a specific restart requirement.

Do not show a blanket restart warning for all settings. Read settings at the operation boundary so saved changes reach the next operation.

Runtime and context ownership

ISettingsPackDefinition supplies catalog metadata and creates one ISettingsPackRuntime for an editor row. That runtime binds the exact context, typed section, lazy view factory, staged writes, and warning delegates. Callers cannot pair an unrelated context with a warning definition.

SettingsPackCollection carries SettingsPackHostContext from the window factory into runtime creation. Use SettingsPackHostContext.Empty without a host or FromApplication(application) with one. A context extracts the typed application through TryGetApplication<TApplication>().

Initialize bindable state in constructors. Perform model changes through explicit editor actions. Elevation Tags uses host data for preview snapshots and accepts no active document as an empty preview. Combined Foundation Tags uses explicit Refresh, Clear Warning, and Install/Repair actions for prerequisite work. It reports that an action is unavailable when it needs an active document.

Context interfaces

The editor implements these base contracts:

public interface ISettingsPackContext
{
    Task<SettingsValidationResult> ValidateAsync(CancellationToken ct = default);
}

public interface ISettingsPackContext<TOptions> : ISettingsPackContext
{
    void Load(TOptions options);
    TOptions BuildOptionsSnapshot();
}

Optional contracts add specific behavior:

Interface Responsibility
ISettingsStateContext Raise StateChanged for editable-state changes.
IPendingChangesContext Expose HasPendingChanges.
IOwnerAwareContext Receive an owner handle provider for dialogs.
ISettingsPackSaveState<TOptions> Accept MarkSaved(committedOptions) as the persisted baseline.
ISettingsWarningContext Identify the warning that validation evaluates.
ISettingsPackSaveValidation Expose BlockSaveOnInvalid to refuse invalid drafts.
IWarningFixProvider Supply a matching warning's Fix action and label.

SettingsValidationResult.Success is a property. Use SettingsValidationResult.FromErrors(...) for invalid values. Exceptions mean validation failed to run. They are not an invalid-result substitute. Honor cancellation and return messages that identify the invalid value and its correction.

Auto-update editor base

SettingsPackAutoUpdateContext<TOptions> in DBTools.Core.Settings.SettingsPack.AutoUpdate implements the common toggle editor. It owns title/description/tooltip text, AutoUpdateEnabled, HasWarning, ToggleEnabled, ClearWarningCommand, WarningId, pending-change tracking, StateChanged, and the validation envelope. It blocks saving invalid options.

The protected base constructor supplies warning identity and editor text:

protected SettingsPackAutoUpdateContext(
    string warningId, string title, string description, string toggleToolTip);

Derived contexts implement:

protected abstract void LoadCore(TOptions options);
protected abstract void CollectValidationErrors(List<string> errors);
protected abstract bool SettingsEqual(TOptions left, TOptions right);
public abstract TOptions BuildOptionsSnapshot();

Load applies the toggle, clears the context warning, calls LoadCore, and notifies state changes. LoadCore sets a baseline through SetBaseline. MarkSaved uses the exact committed options, not the latest editable snapshot. Edits made while a commit is pending therefore remain dirty.

Elevation Tags and Joist Girder Weights use this base. Combined Foundation Tags implements the interfaces directly because its prerequisite state and repair actions need a different context.

Regex pattern lists

RegexPatternListContext owns bindable RegexPatternEntry rows, add/remove commands, a configured maximum, empty-list default seeding, snapshots that omit blank rows, and state-change events. Load takes at most the configured maximum. Removal retains at least one row. Tool contexts retain their binding property names and validation rules.

Elevation Tags and Combined Foundation Tags use the shared list mechanics with at most three rows per pattern list. Do not copy those mechanics into a new context. Joist Girder Weights uses individual FamilyNamePattern, DeadLoadPattern, LiveLoadPattern, and TotalLoadPattern strings rather than pattern lists.

Tool settings examples

Combined Foundation Tags persists TagFamilyPatterns, PierFamilyPatterns, and FootingFamilyPatterns. Empty lists select these tool defaults:

TagFamilyPatterns      ^DB Pier and Foundation Combined Tag(?: No Elevations)?$
PierFamilyPatterns     ^Foundation Pier(?: - Round)?$
FootingFamilyPatterns  ^(?:Footing|Pile Cap)-Rectangular$

Elevation Tags uses TagNamePatterns with default ^DB Elevation Tag - (?:Concrete|Steel|Wall) Label$, plus TypeOffsets keyed by spot-elevation type name. Joist Girder Weights supplies these defaults for blank individual patterns:

FamilyNamePattern  ^(?:(?:[BV]?G)|Vulcraft) Joist Girder$
DeadLoadPattern    (?:^DL$|Dead\s*Load)
LiveLoadPattern    (?:^LL$|Live\s*Load)
TotalLoadPattern   (?:Point\s*Load|Total\s*Load)

Transfer Drafting Views (TDV) uses LibraryOptions, which contains a Files list of LibraryFile values. Its pack owns file selection, validation, and pending changes. Read each tool's DTO and generated JSON context when extending it.

Runtime reads and programmatic writes

ISettingsProvider exposes typed reads and heterogeneous batch writes:

TSettings Get<TSettings>(SettingsSection<TSettings> section)
    where TSettings : class, new();
Task CommitAsync(IReadOnlyCollection<SettingsSectionWrite> writes,
    CancellationToken ct = default);

Inject the provider and typed section. Read once per operation, then pass that snapshot to the work:

var current = settingsProvider.Get(section);
if (!current.AutoUpdateEnabled)
    return;

For view-activated updates, ViewActivationTask<TSettings> reads once during admission and captures the snapshot in the admission. It checks session warnings separately. See Hooks.

A programmatic write uses the same typed metadata:

var current = settingsProvider.Get(section);
current.AutoUpdateEnabled = true;
await settingsProvider.CommitAsync(new[] { section.CreateWrite(current) }, ct);

Batch related section changes in one CommitAsync. A direct commit persists options. The Settings workflow additionally applies flags, baselines, and warning publication.

Save and reset sequence

SettingsWindowFactory opens the raw DBTools.Presentation.Settings.Views.SettingsWindow.xaml resource through ToolWindowFactory. The registered modal session owns the window, error boundary, owner, handlers, and cleanup. Packs remain separate tool-owned views.

SettingsPackViewModel owns one bound runtime, lazy view creation, pending changes, reset state, owner propagation, warning projection, and disposal. SettingsPanelBlock groups rows. SettingsWindowViewModel delegates persistence to SettingsPersistenceWorkflow under Settings/ViewModels.

Save proceeds in this order:

  1. Evaluate the unsaved drafts. A blocking invalid result stops the save. This pass can update editor warning flags but does not change command blocking.
  2. Capture current pack writes and the flags snapshot.
  3. Commit the complete batch with one file swap.
  4. Mark each pack saved against its exact committed options.
  5. Apply committed flags. Validate saved settings in fresh warning-aware runtimes.
  6. Project and publish warning decisions to the ribbon and Settings UI.

The Validate button diagnoses draft values. It does not publish the draft as saved warning state. Opening Settings validates loaded options. Startup checks warning-aware packs without constructing their views. See Feature Warnings.

A validation or writer failure before publication leaves the settings file and saved baselines unchanged. A failure after the swap becomes SettingsPostCommitException, which identifies the operation and phase. Persisted values remain the saved baseline and the window stays open. Concurrent edits remain pending against that baseline.

Reset All commits default flags and every pack's default snapshot. It attempts to apply all committed defaults before warning validation and aggregates application failures. A pack reset commits only that pack. Both actions ask for confirmation and use the normal warning/feedback path. Cancel preserves current state and feedback. Choosing Reset Settings in the load-problem alert already confirms the reset, so it does not prompt twice.

Atomic persistence

SettingsSectionWriter performs these steps:

  1. Reject an empty batch, null entries, and case-insensitive duplicate section names.
  2. Serialize calls on the writer instance and acquire the sibling settings.<year>.json.lock file exclusively.
  3. Re-read the current document under that lock. Replace only the supplied sections.
  4. Serialize with each section's generated metadata into one document.
  5. Write a .<guid>.tmp file in the same directory and publish it with File.Move(source, destination, overwrite: true).
  6. Attempt staged-file cleanup on success, failure, and cancellation.

A competing process can hold the lock for up to 10 seconds before the writer fails with IOException. Cancellation while waiting leaves the file unchanged. The OS releases the lock on handle close or process exit. The empty lock file persists and does not indicate a live lock.

TextFileIO.s_publicationGate serializes file publication process-wide across writer instances. The writer's own semaphore serializes its commits, while the sibling lock file coordinates separate processes.

TextFileIO allows at most six publication attempts for transient sharing, locking, and access-denied failures. It refuses known read-only destinations immediately and surfaces publication access denial as IOException with the original cause. Cleanup does not replace the primary failure. No backup file is retained.

Same-year Revit processes share this file. Re-reading under the cross-process lock preserves other sections published by the previous writer. A case-variant section name replaces that section in place. An absent file starts an empty object. An existing empty, whitespace-only, malformed, or non-object file is corrupt and is not silently reset.
