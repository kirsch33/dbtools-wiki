Settings Packs

Settings Packs are the mechanism for tools to expose user-configurable options in the DBTools Settings window. This guide covers the complete settings lifecycle: from manifest declaration to runtime access and persistence.

Overview

What Are Settings Packs?

A Settings Pack bundles together:

  1. Settings Model - A typed class holding the configuration values
  2. Settings Pack Context - A ViewModel that manages UI state and data binding
  3. Settings Pack View - A WPF UserControl rendered in the Settings window
  4. Warning Definitions - Optional conditions that can disable tool functionality

Settings Packs appear as collapsible cards in the Settings window, organized by ribbon panel (Common, Structural, Testing).

Why Use Settings Packs?

  • Centralized configuration: Users manage all tool settings in one place
  • Automatic persistence: Settings are saved to settings.{YEAR}.json with atomic writes
  • Fresh reads: ISettingsProvider.Get(section) loads the current layered files
  • Feature warnings: Link settings validation to tool availability
  • Consistent UX: All tools share the same settings interface pattern

Apply Timing

The Settings window should describe when saved values take effect, not show a blanket restart warning.

  • Ribbon visibility and similar shell-level flags can apply immediately after save.
  • Tool settings typically apply on the next command run or next view-activation hook.
  • RequiresRestart should be reserved for an explicitly documented pack-specific limitation, not shown globally.

Architecture

The Settings ribbon command resolves SettingsWindowFactory, which loads the embedded raw DBTools.Presentation.Settings.Views.SettingsWindow.xaml view through ToolWindowFactory and receives a registered modal IToolWindowSession. It calls session.ShowDialog(), so owner handling, reflection scope, normal-close cleanup, and generation-retirement teardown are owned by the same session lifecycle as other tool windows. The session change does not change pack loading, Save, Reset All, validation, warning, cancel, or success-banner behavior.

Defining Settings in manifest.yml

Settings packs are declared in the tool's manifest.yml under tool.settingsPacks:

Schema

tool:
  settings:
    configSection: "<section-name>"  # Required: JSON key in settings.{YEAR}.json
  settingsPacks:
    - key: "<unique-pack-key>"       # Required: Globally unique identifier
      title: "<display-title>"       # Required: Shown in Settings window
      warnings:                      # Optional: Associated warnings
        - id: "<warning-id>"         # Required: Unique warning identifier
          title: "<warning-title>"   # Required: Warning card title
          message: "<warning-msg>"   # Required: Explanation shown to user
          disableTools:              # Optional: Tools disabled when warning active
            - "<tool-internal-name>"
            - "<another-tool>"

Settings Model Classes

Basic Settings Model

A settings model is a POCO class with public properties:

namespace DBTools.Structural.JoistGirderWeight.Settings;

public sealed class JoistGirderWeightSettings : IAutoUpdateSettings
{
    public bool AutoUpdateEnabled { get; set; } = true;
    public bool HasWarning { get; set; }
}

Settings DTO Type Contract

Settings DTO graphs must end in built-in leaf types: booleans, strings, or doubles. Nullable values, collections, dictionaries, and nested DTOs are supported when all their keys, elements, and properties follow the same rule. Add-in enums and types or properties with a custom TypeConverter or JsonConverter are not allowed.

Reads use SettingsSectionReader with each section's generated JSON metadata. It layers application defaults with per-year overrides, matches section and property names case-insensitively, and preserves the established scalar conversions. Only a missing file or missing parent directory is absent configuration; any other fault, such as a directory at the file path, propagates. Writes use the source-generated JsonTypeInfo<T> carried by SettingsSection<T>. Reads and commits share one JSON syntax (comments and trailing commas allowed) and case-insensitive section identity: a commit replaces a case-variant section in place, rejects case-variant duplicates in one batch, and does not keep comments.

Section names are single JSON property names. They must be nonempty and cannot contain :; nested configuration paths are not supported.

For properties with initialized defaults, use settable properties so absent keys retain their defaults. Cover these defaults and file compatibility through the real reader. Pure and Local test executables disable reflection-based JSON serialization through their runtime configuration.

Registering Settings

Settings registration happens in two phases within your ToolModule:

Phase 1: RegisterSettings()

Register the typed section used by the tool and its settings pack:

public override void RegisterSettings(
    IServiceCollection services, 
    ToolManifest manifest)
{
    Guard.NotNull(services, nameof(services));
    Guard.NotNull(manifest, nameof(manifest));
    
    var settingsSection = new SettingsSection<FoundationTagsSettings>(
        manifest.GetRequiredConfigSection(),
        FoundationTagsSettingsJsonContext.Default.FoundationTagsSettings);
    services.AddSingleton(settingsSection);
}

This registration:

  1. Reads the configSection from manifest (Tools.FoundationTags)
  2. Publishes one typed SettingsSection<FoundationTagsSettings> identity
  3. Lets consumers read the current layered files through ISettingsProvider.Get(settingsSection)

Phase 2: RegisterSettingsPacks()

Register the full settings pack definition with UI factory:

public override void RegisterSettingsPacks(IServiceCollection services, ToolManifest manifest)
{
    Guard.NotNull(services, nameof(services));
    Guard.NotNull(manifest, nameof(manifest));
    
    var settingsSection = new SettingsSection<FoundationTagsSettings>(
        manifest.GetRequiredConfigSection(),
        FoundationTagsSettingsJsonContext.Default.FoundationTagsSettings);
    var pack = manifest.GetSingleSettingsPack();
    var warning = pack.GetSingleWarning(manifest.Id);
    var panel = manifest.GetRequiredPanel();
    
    services.AddDbtSettingsPackDefinition<FoundationTagsSettings, SettingsPackContext>(
        new SettingsPackRegistration<FoundationTagsSettings, SettingsPackContext>
        {
            SettingsSection = settingsSection,
            PackKey = pack.Key,
            PackTitle = pack.Title,
            RibbonPanel = panel,
            ApplyBehavior = SettingsPackApplyBehavior.NextToolRun,
            ContextFactory = (sp, input) => new SettingsPackContext(
                sp.GetRequiredService<ISettingsWarningService>(),
                input.RequireWarningId(),
                input.HostContext,
                sp.GetRequiredService<IErrorNotifier>(),
                sp.GetRequiredService<ILogger<SettingsPackContext>>()),
            ViewFactory = context =>
                new FoundationTagsSettingsPackView { DataContext = context },
            Warning = new SettingsPackWarningRegistration<SettingsPackContext>
            {
                Id = warning.Id,
                Title = warning.Title,
                Message = warning.Message,
                ToolInternalNamesToDisable = warning.DisableTools,
                FlagGetter = context => context.HasWarning,
                FlagSetter = (context, active) =>
                {
                    context.HasWarning = active;
                    if (active)
                        context.AutoUpdateEnabled = false;
                }
            }
        });
}

Every mandatory registration value and delegate is a C# required member. The pack definition captures the typed section, so its load and staged-write operations cannot silently choose different names. Warning id/title/message and flag delegates are likewise required whenever a warning is configured. AddDbtSettingsPackDefinition also performs runtime non-empty/null validation at the DI boundary; compile-time requiredness does not replace that admission check.

Tool-Owned Contexts at Runtime

Every production settings pack registers a tool-owned context type. Joist Girder Weight constructs JoistGirderWeightSettingsPackContext in its module's ContextFactory; Elevation Tags builds ElevationTagsSettingsPackContext through ElevationTagsSettingsPackContextFactory. When a settings context needs Revit host state, Core passes SettingsPackHostContext to ISettingsPackDefinition.CreateRuntime(...); packs without host needs receive SettingsPackHostContext.Empty. The host value can be created only through Empty or FromApplication(...), and contexts extract a typed host through TryGetApplication<TApplication>(). The definition immediately binds the resulting typed context, view factory, typed persistence section, and warning operations into one ISettingsPackRuntime; callers never pass an erased context back to a definition or warning. Elevation Tags reads the host only to populate preview type snapshots and still uses an empty list when no active document exists. Foundation Tags reads the same value for prerequisite actions and reports the action-unavailable status when no active Revit document exists. Contexts that carry the standard auto-update toggle derive from the Core production base SettingsPackAutoUpdateContext<TOptions> (see Production Base below). The Core AutoUpdateViewModel<TSettings> under Settings/DesignTime is an internal design-time sample for the settings window designer composition, not production infrastructure.

Settings Pack Context

The context is the ViewModel for your settings UI. It must implement ISettingsPackContext<T>.

Required Interface Methods

public interface ISettingsPackContext<TOptions> : ISettingsPackContext
{
    void Load(TOptions options);       // Load settings into bindable properties
    TOptions BuildOptionsSnapshot();   // Create settings object from current state
}

public interface ISettingsPackContext
{
    Task<SettingsValidationResult> ValidateAsync(CancellationToken ct = default);
}

Optional Context Interfaces

Interface Purpose
ISettingsStateContext Fire StateChanged event when properties change
IPendingChangesContext Track HasPendingChanges for save button state
IOwnerAwareContext Receive parent window for file dialogs
ISettingsPackSaveState<TOptions> Establish the persisted baseline with MarkSaved(committedOptions) without overwriting newer edits
ISettingsWarningContext Trigger warning evaluation via WarningId
ISettingsPackSaveValidation Block settings save when ValidateAsync returns invalid

Use ISettingsPackSaveValidation for settings where invalid values should never be persisted (for example, invalid regex patterns that would be ignored at runtime).

After the file commit, the runtime passes each pack its exact committed options snapshot. The context updates its baseline before post-commit warning validation or ribbon application. Those later failures must not make persisted values appear unsaved. Edits made while the commit was pending remain dirty against the committed snapshot. If applying committed flags or warning state fails, the workflow reports the committed operation and phase while keeping the persisted values as the saved state; the settings window remains open.

Production Base: SettingsPackAutoUpdateContext

Auto-update settings pack contexts derive from the Core production base, which owns the shared mechanics: header text (Title, Description, ToggleToolTip), the AutoUpdateEnabled/HasWarning toggle state with ToggleEnabled, ClearWarningCommand, WarningId (validate-aware), BlockSaveOnInvalid (always true), pending-change tracking against a saved baseline (HasPendingChanges), StateChanged notification, and the validation envelope.

public abstract partial class SettingsPackAutoUpdateContext<TOptions> : ObservableObject,
    ISettingsPackContext<TOptions>,
    ISettingsStateContext,
    IPendingChangesContext,
    ISettingsWarningContext,
    ISettingsPackSaveState<TOptions>,
    ISettingsPackSaveValidation
    where TOptions : class, IAutoUpdateSettings, new()
{
    protected SettingsPackAutoUpdateContext(string warningId, string title, string description, string toggleToolTip);

    // Derived contexts own everything shaped by their settings type:
    protected abstract void LoadCore(TOptions options);          // bindable state + SetBaseline(...)
    protected abstract void CollectValidationErrors(List<string> errors);
    protected abstract bool SettingsEqual(TOptions left, TOptions right);
    public abstract TOptions BuildOptionsSnapshot();
}

Load applies the auto-update toggle, clears the warning flag, delegates to LoadCore, and raises the final state change. MarkSaved resets the baseline from the current snapshot only after a successful settings commit. ValidateAsync collects errors from CollectValidationErrors and converts them into a SettingsValidationResult.

Current consumers: ElevationTagsSettingsPackContext and JoistGirderWeightSettingsPackContext. FoundationTagsSettingsPackContext intentionally implements the context interfaces directly — it owns prerequisite runtime state, warning-fix provider behavior, and shared-parameter refresh/install/repair actions that do not fit the base's shape.

Regex Pattern Lists

Settings packs that expose editable regex rows use the Core shell RegexPatternListContext. It owns the bindable RegexPatternEntry collection, add/remove commands, maximum-row guard, default seeding when a loaded list is empty, blank-value omission from snapshots, and StateChanged notifications. Tool contexts keep their own binding-facing property names so XAML remains tool-specific while the repeated list mechanics stay in Core.

Current consumers are ElevationTagsPatternContext and the Foundation Tags settings-pack pattern partial. Foundation Tags still owns prerequisite runtime state, warning-fix behavior, and shared-parameter refresh/install/repair actions; only the regex-list mechanics moved to the shared context.

    public IRelayCommand AddTagPatternCommand => _tagFamilyPatterns.AddPatternCommand;
    public IRelayCommand<RegexPatternEntry?> RemoveTagPatternCommand => _tagFamilyPatterns.RemovePatternCommand;

    public void Load(FoundationTagsSettings options)
    {
        AutoUpdateEnabled = options.AutoUpdateEnabled;
        _tagFamilyPatterns.Load(options.TagFamilyPatterns);
        // ... load other collections
        _baseline = CloneOptions(options);
        NotifyStateChanged();
    }

    public FoundationTagsSettings BuildOptionsSnapshot()
    {
        return new FoundationTagsSettings
        {
            AutoUpdateEnabled = AutoUpdateEnabled,
            TagFamilyPatterns = _tagFamilyPatterns.BuildSnapshot(),
            // ... etc
        };
    }

    public Task<SettingsValidationResult> ValidateAsync(CancellationToken ct = default)
    {
        var errors = new List<string>();
        ValidatePatternGroup(errors, TagFamilyPatterns, "tag family");
        // ... validate other groups
        
        return errors.Count == 0
            ? Task.FromResult(SettingsValidationResult.Success)
            : Task.FromResult(SettingsValidationResult.FromErrors(errors.ToArray()));
    }

    [RelayCommand]
    private void ClearWarning()
    {
        HasWarning = false;
        RefreshRequiredParameters();
        NotifyStateChanged();
    }
}

Custom context constructors should stay passive. Foundation Tags initializes bindable collections and the status prompt in its constructor; active Revit prerequisite reads happen only through explicit Refresh/Clear Warning/Install-Repair actions.

Persisting Settings

Automatic Save (Settings Window)

When the user clicks Save in the Settings window, SettingsWindowViewModel delegates persistence to SettingsPersistenceWorkflow under Settings/Persistence:

var flags = BuildFlagsSnapshot();
await _persistence.SaveAndValidateAsync(flags, _packs.Rows);

Note: The PublishPackChanged / PackChanged / SettingsPackChangedEventArgs event surface was deleted during the Core Full-Tree Cleanup. Consumers read current values through ISettingsProvider when they need them.

The settings window groups visible packs into SettingsPanelBlock instances under Settings/ViewModels. SettingsPackCollection carries the explicit SettingsPackHostContext from the window factory and asks each definition for one runtime. SettingsPackViewModel owns that runtime: lazy view creation, pending-change and reset-target projection, owner-window propagation, state-change subscription, bound warning projection/application, and runtime disposal. The window view model builds rows and panel groups, but it cannot separately pair definitions, contexts, or warning delegates.

Manual Save (Programmatic)

Save settings directly using ISettingsProvider:

var section = serviceProvider.GetRequiredService<SettingsSection<MyToolSettings>>();
var settingsProvider = serviceProvider.GetRequiredService<ISettingsProvider>();
var settings = settingsProvider.Get(section);
settings.SomeValue = newValue;
await settingsProvider.CommitAsync(new[] { section.CreateWrite(settings) });

SettingsSectionWriter (Low-level)

For direct section writes, the settings provider delegates to SettingsSectionWriter:

public sealed class SettingsSectionWriter : IDisposable
{
    public SettingsSectionWriter(string settingsPath);
    public Task CommitAsync(
        IReadOnlyCollection<SettingsSectionWrite> writes,
        CancellationToken ct = default);
}

App composition supplies the base directory and the absolute AppPaths.SettingsFile to SettingsSectionReader, and supplies that absolute settings file path to this writer. When a reader receives a relative user-file name, it resolves that name relative to the base directory. Each settings DTO has a source-generated JsonSerializerContext beside it. Supply its JsonTypeInfo<T> when constructing the section; SettingsSection<T>.CreateWrite(value) carries that metadata into the heterogeneous batch. The reader loads both layers fresh for each Get; the writer validates duplicate names before I/O, reads the existing document once, updates every supplied section while retaining unrelated sections, and performs one file swap.

A validation or writer failure occurs before the swap and leaves baselines and the settings file unchanged. A baseline/default-application or warning-validation failure after the swap is reported as SettingsPostCommitException, whose operation and phase make the already-committed state explicit.

Only an absent settings file starts a new document. An existing empty or whitespace-only file is corrupt and remains unchanged when a commit fails.

Reset All applies the committed flag snapshot and attempts every committed pack default before warning validation. This keeps the editable settings state aligned with the durable batch even when later post-commit validation fails, and aggregates any default-application failures after all packs have been attempted.

The Settings window asks for confirmation before Reset All or a pack Reset. Cancel leaves the current settings and feedback unchanged. Confirm runs the same persistence and warning-validation workflow and then shows the reset success banner. When settings cannot load, choosing Reset Settings in the load-problem alert already confirms the operation, so that path resets directly without a second prompt.

The SettingsSectionWriter implementation ensures atomic, cross-process-safe writes:

  1. Hold an exclusive lock on the sibling file settings.{YEAR}.json.lock from the re-read of the settings document through its swap. A commit waits while another process holds the lock, and fails with an IOException if the lock stays held for more than 10 seconds. Cancellation while waiting leaves the settings file unchanged. The OS releases the lock when its holder closes the handle or exits, so a crashed process never leaves a stale lock. The lock file itself persists; it carries no content.
  2. Under the lock, re-read the current document and replace only the committed sections
  3. Write to a per-commit staged file .{guid}.tmp in the settings directory
  4. Publish with an atomic File.Move(source, destination, overwrite: true); no backup artifact is retained
  5. Serialize in-process publications. Retry sharing, lock, and publication access-denied failures at most six times; reject known read-only destinations immediately. Surface publication access denial as IOException with its original cause.
  6. Attempt to remove the staged file after publication or failure, including cancellation. Cleanup must preserve the original failure.

Same-year Revit processes share one settings file. Because every commit merges into the document that the previous lock holder published, concurrent commits from separate processes preserve each other's sections: a commit replaces only the sections in its own batch. Within one process, the writer instance also serializes its own commits.

Warning Integration

How Warnings Work

Warnings are conditions that disable tool functionality:

  1. Warning activates: Validation fails (e.g., invalid path)
  2. Tools disabled: Ribbon buttons grayed out, commands rejected
  3. User notified: Warning card appears in Settings window
  4. User fixes: Corrects settings, clicks "Clear Warning"
  5. Tools re-enabled: Ribbon buttons active again

Warning Registration

In RegisterSettingsPacks(), set the public registration's Warning property:

new SettingsPackRegistration<TSettings, TContext>
{
    // Required pack registration members omitted for brevity.
    Warning = new SettingsPackWarningRegistration<TContext>
    {
        Id = "core.structural.combined_tags",
        Title = "Combined Foundation Tags Disabled",
        Message = "Combined foundation tag updates are disabled due to a warning...",
        ToolInternalNamesToDisable = new[] { "DBTools.MyCommand" },
        FlagGetter = context => context.HasWarning,
        FlagSetter = (context, active) =>
        {
            context.HasWarning = active;
            if (active)
                context.AutoUpdateEnabled = false;
        }
    }
}

AddDbtSettingsPackDefinition(...) creates the internal warning definition from this registration. Use the complete registration pattern above when declaring the pack.

Validation-Triggered Warnings

Implement ISettingsWarningContext to automatically trigger warnings on validation:

public sealed partial class TdvSettingsPackContext : ObservableObject,
    ISettingsPackContext<LibrarySettings>,
    ISettingsWarningContext  // <-- Key interface
{
    public string WarningId => _warningId;  // From constructor

    public async Task<SettingsValidationResult> ValidateAsync(CancellationToken ct = default)
    {
        var options = BuildOptionsSnapshot();
        var invalidEntries = options.Files.Where(f => !IsValid(f)).ToList();
        
        HasWarnings = invalidEntries.Count > 0;
        
        if (HasWarnings)
            return new SettingsValidationResult(false, new[] { "Invalid library path" });
        
        return SettingsValidationResult.Success;
    }
}

Startup Evaluation (Validate-Aware Packs)

Validate-aware settings packs are evaluated during addin startup (after ribbon composition and before the initial warning publish) so ribbon tools are disabled immediately when underlying configuration is invalid, without requiring the user to open Settings.

The startup evaluator:

  • Receives the validated SettingsCatalog used by the settings shell and warning service
  • Creates bound pack runtimes without constructing WPF views
  • Loads options from ISettingsProvider
  • Runs ValidateAsync only for runtime contexts implementing ISettingsWarningContext
  • Activates warnings on invalid results
  • Does not activate warnings on validation exceptions (exceptions are treated as runtime errors and should surface via normal error flows/logs)
  • Does not proactively clear warnings on startup
  • Disposes every created runtime, retries a failed cleanup once, records persistent cleanup failures with pack identity, and preserves cancellation even when cleanup also fails

Best Practices

Do

  • Use IAutoUpdateSettings for tools with view-activated auto-update
  • Clone settings in context to detect HasPendingChanges
  • Fire StateChanged when any bindable property changes
  • Implement validation that returns meaningful error messages
  • Use existing patterns - check JoistGirderWeight for simple, FoundationTags for complex

Don't

  • Don't save directly from context - let SettingsWindowViewModel.Save() and SettingsPersistenceWorkflow.SaveAndValidateAsync() handle persistence
  • Don't bypass warnings - respect HasWarning in command availability
  • Don't block UI thread - use async for file I/O in validation
  • Don't ignore CancellationToken - validation can be cancelled

  3. Manual testing in Revit validates UI binding

Summary

Settings Packs provide a unified way to expose tool configuration:

  1. Declare in manifest.yml with settingsPacks
  2. Model settings as a typed class (optionally implementing IAutoUpdateSettings)
  3. Register via RegisterSettings() and RegisterSettingsPacks() in your tool module
  4. Access through the registered SettingsSection<T> using ISettingsProvider.Get(section)
  5. Persist automatically through the Settings window or manually via one ISettingsProvider.CommitAsync(...) batch built with SettingsSection<T>.CreateWrite(...)
  6. Warn users when validation fails, disabling affected tools until resolved

The system provides fresh layered reads, batch-atomic persistence, and consistent UX across all DBTools tools.
