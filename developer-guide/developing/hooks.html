Hooks

Hooks are the extensibility mechanism that allows DBTools modules to respond to Revit application events without coupling directly to the Revit API event system. They provide a clean, testable abstraction for behaviors like auto-updating elements when views change or injecting contextual ribbon UI.

Overview

What Are Hooks?

Hooks are interfaces that define contracts for responding to specific application-level events. Rather than subscribing directly to Revit's UIControlledApplication events, tools register hook handlers that the central HookHost dispatches to when events occur.

Why Use Hooks?

Direct Revit Events DBTools Hooks
Scattered subscriptions across tools Centralized event management
Manual exception handling Automatic error handling via ISafeExecutor
Tight coupling to Revit API Testable abstractions
Risk of blocking UI thread Async-first design
Complex lifecycle management Automatic attach/detach

Key Benefits

  1. Centralized Dispatch: All event handling flows through HookHost, ensuring consistent error handling and logging
  2. Async Support: Hook handlers can perform async work without blocking Revit's UI thread
  3. Automatic Lifecycle: Hooks are attached/detached during app startup/shutdown
  4. Settings Integration: View-activated tasks integrate with the settings system for enable/disable control
  5. Warning System: Hooks can set warnings when they fail, disabling auto-update until the user resolves them

The HookHost

HookHost is the central attach/detach coordinator that:

  1. Delegates handler resolution to HookCatalog, which reads hook types from ToolRegistry
  2. Subscribes/unsubscribes Revit events it owns directly (e.g., ViewActivated)
  3. Delegates ViewActivated safe-executor policy to ViewActivatedHookDispatcher
  4. Delegates initialization, queued rollback, and synchronous shutdown aggregation to HookLifecycleCoordinator
  5. Records each attach owner before initialization starts, so shutdown can detach a subscription while its initialization task is incomplete
var initializedActions = await _lifecycleCoordinator
    .InitializeAsync(attachActions, ct, RecordAttachAction)
    .ConfigureAwait(false);

Available Hook Types

ViewActivationHook

Responds to Revit's ViewActivated event, which fires whenever the user switches views. DBTools keeps a single core-owned hook that dispatches registered IViewActivationTask instances.

public sealed class ViewActivationHook
{
    Task OnViewActivatedAsync(
        UIControlledApplication application,
        ViewActivatedEventArgs args,
        CancellationToken ct);
}

Use Cases:

  • Auto-updating elevation tags when entering floor plans
  • Refreshing parameter values on view change
  • Updating cached view-specific data

Important Considerations:

  • Handler runs on the Revit UI thread context
  • Must not block; use async patterns
  • Errors are caught by ISafeExecutor and logged
  • Automation-host suppression is startup-owned: AddinEntry skips HookHost.AttachAsync(...) when startup detects an externally managed call-gate host, so the handler does not perform its own host check.

IHookLifecycle

Manages module-owned lifecycle hooks. Use this for service modules that need application-wide event subscription, such as dialog interception, and for contextual ribbon injectors that manage their own Revit event subscriptions.

public interface IHookLifecycle
{
    Task InitializeAsync(UIControlledApplication application, CancellationToken ct);
    Task RollbackAsync(UIControlledApplication application, CancellationToken ct);
    void Shutdown(UIControlledApplication application);
}

Use Cases:

  • Cross-tool dialog suppression services
  • Application-wide dialog telemetry or warning hooks that must subscribe once per Revit session
  • Contextual ribbon injectors that add and refresh tool-owned UI from Revit events

Lifecycle:

  1. InitializeAsync is called by HookHost.AttachAsync(...).
  2. The handler owns hook lifecycle while a tool-local adapter subscribes to UIControlledApplication.DialogBoxShowing or equivalent reflected event metadata.
  3. RollbackAsync reverses a completed attach when later initialization fails; it may queue work back into the valid initialization context.
  4. Shutdown completes synchronously inside HookHost.Detach() while Revit's application-shutdown callback is still valid.
  5. Implementations own partial initialization before InitializeAsync returns. Dialog Suppression records ownership immediately after the adapter subscribes and invokes its existing unsubscribe path if later logging fails, preserving both the initialization and cleanup failures.
  6. Core's ViewActivated event subscription follows the same transaction as module lifecycles. Its attach and rollback operations are force-queued, and host state is not published until the subscription succeeds.

ContextualRibbonInjector

Base class for dynamic ribbon UI that appears based on application state (typically selection). It implements IHookLifecycle; tool modules register the concrete injector against that lifecycle contract.

public abstract partial class ContextualRibbonInjector : IHookLifecycle, IDisposable

Use Cases:

  • Adding "Edit" buttons to contextual tabs when tool-specific elements are selected
  • Showing/hiding ribbon controls based on selection state
  • Injecting panels into Revit's contextual "Modify" tabs

Lifecycle:

  1. InitializeAsync called during HookHost.AttachAsync(...)
  2. Injector creates its edit event and subscribes to SelectionChanged transactionally. If post-subscription callbacks or initial evaluation fail, it immediately runs its own cleanup in the queued initialization context, attempts event detach, contextual UI removal, and edit-event disposal, and preserves both initialization and cleanup failures.
  3. Contextual edit ExternalEvent handlers validate the tool's registered command type through CommandPreflight before running the edit flow, so ribbon-panel settings warnings and command registration policy are shared with normal ToolCommand execution.
  4. Attach rollback uses the queued RollbackAsync path; normal App shutdown calls synchronous Shutdown to unsubscribe and remove contextual UI before HookHost.Detach() returns. The selection controller retains the exact detach action captured at successful subscription, so shutdown does not need to manufacture or queue a new UIApplication.

ExternalEvent Rule:

  • Create ExternalEvent instances only from standard Revit API execution contexts (for example, inside InitializeAsync/RefreshAsync work that runs through ModelessQueuedCallGate).
  • Do not call ExternalEvent.Create(...) directly from Autodesk ribbon command callbacks.

Shutdown Completion Contract

Revit's IExternalApplication.OnShutdown boundary is synchronous. AppShutdownLifecycle.Shutdown calls AppShutdownWorkflow.RunSynchronously directly in that API turn. It cancels startup and disposes its cancellation source only when startup is already complete or absent, detaches hooks, and disposes runtime hosts before returning. It does not queue Revit work or pump the dispatcher. Unfinished startup or deferred observation produces Result.Failed after every owned teardown action is attempted. IHookLifecycle defines three operations:

  • initialization calls asynchronous InitializeAsync;
  • attach rollback calls asynchronous RollbackAsync, retaining the queued Revit call-gate path because rollback may resume away from the UI callback;
  • application shutdown calls synchronous Shutdown on Revit's callback thread. This method has no cancellation token because it cannot publish or await background work; HookShutdownAction owns only the resulting plain Action.

HookCatalog consumes only this lifecycle contract; it has no concrete Contextual Ribbon type check and no task-completion adapter. The coordinator retains successfully initialized owners for reverse-order attach rollback. HookHost also retains each attempted owner before its initializer runs. Normal shutdown therefore reaches subscriptions created during partial attach or an unfinished rollback. HookAttachAction cancels pending work, prevents later initialization and rollback dispatch, and makes completed shutdown idempotent. Cancellation failure does not prevent its shutdown callback. Failed callbacks remain available for retry. Late attachment completion does not invoke Revit shutdown callbacks from a background thread.

Core owns pending WPF DispatcherOperation handles. Posting registers its owner before BeginInvoke, attaches the returned handle, and rechecks retirement so a late handle is aborted even if shutdown drained the registry while posting was in progress. At the end of synchronous shutdown, DispatcherOperationRegistry.Retire closes posting, releases callbacks and cancellation registrations, and aborts pending operations. It invokes no payload callbacks and leaves their completion tasks pending. Posts refused before queueing return canceled tasks. Ordinary WindowStaticRuntime.Reset does not retire the queue.

Logger, ribbon, notification and progress posts share WpfDispatcher.Post. Callback failures are observed and reported; a failing error reporter remains on the completion task and cannot escape into Dispatcher.UnhandledException. Cancellation of an active operation keeps normal installed behavior. Retirement does not pump WPF to finish tasks.

High-Frequency Hook Logging Policy

For high-frequency event hooks (SelectionChanged, ViewActivated), suppress routine start/completion executor noise and keep diagnostics focused on state changes and failures:

  • Set SafeExecuteOptions.LogStart = false
  • Set SafeExecuteOptions.LogCompletion = false
  • Set SafeExecuteOptions.BannerMode = SafeExecuteOptions.Mode.SuppressAlways for background refresh passes

Use tool-level logs for meaningful state transitions (for example, contextual eligibility changed), and keep deep per-probe diagnostics at Trace so Debug logs stay readable during long Revit sessions. View-activated task runtime failures are the exception to generic banner suppression: Core's ViewActivatedTaskRunner presents one canonical auto-update failure banner, then lets the safe executor capture the failed task outcome without presenting a second generic banner.

The IViewActivationTask System

For the common pattern of "do something when a view activates," DBTools provides a higher-level abstraction: IViewActivationTask. The single ViewActivationHook dispatches to all registered tasks.

IViewActivationTask Interface

public interface IViewActivationTask
{
    string TaskId { get; }
    string DisplayName { get; }
    IReadOnlyCollection<string> WarningIdsToSetOnFailure { get; }
    // Returns this attempt's admission, or null to skip it
    Task<ViewActivationAdmission?> AdmitAsync(UIApplication uiapp, ViewActivatedEventArgs args, CancellationToken ct);
}

// One admitted attempt; the task captures exactly the state its execution uses
public sealed class ViewActivationAdmission
{
    public ViewActivationAdmission(Func<CancellationToken, Task> execute);
    public Task ExecuteAsync(CancellationToken ct);
}

IViewActivationTask has no execution method. The hook executes the admission that this attempt's AdmitAsync returned, once. No admission is stored on the task or reaches another attempt. Each admission captures typed state: ViewActivationTask<TSettings> captures its settings snapshot, and the Foundation Tags prerequisite monitor captures the admitted document and its key.

ViewActivationTask

A base class that provides settings integration and common checks:

public abstract class ViewActivationTask<TSettings> : IViewActivationTask
    where TSettings : class, IAutoUpdateSettings, new()
{
    public async Task<ViewActivationAdmission?> AdmitAsync(...)
    {
        var settings = _settingsProvider.Get(_settingsSection);

        // Built-in checks
        if (!settings.AutoUpdateEnabled) return null;
        if (_warnings.IsWarningActive(...)) return null;

        // Delegate to subclass
        if (!await ShouldRunInternalAsync(uiapp, args, settings, ct)) return null;

        // The admission executes with this attempt's settings snapshot; settings are never read again
        return new ViewActivationAdmission(executionCt => ExecuteInternalAsync(uiapp, args, settings, executionCt));
    }

    protected virtual Task<bool> ShouldRunInternalAsync(...) => Task.FromResult(true);
    protected abstract Task ExecuteInternalAsync(UIApplication uiapp, ViewActivatedEventArgs args, TSettings settings, CancellationToken ct);
}

A settings-read failure can therefore occur only in AdmitAsync, where Core sets the task's warnings.

Registering Hooks

In ToolModule.RegisterHooks()

Override RegisterHooks in your ToolModule to register hook handlers:

public sealed class MyToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        // Register the handler as a service
        services.AddSingleton<MyContextualInjector>();
    }

    public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
    {
        Guard.NotNull(registry, nameof(registry));
        Guard.NotNull(manifest, nameof(manifest));

        registry.RegisterHook<IHookLifecycle, MyContextualInjector>();
    }
}

Registering View Activated Tasks

View-activated tasks use a different pattern. Instead of registering directly as hooks, they're registered as IViewActivationTask services that the single ViewActivationHook collects:

public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
{
    var warningIds = GetWarningIdsOrThrow(manifest);

    services.AddSingleton<IViewActivationTask>(sp => new ViewActivatedTask(
        sp.GetRequiredService<ISettingsProvider>(),
        sp.GetRequiredService<SettingsSection<ElevationTagsSettings>>(),
        sp.GetRequiredService<ISettingsWarningService>(),
        sp.GetRequiredService<ElevationTagsUpdater>(),
        sp.GetRequiredService<IErrorNotifier>(),
        sp.GetRequiredService<ILogger<ViewActivatedTask>>(),
        warningIds));
}

Registration in AppHooksToolModule

The manifest type DBTools.App.Composition.AppHooksToolModule registers the single ViewActivationHook that dispatches to all tasks:

public sealed class AppHooksToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        services.AddSingleton<ViewActivationHook>();
    }

    public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
    {
        registry.RegisterHook<ViewActivationHook, ViewActivationHook>();
    }
}

Implementing Hook Handlers

Step 1: Define Your Handler Class

public sealed class MyViewActivatedTask : ViewActivationTask<MyToolSettings>
{
    public MyViewActivatedTask(
        ISettingsProvider settings,
        SettingsSection<MyToolSettings> settingsSection,
        ISettingsWarningService warnings,
        IErrorNotifier notifier,
        ILogger<MyViewActivatedTask> logger,
        IReadOnlyCollection<string> warningIds)
        : base(settings, settingsSection, warnings, notifier, logger, "mytool.updater", "My Tool Auto-Update", warningIds)
    {
    }
}

Step 2: Implement ShouldRunInternalAsync (Optional)

Filter when your task should run based on view type, document state, etc.:

protected override Task<bool> ShouldRunInternalAsync(
    UIApplication uiapp,
    ViewActivatedEventArgs args,
    MyToolSettings settings,
    CancellationToken ct)
{
    var view = uiapp.ActiveUIDocument?.Document?.ActiveView;
    if (view == null) return Task.FromResult(false);

    // Only run in floor plans
    return Task.FromResult(
        view.ViewType == ViewType.FloorPlan ||
        view.ViewType == ViewType.CeilingPlan);
}

Step 3: Implement ExecuteInternalAsync

Perform the actual work with the settings that admitted this attempt:

protected override Task ExecuteInternalAsync(
    UIApplication uiapp,
    ViewActivatedEventArgs args,
    MyToolSettings settings,
    CancellationToken ct)
{
    var doc = uiapp.ActiveUIDocument?.Document
        ?? throw new InvalidOperationException("No active document.");
    var view = doc.ActiveView
        ?? throw new InvalidOperationException("No active view.");

    var gate = new InlineCallGate(uiapp);
    var tx = new TransactionRunner(gate);

    var updater = new MyAutoUpdater(tx, doc, view, Logger, settings);
    updater.Run();

    return Task.CompletedTask;
}

Step 4: Register in Your ToolModule

public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
{
    var warningIds = new[] { "mytool.auto_update.warning" };

    services.AddSingleton<IViewActivationTask>(sp => new MyViewActivatedTask(
        sp.GetRequiredService<ISettingsProvider>(),
        sp.GetRequiredService<SettingsSection<MyToolSettings>>(),
        sp.GetRequiredService<ISettingsWarningService>(),
        sp.GetRequiredService<IErrorNotifier>(),
        sp.GetRequiredService<ILogger<MyViewActivatedTask>>(),
        warningIds));
}

Implementing Contextual Ribbon Injectors

For tools that need dynamic ribbon UI (like SGT's "Edit" button on selected girts):

Step 1: Implement IHookLifecycle

public sealed class MyContextualInjector : IHookLifecycle
{
    private readonly ILogger<MyContextualInjector> _logger;
    private readonly ISafeExecutor _executor;
    private Action? _detach;

    public Task InitializeAsync(UIControlledApplication application, CancellationToken ct)
    {
        if (_detach != null) return Task.CompletedTask;

        // Subscribe to selection changes
        // Use ModelessQueuedCallGate for safe async access
        return _gate.RunAsync(app =>
        {
            app.SelectionChanged += OnSelectionChanged;
            _detach = () => app.SelectionChanged -= OnSelectionChanged;
        }, ct);
    }

    public Task RollbackAsync(UIControlledApplication application, CancellationToken ct)
    {
        if (_detach == null) return Task.CompletedTask;
        return _gate.RunAsync(_ => Detach(), ct);
    }

    public void Shutdown(UIControlledApplication application)
        => Detach();

    private void Detach()
    {
        _detach?.Invoke();
        _detach = null;
        RemoveInjectedUI();
    }
}

Step 2: Handle Selection Changes

private async void OnSelectionChanged(object? sender, SelectionChangedEventArgs e)
{
    if (sender is not UIApplication uiapp) return;

    await _executor.RunWithoutThrowingAsync(
        () => RefreshAsync(uiapp, CancellationToken.None),
        _logger,
        notifier: null,
        opts: new SafeExecuteOptions
        {
            Name = "My Contextual Selection Hook",
            BannerMode = SafeExecuteOptions.Mode.SuppressAlways
        },
        ct: CancellationToken.None);
}

Step 3: Inject UI into Contextual Tabs

private void EnsureInjected(UIApplication uiapp)
{
    var ribbon = ComponentManager.Ribbon;
    if (ribbon == null) return;

    var targetTab = TryGetContextualTab(ribbon);
    if (targetTab == null) return;

    var panel = EnsurePanel(targetTab);
    var btn = BuildButton();

    btn.CommandHandler = new RibbonButtonCommand(OnButtonClick);
    panel.Source.Items.Add(btn);
}

Hook Execution Order

Registration Order

Hooks are resolved in the order they were registered:

  1. AppHooksToolModule registers ViewActivationHook (core)
  2. Tool modules register their IViewActivationTask implementations
  3. Tool modules register IHookLifecycle implementations for contextual ribbon lifecycle work

  2. Or coordinate within a single handler that manages multiple sub-tasks

Common Patterns

Auto-Update on View Change

The most common pattern for tools like Elevation Tags:

// 1. Define settings with IAutoUpdateSettings
public class MySettings : IAutoUpdateSettings
{
    public bool AutoUpdateEnabled { get; set; } = true;
    public bool HasWarning { get; set; }

// 2. Create a task extending ViewActivationTask<TSettings>
public class MyAutoUpdateTask : ViewActivationTask<MySettings>
{

    protected override Task ExecuteInternalAsync(...)
    {
        // Perform update logic with the admitted settings
    }

// 3. Register in ToolModule
services.AddSingleton<IViewActivationTask>(...);

public class MyInjector : ContextualRibbonInjector

Warning Integration

Feature warnings are for actionable prerequisite/configuration failures (e.g., missing shared parameters, invalid settings). They should not be activated for transient/runtime exceptions.

// Example: set warning only for actionable prerequisite failure
var eval = MyPrereqEvaluator.Evaluate(uiapp, doc, tx, logger);
if (eval.Kind == PrereqKind.Invalid)
{
    foreach (var warningId in WarningIdsToSetOnFailure)
        warnings.SetWarning(warningId, true);
    return;
}

// Runtime exceptions propagate: Core shows the failure banner and skips the task for this document session (do NOT set warnings)
updater.Run();

The warning IDs must be defined in the tool's settings pack and match entries in manifest.yml.

Creating New Hook Types

To add a new hook type (advanced):

Prefer the existing lifecycle contract

For attach/shutdown lifecycle work, implement IHookLifecycle and register the concrete type through ToolRegistry.RegisterHook<IHookLifecycle, TImplementation>(). Do not add a new hook contract for contextual ribbon or dialog suppression variants.

Event-specific contracts require Core host support

Add a new hook contract only when the Revit event needs a different dispatch shape than attach/shutdown lifecycle. The Core hook catalog must explicitly allow the contract and HookHost must own the subscription/detach path.

Step 1: Define the Interface

// In DBTools.Core/Tools/
public interface IDocumentClosingHookHandler
{
    Task OnDocumentClosingAsync(
        UIControlledApplication application,
        DocumentClosingEventArgs args,
        CancellationToken ct);
}

Step 2: Add catalog support, resolution, and subscription

public async Task AttachAsync(UIControlledApplication application, CancellationToken ct)
{
    // ... existing code ...

    var closingHandlers = ResolveHandlers<IDocumentClosingHookHandler>();
    if (closingHandlers.Count > 0)
        application.DocumentClosing += OnDocumentClosing;

    _closingHandlers = closingHandlers;
}

private async void OnDocumentClosing(object? sender, DocumentClosingEventArgs args)
{
    if (_closingHandlers == null || _closingHandlers.Count == 0) return;

    try
    {
        await _executor.RunWithoutThrowingAsync(
            async () =>
            {
                foreach (var handler in _closingHandlers)
                    await handler.OnDocumentClosingAsync(_application!, args, CancellationToken.None);
            },
            _logger,
            notifier: null,
            opts: new SafeExecuteOptions { /* ... */ },
            ct: CancellationToken.None);
    }
    catch { /* Suppress to protect Revit */ }
}

Step 3: Add Detach Logic

public void Detach()
{
    // Unsubscribe direct host events, complete every lifecycle action,
    // aggregate contextual failures, then clear ownership.
}

Performance Considerations

Don't Block the UI Thread

Hooks run in response to Revit events. Blocking causes UI freezes:

// BAD - blocks UI
public Task ExecuteAsync(...)
{
    Thread.Sleep(5000);  // Never do this!
    return Task.CompletedTask;
}

// GOOD - async work
public async Task ExecuteAsync(...)
{
    await SomeAsyncOperation();
}

Use SafeExecutor Options Wisely

For frequent hooks like view activation, suppress banners:

new SafeExecutionOptions("View activation")
{
    BannerMode = SafeExecutionOptions.Mode.ErrorOnly  // Only show errors
}

SafeExecutionOptions.LogFailure defaults to true. Disable it only for a lifecycle-owned background task whose already-published observer records the same fault after task observation; the task must still fail fast and remain observable. Ordinary hooks retain the default failure log.

Filter Early with ShouldRunInternalAsync

Avoid expensive work when the hook shouldn't run:

protected override Task<bool> ShouldRunInternalAsync(...)
{
    // Quick checks first
    var view = uiapp.ActiveUIDocument?.Document?.ActiveView;
    if (view == null) return Task.FromResult(false);
    if (view.ViewType != ViewType.FloorPlan) return Task.FromResult(false);

    // Only then check more expensive conditions
    return Task.FromResult(true);
}

Batch Operations in Transactions

When modifying elements, batch changes in a single transaction:

protected override Task ExecuteInternalAsync(...)
{
    using var tx = new Transaction(doc, "Auto Update");
    tx.Start();

    foreach (var element in elementsToUpdate)
        UpdateElement(element);

    tx.Commit();
    return Task.CompletedTask;
}

SGT Contextual Ribbon

The Super Girt Tool injects an "Edit" button into the contextual "Modify | Structural Framing" tab:

public sealed class ContextualRibbonInjector : ContextualRibbonInjector
{
    public Task InitializeAsync(UIControlledApplication application, CancellationToken ct)
    {
        return _gate.RunAsync(app =>
        {
            EnsureEditEventCreated(); // ExternalEvent.Create in API-safe context
            app.SelectionChanged += OnSelectionChanged;
            _subscribed = true;
            EnsureInjected(app);
            EvaluateAndToggle(app);
        }, ct);
    }

    private void EvaluateAndToggle(UIApplication uiapp)
    {
        var (hasGirts, systemIds) = EvaluateSelection(uiapp);
        UpdateSystemIds(systemIds);
        ToggleButtons(hasGirts, hasGirts);
    }

    private void EnsureInjected(UIApplication uiapp)
    {
        var targetTab = TryGetContextualModifyStructuralTab(ribbon);
        var panel = EnsurePanel(targetTab);
        var btn = BuildButton();
        panel.Source.Items.Add(btn);
    }
}

AppHooksToolModule Registration

The core hook module that wires up view-activated handling:

public sealed class AppHooksToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        services.AddSingleton<ViewActivationHook>();
    }

    public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
    {
        registry.RegisterHook<ViewActivationHook, ViewActivationHook>();
    }
}

Common Issues

Symptom Possible Cause Solution
Hook never fires Not registered in RegisterHooks Verify RegisterHook<>() call
Handler not resolved Service not registered Add AddSingleton<>() in RegisterServices
UI thread deadlock Sync-waiting on async in hook Use async void for event handlers, never .Wait()
Hook runs but no effect AdmitAsync returning null Check settings (AutoUpdateEnabled, HasWarning)
Exception in hook Various Check logs; ISafeExecutor logs all errors
