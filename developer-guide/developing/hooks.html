Hooks

Hooks attach tool behavior to Revit application events. Core's HookHost resolves registered implementations, owns the shared ViewActivated subscription, and coordinates initialization, rollback, and shutdown. Tool-owned lifecycle hooks manage subscriptions that need their own event adapters.

Use IViewActivationTask for work triggered by a view change. Use IHookLifecycle for owned subscriptions such as contextual ribbon UI or dialog suppression. Register services through the tool module. Do not attach another copy of Core's ViewActivated handler.

Hook architecture

flowchart LR
    Revit[Revit events] --> Host[HookHost]
    Registry[ToolRegistry and DI] --> Host
    Host --> View[ViewActivationHook]
    Host --> Lifecycle[IHookLifecycle implementations]
    View --> Tasks[IViewActivationTask services]

Core's AddDbtHookRuntimeServices registers the single ViewActivationHook service beside HookHost. The hook collects IEnumerable<IViewActivationTask> from DI; tools contribute tasks, not hook registrations. ViewActivationHookDispatcher owns the outer safe-execution boundary. ViewActivationTaskRunner evaluates admissions and executes admitted tasks.

ToolRegistry records only lifecycle hooks, in registration order, through RegisterLifecycleHook<T>(). HookCatalog resolves the required ViewActivationHook service and each registered lifecycle implementation from the service provider. Resolution fails when the view-activation hook or a lifecycle service is missing, or when a lifecycle service does not implement IHookLifecycle.

Hooks run in response to Revit UI callbacks. Returning Task does not move API work to a background thread. Use asynchronous I/O where appropriate, avoid blocking the UI, and reacquire a valid Revit call gate before API work after an await. Modularity describes the synchronous callback restriction.

Registering hooks

Register both the concrete service and its lifecycle registration:

public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
{
    services.AddSingleton<ContextualEditHook>();
}

public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
{
    registry.RegisterLifecycleHook<ContextualEditHook>();
}

This excerpt assumes a tool-owned ContextualEditHook : IHookLifecycle whose constructor dependencies are registered. Manifest and module setup is described in Creating New Tools.

View-activation tasks use a factory registration. The Elevation Tags task needs manifest warning IDs in addition to its registered service dependencies:

var warning = manifest.GetSingleSettingsPack().GetSingleWarning(manifest.Id);
var warningIds = new[] { warning.Id };
services.AddSingleton<ElevationTagAlignmentService>();
services.AddSingleton<IViewActivationTask>(sp => new AlignOnViewActivatedTask(
    sp.GetRequiredService<ISettingsProvider>(),
    sp.GetRequiredService<SettingsSection<ElevationTagsSettings>>(),
    sp.GetRequiredService<ISettingsWarningService>(),
    sp.GetRequiredService<ElevationTagAlignmentService>(),
    sp.GetRequiredService<IBannerNotifier>(),
    sp.GetRequiredService<ILogger<AlignOnViewActivatedTask>>(),
    warningIds));

This excerpt follows Elevation Tags' App/Composition/ServiceCollectionExtensions.cs. The IReadOnlyCollection<string> warningIds constructor argument comes from the manifest, not automatic DI resolution. Every task must have a nonblank unique TaskId. All entries in WarningIdsToSetOnFailure must match registered warning definitions. The task registry validates these identities at construction.

The IViewActivationTask System

The public contract separates admission from execution:

public interface IViewActivationTask
{
    string TaskId { get; }
    string DisplayName { get; }
    IReadOnlyCollection<string> WarningIdsToSetOnFailure { get; }
    Task<ViewActivationAdmission?> AdmitAsync(
        UIApplication uiapp, ViewActivatedEventArgs args, CancellationToken ct);
}

AdmitAsync returns null to skip the attempt. A non-null ViewActivationAdmission captures the state that attempt will use:

new ViewActivationAdmission(executionCt => ExecuteAsync(snapshot, executionCt));

The hook invokes the returned admission callback once for that attempt. Create a new admission for each event so it captures that event's state.

ViewActivationTask

Derive from ViewActivationTask<TSettings> for an auto-update task with typed settings. TSettings must implement IAutoUpdateSettings and have a public parameterless constructor. Its base constructor receives:

ViewActivationTask(
    ISettingsProvider settingsProvider,
    SettingsSection<TSettings> settingsSection,
    ISettingsWarningService warnings,
    IBannerNotifier notifier,
    ILogger logger,
    string taskId,
    string displayName,
    IReadOnlyCollection<string> warningIds);

The base admission sequence is:

  1. Check cancellation and read the current typed settings.
  2. Skip when AutoUpdateEnabled is false.
  3. Skip when any configured warning is active.
  4. Call the optional ShouldRunInternalAsync predicate.
  5. Capture that settings snapshot in an admission calling ExecuteInternalAsync.

Override these methods with the exact signatures:

protected override Task<bool> ShouldRunInternalAsync(
    UIApplication uiapp, ViewActivatedEventArgs args,
    MyToolSettings settings, CancellationToken ct)
{
    var view = args.CurrentActiveView;
    return Task.FromResult(view != null &&
        (view.ViewType == ViewType.FloorPlan || view.ViewType == ViewType.CeilingPlan));
}

protected override Task ExecuteInternalAsync(
    UIApplication uiapp, ViewActivatedEventArgs args,
    MyToolSettings settings, CancellationToken ct)
{
    return _updater.UpdateAsync(uiapp, args.CurrentActiveView, settings, ct);
}

This excerpt assumes a tool-owned updater with that operation. Inject its real implementation. Filter cheap conditions before expensive work. Use shared transaction services for modifications and synchronous callbacks inside them. Do not create a transaction around asynchronous work.

The base exposes Logger and a protected banner helper. It reads no settings again during execution, so the admitted values remain consistent and settings-read failures occur at admission.

Dispatch and failure policy

The hook resolves the document from args.CurrentActiveView and returns when there is no active document/view. It visits tasks in DI registration order. Each task is evaluated and executed through the safe executor.

Outcome Result
Null admission Skip the task for this event.
Admission failure Record a document-session failure and activate the task's warning IDs.
Execution failure Show the canonical auto-update failure banner and record a document-session failure. Do not automatically activate feature warnings.
Cancellation Preserve the canceled outcome rather than classify it as a runtime failure.

A runtime failure suppresses subsequent attempts for the task/document session. The gate uses DocumentSessionKey. Save As or the first save can create a new key, and reopening a document starts a new session. Clearing a feature warning alone does not erase the recorded runtime failure for that key.

Tool prerequisite checks may explicitly activate an actionable warning and return without executing the update. Unexpected updater exceptions propagate. Feature Warnings owns the distinction between invalid configuration, admission failure, and execution failure.

Core suppresses routine logs and presentation on the outer event dispatch. Admission uses error-only banners without start/completion logs. An admitted execution logs start/completion, suppresses generic executor banners, and uses one canonical runtime-failure banner. Keep detailed probes at Trace and log meaningful state changes. Do not suppress failure logs unless another published lifecycle owner observes and records that exact failure.

IHookLifecycle

Lifecycle hooks implement three operations:

public interface IHookLifecycle
{
    Task InitializeAsync(UIControlledApplication application, CancellationToken ct);
    Task RollbackAsync(UIControlledApplication application, CancellationToken ct);
    void Shutdown(UIControlledApplication application);
}

InitializeAsync acquires subscriptions and other owned state. If initialization fails partway, the implementation must undo its own partial work and preserve both initialization and cleanup failures. Record ownership immediately after subscription, before later logging or callbacks can fail.

RollbackAsync reverses attachment when later startup work fails. It can queue into a valid Revit context because its continuation may run outside the original UI callback. Shutdown runs synchronously in Revit's shutdown callback. It must finish owned unsubscribe/removal work before returning. It has no cancellation token and cannot publish background work for later completion.

Host ordering and rollback

HookHost.AttachAsync resolves handlers, initializes lifecycle actions in registration order, then force-queues its ViewActivated subscription. It publishes attached state only after all actions succeed.

The host records each attempted owner before initialization begins. Successfully initialized actions roll back in reverse order if attachment fails. The failing initializer owns its partial cleanup. Normal shutdown also reaches attempted owners whose initialization or rollback is incomplete.

HookAttachAction cancels pending attachment, prevents later initialization or rollback dispatch after shutdown is requested, and makes completed shutdown idempotent. Cancellation failure does not prevent its shutdown callback. A failed callback remains available for retry. Late asynchronous attachment completion cannot invoke Revit shutdown callbacks from a background thread. HookLifecycleCoordinator attempts every reverse-order teardown action and aggregates contextual failures.

Hooks and view tasks follow registration order. Group dependent operations in one hook or task when their ordering is part of the behavior.

Contextual ribbon injectors

DBTools.Core.Tools.Hooks.ContextualRibbon.ContextualRibbonInjector implements IHookLifecycle and IDisposable. Derive from it for tool-specific Edit buttons on contextual tabs. Super Girt Tool (SGT) supplies ContextualEditHook as an example.

The derived type supplies tool/button/event names, the registered contextual command type, target tabs, selection evaluation, button construction, and edit flow. The base owns selection-change observation, injected controls, system-ID state, safe execution, and the edit ExternalEvent.

Initialization queues API work to create the edit event, subscribe to selection changes, and evaluate the initial state. A partial failure immediately attempts unsubscribe, contextual UI removal, and edit-event disposal. Rollback uses the queued cleanup path. Normal shutdown uses synchronous cleanup and the exact detach action captured at successful subscription.

Create ExternalEvent objects only in valid Revit API contexts. Autodesk ribbon command callbacks are not such a context. The base creates/refreshes its edit event through its managed Revit entry path. Contextual edit validates ContextualEditCommandType through CommandPreflight, sharing normal command registration and warning policy.

Do not duplicate the base's event subscription or button registry in a derived type. FindTargetTabs, EvaluateSelection, BuildButton, and RunEditFlow are the tool-specific extension points.

Synchronous shutdown

Revit's IExternalApplication.OnShutdown is synchronous. AppLifecycleCoordinator.Shutdown invokes AppShutdownWorkflow.RunSynchronously through AppShutdownLifecycle.CleanupSynchronously in that callback. It cancels startup, detaches hooks, and disposes runtime hosts before returning. It disposes the startup cancellation source only when startup is complete or absent. It neither queues Revit work nor pumps the dispatcher. Unfinished startup or deferred observation yields Result.Failed after owned teardown attempts.

Core tracks WPF DispatcherOperation handles. Posting records ownership before BeginInvoke and rechecks retirement after the handle arrives. DispatcherOperationRegistry.Retire closes posting, releases callbacks and cancellation registrations, and aborts pending operations without executing their payloads. Their completion Tasks remain pending. Posts refused before queueing return canceled Tasks. WindowStaticRuntime.Reset retires that queue before it resets the window surfaces, and WindowStaticRuntime.Configure opens it again. App shutdown calls Reset after runtime host teardown, so posting stays open while hosts dispose.

Logger, ribbon, notification, and progress posts use WpfDispatcher.Post. Callback faults remain observable. A fault in an error reporter stays on the completion Task rather than escaping into Dispatcher.UnhandledException. Shutdown must not pump WPF or await retired dispatcher work.

Extending and debugging hooks

Use IHookLifecycle for another owned application subscription. Add an event-specific contract only when its dispatch shape requires one. Such a change must add its Core registration, resolution, subscription, safe-execution policy, rollback, synchronous detach, and tests together. ToolRegistry accepts only lifecycle hooks.

Symptom Check
Lifecycle hook never initializes Register both its concrete DI service and its RegisterLifecycleHook<T>() registration.
View task never runs Check its IViewActivationTask registration, settings, active warnings, predicate, and document-session failure gate.
Startup rejects the task Check nonblank unique task IDs and known warning IDs.
Handler resolution fails Register the concrete type and its constructor dependencies.
UI freezes Remove synchronous waits and long work from UI callbacks. Re-enter the gate for API work after an await.
Cleanup fails Inspect contextual errors for each unsubscribe, UI removal, and disposal attempt.

Inspect %APPDATA%/DBTools/Logs/ first. Use the Settings Debug Mode control for runtime diagnostics rather than adding an unrelated logging configuration.
