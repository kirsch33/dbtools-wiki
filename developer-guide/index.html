Requirements

  • the .NET SDK pinned in global.json; build.sh and build.ps1 install it when it is missing;
  • Python 3.10 or later on Linux and WSL;
  • Desktop Revit 2026 (2026.5 or later) or Revit 2027 to run the add-in. Building does not need Revit.

Building

./build.sh                                     # BuildAll: build, validate and publish both years
./build.sh BuildApp -y 2026                    # product assemblies for one year
./build.sh AssembleDistributionCandidate -y 2026
pwsh -NoProfile -File build.ps1 BuildAll       # native Windows

BuildAll, ValidateDistributionCandidate, PromoteToDist, BuildBundle and BuildInstaller always build every supported year; a -y that omits one fails. See Build Pipeline.

Testing

./test.sh test --tool GM --scope pure                        # one tool, without Revit
./test.sh test --tool APP --scope local -y 2026              # in Revit, through the daemon
./test.sh test --filter "FullyQualifiedName~SomeTestName"
./test.sh test --scope all

Revit-hosted tests (the local scope) run on the dbtools-daemon fleet. See Test Pipeline for the design and Testing Tools for the options.

Writing documentation

The wiki is built with DocFX from wiki/. Run bash .github/scripts/build-docs.sh conceptual to build the pages into wiki/_site; the Documentation workflow publishes the site through the wiki server. Write developer and user pages in the style of Unix reference documentation (Debian and GNU manuals, man pages):

  • State what a component is, what it does, how it works, how to use it and its limits. Put the main point first.
  • Use plain declarative sentences in the present tense and the active voice; use the imperative in procedures.
  • Use the names the code uses, one term per concept. Use lists for steps and parallel items, tables for tabular data, and code blocks for commands, paths and literal values. Document commands as a synopsis, options and examples.
  • Describe the current behavior only. Leave out change history, status and verification notes, dates, issue numbers, and the vocabulary of the process that produced a change. Keep a history note only for a migration step or compatibility break the reader needs.
  • Leave out filler, hedging and repeated summaries. State each real limitation once, where it applies.
  • Verify every technical claim against the current code, scripts and configuration before you write or keep it.

The same rules apply to source comments, CLI help and messages. A comment explains a reason, an invariant or a non-obvious API behavior, not what the code already says. CLI help uses man-page form: a synopsis, then one line per option with its default. An error message names what failed, the relevant value or path and, where useful, what to do.
