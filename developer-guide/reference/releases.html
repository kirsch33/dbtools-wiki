NAME

releases - build and publish a version of dbtools

Install release builds. Each release gets the next MAJOR.MINOR.PATCH version and a v<version> Git tag. Start at 0.1.0 and increase PATCH for each release. For a release with substantial changes, increase MINOR and reset PATCH to zero. Reserve 1.0.0 for the end of prerelease development.

The Windows installer, installed-apps entry, Contents/dbtools/<version>/ directory and Revit Settings show the same version. The DLL content versions identify their build inputs separately.

PREREQUISITES

Use a clean checkout on WIN-DEV with Inno Setup 6.7.1 or a later 6.x and the OpenSSH client. The Windows Sandbox acceptance step needs the dbtools-daemon client with relay settings and credentials for the current user. Use GitHub CLI 2.48 or later and Python 3.10 or later on Linux.

STEPS

Publish a release

  1. On WIN-DEV, set $commit to the approved commit SHA and $version to the approved version. Build from that commit in the repository root. BuildInstaller validates and bundles both Revit years.

    $commit = '<approved-commit-sha>'
$version = '0.1.0'
git fetch origin
if ($LASTEXITCODE -ne 0) { throw 'Could not fetch the approved commit.' }
git switch --detach $commit
if ($LASTEXITCODE -ne 0) { throw 'Could not check out the approved commit.' }
dotnet build build/Build.proj -t:BuildInstaller "-p:Version=$version"
if ($LASTEXITCODE -ne 0) { throw 'BuildInstaller failed.' }

  2. Package the staged release for Windows Sandbox acceptance.

    dotnet build build/Build.proj -t:PackageSandboxValidationInput "-p:Version=$version"
if ($LASTEXITCODE -ne 0) { throw 'PackageSandboxValidationInput failed.' }

    Use the archive path printed by the build. Require a pass for each Revit year before continuing. Follow the distribution acceptance commands.

  3. Check the installer on WIN-DEV. Run Setup with Revit closed. Confirm the version in the installer filename, installed-apps entry, bundle payload directory and Revit Settings.

  4. Archive the bundle and copy it, the installer and the build record to the release asset directory on Linux. The build record gives the commit and version that the build used. Set $destination to the Linux account, host and absolute directory.

    $installer = ".artifacts/release-assets/dbtools-Setup-$version.exe"
$bundle = ".artifacts/release-assets/dbtools-$version.bundle.zip"
$record = '.artifacts/build.json'
$destination = '<account>@<linux-host>:/absolute/path/to/release-assets/'
tar.exe -a -cf $bundle -C .artifacts/bundle dbtools.bundle
if ($LASTEXITCODE -ne 0) { throw 'Could not archive dbtools.bundle.' }
scp.exe $installer $bundle $record $destination
if ($LASTEXITCODE -ne 0) { throw 'Could not copy release assets to Linux.' }

  5. On Linux, add release-notes.md to the release asset directory. From the repository root, set release_dir to that absolute directory and repo to the GitHub repository for origin in OWNER/REPO form. The commit and version come from the build record. Compute the checksums, tag that commit and publish.

    record="$release_dir/build.json"
commit=$(python3 -c 'import json, sys; print(json.load(open(sys.argv[1]))["sourceCommit"])' "$record")
version=$(python3 -c 'import json, sys; print(json.load(open(sys.argv[1]))["productVersion"])' "$record")
tag="v$version"
installer="dbtools-Setup-$version.exe"
bundle="dbtools-$version.bundle.zip"
(cd "$release_dir" && sha256sum -- "$installer" "$bundle" > SHA256SUMS) &&
  git fetch origin &&
  git tag -a "$tag" "$commit" -m "dbtools $version" &&
  git push origin "refs/tags/$tag" &&
  gh release create "$tag" "$release_dir/$installer" "$release_dir/$bundle" "$release_dir/SHA256SUMS" \
    --repo "$repo" --verify-tag --title "dbtools $version" \
    --notes-file "$release_dir/release-notes.md"

Prune releases

Keep the five highest published versions and every v<MAJOR>.0.0 release. Retention sorts numeric version components and considers published releases with v<MAJOR>.<MINOR>.<PATCH> tags made of digits and dots after the v. Drafts and releases with other tags are untouched. Pruning keeps the Git tags.

  1. From the repository root, save the release list. Save and print the dry-run output for approval. It lists the tags and release IDs to delete.

    gh api --paginate --slurp "repos/$repo/releases?per_page=100" > "$release_dir/releases.json" &&
  python3 build/Release/prune-releases.py --dry-run "$release_dir/releases.json" > "$release_dir/prune.json" &&
  cat "$release_dir/prune.json"

  2. After the owner approves the printed list, apply that saved list. If the live selection differs, get approval for a fresh dry run before applying it.

    python3 build/Release/prune-releases.py --apply "$repo" "$release_dir/prune.json"

CHECK

Run the retention test offline from the repository root.

python3 -B -m unittest discover -s build/Release -v
