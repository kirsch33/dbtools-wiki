NAME

documentation - how to write and check wiki pages

SYNOPSIS

---
template: user-tool   # user-tool | user-topic | dev-tool | dev-component | reference | how-to | dev-topic
sources:              # code the page describes
  - src/Tools/Structural/JoistGirderWeight/
---

python3 build/Documentation/lint_wiki.py wiki
bash wiki/build-docs.sh conceptual
bash wiki/build-docs.sh full-api

Both build modes use wiki/docfx.json and write to wiki/_site.

Model pages: Update Joist Girder Weights, dbtools.JoistGirderWeight, Architecture overview.

DESCRIPTION

A wiki page reads like a good man page: short, plain and exact. It gives the facts for a task, and stops.

TEMPLATES

The title is the only H1. Sections are H2s in capital letters, in this order. Leave out a section that has nothing to say.

Template Use it for Sections
user-tool A ribbon tool or a service NAME, SYNOPSIS, DESCRIPTION, OPTIONS, REQUIREMENTS, SETTINGS, RESULTS, MESSAGES, FILES, LIMITS, EXAMPLES, SEE ALSO
user-topic Installation, basics, settings, troubleshooting NAME, SYNOPSIS, DESCRIPTION, topic sections, MESSAGES, FILES, SEE ALSO
dev-tool A tool assembly NAME, SYNOPSIS, DESCRIPTION, STRUCTURE, CONTRACTS, FLOW, DATA, DIAGNOSTICS, TESTS, SEE ALSO
dev-component An architecture area or a project The same as dev-tool
reference build.sh, test.sh, manifest.yml, settings files NAME, SYNOPSIS, DESCRIPTION, OPTIONS, EXIT STATUS, ENVIRONMENT, FILES, EXAMPLES, SEE ALSO
how-to One task NAME, SYNOPSIS, PREREQUISITES, STEPS, CHECK, SEE ALSO
dev-topic Index and troubleshooting pages, this page NAME, SYNOPSIS, DESCRIPTION, topic sections, SEE ALSO

For a ribbon tool, REQUIREMENTS, RESULTS, MESSAGES and LIMITS replace the man-page INPUTS, OUTPUT, DIAGNOSTICS and BUGS. Other sections keep their man-page meaning, except these:

Section What it holds
NAME <title> - <what it does>, under 80 characters
SYNOPSIS User page: the ribbon path. Developer page: a text block with source, assembly and entry point.
REQUIREMENTS What the model must contain, as a table with names, units and rules
RESULTS What a run changes and shows, and its Undo-list name
MESSAGES Only messages whose meaning or fix the text does not make clear
LIMITS Real limits, and traps that silently give a wrong result
CONTRACTS Rules the code keeps, each with the test that checks it, if any

RULES

  1. Write complete, short sentences, one idea each. Aim for 20 words or fewer. Keep the verbs and articles. Write "If a pattern is not valid, the command changes nothing", not "Bad pattern: no change".
  2. Use the names the reader sees: UI labels, parameters and messages, or code names on a developer page. Invent no labels or symbols.
  3. Define each term once, where it first appears, with its unit.
  4. Use the present tense, the active voice, and the imperative for steps.
  5. Use a table for items that readers scan. Each cell is still plain English.
  6. Put each fact in one place, and link to it.
  7. Describe current behavior only. Leave out dates, history, plans and the words below. Put <!-- lint: migration --> before a needed migration step.
  8. Give no line numbers. Name the file and the symbol.
  9. Show UI labels in bold, and messages, parameters and values in backticks, exactly as they appear. Write variable parts as <name>.
  10. Give each user tool page one or two screenshots. Until one exists, leave <!-- screenshot: <window or banner>, <state> -->.
filler   simply just easily easy basically actually really very "note that"
         please "in order to" "it is important" obviously "of course" various
         robust seamless leverage comprehensive powerful utilize via e.g. i.e. etc.
history  currently now (in time) new newly previously "no longer" formerly
         legacy (except in a code name) "has been" "was changed" "was renamed"
         "was removed" recently "before <month> <year>"
process  agent review wave lane epoch Desloppify campaign regression

Aim for at most 600 words outside code on a tool page and 800 on an architecture page. The largest tools need more.

CONTENT

Choose facts for the reader's task, not for the code.

A user page holds what a typical user acts on, including the traps that silently give a wrong result. Leave out rare edge cases and internal mechanics, such as check order, banner kinds and settings-file names.

A developer page holds what a developer needs to change the code safely, and links to the user page for behavior. It copies no manifest.yml or signatures.

CHECKS

  1. Facts. Check each claim against the code, by file and symbol, and copy labels and messages from it. Do not print the code inventory.
  2. Revit-only claims. Keep one only with a Revit test or the owner's confirmation.
  3. Second writer. Another writer checks the claims. Fix each finding.
  4. Reader test. Give a fresh reader only the page text and 3 or 4 realistic tasks. Ask for answers and for every sentence it read twice. Fix those sentences and any wrong answer. Fill only the gaps that a typical reader hits, not every gap the test finds.
  5. Build. The build fails on a source line reference or a DocFX warning.

Markdown traps:

  • A definition list needs : plus three spaces, and four-space continuation lines.
  • In a table cell, a pipe in code shows a stray backslash.
  • Link only to wiki pages, or DocFX reports InvalidFileLink.
  • Check links against the generated heading IDs.
