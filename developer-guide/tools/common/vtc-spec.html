VTC As-Built Spec

This file records the current VTC design after the March 6, 2026 native-only Revit Links rewrite.

The current ownership boundary has one document façade: Revit/Template/TemplateRuntime. App composition supplies its concrete extractor, Revit-link adapter, difference evaluator, applier, and materializer. App batch-session orchestration consumes the focused App/Sessions/ITemplateSessionRuntime port implemented by that façade; tests replace the external port without redeclaring or shadowing the production runtime. Comparison owns SettingPreviewItem, window comparison state, the diff-tree filter contract, substantive Comparison views, and the UI-neutral RevitLinkActionSourceResolver; Library owns its concrete Library view; Template Apply owns pending overrides, apply outcomes, Revit-link batch execution, and expected conflict classification; App owns keyed outcome projection plus Revit-link prompting, modal hosting, refresh, result presentation, and cross-pane request handling. App composes outcome-only runtime templates into Comparison views; feature packages do not import App. AlertPresenter is the only App-facing alert boundary, so no workflow or view-model consumer receives IAlertService.

Sources: src/Tools/Experimental/VTC/Revit/Template/TemplateRuntime.cs, src/Tools/Experimental/VTC/Features/TemplateApply/Execution/TemplateApplier.Operations.cs, src/Tools/Experimental/VTC/Features/Comparison/Window/VtcWindowComparisonCoordinator.cs

Scope

  • VTC compares two view templates from the current document.
  • Category edits remain staged locally until Process.
  • Import Categories are not a separate subsystem; they are ordinary category rows routed to the imported tab.
  • Revit Links are limited to settings that the active public Revit API can both read and write.

VG Tab Structure

VTC still mirrors Revit VG organization at the tree level:

  • ModelCategories
  • AnnotationCategories
  • AnalyticalModelCategories
  • ImportedCategories
  • Filters
  • RevitLinks
  • Worksets
  • DesignOptions

Imported categories are detected in VtcCategoryClassifier; Revit Links are a dedicated tab whose children are grouped link-setting rows.

Import Categories

Extraction and compare

  • ExtractCategories(...) emits imported parents and imported layers/subcategories as VtcCategoryGraphicsData.
  • AddCategoryChanges(...) keeps those rows in the same category compare pipeline as all other categories.
  • Imported rows keep SettingType=CategoryOverride; there is no import-specific apply path.

Edit/process behavior

  • Inline edit buttons, Inspector-side edit actions, Preview, pending override retention, BatchApply, save-merged, and snapshot apply all reuse the standard category path.
  • Missing-side imported selections reset visibility/graphics the same way as any other category row.

Revit Links

Contract

The linked-file blob is deleted. The active contract is:

  • VtcTemplateSettingsModel.RevitLinks
  • VtcRevitLinkTargetInfo
  • VtcRevitLinkSettingData
  • VtcRevitLinkSettingValue
  • VtcCopyRevitLinkSettingsOptions

Each row is one target plus one native setting, not a mixed payload.

Target kinds

VTC extracts both:

  • RevitLinkType
  • RevitLinkInstance

Targets are keyed separately, labeled separately, and copied separately.

Supported setting matrix

VTC derives support from runtime member availability on RevitLinkGraphicsSettings.

Supported desktop Revit 2026.5+ and 2027 metadata:

  • LinkVisibilityType
  • LinkedViewId

The current Revit 2026 metadata source is the pinned 2026.4.10 portable package used for cross-platform compilation, not proof of installed-Revit-2026.5 API parity.

  • ViewFilterType
  • NestedLinks
  • ObjectStyles
  • ColorFill
  • ViewRange
  • Phase
  • PhaseFilter
  • ViewDetailLevel
  • Discipline

The adapter binds directly to typed Revit API members; all 11 setting kinds are emitted and copied in every supported year.

Extraction

  • ExtractRevitLinks(...) enumerates link targets, reads View.GetLinkOverrides(...), and emits one VtcRevitLinkSettingData row for each of the 11 setting kinds.
  • Simple settings use native LinkVisibility or ElementId values directly.
  • Phase, Phase Filter, Detail Level, and Discipline use their public getter/setter pairs and are stored as one explicit row each.
  • VTC stores template display settings as typed VTC enums (DetailLevel, DisplayStyle, PartsVisibility, ViewDiscipline, VtcShowHiddenLinesMode) and only converts to Autodesk Revit enums at the Revit service boundary.
  • Linked element names are resolved from the linked document only when available. Those names are the canonical cross-model identity for Linked View, Phase, and Phase Filter.

Compare and tree shape

  • RevitLinkDiffEvaluator produces explicit diff rows keyed as link.{type|instance}.name.{link}.{setting}.
  • TemplateDifferenceEvaluator compares typed SettingValue cases instead of storing object payloads, so display/apply/App consumers pattern-match the concrete setting shape directly.
  • LinkName is the canonical cross-model key. If it is ambiguous within a target kind, compare fails instead of guessing.
  • DiffTreeBuilder groups those rows under Revit Links by LinkDisplayName, so the main tree shows link groups with native setting leaves.

Apply and reset semantics

  • ApplyRevitLinkSettingChange(...) reads current link overrides, mutates only the selected native setting, and writes the updated RevitLinkGraphicsSettings back through View.SetLinkOverrides(...).
  • Apply resolves Revit-link targets by canonical LinkName only; there is no alternate id-path during snapshot/process apply.
  • Linked View, Phase, and Phase Filter are remapped by linked-element name during apply, and dependent rows prime the required top-level visibility mode before SetLinkOverrides(...) runs.
  • Missing-side selections reset only the selected setting to host/default behavior; they do not use a compare-only fallback path.

Copy

  • Copy always handles all 11 Revit-link setting kinds from one link target to another, matching the complete set emitted during extraction.
  • CopyRevitLinkSettings(...) reads and writes RevitLinkGraphicsSettings through typed API members.
  • Linked View, Phase, and Phase Filter copy by resolving the source linked-element name and finding the same name in the target linked RVT; raw linked-document ids are not reused.
  • If the source linked document is unloaded and that name cannot be resolved, copy reuses the raw linked-element id only when source and target reference the same linked model. Cross-link copy fails instead of reusing an unverifiable id.
  • The focused Revit-link modal and copy command operate on one concrete template side at a time. When both sides contain the row and no side is already selected, VTC prompts for the target template instead of silently defaulting to Left.
  • RevitLinkActionSourceResolver first selects the only available side or a viable selected side. It reports no Revit-link value or a genuinely ambiguous two-sided input without presenting UI; App owns the corresponding error or prompt.
  • Opening the focused modal from a leaf row scopes back to the full link group, so the modal always shows all 11 setting kinds for one link target.

Removed Design

Deleted from the active design:

  • VtcLinkedFileOverrideData
  • linked CategoryOverrides
  • host category override masquerading
  • copy flags for unsupported linked-category payloads
  • compare-only linked-category UI

A former in-tree VTC_Enhanced_Design.md design document was superseded by this rewrite and has since been removed; this spec is the live source of truth.

Verification State

Library JSON is admitted as one current snapshot shape. Required top-level members and collections must be present, explicit nulls and invalid required nested elements are rejected, and the same validation runs before saving an in-memory snapshot. Saved Revit-link rows require visibility modes from 0 through 2, no mode for linked-view ids, detail levels from 0 through 3, defined discipline values, and no enum payload on other setting kinds. GetSavedTemplates returns an empty list for DirectoryNotFoundException without creating the cache directory. Other enumeration failures raise TemplateStorageException with operation enumerate. TemplateExists returns false for a missing file or cache directory; any other probe failure raises TemplateStorageException (operation probe), so a save is refused instead of overwriting. An existing name is replaced only after the user answers Replace. Without that answer SaveTemplate publishes with overwrite disabled, so a template another process saves under the name after the probe is kept and the save fails with TemplateStorageException.

TemplateStorage alone derives cache file paths from a logical template name. Its list metadata carries only name and modification time; load/delete/existence use the logical name, and rooted or separator-containing names are rejected before path derivation. DiffTreeBuilder is construction-only, while DiffTreeIndex retains the rebuilt roots and owns canonical key/path/selection and Revit-link subtree lookup for all live tree consumers.
