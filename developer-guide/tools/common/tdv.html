TDV - Transfer Drafting Views

TDV (Transfer Drafting Views) is a tool for importing and exporting drafting views between Revit documents and a central library. It enables teams to maintain a shared collection of standard drafting views that can be distributed across projects.

Overview

TDV provides two primary operations:

  1. Export to Library - Copy drafting views from the active document to a central library file
  2. Import from Library - Copy drafting views from a library file to the active document

The tool handles worksharing, creates local copies for edits, and synchronizes changes back to the central library file after export operations.

Features

Core Capabilities

  • Bi-directional transfer - Import and export drafting views between documents
  • View type mapping - Map source view types to destination view types, or retain original type
  • Conflict detection - Real-time detection of naming conflicts with existing views and duplicate destination names inside the current selection
  • Replace mode - Option to replace existing views with the same name
  • Preview panel - Live preview of selected drafting views with pan/zoom support
  • Batch transfer - Transfer multiple views in a single operation
  • Destination transaction grouping - Every batch group and item transaction is bound to the same explicit destination document for atomicity, including non-active library destinations
  • Progress tracking - Per-view progress feedback during transfer operations

Crash Hardening (2026-02-07)

The TDV import/export apply path was hardened after a Revit 2026 hard-crash investigation:

  • Destination-bound transactions - The transfer group and per-view transactions are now started against the explicit destination Document, not implicitly against ActiveUIDocument.
  • Cross-document safety checks - TDV now validates that source/destination contexts are valid live documents and not the same document.
  • Transfer run diagnostics - Transfer start logs include run id plus source/destination title and path to improve post-crash forensics.
  • Non-activating library open - TDV now opens library files with Application.OpenDocumentFile(...) (no activate) so the host model stays active during transfer and cleanup.
  • Close-failure truth - Required save/sync close treats a Document.Close(...) == false result as an operational failure. Best-effort cleanup (TryCloseAsync) returns false only when Revit refuses to close the active document; unexpected cleanup failures propagate instead of being converted into a warning-only result.

Library Management

  • Multiple library files - Configure multiple library files with fallback paths
  • Path validation - Automatic validation of library file accessibility
  • Local copy workflow - Creates local copies from central files for worksharing
  • Automatic sync - Syncs changes back to central after export with detailed comments

View Transfer Details

When transferring views, TDV:

  1. Validates destination names before entering the transfer transaction
  2. Creates or prepares the destination view with the selected view type
  3. Copies the view scale and description parameters
  4. Copies all elements from the source view (excluding viewports, title blocks, schedules, etc.)
  5. Copies element graphic overrides from source to destination

If any of those steps fail, the per-view transaction rolls back and TDV records the row as failed instead of reporting partial success. DestinationTransactionGroup receives the destination Document at begin, rejects item or finalization calls for any other document, and runs each item transaction against that owned destination. This keeps import (library -> host) and export (host -> non-active library) under the same real Revit group rather than resolving the group from ActiveUIDocument. Successful row state and add/replace counts are queued until the group returns an observed Committed outcome. An observed RolledBack outcome marks attempted rows discarded; an unknown or failed finalization withholds success without claiming either commit or rollback. Operation, finalization, and disposal failures remain ordered in the logged exception chain while the row result keeps the stable per-view error code and message shape.

View Type Resolution Rules

The row View Type combobox is destination-scoped for the active transfer direction:

  • Import (library -> host): combobox options are drafting view types from the host document.
  • Export (host -> library): combobox options are drafting view types from the library document.

Retain Original always resolves to the source view's drafting type name for that row. If that type name is missing in the destination document, TDV creates it by duplicating an existing destination drafting ViewFamilyType and renaming the duplicate.

If source type name resolution fails, TDV records a per-view SourceTypeNameUnavailable error and does not silently fall back.

Architecture

TDV's manifest entrypoints and DI live in App/Composition. App/Sessions/WindowSession creates a registered stable modal shell through Core's ToolWindowFactory, owns the owner provider, logger display, alerts, banners, initial load, normal-close cleanup, and result projection. App/Views/TdvWindow.xaml is embedded raw XAML with the named header, grid, preview, and actions sections inlined. The separate library settings view is also raw XAML, loaded with ToolWindowXaml.LoadElement. Both resources have explicit logical names and contain only stable/framework WPF types. TdvWindowViewModel remains the App orchestration edge. App/Persistence/CachePaths supplies cache roots to the Library and Preview capabilities. Preview image caching and its session temp-directory lifecycle remain in Features/Preview/State.

Transfer is a single Revit-facing transfer service split across focused partial files: constructor/shared guards, catalog operations, apply-selection orchestration, and per-row transfer steps. The split is organizational only; it does not introduce an additional service boundary around Revit transaction state. DraftingViewAdapter.cs owns drafting-view enumeration/name lookup, DraftingViewTypeAdapter.cs owns drafting-view type lookup and missing destination type creation, DraftingViewAdapter.Transfer.cs owns drafting-view create/copy/clear/override transfer operations, and PreviewExporter.cs owns preview export behavior.

Transfer.RunState.cs keeps the private per-run selection accounting beside, but out of, the apply-selection orchestration file. It holds duplicate destination names, deferred committed-row successes, cancellation, rollback/unknown-finalization row reporting, and the final TransferResult; it is compiled into the same Transfer partial class, not a second service or transaction boundary.

Transfer command orchestration is split by operation direction. ExportTransferWorkflow and ImportTransferWorkflow own their feature-specific document and outcome decisions, while LibraryTransferWorkflow owns shared catalog selection, library-open coordination, close warnings, and host reactivation requests. The Library workflow consumes its Library-owned ILibrarySelectionDialog port; the two Transfer workflows consume the Transfer-owned ITransferDialog port. App/Sessions/WindowSession implements both inward ports: it owns library-selection presentation, loads the embedded TDV view and shows its stable shell modally with the application-provided IWindowOwnerHandleProvider, and projects the window counts/errors into TransferDialogResult. The App type deliberately uses window/session language; no feature-named presentation adapter is exiled under App. LibraryDocumentService stays focused on Revit document open/save/sync/close calls, while LibraryCatalog owns library path validation from the current TDV settings snapshot.

Service Registration

TDV registers its tool services from App/Composition/TdvToolModule through App/Composition/ServiceCollectionExtensions.AddTdv(). Registrations stay scoped because TDV consumes Revit run-scope dependencies. The composition root supplies the current Revit year and library-file metadata probe, keeps concrete Revit adapters in their feature Revit wings, and wires the import/export workflows at the tool edge.

services.AddScoped<Transfer>(sp =>
    new Transfer(gate, tx, groups, logger));
services.AddScoped<Func<LibraryCatalog>>(sp =>
    () => new LibraryCatalog(
        settings.Get<LibraryOptions>().Files.ToList(),
        RevitInstanceIdentity.RevitYear,
        RevitYearProbe.Probe));
services.AddScoped<LibraryDocumentService>(sp =>
    new LibraryDocumentService(
        gate,
        logger,
        CachePaths.LibraryLocalsRoot,
        RevitInstanceIdentity.RevitYear,
        RevitYearProbe.Probe));
services.AddScoped<WindowSession>(sp =>
    new WindowSession(
        transferService, alerts, loggerFactory, loggerWindowHost, ownerHandleProvider, windowFactory));
services.AddScoped<ILibrarySelectionDialog>(sp =>
    sp.GetRequiredService<WindowSession>());
services.AddScoped<ITransferDialog>(sp =>
    sp.GetRequiredService<WindowSession>());

Transfer Service Operations

The concrete Transfer defines:

Method Description
BuildViewItemsAsync Collects drafting views from source document
ApplySelectionAsync Executes transfer work in one continuous Revit API callback
WouldConflictAsync Checks for naming conflicts
ExportPreviewAsync Generates preview image for a view

ApplySelectionAsync must start inside an active Revit API callback. The supplied gate and transaction runner must keep transfer execution in that initiating callback. The three query methods can queue each complete operation independently.

UI Components

Main Window (TdvWindow)

The registered modal shell retains the title "Transfer Drafting Views", initial size 1400 × 700, minimum size 1200 × 600, centered placement, taskbar entry, and resizable layout. The named sections in the raw view retain their controls and commands:

  • TransferHeaderView: conflict warning, type filter, search, and separator.
  • TransferGridView: drafting-view transfer grid and row visuals.
  • TransferActionsView: status, selection/transfer actions, and errors.
  • TransferPreviewView: preview panel, cursor-relative wheel zoom, mouse panning, zoom button, and image-update zoom.

The Sandbox manifest also declares these shell dimensions, taskbar visibility, and centered placement. The authenticated discovery bridge carries them into the same stable options used by the raw Sandbox host.

The main raw view merges Presentation's theme once at its root; the standalone library settings view merges its own theme. String item lists and tooltips use explicit text templates. Row-state triggers use enum names as strings. The existing stable PreviewZoomBehavior owns zoom-on-image-update and defers its zoom operation until layout. DBTools.Presentation.Tools.TDV.TdvPanZoomBehavior owns mouse pan/zoom and releases capture, cursor state, and subscriptions during retirement.

ProgressOverlay.For(session.Window) attaches after the view is loaded and before showing the dialog. A normal Closed notification clears UI actions, cancels obsolete preview/conflict requests, disposes the view model, and removes its cache files. The host retires the session and releases owned subscriptions, behavior state, the initializer, overlay registration, and owner. TDV's cleanup and result contract uses the normal Closed notification, including a window closed before ShowDialog; a normal early close still permits library-document cleanup. Late callbacks and catalog results leave a disposed view model alone. A load failure after close does not show an alert or log a load error, and failure to present a load-error alert still requests close. Dev Mode retirement diagnoses a pending load, preview, conflict refresh, or transfer instead of cancelling tasks during retirement. Idle retirement is synchronous and does not pump the dispatcher.

The library settings page uses stable tree selection and a focus-request counter. Selecting a main library entry with an empty or whitespace alias focuses and selects the alias text at Background priority. Entries with an existing alias and fallback entries do not take focus.

Preview Features

The preview panel supports:

  • Debounced loading - 200ms debounce prevents excessive exports
  • Bounded cache - Keeps up to 32 preview images; the oldest inserted view is evicted first (first-in-first-out)
  • Pan and zoom - Interactive image manipulation via PanZoomBehavior
  • Zoom Extents - Fits + centers the preview image in the viewport
  • Best-effort cropping - Preview exports are cropped to content bounds (non-background pixels) so extents-based zoom targets the real view content
  • Honest placeholder states - The empty-state text now distinguishes no row selected from preview export failed
  • Latest-request ownership - Each debounced request captures and owns one local cancellation source/token. Selection, image, unavailable, and exception terminal publications all re-check both that token and the captured sequence; a superseded request can log its fault but cannot overwrite the latest preview. Expected cancellation emits no exception stacktrace.
  • Dark theme background - Consistent preview appearance (RGB: 43, 44, 61)

Library Settings

TDV uses the LibrarySettings class to store library file configurations:

public sealed class LibraryFileEntry
{
    public string? MainPath { get; set; }

Each library entry supports:

  • Main path - Primary path to the library RVT file
  • Fallback path - Alternative path (e.g., for different network locations)
  • Alias - Optional friendly name used in the Import/Export library picker

Settings Pack

The SettingsPackContext provides the settings UI with:

  • Tree-based library file management
  • Add/remove library files
  • Add/remove fallback paths
  • Real-time path validation
  • Pending changes tracking

The settings-pack factory supplies the current Revit year and metadata probe from the TDV composition root, so library validation stays consistent with runtime import/export checks without making settings UI code depend on Revit/Services.

Runtime library validation follows the same boundary: LibraryTransferWorkflow receives a Func<LibraryCatalog> from the composition root, so transfer workflows do not import the mutable TDV settings type directly.

Settings Path Presentation

Library paths in settings are rendered with:

  • Validation icon at the left of each tree row (green check / red error)
  • Tooltip showing the full absolute path
  • Compact display text that keeps root + filename + the final 3 folder levels

This avoids horizontal scrolling while preserving useful location context.

Path Validation

Library paths are validated for:

  • File existence
  • .rvt extension
  • Revit version compatibility (file's saved version must match the current Revit session)
  • Revit metadata readability (BasicFileInfo probe failures now mark the path invalid instead of allowing access)
  • Accessibility

Invalid paths trigger a settings warning that disables the import/export commands.

Library warnings are evaluated on startup, so the Import/Export ribbon tools may be disabled immediately if configured library paths are invalid.

Revit Version Validation

Library files are checked at two points to prevent version mismatches or unreadable-version access:

  1. Validation time (LibraryCatalog.ValidatePath): Uses the injected Revit metadata probe to read the file's saved Revit version and compare it against the current session. Mismatched files are marked invalid with a descriptive failure reason. If the metadata probe throws or returns no saved year, the path is also marked invalid and TDV logs the probe failure with the full exception instead of allowing access.

  2. Open time (LibraryDocumentService.OpenLibraryAsync): A belt-and-suspenders check before opening. Throws InvalidOperationException if the file version doesn't match, which is caught by the command's try/catch and displayed as a banner.

This prevents two dangerous scenarios:

  • Workshared files: WorksharingUtils.CreateNewLocal() would throw a version mismatch error at open time
  • Non-workshared files: Revit would silently upgrade the file, which is destructive

Library Open Error Presentation

When opening a library document, TDV routes import and export through LibraryTransferWorkflow.OpenLibraryAsync(...). Revit document open work still happens in LibraryDocumentService.OpenLibraryAsync(...); open failures propagate through the direction-specific workflow to the command ISafeExecutor boundary instead of being flattened into the same null path used for cancelled library selection.

Error Handling

Per-View Error Codes

Transfer failures are categorized by error code:

Code Description
Unknown Unspecified error
DestinationTypeMissing Target view type not found
SourceTypeNameUnavailable Cannot read source view type
CreateViewFailed Failed to create or prepare destination view
CopyElementsFailed Failed to copy view elements
OverridesFailed Failed to copy graphic overrides
DestinationNameRequired Destination view name was blank
DuplicateTargetName Another selected row used the same destination view name
DestinationNameConflict Destination view already existed and Replace was not enabled
ClearDestinationViewFailed Existing destination contents could not be cleared
MetadataCopyFailed View scale/description copy failed
TransactionRolledBack Revit discarded attempted changes for the run

Error Reporting

After each transfer attempt, TDV now always surfaces result UX:

  • Top banner on the TDV window (success/warning) with selected/processed/result counts
  • Summary alert with:
    • Selected, processed, added, replaced, failed, and not-attempted counts
    • Optional per-view issue table when failures exist
    • Action buttons: Accept and Transfer More and Close Tool
    • Copy-to-clipboard for per-view issue rows

TDV also records and surfaces selection accountability:

  • Transfer logs now include selected view identifiers/names (bounded preview)
  • Result payload includes SelectedCount, ProcessedCount, FailedCount, UnprocessedCount, Cancelled, and the observed FinalizationOutcome; AllChangesDiscarded is derived only from RolledBack
  • TDV now carries per-row transfer state through the shared RowState enum from Transfer into the row view models and XAML triggers instead of routing string status literals through presentation code
  • TDV logs per-view operation failures with the preserved exception object while recording only the stable row-facing code/message in TdvApplySelectionResult
  • Success row callbacks and committed add/replace counts publish only after an observed Committed transaction-group outcome
  • An observed rollback marks attempted rows discarded. Unknown finalization zeroes projected success, marks attempted rows failed with Unknown, and reports that the destination edit state is unverified without claiming rollback.
  • Save/sync paths always attempt library-document close. A Document.Close(...) == false result is a required-close failure, not success. A sole save, sync, or close failure preserves its original exception; when both the primary operation and close fail, TDV throws one ordered AggregateException with the primary failure first.
  • Best-effort cleanup returns false only for Revit's active-document refusal. Other cleanup failures propagate; when an export has already failed, TDV reports one ordered AggregateException with the transfer failure first and the cleanup failure second.

Revit API Operations

Getting Drafting Views

new FilteredElementCollector(doc)
    .OfClass(typeof(View))
    .WhereElementIsNotElementType()
    .Cast<View>()
    .Where(v => v.ViewType == ViewType.DraftingView && !v.IsTemplate)

Copying View Contents

Elements are copied using ElementTransformUtils.CopyElements with a custom IDuplicateTypeNamesHandler that uses destination types when duplicates are found.

Destination Name Validation

TDV no longer auto-suffixes destination drafting view names during apply. If a selected row targets a blank name, collides with an existing destination view while Replace is off, or duplicates another selected row's destination name, the row is blocked/fails explicitly.

Skipped Categories

The following categories are excluded from copy operations:

  • Title Blocks
  • Viewports
  • Views
  • Schedules
  • Guide Grids

Export Command Flow

  1. Validate library paths are configured
  2. Prompt user to select a library file
  3. If workshared, create a per-operation local copy under the TDV cache folder
  4. Open library document
  5. Show the registered TDV modal session for view selection
  6. Execute transfer to library
  7. Sync changes to central with comment
  8. Close library and reactivate original document
  9. Surface a warning only when cleanup is refused because the library is active; otherwise propagate a close failure so a successful export is never reported after a required close failure

Import Command Flow

  1. Validate library paths are configured
  2. Prompt user to select a library file
  3. If workshared, create a per-operation local copy under the TDV cache folder
  4. Open library document
  5. Show the registered TDV modal session for view selection
  6. Execute transfer to active document
  7. Close library (no sync needed)
  8. Surface a cleanup warning if the library document could not be closed automatically
