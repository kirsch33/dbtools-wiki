View Template Comparer (VTC) — Developer Guide

VTC compares two Revit view templates, stages category edits locally, and applies selections plus eligible pending overrides through one ApplySelectedChangesCommand path (user-facing button label stays "Process").

Current Architecture

Test ownership

AlertBodyTemplateProviderTests belongs to VTC App composition. The VTC Pure project exercises the provider and its raw AlertBodyTemplates.xaml resource (DBTools.ToolViews.VTC.AlertBodyTemplates.xaml) through a plain reference to the normal desktop VTC owner; this is WPF-only and does not start a Revit host.

Command + application shell

  • VtcCommand remains the Revit entrypoint.
  • VtcCommand validates the DBTools command context and delegates application assembly to App/Composition/VtcWindowLauncher.
  • VtcWindowLauncher owns modal launch flow: it resolves document-scoped templates, handles the no-template alert, delegates collaborator construction to VtcWindowCompositionFactory, creates VtcWindowSession through Core ToolWindowFactory, and, after dialog close, ensures the logger window when Debug Mode is on. It always retires the comparer and linked-file windows; a dialog failure stays ahead of every retirement failure.
  • VtcWindowCompositionFactory creates one document-scoped graph: TemplateExtractor, RevitLinkSettingsAdapter, TemplateDifferenceEvaluator, TemplateApplier, TemplateMaterializer, and the single outward TemplateRuntime.
  • TemplateRuntime is the only document façade. It owns template-ID resolution and exposes compare, extract, apply, materialize, Revit-link copy, and pattern queries without retaining a second pass-through comparison façade. App batch-session consumers depend on the focused ITemplateSessionRuntime port; the Revit façade implements it, and pure tests substitute only that external boundary rather than shadowing the production class.
  • VtcWindowSession owns the modal tool-window session. Core ToolWindowFactory supplies the stable shell for the raw VTC view; Comparison owns the comparison workspace, Inspector, and Preview views; Library owns its concrete workspace view; the focused Revit-link modal reuses the Comparison-owned diff control.
  • AlertPresenter is the one VTC presentation boundary. Composition supplies the raw alert service only to that presenter; App view-model and workflow consumers use the presenter for standard alerts plus bespoke requests and selections.
  • VtcWindowBatchWorkflow owns only App session reactions for Process and Library work. The App view-model owns Revit-link prompts, modal hosting, refresh, and result presentation; TemplateRuntime delegates Revit-link batch apply/copy execution and expected-conflict classification to Template Apply. There is no App-facing feature workflow, callback inversion, or raw alert-service escape.

Dev Mode view hosting

VTC views are raw XAML EmbeddedResource items with explicit logical names. The main view uses DBTools.ToolViews.VTC.VtcWindow.xaml; the remaining resources are DBTools.ToolViews.VTC.AlertBodyTemplates.xaml, DBTools.ToolViews.VTC.ComparisonWorkspaceView.xaml, DBTools.ToolViews.VTC.ComparisonInspectorView.xaml, DBTools.ToolViews.VTC.ComparisonPreviewView.xaml, DBTools.ToolViews.VTC.DiffViewControl.xaml, DBTools.ToolViews.VTC.LibraryView.xaml, and DBTools.ToolViews.VTC.RevitLinkSettingsWindow.xaml. VtcWindowSession reads the main resource through Core ToolWindowFactory and owns once-only owner attachment and cleanup. VTC has no custom close gate or native pick loop.

Shared VTC resource dictionaries live in the stable DBTools.Presentation/Tools/VTC/ owner as VtcDiffViewStyles.xaml and VtcComparisonViewStyles.xaml. Stable converters in the flat DBTools.Presentation.Tools.VTC namespace are VtcConflictConverter and VtcRawViewConverter. VtcResourceTemplateSelector resolves App-owned outcome templates and always returns an empty template for standalone views. Alert bodies use full-name string keys with the stable TypeNameTemplateSelector; every content and item slot has an explicit template, immutable record values use OneTime bindings, and mutable view-model state uses INotifyPropertyChanged.

The conversion preserves live comparison and Inspector bindings, preview navigation only for navigable setting keys, workspace path realization and selection, eligible left-button double-click override editing, Library split-button menu placement, and modal close behavior. Keyboard focus moves to the comparison row after the inspector tab loads. Pending navigation focus and close requests are aborted on retirement.

Each raw view merges Theme once, before the VTC style dictionaries. The shared dictionaries do not merge Theme again. Vtc.TreeView keeps its original implicit TreeView base and VTC overrides; each tree retains its existing scrolling and virtualization settings. Named item selectors specify TextSearch.TextPath for prefix typing and automation names on their template text. SavedTemplateInfo, ViewFilterOption, LinePattern, FillPatternData, and TemplateOption return their display label from ToString() so item-container automation peers and text fallbacks also use the displayed label without changing the themed container styles.

Two interaction changes are intentional: override editing responds only to the left mouse button, and the linked dialog’s context-menu selection commands now resolve through its own view model and work. The raw linked view itself carries the “Linked file override differences” automation name. The main window initializer retains the VtcWindow log prefix.

Core services

  • TemplateSnapshot stores explicit Revit-link setting rows in RevitLinks; the old linked-file blob payload is gone.
  • Display settings now use typed VTC enums for detail level, display style, parts visibility, discipline, and show-hidden-lines, with explicit conversion only at the Revit API boundary.
  • SettingDifference.LeftValue / RightValue store typed SettingValue cases instead of object, and compare/apply/App paths pattern-match those cases rather than recovering payload shape with runtime casts.
  • TemplateDifferenceEvaluator is host-neutral under Features/Comparison; TemplateExtractor and RevitLinkSettingsAdapter own Revit mechanics behind TemplateRuntime.
  • SettingPreviewItem and DiffTreeProjector.ViewFilter are Comparison-owned input/state contracts, so feature projections do not import App view models.
  • DiffTreeNode contains comparison and local display state only. PendingOverrideState owns pending override DTOs without tree or UI dependencies, and TemplateApplyResult remains the sole apply-outcome authority. The App view-model projects that result onto current setting keys for row feedback and filtering without storing outcomes on comparison nodes.
  • VtcWindowBatchWorkflow.SavedTemplates treats template extraction/merge and the cache save/delete as the mutation boundary. After a committed mutation, list refresh has its own error boundary: log the refresh failure with the template name and show one warning that the cache operation succeeded; show success only after the list refresh succeeds. Both save commands ask "Replace saved template 'X'?" through AlertPresenter before overwriting an existing name; Cancel writes nothing.
  • DiffTreeBuilder only constructs a tree from differences. DiffTreeIndex retains the rebuilt roots and owns key lookup, canonical-node paths, tree-order selection collection, and Revit-link subtree queries for the coordinator, preview projection, and focused Revit-link modal.

Owner layout

VTC is multi-feature: Features/{Comparison,Library,RevitLinks,TemplateApply} own their domain/planning/state/Revit/UI layers. Tool-wide vocabulary remains under the small root Domain, including persisted RevitLinkSetting, RevitLinkSettingKind, RevitLinkSettingValue, RevitLinkTarget, and RevitLinkTargetKind; application views, view models, resources, sessions, and composition live under App; shared Revit document adapters live under Revit/Template. The former Shell, Shared, and root UI organizers are dissolved.

  • Extraction, diff computation, and native Revit-link loading/copy/apply logic live in focused owners rather than overlapping façades. Comparison owns window comparison state and UI-neutral source selection; Template Apply owns batch execution and expected conflict classification; RevitLinkSettingsAdapter owns extract/copy mechanics and reads and writes RevitLinkGraphicsSettings directly, while RevitLinkTargetResolver owns target lookup plus linked-document name/id remapping.
  • Local Revit tests compose the same concrete runtime graph; no compatibility façade or forwarding alias remains.
  • The App outcome projection remains App-owned. It is composed into Comparison views through runtime templates, while Comparison emits only selected-node, override-edit, and preview-setting requests for App cross-pane/modal coordination.

Imported Categories

  • Imported Categories stay inside the normal CategoryOverride pipeline.
  • CategoryTabClassifier routes model categories with positive IDs to ImportedCategories. Other category types retain their native tab routing.
  • Extraction, compare, inline edit, preview, Process, merged-save, and snapshot apply all reuse the same category contracts and VM state as any other category row.
  • Tree rendering keeps imported categories under their own native-looking tab; imported layers/subcategories still inherit the imported parent tab.

Revit Links

Native-only contract

  • Revit Links no longer use VtcLinkedFileOverrideData, CategoryOverrides, host-category masquerading, or compare-only linked-category blobs.
  • VTC emits one explicit VtcRevitLinkSettingData row for each of the 11 Revit-link setting kinds.
  • Revit-link rows now use one canonical key: target kind (type or instance), canonical LinkName, and setting kind.
  • Cross-model compare/save/load/apply no longer switches between doc-local ids and alternate matching paths. If LinkName is ambiguous for a target kind, VTC now fails instead of guessing.
  • The diff tree groups those rows under Revit Links by link display name, so the main tree shows all 11 leaf settings instead of one opaque link blob row.

Supported API surface

  • Supported desktop Revit 2026.5+ and 2027 public API metadata includes:
    • ViewFilterType
    • NestedLinks
    • ObjectStyles

Revit 2026 API/reference metadata currently derives from the pinned 2026.4.10 portable package for cross-platform compilation; it is not installed-Revit-2026.5 API-parity proof.

  • ColorFill
  • ViewRange
  • Phase
  • PhaseFilter
  • ViewDetailLevel
  • Discipline
  • VTC always emits and copies all 11 Revit-link setting kinds through typed RevitLinkGraphicsSettings members.
  • Type-level and instance-level link targets are both extracted through View.GetLinkOverrides(...) / View.SetLinkOverrides(...).

UI and copy flow

  • The context menu now exposes “Open Revit Link Settings...” and “Copy Revit Link Settings To...”.
  • Those actions only appear on a concrete Revit-link group or leaf row, not on the Revit Links tab root.
  • Opening the focused modal from any Revit-link leaf now scopes the modal back to that link target’s full setting group instead of showing a one-row subset.
  • RevitLinkActionSourceResolver is the Comparison-owned, UI-neutral selection rule: it chooses the sole available side or a viable selected side, and reports ambiguity only when both sides remain viable. App owns the resulting prompt and all user-visible effects.
  • If both Left and Right contain the same Revit-link row and no side is already selected, VTC prompts for which template the modal/copy action should operate on instead of silently defaulting to Left.
  • The focused modal rehosts all 11 Revit-link rows present in the main tree, and a successful modal apply refreshes the main comparison so the tree is not left stale.
  • Applying from the focused modal uses BatchApply in one VTC Process Apply transaction, with one subtransaction per setting and one Undo entry. A missing comparison key is an ElementNotFound conflict; an unexpected fault rolls back the whole apply.
  • Copy uses GetRevitLinkTargets() plus CopyRevitLinkSettings(...) and always handles all 11 Revit-link setting kinds, matching extraction.
  • Copy runs each target in a Copy Revit Link Settings transaction, then assimilates those transactions into one Undo entry. An expected failure rolls back only that target; an unexpected fault rolls back every target.
  • Linked View, Phase, and Phase Filter are remapped by linked-element name when source and target point at different linked RVTs; raw linked-document ids are not copied across models.
  • When the source linked document is unloaded and that remap name is unavailable, copy reuses the raw id only if source and target reference the same linked model. Cross-link copy fails instead of guessing.

Removed behavior

  • Deleted behavior:
    • compare-only linked-category extraction
    • CopyCategoryOverrides-style linked copy flags
    • one-row linked-file blob compare/apply semantics
    • linked-model Model/Annotation/Import Categories masquerading as host category rows
  • VTC now either reads and writes a setting through public API or omits it entirely.

Process + Serialization

  • ApplySelectedChangesCommand still batches selections plus eligible pending category overrides, with per-setting SubTransaction isolation for expected conflicts.
  • An apply failure becomes a per-setting conflict only after its subtransaction confirms RolledBack. A thrown rollback failure or another status aborts the batch with a BatchApplyException containing both causes, ordered apply failure then rollback failure. Unconfirmed rollback never publishes a pending-override conflict key.
  • Create Merged runs template creation and the pending-override batch in one TransactionGroup (TemplateRuntime.CreateMergedTemplate), assimilated into one Undo entry named Create Merged View Template. Expected per-setting conflicts are reported and keep the new template; any other fault rolls the group back and leaves no template, so a retry with the same name succeeds.
  • TemplateMaterializer copies the Left template with ElementTransformUtils.CopyElements, using a duplicate-type handler that keeps destination types so Revit opens no modal dialog. It catches no copy failures, so any fault rolls back the group and reaches RunOrReport as an Error alert.
  • TemplateStorage admits one complete current TemplateSnapshot graph on both load and save, including required collections, nested elements, and enum values. Incompatible data uses the existing storage exception channel; no normalization or old-format recovery is performed.
  • TemplateStorage is the sole cache-path owner. Callers use logical template names; SavedTemplateInfo exposes only the name and modification time, and rooted or separator-containing names are rejected rather than normalized.
  • Library enumeration and existence checks are pure queries when the cache directory is absent. Enumeration returns an empty list for DirectoryNotFoundException; other enumeration failures raise TemplateStorageException with operation enumerate. TemplateExists returns false for a missing file or folder and raises TemplateStorageException for other probe failures. Only SaveTemplate creates the directory.
  • TemplateExtractor has no duplicability probe or logger dependency; the unused CheckDuplicability surface was deleted with all constructor callsites updated.
  • Revit-link rows participate in Preview, Process, create-merged, and save-merged as ordinary diff rows.
  • BuildMergedModel(...) now persists explicit RevitLinks rows instead of the deleted linked-file blob contract.
  • Merged-template construction is Application-owned: Features/Application/Planning/VtcMergedTemplateBuilder derives the merged VtcTemplateSettingsModel from comparison result, selections, base side, and name. Application view-model operations keep only effect orchestration and call the feature builder.
  • Missing-side Revit-link selections now reset only the selected native setting row to its default/host state.
  • Snapshot-style compare/save/load/apply reuses the same canonical LinkName keys as normal compare; it does not switch between id keys and alternate lookup routes.
