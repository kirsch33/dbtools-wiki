Application boundary

manifest.yml binds:

  • module: DBTools.SGT.App.Composition.SgtToolModule
  • command: DBTools.SGT.App.Composition.SgtCommand
  • window: DBTools.SGT.App.Views.SgtWindow
  • design-time view model: DBTools.SGT.App.DesignTime.SgtWindowDesignTimeViewModel (used by the Sandbox window)

App/Views/SgtWindow.xaml, PreviewView.xaml, OpeningView.xaml and GirtView.xaml are raw EmbeddedResource views. ToolWindowFactory owns the modal shell. SgtWindow is a composition object: it supplies the view model, composes the three child elements, attaches the preview presenter and releases the view graph through the host session. The payload has no XAML code-behind and no WPF-derived view type. SgtWindowDesignTimeViewModel and SgtWindowSamplePopulator supply the Sandbox design-time model.

The Sandbox creates the raw SgtWindow shell from its manifest entry, then calls the ISgtSandboxViewComposer callback that SgtWindowDesignTimeViewModel implements. SgtWindowRawViewComposer serves that callback and the live window, so the sample gets the same Girt, Openings and Preview fragments, preview input behavior and session cleanup. The callback interface is in Presentation, not Core, because the Sandbox and the tool can use different load contexts while Presentation is the shared WPF owner.

Dependencies

  • Features and App may use Domain/Plans/Projection/PlanBaselineMapper, which captures a Plan as a PlanBaselineSnapshot and rebuilds the editable plan from that snapshot and PlacedSystem: girt rows from the stored girt members through PlanProjectionMapper, opening rows and wall geometry from Placed, runtime collections derived from those rows, and the snapshot kept in Plan.BaselineSnapshot.
  • Edit startup reads one live snapshot, lets Change Review apply remembered decisions, and then the edit builder analyzes that plan against the current target.
  • Persistence owns the SettingsData transport and admission (SystemStorageMapper.Plan.cs), StoredSystem, ISystemRepository and the Revit adapter. Features do not depend on Persistence for baseline projection; Persistence does not depend on App.
  • Domain does not depend on App, Features, Persistence, CommunityToolkit, ObservableCollection or WPF. Features do not depend on App. Feature ports are implemented or composed at the App boundary.
  • EndpointAssociationOpeningEdgeSide is the only opening-edge representation in Domain, Features, App state and the persistence transport. Text conversion happens only at serialization, UI labels and cache keys.
  • WallAnalysis can call Placement planning and model-write contracts; Placement does not depend on WallAnalysis. App depends on both and owns the analysis lifecycle.

Orientation analysis and resolved members

Resolved member contracts

Preview (Elevation, Section and 3D) and placement read the same resolved data. ResolvedMemberContractResolver builds one ResolvedMemberContract per member: identity (role, type, opening key and edge), orientation (warm-state key, canonical and probe rotation, Flip, Y and Z justification), the world line and frame, and the normalized section geometry from the exact warmed state. Preview does not compute transforms, signs or depths of its own. Opening members are listed once as OpeningMemberSegmentContract values (OpeningMemberContractCatalog); preview meshes, hit testing and placement enumerate that list, so segment order and index are the same in every preview mode and in the placed members. The resolver also derives the secondary section axis from the role and wall frame, so girts, headers and sills face the same way in the preview as when placed, also on mirrored or rotated walls.

Warmed profile states

Profile warming (ProfileWarmStateProbe) places temporary instances and captures one exact state per key of quarter-turn rotation, Flip state, raw Y and Z justification and horizontal or vertical axis mode (MemberProfile.ExactStatesByKey). Each probe applies the parameters in a fixed order: cross-section rotation (plus the wall compensation below), then Flip Facing, then Y justification and Z justification, then zero offsets, then one regeneration. Placement applies a resolved orientation in the same order.

Rotated walls

WallRotationCompensationEvaluator takes the wall's along-axis azimuth, finds the nearest right angle and returns the negated residual as compensation. Vertical roles (jambs) are probed at each canonical quarter turn plus that compensation; horizontal roles (girts, headers, sills) are probed at the canonical quarter turns only. Rows keep the canonical quarter-turn values (0, 90, 180, 270). Placement adds the compensation to the cross-section rotation of vertical members only.

Opening frame direction

When the wall frame is swapped relative to the linked wall (IsFrameSwapped), live openings are mirrored along the wall: start and end become length − end and length − start. Preview and placement use the resulting along-wall distances; there is no separate branch for mirrored links.

Seating rules

Orientation analysis (FamilyOrientationAnalyzer) tries each Y and Z justification pair on a probe instance, regenerates once per pair and measures web and flange seating.

  • Web seating mode (WebSeatingMode): open sections (Channel, Zee, Angle) in horizontal roles use EdgeContact; HSS sections and jamb roles use FaceCoplanar. Zee and Angle types are not offered for opening roles.
  • Seating planes: a girt's web seats on the elevation plane. Head, sill and jamb web seating planes use the structural target origin, including layer and wall offsets, not the raw wall-frame origin.
  • Mirrored links: the flange must seat on the negative side of the depth axis for a mirrored link and on the positive side otherwise.
  • Square HSS: every non-end-cap face is a candidate web and flange face, and either seating side is accepted.
  • Rectangular HSS: calibration records deep and shallow face IDs (HssDeepFaceIds, HssShallowFaceIds). Horizontal roles seat a deep face on the exterior plane; jamb roles seat a deep face on the opening-edge plane. Without that metadata, the larger of the web and flange face sets counts as deep.
  • Angles: for girts, the short leg is the web face and the long leg is the flange face (AngleShortLegFaceId, AngleLongLegFaceId).
  • Faces are resolved again after each regeneration, because Revit geometry objects are not stable across regenerations. Non-finite distances or dot products reject a candidate pair.
  • Temporary probe transactions report Revit blocking failures as type warnings or failures in the analysis result (TemporaryTransactionRunner).

Persistence

Persistence/ISystemRepository.cs defines storage operations; Persistence/Revit/SystemRepository.cs implements them. StoredSystem contains PlacedSystem, PlanBaselineSnapshot settings, and ItemDecisionLedger.

  • PlanBaselineSnapshot stores user configuration. PlacedSystem stores the last successful wall and opening geometry and element identities. ItemDecisionLedger stores review decisions and provisional target and pairing overrides. Startup resolves the effective target and retains Placed geometry until Change Review accepts a live observation.
  • Domain/Plans/Projection/PlanBaselineMapper.cs captures settings and rebuilds the editable plan from settings and Placed without a Persistence dependency. SystemStorageMapper.Plan.cs maps and admits the serialized transport.
  • SystemStorageMapper.Data.cs defines the SystemData envelope with FormatVersion, PlacedData, LedgerData, and SettingsData. PlacedOpeningData contains OpeningRowData; opening roles use OpeningRoleData and recursive OpeningConfigData. Members use MemberConfigData, MemberSpanData, and MemberSpanEndpointData. Nullable transport collections and entries are validated before Domain construction.
  • SystemStorageMapper accepts format version 3. Required fields must be present, enum values must be defined, and unknown fields are rejected. Payloads are limited to 4,000,000 characters. InspectFormatVersion admits one integer formatVersion for version inspection; DeserializeSystem rejects other versions. Unsupported storage is purged inside the session group.
  • WallFramingMode is the placement-mode value in the live plan, baseline, hashing, and projections. The transport stores it in SettingsData.PlacementMode; FoundationModeEnabled is the UI checkbox.
  • Revit family, type, instance, wall, link, and opening identities use long, including framing-type selections, orientation/profile/calibration keys, and placement update records. Numeric JSON deserialization accepts values within the 32-bit range and above Int32.MaxValue. Counts, indexes, rotations, enum values, and manual-opening surrogate IDs use int. Geometry face IDs use int to match Revit's Face.Id.
  • Domain/Id/SystemId identifies the system throughout the live plan, edit analysis, Change Review, placement projection, and workflow. ContextualEditHook parses selected tag text once for an edit launch and retains invalid-ID diagnostics. Repository, wall-writer, and Revit tag/storage boundaries unwrap the GUID.

The Extensible Storage system schema is DBTools_SGT_SystemV2. The repository validates its field contract before reading or writing. Owned schemas with unsupported identities are purged inside the session group.

Cancellation and access failures propagate; malformed JSON is a named load failure. The UI coordinator reports load failures before applying defaults, preserving current UI values.

Plan admission and synchronization

  • PlanStore.Initialize prepares and validates a candidate before it replaces the live plan or advances its revision. A rejected initialization keeps the accepted plan and sends no event; a successful one publishes one initialized event after the lock is released.
  • Plan admission rejects duplicate member keys. Undo of a segment deletion relies on unique keys to match surviving group rows.

Every Plan and PlanBaselineSnapshot has a required WallTarget. Host wall, linked wall and link-instance IDs are 64-bit through persistence, Revit lookup, hashing, opening identity, placement and preview. Opening element IDs and compound-wall material IDs are also 64-bit; manual-opening surrogate IDs and layer indexes are int. Plan.Clone() detaches each mutable collection that UI projection uses: editable girt and opening rows, runtime member and opening definitions, baseline lists, type options, layer snapshots, orientation and profile maps, grid collections and the execution context. Shared leaf values are immutable.

PlanStore owns a detached accepted plan.

  • Initialization copies its input before it prepares or stamps it. Reads and notifications return detached snapshots.
  • Update is the write boundary. Rejected changes and mutator exceptions keep content and version; a no-op update publishes no event. An accepted update advances the version once and detaches the candidate before storage, so a retained reference cannot change accepted state.
  • Notifications run outside the write lock. Shared wall-layer collections are read-only.

Member segment replacement materializes and filters candidates before it replaces the segments. Empty or all-short input, and enumeration failure, keep the previous segments. Replacement from the member's own segment view is valid.

Plan-change admission uses one lock and one latest-pending slot:

  1. Enqueue clones the accepted plan and assigns a monotonic request revision.
  2. An arrival while a dispatcher callback is scheduled replaces the pending snapshot; the scheduled callback applies the latest revision.
  3. The apply turn clears the pending slot and marks itself applying before it projects.
  4. An arrival during apply fills the pending slot without recursion; completion schedules exactly one later Dispatcher.BeginInvoke turn.

The coordinator does not pump frames and does not drop an arrival. The request revision identifies the refresh; Plan.Version is plan data and diagnostic context. If applying one snapshot fails while a newer one is pending, the pending dispatch is still attempted. If both fail, the first failure is reported first, and the failed dispatch resets admission so a later change schedules normally.

PlanSynchronizationCoordinator.TryApplyPartialEdit owns every UI-originated partial plan write: the opening parent-row commit, the girt and opening segment flyouts, the PreviewEditingWorkflow entry points (snap, typed gap, segment delete, merge) and jamb segment add and delete.

  • Each such write, and SyncPlanFromUI (the UI-edit preview pass, Place and Update, Change Review), refreshes every pane from the written plan before it returns. It applies the refresh its own write queued (ApplyPendingPlanRefreshOnUI, in the same ApplyPlanRefresh batch as every other plan refresh), so no queued pass or later write projects stale rows over the edit, and a field typed after the write keeps its text.
  • Before it projects, the coordinator applies a refresh still queued by a plan written outside it (Undo or Redo of a preview-only edit, PlanStore.Initialize). It then projects the whole UI (TryProjectPlanFromUI) and writes the edit on top of that projection as one plan version, so unsaved valid drafts are written with it. Examples: a wall offset pushed on LostFocus whose Background sync has not run when a Send-priority opening commit arrives, or an edit made while a 3D scene builds.
  • While any field is invalid it writes nothing, records no Undo entry and shows the blocked-sync status (Fix invalid fields, Fix invalid rows or Preview blocked).
  • Only a write outside the coordinator still refreshes at Background priority; a field typed between that write and its refresh takes the refreshed value.
  • Each writer builds its change from a detached copy of the projection. A PreviewEditOutcome is a pair of plan changes that PreviewEditingWorkflow writes once through the coordinator and then records, so Undo and Redo replay only that change and the drafts written with it stay. A rejected opening segment edit aborts the write.
  • Deleting girt rows is a grid draft without a plan write and is never refused. GirtProjectionMapper.ApplyProjectedRowsToPlan normalizes every segment group in the projection with SegmentGroupRenumberer, so the next sync leaves no gap in the order, no parent key of a deleted row and no group of one row.
  • Accepted typed gap edits enter the same history; Undo and Redo restore the previous raw override, and each accepted typed edit clears the redo branch.
  • The 2D gap editor (PreviewView2DGapEditor) survives redraws: PreviewView2DState.ClearCanvas is the only canvas clear and keeps an open editor, its anchor is placed again under the current pan and zoom, and keys typed in it go to the editor.
  • Undo and Redo bypass admission: they replace the plan and so every pane's fields.
  • A refused type change (girt segment flyout, or an unavailable type in the girt grid) reports through GirtPaneViewModel.ShowRefusedTypeChange and sets no blocker. Only a girt row that keeps a rejected type, or an extent validation fault, sets the girt-pane blocker; the next girt row edit, row add or delete, bulk repair of that row or plan refresh clears it.

EndpointAssociationOpeningEdgeSide is the only opening-edge type across extents, member gaps, preview editing and persistence. Domain/Extents/OpeningEdge owns the closed OpeningEdgeExtent, DualOpeningEdgeExtent and OpeningEdgeEndpoint family: named wall, fixed-distance, grid and neighbor-opening variants keep the persisted extent fields. Strings are used only where a UI label or a serialized composite key requires text.

Preview girt segmentation carries MemberSpanEndpointKind from endpoint selection through ordinary and opening-edge gap resolution.

Girt segment boundaries

Domain/Girt/SegmentBoundary/GirtSegmentBoundarySet decides where a girt can start, end and split.

  • For a girt at elevation z, an opening blocks it when the opening spans z (inclusive, 1e-6 ft tolerance), is framed, is not bypassed by the row, is not the row's interior opening, and has a nonzero width after its span is clamped to the wall.
  • Start-capable boundaries: the wall start and the higher edge of each blocking opening. End-capable boundaries: the lower edge of each blocking opening and the wall end. The row's interior opening adds its lower edge as start-capable and its higher edge as end-capable.
  • GirtSegmentBoundarySet.Split is the only girt segment computation. It omits every span shorter than MemberRules.MinimumLength (0.5 ft). Its callers: plan-row segmentation (GirtSegmentationReconciler), preview (PreviewGirtSegmentBuilder), placement (MemberSegmentResolver.ResolveGirtSegments), the usable-span check (MemberResolutionExtentsProjection.HasUsableGirtSpan) and the snap offer (GirtExtentSnapPlanEditor.ResolveBoundaryEdges).
  • MemberSegmentResolver is an internal, girt-only resolver; WallHydrator resolves every member through it and rejects a non-girt member with MemberSegment/RoleUnsupported.

GirtSegmentBoundarySource supplies the wall length, openings, grid positions and the framing predicate. FromOpenings has the only production predicate, which frames every opening. FromPlan builds the source from plan rows (segmentation, the resolver, the snap editor); MemberResolutionExtentsProjection.GirtBoundaries builds it from runtime opening definitions (preview, placement, usable-span check). TryResolveT clamps an opening edge to the wall like the boundary set.

GirtSegmentationReconciler splits each segment group from its first sibling's start to its last sibling's end (clamped to the wall) and reuses row identities by overlap. The first and last child keep the group's outer anchors and endpoint gaps, also when Split omits an outer pier shorter than the minimum length; only ends between two children become opening-edge anchors. A group with one span becomes one row. A group with no span keeps its rows as authored, and placement reports them. An interior row leaves its segment group, and SegmentGroupRenumberer.RenumberSegmentGroup normalizes the remaining rows (a group of one row dissolves).

Girt endpoint anchors

Domain/Girt/EndpointAnchor/GirtEndpointAnchor is the stored anchor of one girt endpoint and the only reader of stored girt anchors. Its kinds:

Kind Stored as Meaning
Wall ExtentKind.FullLength Wall end
Grid ExtentKind.Grid Grid line
OpeningEdge ExtentKind.OpeningEdge, opening key + Left or Right Lower-T (Left) or higher-T (Right) edge of an opening

Girt endpoints never use ExtentKind.MemberEdge; that kind is only for opening-member (jamb, header, sill) segments.

Gaps:

  • An opening-edge endpoint stores a user gap only in OpeningEdgeGapOverridesFeet["<key>:<Left|Right>"]. Otherwise the gap is derived from the jamb at that edge and elevation (GirtGapResolver.GetDefaultOpeningEdgeGapFeet), and is 0 when there is no jamb. GirtGapResolver.GetOpeningEdgeGapFeet is that rule; preview, the gap editor and placement all call it.
  • StartGapOverrideFeet and EndGapOverrideFeet apply only to Wall and Grid anchors. Their rule is GirtGapResolver.GetEndpointGapFeet, called by preview (MemberGapResolver.GetEffectiveEndpointGapFeet), the gap editor and placement (GirtEndpointGapEvaluator.ComputeEndpointCutbackFeet): the override when set; otherwise, when the end lies within 1e-4 T of an edge that can bound it (a start on a higher edge, an end on a lower edge of a boundary opening in the girt's own boundary set), the gap derived from that edge's jamb; otherwise 0.
  • When the plan cannot resolve a gap handle (for example the edge of an opening deleted before the preview redraws), PreviewEditingWorkflow.TryGetMemberGapFeet shows a Gap edit failed banner and no gap editor opens.

Anchor writes:

  • GirtPlanRow.SetAnchor clears the endpoint gap when it writes an opening edge.
  • GirtPlanRow.ReplaceAnchor (snap edits, merges) also clears the gap entries of the old and new edges.
  • GirtPlanRow.Reanchor (the resolver) clears the endpoint gap and the lost edge's entry and keeps the entry of the edge it moves to.
  • GirtPlanRow.AbsorbPayload takes in a merged row's payload: bypass lists are united and gap entries are added; on a key conflict the receiving row's entry wins. The resolver merge (the survivor receives), the preview segment merge (the kept row receives) and the segmentation group proxy (the first sibling receives) use it.
  • Interior intent is derived, not stored: a row whose start is the lower edge and whose end is the higher edge of one opening that it does not bypass spans that opening (GirtEndpointAnchor.FindInteriorOpeningKey, exposed as GirtPlanRow.InteriorOpeningKey).

Re-anchoring

GirtEndpointAnchorResolver.Resolve is the only re-anchoring rule. MemberSegmentationReconciler.Recompute runs it after opening-role normalization and before opening and girt segmentation. Recompute runs on each UI-edit or plan-mutation preview refresh, after committed opening edits, and in PreparePlacementPlan before Place or Update preflight; a render-only preview draws the plan as stored.

  1. An endpoint is lost when its grid is gone (GridRemoved), its opening is gone (OpeningRemoved), or its opening edge is not capable for that end in the row's boundary set (OpeningNotBoundary; for example the opening no longer spans the girt, lies outside a shortened wall or is bypassed by the row).
  2. A lost end uses the row's other end as reference: a start moves to the nearest start-capable boundary at or before reference − minimum length, an end to the nearest end-capable boundary at or after reference + minimum length. The wall ends are the fallback. When both ends are lost, the start moves to the wall start and the end to the first end-capable boundary at or after the minimum length.
  3. The re-anchored end loses its endpoint gap and the gap entry of its lost edge; the edge it moves to keeps its entry. Bypass keys and gap entries of openings no longer in the plan are removed.
  4. Siblings of one segment group that now overlap merge into the earlier sibling. The survivor keeps its member key; each side keeps the outermost anchor that was not re-anchored (with its gap); bypass lists and gap entries are united with GirtPlanRow.AbsorbPayload; opening-member targets that named an absorbed row are rewritten to the survivor; and the group is normalized with SegmentGroupRenumberer.
  5. Segmentation then splits the plan again and reuses identities by overlap.

PlanSynchronizationCoordinator.NotifySegmentedStateRecompute reports MemberSegmentationSummary.ReanchoredGirtEndpoints ("Re-anchored N girt end(s) to the nearest opening or wall edge.") and MergedGirtRows ("Merged N overlapping girt segment(s) into their neighbors.").

Snap edits

GirtExtentSnapPlanEditor.Create accepts an opening edge for a girt's start or end only when IsBoundaryCapable finds it capable for that end in the boundary set of the edited row; otherwise it fails with GirtSnap/BoundaryInvalid. The snap removes that opening from the row's bypass list; a start on the lower edge of the opening whose higher edge is the end makes that opening interior. An edit that leaves no span of the minimum length fails with GirtSnap/NoUsableSpan. Create and ResolveBoundaryEdges apply the same test (IsBoundaryCapable, then HasUsableSpanAfterEdit over GirtSegmentBoundarySource.FromPlan), so ResolveBoundaryEdges offers exactly the edges Create accepts; an edit whose other end does not resolve fails with GirtSnap/NoUsableSpan. PreviewEditingWorkflow.ResolveGirtSnapEdges gives a handle on the row's own start or end that end's accepted set; any other segment handle is unrestricted. The snap index has no free-along target.

Positions and progress

Runtime resolution reports an opening-member split-label position more than 0.01 ft outside the wall through RuntimeHorizontalPositionResolution.OutOfRangeResult: a clamped T for rendering, OutOfRange = true and the reason SplitOutOfRange. Non-finite split text is invalid (MemberEdgeInvalid). A header or sill split label outside the wall fails placement with Extents/PositionResolutionFailed; preview can draw the clamped member. Grid positions are clamped to the wall. Stored girt endpoints accept only Wall, Grid or OpeningEdge; runtime AlongExtent still represents a resolved Wall-to-Grid span.

Wall-analysis progress uses (string message, double? progress01) throughout. Non-null values are normalized to [0,1]; null means indeterminate. Framing orientation analysis returns one FramingTypeOrientationAnalysisResult value and passes no orientation records through progress. Profile warm-state extraction uses the caller's logger.

Workflows

Window session

Lifecycle

App/Sessions/WindowSession/WindowSessionLifecycle.cs owns the lifecycle states, close intent, startup outcome and finalization result.

  • The modal driver is synchronous and always returns a completed task, because both Revit command callers block immediately.
  • A relink hides the window, runs the synchronous picker, then calls ShowDialog again in the same command frame. One owned ContextIdle callback resumes target analysis after the window is visible. The driver rejects a modal return before the pick or shown handshake completes, and never posts the modal re-entry.
  • WindowSessionOperationObserver observes the current initial-analysis or target-analysis task on the owning dispatcher. A completed task delivers inline; a pending task delivers through one owned dispatcher operation while the modal frame is active. Closing during analysis cancels the analysis and keeps the window and transaction group alive until the outcome arrives. Retirement revokes the callbacks and aborts the operation.
  • Forced retirement clears commit intent, releases payload resources and publishes cancellation. If the synchronous picker is still on the stack, cancellation and transaction rollback wait until it returns; no target analysis or banner runs afterward. An ordinary Closed cleanup is a separate state and keeps an accepted commit. Native window and dispatcher references are captured before registration retirement.
  • Transaction operations complete through the inline Revit call gate, before the command returns.

App/Sessions/WindowSession/Revit/SgtWindowSession.cs supplies Revit picking and startup, window resource effects and error-boundary integration. RunModalFlowAsync is the production entry point. Launch uses a closed WindowSessionLaunchRequest: New requires a concrete WallTarget; Edit requires a non-default SystemId. WindowSessionBuilder requires an inline Revit call gate and rolls back construction failures with ordered cleanup. The command consumes only completed lifecycle tasks.

Close and the transaction group

The session owns one transaction group, Super Girt Tool. SGT refuses a document that is already modifiable at launch.

  • Native X and Alt+F4 reuse the WPF close already in progress. An active analysis delays close until its outcome settles.
  • An accepted Closed releases the mandatory preview and window resources, then finalizes the group inline. A successful close intent with a healthy, successful session assimilates the group; Cancel, errors and forced retirement roll it back.
  • A programmatic close that throws, or returns without Closed, rolls back once and leaves a close-only retry for X, Alt+F4 and Cancel. The retry does not finalize again.
  • No transaction is committed outside the session group.
  • Model commit requires an explicit successful startup and model outcome and a healthy group. Failures of mandatory preview or window cleanup select rollback before assimilation. Synchronous transaction, cleanup and finalization failures propagate.

App/Sessions/WindowSession/WindowSessionUIStatePersistence.cs saves only cosmetic state: expanded panels, column widths and bulk-edit defaults. It is best-effort and never gates or delays the model commit.

  • Neither OK nor Cancel waits for the disk write. A successful commit with a pending save logs that preferences are saved in the background, without a banner. An already-failed save shows a warning through the Revit default-owner notifier after the close.
  • A finally block always attaches the disk-task observer, also when finalization throws. The observer logs a later disk failure and does not touch the retired window. Cancel releases the transaction and window first, then observes the save without changing the Cancelled outcome.
  • A failed cosmetic save does not change a completed model commit.

Error boundary

WindowInitializer attaches the Core error boundary of the window. WindowErrorBoundaryRegistry owns the dispatcher subscription and routes DB Tools failures to the most recently attached active window, or the most recently attached window when none is active. A DB Tools failure is thrown from, or passes through, an assembly named DBTools or starting with DBTools.; this includes DBTools.HandyControl and the Helix code merged into DBTools.Presentation, but not another add-in's HandyControl or Helix copy. WindowErrorBoundary classifies, presents and records the handled state.

SgtWindowSession subscribes to its own boundary; a missing host fails session construction. When Core handles a failure on the SGT window, the session records the original exception and any presentation failure, requests a rollback close while it keeps the modal frame, completes its cleanup, unsubscribes, and propagates the original failure, ahead of cleanup or modal-assertion failures, through the command's safe-execution boundary. SGT does not attach its own dispatcher exception handler; Core neither handles nor signals other add-ins' exceptions.

A ShowDialog failure before ContentRendered cannot have started analysis, so rollback, resource release and finalization run synchronously on the Revit UI thread, and only the cosmetic save can remain. Broken modal-continuation invariants are collected as finalization failures and do not skip rollback or cleanup. When the modal frame is already gone, the session records that invariant, does not await incomplete dispatcher work, downgrades finalization to rollback and continues every safe cleanup step. The safe-execution boundary owns user-facing reporting.

View model

The view model owns queued plan, preview and render dispatcher operations.

  • Disposal stops both refresh coordinators, drops the pending plan snapshot and aborts queued callbacks before it cancels analysis. Late preview results cannot publish to a retired view.
  • Girt and opening projection publishes validation flags, but those notifications do not queue another UI edit; segment group display refresh is suppressed the same way. Invalid rows and refreshed group labels therefore cannot start a preview loop.
  • Each analysis run owns its cancellation source until its finally completes. A newer run or disposal cancels the active run without disposing its source early. An idle source is canceled and disposed immediately when replaced. Canceled or superseded results cannot publish a plan or change preview mode after an await. A disposed view model creates no new idle source.

Change Review

Features/ChangeReview owns the detached review candidate, row decisions, target precedence, the decision ledger, relink pairing and the dialog. The dialog is an embedded raw XAML view with no x:Class or code-behind. Accept, Keep and Ignore are the only decision terms in the UI and the code. Opening labels use the source name and the along-wall range; the opening key is internal.

ChangeReviewWorkflow synchronizes the accepted plan before it captures its revision, reads one live snapshot and analyzes a confirmed candidate before it publishes it. Confirm writes only the detached plan and ledger state. A later Place or Update command writes the model and sets Placed from the write result, so several model commands can follow one review while the session group stays open.

The lifecycle owns the review child and any relink picker. It retires the child in finally, closes the child before it hides the parent for a pick and resumes the same modal driver after the picker returns. Cancel, native close, command failure and forced retirement roll back the session group; only a successful close assimilates it, as one Undo entry named Super Girt Tool.

  • ChangeReviewPlanBuilder decides: it resolves each item's decision once and derives both the candidate plan and the ledger that Confirm saves; rows show the resolved decision. AllowedDecisions is the matrix of allowed decisions and ProposeDecision the default rule. The dialog offers the matrix's decisions (SetInvalidated removes Ignore for a released user-created opening unless Ignore is already selected) and preselects an allowed proposal. The builder applies a proposal to an undecided item that needs no attention only when the matrix allows it.

  • Without a live observation a row offers only Keep and Ignore.
  • The live snapshot carries the grid crossings along the Placed wall and the observed wall; girt grid anchors resolve against the grids of the wall the review adopts.
  • Rows show the opening source name (or Manual opening for an unnamed manual row), source, status and decision; effects appear in the details pane of the selected row. Placement validation messages include the along-wall range where it matters. The canonical key is never shown.

Openings, Orientation, WallAnalysis and BulkEdit

Opening keys are canonical GUID-N strings and stay the same when the source changes. OpeningLiveReference and WallTargetReference carry owning-document UniqueIds and, where needed, the UniqueId of the host link instance. OpeningRuntimeIdIndex assigns ordinal IDs 1..n per projection; it never derives them from key bits or element IDs.

Opening rows store along-wall start and end distances in feet. OpeningGeometryResolver derives the normalized frame from those distances and the current wall length, so a manual opening does not stretch with the wall. A local geometry edit converts a Live opening to Manual and keeps its live reference and source name. Held and Unframed rows are read-only and show (awaiting review) or (not framed). Only Unframed removes an opening from girt boundaries and opening members; an opening with all roles off still splits girts. OpeningRoleRules.ApplySeedDefaultsForEnabledRoles is the shared seeding rule: a geometry change removes roles that no longer apply, seeds roles that now apply and keeps applicable overrides and user-disabled roles.

GeometryFingerprint.Compare owns the wall and opening change tolerances (0.01 ft and 1 inch), including type, layer material and function, frame, reflection and framing-mode changes. Live geometry takes material names from the owning document; WallGeometryContext stores no wall identity.

  • Openings owns Revit opening queries, editable-row mutation, synchronization and projection, and the opening pane view models. Opening identities, ranges, contracts and feet geometry are in Domain/Openings, beside EditableOpeningRow.
  • Opening bounds accept only complete, finite source candidates. Complete cut-face bounds replace every fallback. Otherwise solid bounds seed the result, the width replaces the solid's horizontal bounds before the profile union, and the vertical order of precedence is profile, parameters, solid. Missing geometry, solids, cut generators or profile loops fall through to the next source; traversal, symbol-geometry, triangulation, transform and non-finite-vertex faults keep their original exception and stack. If any supported insert exhausts every source, the query returns one typed OpeningQuery/Incomplete failure and no partial list. Wall-context failures stay typed, and opening-row recovery matches the code UI/PlanMissing, not message text.
  • Orientation: Orientation/Revit/Analysis owns the family-orientation analyzer and solver inputs; Orientation/Analysis has the portable rotation math and solver results; shared orientation values are in Domain/Orientation.
  • WallAnalysis owns the plan-builder contract and Revit geometry extraction, calibration, profile warming, seeding and plan construction under WallAnalysis/{Domain,Revit/{Geometry,Planning}}. WallContextResolver accepts only a closed WallTarget and produces a ResolvedWallContext, the only host or link input to WallGeometryBuilder.
    • Calibration checks cancellation before argument validation and cache access. Argument defects throw; typed SpecFailureException failures become calibration results; only successes are cached.
    • Family calibration runs per family: it logs a failed family and continues, and each type of that family then carries the typed failure, with family and type names, as a per-role orientation failure. The orientation analyzer throws SpecFailureException for expected family incompatibilities, and WallAnalysisFramingTypeAnalyzer converts them per role.
    • Host and linked frame construction share one typed frame-failure boundary in WallGeometryBuilder. Cancellation, rollback failures and invariant defects propagate.
    • When every profile fails, ProfileLoopsAllFailed keeps up to five type IDs and their causes in numeric order and reports how many it omitted. Per-type logs and partial-success warnings stay available.
  • New and edit analysis both pass PlanAdmissionValidator before they return success. Edit analysis keeps the stored configuration and analyzes the current geometry of the selected wall.
  • PlanSeedingStep is the only initial seeding owner. App reports the projected girt and opening counts without adding rows or writing UI values into the plan. A non-foundation plan keeps the no-openings notice.
  • BulkEdit owns the bulk-edit flyout, centered on BulkEditFlyoutViewModel. A failed apply tries to restore every captured girt and opening-role snapshot in request order, then propagates the apply failure followed by every restoration failure.

Placement owns GirtTypeItem, GirtTypeCatalog and GirtPaneViewModel.GirtTypeDisplay for the girt grid. Opening, bulk and preview selectors use immutable FramingTypeOption values. The shared combo-box item style, also used by the girt grid, binds IsSelectable and shows ProfileWarningText; selection setters refuse unavailable types. Placement preflight checks opening member profiles before placement.

SmartDefaultsResolver, SmartDefaultsInput, TypeDrivenDefaultsInput and FamilyResolutionInput are pure contracts. Girt and opening rows apply resolved values through their own methods; Domain never references feature view models.

  • Features/BulkEdit owns the bulk-edit flyout, centered on BulkEditFlyoutViewModel. Bulk apply changes girt and opening rows with both reactive-sync suppressions active. After a successful commit, the girt owner refreshes the Flip capability and option lists of the selected rows while still suppressed, and clears an earlier type-change blocker only when its own row now has a valid orientation. Opening-only edits and failed applies keep that blocker. One UI-edit preview refresh then writes the committed rows to the plan. A failed apply restores its row snapshots and reports one bulk error without projecting the transient edits.

Limitations

Domain storage accepts only format version 3 and does not migrate other formats. Girt endpoint anchors accept only wall, grid, and opening-edge anchors; MemberEdge is reserved for opening-member segments. Zee and Angle types are unavailable for opening roles.

The Revit API does not expose the Undo stack. Check the single Super Girt Tool Undo entry in Revit after a successful close.
