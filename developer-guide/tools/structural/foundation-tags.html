Combined Foundation Tags

Overview

Combined Foundation Tags updates pier/footing association parameters and moves combined tags to footing corners. Source: src/Tools/Structural/FoundationTags/. The assembly and tool ID are DBTools.FoundationTags.

Architecture

Ownership

App/Composition/FoundationTagsToolModule binds settings, registers the pack, and delegates feature registration to ServiceCollectionExtensions.AddFoundationTagsFeatures. Features/UpdateCombinedFoundationTagsWorkflow and Features/Move/MoveCombinedFoundationTagsWorkflow own manual execution and completion reporting. Queued result-selection gates receive the workflow logger.

Pure geometry types are Point2D, FoundationTagsPoint, FootingCornerPoints, and NearestPointResult. FoundationTagsGeometry owns SelectCornerByViewOrientation, FindNearestPoint2D, and IsValidCornerName.

Data and contracts

Settings

Configuration section: Tools.FoundationTags. Pack: structural.foundation_tags, titled Combined Foundation Tags. AutoUpdateEnabled defaults to true. Pattern lists default empty and resolve to:

Property Default pattern
TagFamilyPatterns ^DB Pier and Foundation Combined Tag(?: No Elevations)?$
PierFamilyPatterns ^Foundation Pier(?: - Round)?$
FootingFamilyPatterns ^(?:Footing\|Pile Cap)-Rectangular$

The UI allows three patterns per group through Core RegexPatternListContext. It validates syntax and tracks pending changes. FamilyNameClassifier compiles the configured patterns for both workflows.

Workflows

Update

Features/CombinedFoundationTagsUpdater collects visible FamilyInstance elements from the active view. Configured family patterns classify piers and footings. Updates affect host-document instances.

  1. Compute each pier's top as Top Level elevation plus Top Offset.
  2. Write Foundation Pier Top by GUID.
  3. Find the nearest pier to each footing using XY location points, within two feet inclusive.
  4. Write that pier's type mark to Associated Pier and its top to Associated Pier Elevation.
  5. Publish current-run result IDs and timestamped selection sets.

The updater creates one Core GroupPlacementQuery.CreateRunQuery(document) per run. It caches group membership, ancestor placement checks and each group type's instance count. UpdateParameterWriter compares the current and target values before checking group restrictions. For repeated groups, it skips only changed parameters whose InternalDefinition.VariesAcrossGroups is false. Equal values succeed without writing. Varying parameters still write, so a footing can be Modified and Failed in one run. This includes nested members when any enclosing group type has multiple placed instances. A single placement remains writable. Group failures enter Failed once per element and share the ten-line detailed log limit. The final diagnostic reports the total failed/skipped count.

When a pier-top write is skipped for a repeated group, its computed top remains available to footings. If computation fails, both grouped and ungrouped piers supply the stored top instead. Length parameters cannot vary between group instances, and the Revit API cannot enter group edit mode. Text parameters such as Associated Pier can vary when the project definition permits it.

A missing or invalid Top Level records a pier failure. Missing Top Offset uses zero. Piers without LocationPoint cannot participate in nearest-point matching. Equal-distance ties retain the first candidate.

Without a pier, the updater clears the association text to an empty string. It keeps a stored elevation and reports failure because these length parameters cannot be cleared. Parameter.ClearValue requires HideWhenNoValue, which the shipped definitions do not set. An elevation without a stored value needs no clearing. Double writes compare values rounded to two decimal places in internal feet. String comparison is ordinal.

UpdateParameterWriter returns failures for missing, read-only, wrong-storage, or rejected parameter writes. The updater records these failures and continues. A footing can appear in both Modified and Failed sets when one parameter changes and another fails. Unexpected exceptions escape the parameter transaction and roll back the run.

Parameter writes and selection-set publication use separate transactions inside one transaction group. The group assimilates to one Undo entry. A selection-set failure preserves committed parameter writes, then propagates after assimilation. Other failures attempt group rollback and preserve concurrent cleanup faults.

UpdateRunState counts distinct element IDs and records grouped skips as a subset of Failed. UpdateRunResult contains UpdatedCount, FailedCount, GroupSkippedCount, and read-only snapshots of Modified and Failed IDs. UpdateRunMessage appends the grouped skip count and the group edit reason to the existing banner counts. Automatic runs use the same updater without a result banner. Grouped skips return successfully and do not suppress later activations. The manual workflow offers Select Modified and Select Skipped when updates exist. Those banner actions check that the source document is still active before selecting IDs. With no updates, it shows an Info or Warning toast without selection actions.

If neither Modified nor Failed contains an ID, selection-set publication returns without creating or pruning sets.

Selection sets use DB Tools - FoundationTags - Modified Elements (...) and DB Tools - FoundationTags - Skipped Elements (...) names with Eastern-time timestamps. Repeated names receive suffixes starting at (2). Pruning retains five sets across both kinds, ordered by descending element ID.

Move

Features/Move/MoveCombinedFoundationTagsRunner collects visible IndependentTag instances, resolves a tagged host or linked structural foundation, and filters tag family/type names by the configured patterns. Only the host tag moves. Linked footing geometry transforms into host coordinates.

The desired name is the trimmed tag name, or its type name when the tag name is blank. Supported values are case-insensitive Top Right, Top Left, Bottom Right, and Bottom Left.

The runner tessellates fine-detail footing geometry, including nonvisible objects, in the instance's local frame. Local XY extents define four rectangular corners. FoundationTagsGeometry.SelectCornerByViewOrientation labels them against the view's RightDirection and UpDirection. The edge most aligned with view-right becomes horizontal. A tie uses the second declared edge. The tag retains its current Z.

Unsupported names, missing point locations, and geometry without usable corners are skips. All candidate moves share DB Tools - Move Combined Foundation Tags. Unexpected transform, geometry, tessellation, or tag-write errors log the tag ID and propagate, rolling back every move. MoveRunResult separates moved, skipped, candidate, total-view-tag, structural-foundation, and pattern-rejection counts, with rejected-name samples for diagnostics.

Background checks (the monitor, its retry and the automatic update) only record invalid prerequisites: they activate core.structural.combined_tags, which disables the commands, and show no banner. A family document has no project parameters, so it refuses one with SafeExecutionRefusedException and leaves the warning unchanged. It returns true when every row is OK. Otherwise it activates the warning and shows one Warning alert, Required shared parameters need repair, that names the command and lists each failing parameter with its status and description, with the buttons Cancel and Repair. Repair runs EnsureInstalledAndValid with PrerequisiteRepairPrompt, owned by the command's window owner. Cancel, in the alert or in the schedule prompt, changes nothing and throws OperationCanceledException: safe execution logs one Warning, [Cancel] <command> canceled after <n>ms, shows no banner, and Revit sees Result.Cancelled. A successful repair clears the warning and shows a Success banner, Install/Repair succeeded. Run <command> again. with the repair Summary; EnsureReady then returns false, so the command returns normally without its workflow and Revit keeps the repair (Result.Succeeded). A failure of the success banner is logged and does not fail the command. A refused repair (InvalidOperationException) logs a Warning and becomes SafeExecutionRefusedException, so safe execution shows its Warning banner. The commands are the only callers of the workflows, so the workflows do not check the parameters again. Unexpected validation faults remain errors and do not assert invalid prerequisites.

PrerequisiteSharedParameterInstaller reads every binding through Core's SharedParameterBindingLookup. When Revit's binding map holds a dead key (see shared parameter migration), the status rows, PlanRepair and EnsureInstalledAndValid throw SafeExecutionRefusedException with Revit's parameter bindings for this model are in an invalid state; save, close and reopen the model, then try again. and change nothing. Settings shows it under Status not available in place of the list, and as the status message and banner of a failed Install/Repair. Settings → Combined Foundation Tags shows the status of the active document and offers Install/Repair; the warning card's Fix action (FixLabel Install/Repair) runs the same repair. A successful repair clears the warning and re-enables the commands. Construction of the settings context is passive and leaves the list unchecked. FoundationTagsSettingsPackView binds its ShownCommand to LoadRequiredParametersCommand and runs it from its Loaded event, so the pack reads the active document each time it is shown. The view compiles into DBTools.Presentation, so it binds the command by name and does not reference the context type. The Settings window is modal, so the active document cannot change while it is open; each opening creates a new context. SettingsRuntime receives the settings host's UIApplication explicitly and classifies the active document (ActiveDocumentKind: None, Family or Project). Without a project the list stays empty, HasRequiredParameters is false, and the view shows the theme's empty state with RequiredParametersEmptyTitle and RequiredParametersEmptyDetail (No project open, A family is active, or Status not available with the failure message). CanInstallOrRepair is true only after the status of a project loaded, and gates Install/Repair; FixWarningAsync throws {action} requires an active Revit document. or {action} requires a project. The active document is a family. LoadRequiredParameters replaces immutable RequiredParameters status rows. RequiredParametersList shows one item per parameter: the name with a status chip at the right (green for OK, amber otherwise); a muted line with the data type, category and group (Length · Structural Foundations · Identity Data); for a status other than OK, the Description; and the schedule use. Data type, category and group are the required values by the names Revit shows (PrerequisiteParameterLabels): LabelUtils.GetLabelForSpec, the project's Category.Name or else LabelUtils.GetLabelFor, and LabelUtils.GetLabelForGroup. Every line wraps, so each value reads in full at any window width without horizontal scrolling or a tooltip. Install/Repair uses embedded definitions in group DBTools.Structural.FoundationTags. Their columns and values match the company file: VISIBLE 1, an empty DESCRIPTION, USERMODIFIABLE 1 and HIDEWHENNOVALUE 1. Only the group name differs; a project does not store it. It creates a temporary shared-parameter file, restores Revit's original shared-parameter path, and attempts temporary-file deletion. The embedded definitions supply the required parameters.

EnsureInstalledAndValid(IPrerequisiteRepairConfirmation) runs a read-only preflight. PlanRepair returns the project plan without family details. It uses Core's CheckMigrate, CheckRebind and CheckBind to find value refusals. It also lists each schedule field and every rule from a view filter that Revit removes with a replaced parameter or an empty duplicate. FindScheduleFields scans main and embedded schedules. FindFilterRules lists all rules from affected filters, but it does not show their AND/OR logic or inverted rules. The confirmation tells the user to record that logic before Continue. A rebind keeps schedule fields and view filter rules.

The method also plans loaded families through Core's family migration (SharedParameterFamilyMigration.Plan). It creates one SharedParameterFamilyTarget per required parameter, with the embedded definition and the required category plus every category that a matching parameter already binds. A known refusal, such as a WRONG_DATA_TYPE, a Length value on a member of a group placed more than once, or a family use that Core cannot change, stops before any change.

The preflight cannot predict target-only project values that family migration creates. A later project migration can refuse after Continue when it finds a value that it cannot keep. That migration runs inside the repair transaction group, which rolls the family and project changes back.

When the project plan lists schedule fields or view filter rules, the confirmation decides before any deletion. A declined repair returns a result with Canceled set and changes nothing. After Continue the repair plans again, including families, before it opens the transaction group. A refusal of either new plan stops it. If the refusals, schedule fields or filter rules differ (PrerequisiteRepairPlan.IsSameAs), it changes nothing and asks again with the new plan. A family loaded while the question was open is therefore changed or refused like any other. Repair cannot keep or recreate the listed schedule fields or view filter rules. The user adds the company parameter and restores every listed rule by hand. The repair runs in one transaction group and assimilates it only after every prerequisite is OK. A failure or refusal at any step rolls the group back and leaves the project unchanged, so the warning stays active. It first changes the loaded families (SharedParameterFamilyMigration.Migrate): each family parameter with a required name and another GUID becomes the company parameter, with its group, kind, formula, references and values, and the family is reloaded. Only then does it delete a parameter with another GUID: Revit removes a deleted shared parameter from the labels of the loaded families that use it, which is how labels lost their parameter before this order. A parameter with the required name and another GUID is a GUID_MISMATCH that moves its values to the company parameter, and an element whose two values differ refuses. An unbound company parameter can already exist because a loaded family defines its GUID. Preflight checks its first binding with CheckBind; the repair binds it after migrations and rebinds. Only a missing company parameter is created by the final install step. The repair then replaces each GUID_MISMATCH parameter through Core's shared parameter migration. A replacement keeps the old categories (a type binding becomes an instance binding of the same categories), the parameter group, the variance between group instances, and every value: element values on the same elements, and type values copied to every instance of the type. The company definition replaces the old visibility, description, user-modifiable and hide-when-no-value settings; each difference is reported. Next it rebinds an installed required parameter that is bound as a type parameter or lacks the required category (WRONG_BINDING_TYPE, WRONG_CATEGORY) through SharedParameterMigration.Rebind, which keeps its GUID, categories, group, the variance between group instances and every value, and copies each type value to every instance of that type. It then binds an existing unbound company parameter through SharedParameterMigration.Bind. The final install step creates and binds definitions that do not exist yet. A family type parameter with no placed instance stays on its type because an instance binding does not change it. The family plan refuses, naming the family: a label or nested family that uses a required name with another GUID directly (in Revit 2027 one line per label with its detail group, position and formatting), a type parameter in a family of a category that the parameter binds as an instance parameter, a nested shared family, an in-place or non-editable family that defines the name or may define it, another data type, and an element whose family value and project value differ. A global parameter with a required name is not a project parameter; repair ignores it. Automatic updates and monitoring

CombinedFoundationTagsAutoUpdateTask runs Update in FloorPlan and CeilingPlan views when enabled and no warning blocks it. Invalid prerequisites set the warning without a banner. NotApplicable and TransientNotReady evaluations skip execution. An unexpected runtime fault sets no prerequisite warning. Core's ViewActivationHook suppresses the failed task for that document session.

PrerequisiteMonitorTask checks prerequisite state, sets or clears the warning without a banner, logs an invalid state at Information, and schedules an Idling retry for transient initialization states. PrerequisiteRetryCoordinator retains each original event source and detach callback. Evaluation faults log and can be checked again on the next view activation. The monitor disposes its own retry coordinator at synchronous App shutdown. An injected coordinator remains caller-owned. Disposed lifetimes reject scheduling. Failed-detach entries retain cleanup state without retry work. A late Idling event can retry detachment.

Limitations

Association updates use host-document pier and footing instances. Move supports host tags referencing host or linked foundations and only the four listed corner names. Length values cannot be cleared with the shipped shared-parameter definitions.

Install/Repair does not change a label that uses a required name with another GUID directly: Revit 2026 has no label API, and the Revit 2027 reference assembly exposes only reads. It refuses and names the family instead. It cannot open an in-place or non-editable family; it refuses one that defines the parameter, and one for which a rolled-back rebind of the project parameter cannot tell. Family files on disk keep the other GUID.
