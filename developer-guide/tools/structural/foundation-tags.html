Combined Foundation Tags

Overview

Combined Foundation Tags updates pier/footing association parameters and moves combined tags to footing corners. Source: src/Tools/Structural/FoundationTags/. The assembly and tool ID are DBTools.FoundationTags.

Architecture

Ownership

App/Composition/FoundationTagsToolModule binds settings, registers the pack, and delegates feature registration to ServiceCollectionExtensions.AddFoundationTagsFeatures. Features/UpdateCombinedFoundationTagsWorkflow and Features/Move/MoveCombinedFoundationTagsWorkflow own manual execution and completion reporting. Queued result-selection gates receive the workflow logger.

Pure geometry types are Point2D, FoundationTagsPoint, FootingCornerPoints, and NearestPointResult. FoundationTagsGeometry owns SelectCornerByViewOrientation, FindNearestPoint2D, and IsValidCornerName.

Data and contracts

Settings

Configuration section: Tools.FoundationTags. Pack: structural.foundation_tags, titled Combined Foundation Tags. AutoUpdateEnabled defaults to true. Pattern lists default empty and resolve to:

Property Default pattern
TagFamilyPatterns ^DB Pier and Foundation Combined Tag(?: No Elevations)?$
PierFamilyPatterns ^Foundation Pier(?: - Round)?$
FootingFamilyPatterns ^(?:Footing\|Pile Cap)-Rectangular$

The UI allows three patterns per group through Core RegexPatternListContext. It validates syntax and tracks pending changes. FamilyNameClassifier compiles the configured patterns for both workflows.

Workflows

Update

Features/CombinedFoundationTagsUpdater collects visible FamilyInstance elements from the active view. Configured family patterns classify piers and footings. Updates affect host-document instances.

  1. Compute each pier's top as Top Level elevation plus Top Offset.
  2. Write Foundation Pier Top by GUID.
  3. Find the nearest pier to each footing using XY location points, within two feet inclusive.
  4. Write that pier's type mark to Associated Pier and its top to Associated Pier Elevation.
  5. Publish current-run result IDs and timestamped selection sets.

The updater creates one Core GroupPlacementQuery.CreateRunQuery(document) per run. It caches group membership, ancestor placement checks and each group type's instance count. UpdateParameterWriter compares the current and target values before checking group restrictions. For repeated groups, it skips only changed parameters whose InternalDefinition.VariesAcrossGroups is false. Equal values succeed without writing. Varying parameters still write, so a footing can be Modified and Failed in one run. This includes nested members when any enclosing group type has multiple placed instances. A single placement remains writable. Group failures enter Failed once per element and share the ten-line detailed log limit. The final diagnostic reports the total failed/skipped count.

When a pier-top write is skipped for a repeated group, its computed top remains available to footings. If computation fails, both grouped and ungrouped piers supply the stored top instead. Length parameters cannot vary between group instances, and the Revit API cannot enter group edit mode. Text parameters such as Associated Pier can vary when the project definition permits it.

A missing or invalid Top Level records a pier failure. Missing Top Offset uses zero. Piers without LocationPoint cannot participate in nearest-point matching. Equal-distance ties retain the first candidate.

Without a pier, the updater clears the association text to an empty string. It keeps a stored elevation and reports failure because these length parameters cannot be cleared. Parameter.ClearValue requires HideWhenNoValue, which the shipped definitions do not set. An elevation without a stored value needs no clearing. Double writes compare values rounded to two decimal places in internal feet. String comparison is ordinal.

UpdateParameterWriter returns failures for missing, read-only, wrong-storage, or rejected parameter writes. The updater records these failures and continues. A footing can appear in both Modified and Failed sets when one parameter changes and another fails. Unexpected exceptions escape the parameter transaction and roll back the run.

Parameter writes and selection-set publication use separate transactions inside one transaction group. The group assimilates to one Undo entry. A selection-set failure preserves committed parameter writes, then propagates after assimilation. Other failures attempt group rollback and preserve concurrent cleanup faults.

UpdateRunState counts distinct element IDs and records grouped skips as a subset of Failed. UpdateRunResult contains UpdatedCount, FailedCount, GroupSkippedCount, and read-only snapshots of Modified and Failed IDs. UpdateRunMessage appends the grouped skip count and the group edit reason to the existing banner counts. Automatic runs use the same updater without a result banner. Grouped skips return successfully and do not suppress later activations. The manual workflow offers Select Modified and Select Skipped when updates exist. Those banner actions check that the source document is still active before selecting IDs. With no updates, it shows an Info or Warning toast without selection actions.

If neither Modified nor Failed contains an ID, selection-set publication returns without creating or pruning sets.

Selection sets use DB Tools - FoundationTags - Modified Elements (...) and DB Tools - FoundationTags - Skipped Elements (...) names with Eastern-time timestamps. Repeated names receive suffixes starting at (2). Pruning retains five sets across both kinds, ordered by descending element ID.

Move

Features/Move/MoveCombinedFoundationTagsRunner collects visible IndependentTag instances, resolves a tagged host or linked structural foundation, and filters tag family/type names by the configured patterns. Only the host tag moves. Linked footing geometry transforms into host coordinates.

The desired name is the trimmed tag name, or its type name when the tag name is blank. Supported values are case-insensitive Top Right, Top Left, Bottom Right, and Bottom Left.

The runner tessellates fine-detail footing geometry, including nonvisible objects, in the instance's local frame. Local XY extents define four rectangular corners. FoundationTagsGeometry.SelectCornerByViewOrientation labels them against the view's RightDirection and UpDirection. The edge most aligned with view-right becomes horizontal. A tie uses the second declared edge. The tag retains its current Z.

Unsupported names, missing point locations, and geometry without usable corners are skips. All candidate moves share DB Tools - Move Combined Foundation Tags. Unexpected transform, geometry, tessellation, or tag-write errors log the tag ID and propagate, rolling back every move. MoveRunResult separates moved, skipped, candidate, total-view-tag, structural-foundation, and pattern-rejection counts, with rejected-name samples for diagnostics.

Prerequisites and repair

Manual commands and automatic updates validate shared parameters without modifying them. The required definitions are owned by Features/Prerequisite/PrerequisiteRequiredParameters:

Parameter GUID Type Instance category Initial group

Associated Pier Elevation 56651179-1f6f-4f3b-b269-adb0532dc124 Length Structural Foundation Identity Data

The GUIDs match the company's DB shared parameter file (group DB Structural), so projects that use that file already satisfy the prerequisites. A project with a parameter that has a required name and another GUID, such as one set up with the DB Tools GUIDs used before November 2026, reports GUID_MISMATCH. The data type check uses ForgeTypeId.NameEquals, which ignores the schema version, so a parameter created in an earlier Revit (autodesk.spec.aec:length-2.0.0) matches SpecTypeId.Length of a later one.

Background checks (the monitor, its retry and the automatic update) only record invalid prerequisites: they activate core.structural.combined_tags, which disables the commands, and show no banner. The commands report the problem when the user runs them. UpdateCombinedFoundationTagsCommand and MoveCombinedFoundationTagsCommand call Features/Prerequisite/PrerequisiteRepairOffer.EnsureReady before their workflow. A family document has no project parameters, so it refuses one with SafeExecutionRefusedException and leaves the warning unchanged. It returns true when every row is OK. Otherwise it activates the warning and shows one Warning alert, Required shared parameters need repair, that names the command and lists each failing parameter with its status and description, with the buttons Cancel and Repair. Cancel changes nothing. Repair runs EnsureInstalledAndValid with PrerequisiteRepairPrompt, owned by the command's window owner. A successful repair clears the warning and shows a Success banner, Install/Repair succeeded. Run <command> again. with the repair Summary; a canceled schedule prompt changes nothing and shows nothing more. A refused repair (InvalidOperationException) logs a Warning and becomes SafeExecutionRefusedException, so safe execution shows its Warning banner. Otherwise EnsureReady returns false; in both cases the command does not run its workflow. The command returns normally after a repair, so Revit keeps the repair; a failure of the success banner is logged and does not fail the command. The workflows keep PrerequisiteGuard, which refuses with SafeExecutionRefusedException and activates the warning when a caller runs them without the offer. Unexpected validation faults remain errors and do not assert invalid prerequisites.

Settings → Combined Foundation Tags shows the status of the active document and offers Install/Repair; the warning card's Fix action (FixLabel Install/Repair) runs the same repair. A successful repair clears the warning and re-enables the commands. Construction of the settings context is passive and leaves the list unchecked. FoundationTagsSettingsPackView binds its ShownCommand to LoadRequiredParametersCommand and runs it from its Loaded event, so the pack reads the active document each time it is shown. The view compiles into DBTools.Presentation, so it binds the command by name and does not reference the context type. The Settings window is modal, so the active document cannot change while it is open; each opening creates a new context. SettingsRuntime receives the settings host's UIApplication explicitly and classifies the active document (ActiveDocumentKind: None, Family or Project). Without a project the list stays empty, HasRequiredParameters is false, and the view shows the theme's empty state with RequiredParametersEmptyTitle and RequiredParametersEmptyDetail (No project open, A family is active, or Status not available with the failure message). CanInstallOrRepair is true only after the status of a project loaded, and gates Install/Repair; FixWarningAsync throws {action} requires an active Revit document. or {action} requires a project. The active document is a family. LoadRequiredParameters replaces immutable RequiredParameters status rows. RequiredParametersList shows one item per parameter: the name with a status chip at the right (green for OK, amber otherwise); a muted line with the data type, category and group (Length · Structural Foundations · Identity Data); for a status other than OK, the Description; and the schedule use. Data type, category and group are the required values by the names Revit shows (PrerequisiteParameterLabels): LabelUtils.GetLabelForSpec, the project's Category.Name or else LabelUtils.GetLabelFor, and LabelUtils.GetLabelForGroup. A value that Revit cannot name reads Unknown data type (<id>), Unknown category (<value>) or Unknown group (<id>), never the bare identifier. Every line wraps, so each value reads in full at any window width without horizontal scrolling or a tooltip. The list is a ListBox whose template has no scroll viewer, because the Settings page scrolls; it keeps keyboard focus, and each item exposes AutomationProperties.Name (the parameter), ItemStatus (the status) and HelpText (the description). Nothing uses its selection. The item bindings use OneTime. HasWarning belongs to the session context and is not persisted in FoundationTagsSettings.

Install/Repair uses embedded definitions in group DBTools.Structural.FoundationTags. Their columns and values match the company file: VISIBLE 1, an empty DESCRIPTION, USERMODIFIABLE 1 and HIDEWHENNOVALUE 1. Only the group name differs; a project does not store it. It creates a temporary shared-parameter file, restores Revit's original shared-parameter path, and attempts temporary-file deletion. The embedded definitions supply the required parameters.

EnsureInstalledAndValid(IPrerequisiteRepairConfirmation) first works out its whole plan without a change (PlanRepair returns the same PrerequisiteRepairPlan): every refusal, through Core's CheckMigrate and CheckRebind, and every schedule field that Revit removes because the repair deletes a parameter that the field uses, a replaced parameter or an empty duplicate (SharedParameterMigration.FindScheduleFields: main and embedded definitions, and combined parameter fields that include it). A rebind keeps its fields, so it adds none. A refusal throws before any change, including a parameter with the company GUID and another spec (WRONG_DATA_TYPE) and a Length value on a member of a group placed more than once, so no prompt describes a repair that would refuse. When the plan lists schedule fields, the confirmation decides before any change; a declined repair returns a result with Canceled set and changes nothing. After Continue the repair plans again before it opens the transaction group; if the refusals or the schedule fields differ (PrerequisiteRepairPlan.IsSameAs), it changes nothing and asks again with the new plan. Repair cannot keep or add the fields again; the user adds the company parameter to those schedules by hand. The repair runs in one transaction group and assimilates it only after every prerequisite is OK. A failure or refusal at any step rolls the group back and leaves the project unchanged, so the warning stays active. It first replaces each GUID_MISMATCH parameter through Core's shared parameter migration. A replacement keeps the old categories (a type binding becomes an instance binding of the same categories), the parameter group, the variance between group instances, and every value: element values on the same elements, and type values copied to every instance of the type. The company definition replaces the old visibility, description, user-modifiable and hide-when-no-value settings; each difference is reported. Next it rebinds an installed required parameter that is bound as a type parameter or lacks the required category (WRONG_BINDING_TYPE, WRONG_CATEGORY) through SharedParameterMigration.Rebind, which keeps its GUID, categories, group, the variance between group instances and every value, and copies each type value to every instance of that type. Repair refuses, and changes nothing, when the old parameter or the parameter with the company GUID has another spec, when a value cannot be written or read back, when a type value has no instance, when a rebar container overrides the parameter, when a Length parameter holds values on members of a group placed more than once (Revit lets such a value change only in group edit mode and does not let a Length parameter vary between group instances), when several parameters have the required name and none has the required GUID, or when a same-name duplicate of an installed required parameter holds values (SharedParameterMigration.HoldsAnyValue); the message names each such duplicate. A write that Revit blocks for another reason takes the same path. SharedParameterMigrationException lists every value that could not be carried over. A global parameter with a required name is not a project parameter; repair ignores it. The returned PrerequisiteRepairResult holds one SharedParameterMigrationReport per replaced parameter, one SharedParameterRebindReport per rebound parameter, each deleted duplicate and each removed schedule field. Settings appends its Summary to the status message and the banner: the kept and copied value counts, the definition differences, the deleted duplicates, the removed schedule fields with PrerequisiteRepairResult.ScheduleAction (add the company parameter to each schedule again by hand) and, after a replacement, the action Reload the tag families that use the company shared parameters. Tag family labels keep the old GUID until the families are reloaded. Repair deletes a same-name duplicate of an installed required parameter (DUPLICATE_NAME) only when it holds no values. Deleting a replaced parameter or a duplicate also removes the schedule fields that use it; Revit removes a combined parameter field whole. Settings uses PrerequisiteRepairPrompt, the production IPrerequisiteRepairConfirmation. It shows a Warning alert through Core's IAlertService, owned by the settings window (IOwnerAwareContext), with each schedule, field and parameter, the manual step, and the buttons Cancel and Continue. Cancel leaves the status message Install/Repair canceled. Nothing changed., shows no banner and keeps the warning; this applies to the pack button, to FixWarningAsync and to Repair in PrerequisiteRepairOffer. Loading calls PlanRepair and marks each row with ScheduleUse ("Used in N schedules") and ScheduleUseDetails (one Schedule: Field line each), shown at the end of that parameter's item with the WarningBar surface. Tests answer the confirmation or the alert service with fakes. The Revit API does not expose the formula of a calculated field, so FindScheduleFields cannot list a calculated field that uses the parameter. An instance binding already containing the required category remains unchanged. Hosted tests cover these paths with text and length values, extra categories, type bindings, two group instances with distinct values, a failure after values are written, an incompatible spec, and schedule fields in main, combined and embedded definitions with Cancel and Continue. Elements in design options and elements owned by another user in a workshared model are not tested. The updater accesses these parameters by GUID.

The warning disables Update, Move, and Organize Foundation Types. Its title is Combined Foundation Tags Disabled. Clear it after resolving the prerequisite issue.

Automatic updates and monitoring

CombinedFoundationTagsAutoUpdateTask runs Update in FloorPlan and CeilingPlan views when enabled and no warning blocks it. Invalid prerequisites set the warning without a banner. NotApplicable and TransientNotReady evaluations skip execution. An unexpected runtime fault sets no prerequisite warning. Core's ViewActivationHook suppresses the failed task for that document session.

PrerequisiteMonitorTask checks prerequisite state, sets or clears the warning without a banner, logs an invalid state at Information, and schedules an Idling retry for transient initialization states. PrerequisiteRetryCoordinator retains each original event source and detach callback. Evaluation faults log and can be checked again on the next view activation. The monitor disposes its own retry coordinator at synchronous App shutdown. An injected coordinator remains caller-owned. Disposed lifetimes reject scheduling. Failed-detach entries retain cleanup state without retry work. A late Idling event can retry detachment.

Testing

Pure tests cover geometry, rotated views, corner names, regex classification, prerequisite lifecycle, and write results. Revit-hosted tests under Tests/Integration/Revit/ cover commands, modules, updates, moves, monitoring, repair, and settings. The GM test model has the three parameters from the company file. A test that needs invalid prerequisites deletes, unbinds, rebinds or replaces a parameter with Tests/Support/FoundationTagsPrerequisiteStates inside a transaction group that it rolls back.

./test.sh test --tool FoundationTags --scope local -y 2026

Limitations

Association updates use host-document pier and footing instances. Move supports host tags referencing host or linked foundations and only the four listed corner names. Length values cannot be cleared with the shipped shared-parameter definitions.
