DBTools.Core

DBTools.Core is the shared infrastructure library of DB Tools. It contains the Revit execution layer (call gates and run scopes), transaction management, safe execution, logging, settings, the tool module system and shared UI components.

Property Value
Assembly DBTools.Core.dll
Targets Desktop net10.0-windows (Revit 2026 (2026.5 or later) and Revit 2027); portable net10.0
WPF Desktop target only (UseWPF=true)
Nullable Enabled

Responsibilities

  1. Revit execution: thread-safe Revit API access through call gates and run scopes.
  2. Transactions: transaction and sub-transaction handling with rollback on failure.
  3. Safe execution: central error handling with user notification and logging.
  4. Logging: Serilog-based structured logging with a UI sink.
  5. Settings: typed settings sections with persistence and validation.
  6. Tool modules: discovery, registration and lifecycle of tools.
  7. Shared UI: window support, alert dialogs, progress overlays and behaviors.

Build

  • Desktop builds compile the complete Core for one Revit year. Pure tests and the Sandbox use that same image. Revit references are compile-only.
  • Portable builds ($(DBT_PortableTargetFramework)) compile only the explicit source list in DBTools.Core.csproj, without WPF, Revit, merging or content identity.
  • Designer builds (DBT_IsDesignerBuild=true) exclude Revit sources so the XAML designer can load without the Revit SDK.
  • _wpftmp builds (temporary projects during BAML compilation) exclude Revit and Tools sources except src/DBTools.Core/Revit/Execution/RunScope/AppRunScopeProfile.cs.

A default desktop build writes its assembly to the artifact locations that the shared build props select. Revit-hosted test projects reference the evaluated Core TargetPath, not the product staging tree.

Shared parameter migration

GroupPlacementQuery.IsInGroupPlacedMoreThanOnce(document, elementId) walks the element's group and every enclosing group. It checks GroupType.Groups.Size for all placed instances of each type, including nested instances. It returns false for an ungrouped element or a chain of group types placed once. SharedParameterMigration uses this check before grouped value writes. GroupPlacementQuery.CreateRunQuery(document) creates a query for a run whose group placements do not change. It caches each element's membership, ancestor reads and each group type's placement count. Discard the query when the run ends. Foundation Tags creates one query per run, then restricts only changed parameters that do not vary between group instances.

SharedParameterMigration.Migrate(document, source, target, requiredCategories) replaces the project parameter source with the shared parameter target that has another GUID, for example a parameter that a project received from an older shared parameter file. target is an ExternalDefinition from the open shared parameter file; the file stays open until Migrate returns, and the project must not bind the target GUID. Loaded families may define it already; Migrate then binds that parameter. The caller supplies its own definitions and categories.

Migrate changes the project only when it can carry over every value. Before any change it:

  1. Refuses a global parameter, and refuses unless the source spec NameEquals the target spec. The message names both specs, for example 'Associated Pier Elevation' exists as Area; expected Length; nothing changed.
  2. Refuses when a rebar container overrides the source; the override cannot be carried to the target.
  3. Plans one write per value, read by storage type (String, Double, Integer, ElementId); unset values are skipped. An instance-bound source keeps each element value. A type-bound source copies each type value to every instance of that type in the bound categories; it refuses when a type has a value and no instance. When the target already exists, it also records target-only values on elements in categories added to the target binding.
  4. When loaded families define the target already, the binding makes source and target one parameter. Each element keeps the value that is not empty: an old value is written to the target, a target-only value is restored if binding changes it, and an element that has one value for the source and another for the target refuses.
  5. Compares the source definition with the target: name, visibility, hide-when-no-value, and, through an element that has the parameter, description and user-modifiable. The target is canonical; each difference is reported and logged.

One transaction group then holds these transactions:

  1. Delete the source. Bind the target as an instance parameter of the source categories and requiredCategories, in the source parameter group. Set its variance between group instances to the source's and verify it.
  2. Write every planned value to its element, then read each one back.

Revit refuses a changed value on a member of a group placed more than once (directly or through a nested group) when the parameter does not vary between group instances ("Changes to groups are allowed only in group edit mode"), and the API has no group edit mode. When the source does not vary and a planned write changes such a value, step 1 also turns the variance on. A third transaction turns it off after the writes; Revit reports every element whose value it aligned with another instance of its group, and any such element, or any value read back afterwards that differs, rolls the group back. A source that does not vary holds one value per group member, so its values come back unchanged. Revit does not let every spec vary: in Revit 2026 and 2027 Text, Area, Material and URL can vary, and Integer, Number, Length and Yes/No cannot. For a spec that cannot vary, such a value is refused in the plan, before any change, and the message lists the grouped elements. A target-only value that a loaded family exposes on a member of a group placed more than once is the same in every placement, because Revit refuses another value while the parameter does not vary. The binding keeps it, so it needs no write and does not refuse, for any spec. Revit reports whether a parameter can vary only when variance is set. For Migrate and copied type values in Rebind, the plan trial-binds when the original binding does not vary and a candidate write is on a repeated group member. It checks whether the parameter can vary only if binding changes the value and a write is needed. The trial runs in a transaction (or a subtransaction inside an open transaction) that always rolls back. CheckMigrate and CheckRebind therefore find this refusal too. The trial binds the parameter in the same transaction, so its rollback leaves no dead binding key (see below). Hosted tests cover one group type with several instances, a group type with a standalone instance and copies nested in other groups, nested groups, a detail group, type values copied to grouped instances, Text and Length target-only values on repeated groups, a Length value in a group placed once, a Length refusal for source values, an aligned value that rolls back, and a failure while the variance is on that restores the values and the variance. The API cannot create attached detail groups or design options, so those are not tested.

If any write or read-back fails (read-only, rejected by Revit, a Revit exception, a grouped value that Revit aligned), or any step throws, the group rolls back and the project keeps the source with its binding and values. A write that Revit blocks for any other reason takes the same path. A refusal, or a rollback after failed writes, throws SharedParameterMigrationException; its Failures list each value that could not be carried over as a SharedParameterValueFailure with the element ID and reason, and each is logged as a warning. Any other failure propagates its own exception after the rollback. A caller with more repair steps runs Migrate inside its own transaction group, which then rolls the migration back with the rest.

Rebind(document, parameter, requiredCategories) uses the same plan and transaction group to bind a shared parameter as an instance parameter of its categories and requiredCategories, for a type-bound parameter or one that lacks a category. Its plan includes values already exposed by loaded families in added categories. The check trial-binds with the same categories. Revit's BindingMap.ReInsert resets the variance between group instances and aligns grouped values, so Rebind records every value first, restores the variance, writes the values back and reads them back, with the same group handling as Migrate. It keeps the GUID and parameter group, copies each type value of a type-bound project parameter to every instance of that type, refuses when a valued project type has no instance or a rebar container overrides the parameter, and returns SharedParameterRebindReport. It also refuses before a change when a placed family defines the target GUID only as a type parameter in a category that the rebind adds; in a category that an instance binding already has, the family type value stays on its type. Element.get_Parameter(Guid) also returns an empty parameter with that GUID on each instance of such a family, and on the type of an instance parameter; only the parameter that holds the value is in Element.Parameters, so the plan decides whether a type defines the GUID from that set. An unplaced family type parameter stays on its type because the instance binding does not change it.

CheckMigrate(document, source, target, requiredCategories) and CheckRebind(document, parameter, requiredCategories) run the same checks and plan without a change, and throw the same refusals, so a caller can find every refusal before it changes the project. CheckMigrate plans values in the same additional categories as Migrate. For planned writes on repeated group members, each check trial-binds in a transaction that always rolls back. It checks variance only if binding changes a value and a write is needed. CheckRebind uses the same rule for copied type values and values in added categories, with the same categories as Rebind. Such a check transaction must report RolledBack; when Revit reports another status or the rollback throws, the check throws SharedParameterRollbackException. It is not an InvalidOperationException, so a caller that shows refusals as messages lets it propagate as a failure, and a caller's own transaction group rolls back.

Bind(document, parameter, requiredCategories, parameterGroup) binds an existing unbound shared parameter as an instance parameter. It records values exposed by loaded families in those categories, restores each value that binding changes and reads every value back. CheckBind runs the same plan without a lasting change. Both methods refuse before a change when a value cannot be kept or a placed family defines the target GUID only as a type parameter. A family type parameter with no placed instance stays on its type because the instance binding does not change it.

HoldsAnyValue(document, parameter) is true when an element or type in the bound categories has a value, or a rebar container overrides the parameter. It does not inspect an unbound parameter. Removing a binding removes its project-bound element values, but a loaded family can still define the same shared GUID and expose family values. Bind records those exposed values before it creates an instance binding.

SharedParameterBindingLookup.Contains, Get and Find look up a binding in Document.ParameterBindings. After a lookup of a binding, a rollback that undoes a change to its variance between group instances leaves a dead key in the binding map, unless the rolled-back changes inserted or reinserted the binding. Every later Contains or get_Item in that document then throws InvalidObjectException until the model is reopened. The kind of rollback (a transaction or a transaction group) and the bound categories do not matter. Core binds the parameter in the transaction or transaction group that changes its variance, so its own rollbacks restore the map; another add-in's rollback, or an Undo of the variance setting, can leave the dead key. The lookups catch only that exception from the lookup and throw SafeExecutionRefusedException with InvalidStateMessage: Revit's parameter bindings for this model are in an invalid state; save, close and reopen the model, then try again. They do not retry. Migrate, Rebind, Bind, CheckMigrate, CheckRebind, CheckBind and HoldsAnyValue read bindings through them and refuse with that message. A hosted test leaves the dead key in a document that it creates and closes.

Deleting a parameter also removes every schedule field that uses it, with the field's sorting, grouping and filter entries; Revit removes a combined parameter field whole. GetDependentElements does not list those schedules. Migrate deletes the source and a caller that deletes a valueless parameter loses such fields as well. BindingMap.ReInsert, and so Rebind, keeps them. The API cannot recreate every field (calculated and percentage fields, for example), so Core does not try. FindScheduleFields(document, parameter) lists, without a change, each field that a delete would remove as a SharedParameterScheduleField: the schedule ID and name, the field heading, and whether the field is a combined parameter field or belongs to an embedded schedule. It reads the main and embedded definition of every schedule. The API does not expose the formula of a calculated field, so a calculated field that uses the parameter is not listed. A caller shows the list and lets the user decide before it deletes the parameter. Deleting a parameter also removes, from each view filter that uses it, every rule set (ElementParameterFilter) that has a rule on the parameter, with all of that set's rules. The filter keeps its categories, its other rule sets and its AND/OR structure, so it can select other elements; a filter with no rules left applies to every element of its categories. Hosted tests show this for a single rule set, an AND and an OR of two rule sets, and category-specific rule sets. FindFilterRules(document, parameter) lists the rules of each removed rule set as SharedParameterFilterRule: the filter ID and name, the rule parameter name and the rule in plain words (equals 'P-1', is greater than 2.5 in internal units, has no value, not: ...). It includes category rules but does not show the filter's AND/OR logic or inverted rules. The caller must record that logic before the delete. When the API does not expose the deleted parameter's rule, it adds an a rule entry.

A successful Migrate returns SharedParameterMigrationReport: the kept value count, the number of copied type values, and the definition differences. Combined Foundation Tags uses CheckMigrate, CheckRebind, CheckBind, FindScheduleFields, FindFilterRules, Migrate, Rebind, Bind, HoldsAnyValue and the family migration below in Install/Repair. Install/Repair plans family and project changes before confirmation. It cannot inspect final project values that family migration creates. If a later project migration finds a value it cannot keep, it refuses inside the outer transaction group and rolls the repair back. That refusal may appear after confirmation.

Shared parameters in loaded families

A loaded family keeps its own definition of a shared parameter, and its formulas, dimension labels and annotation labels refer to the parameter by GUID. Revit registers each shared parameter of a loaded family in the project as a SharedParameterElement. When the project deletes that element (as Migrate and a delete of a duplicate do), Revit also removes the parameter from the labels of the loaded families that use it, so a tag shows no value. A caller therefore replaces the parameter in the families first, and deletes the old GUID only when nothing in a family uses it.

SharedParameterFamilyMigration does that for any set of definitions. Its input is one SharedParameterFamilyTarget per definition: the ExternalDefinition from the open shared parameter file and the categories that the project binds, or will bind, it to as an instance parameter. A family matches a target by name, ignoring case.

  • FindFamilyNames(document, name, targetGuid) opens no family. It returns the loaded families whose types, or placed elements for an instance parameter, show a shared parameter with the name and another GUID where no project binding of that parameter to the family's category explains it. A label that uses the parameter directly shows on nothing, so this misses it. A parameter shows on a type or element only when it is in Element.Parameters (see Rebind above).
  • Plan(document, targets) changes nothing. When the project has a shared parameter with a target name and another GUID, it opens every editable loadable family with Document.EditFamily, inspects it and closes it unsaved; otherwise it opens none. It also opens editable nested families recursively. For a non-editable nested family, it checks parameters on its symbols and placed instances without opening it. In a carrier path, it refuses if those elements expose the old GUID. A non-editable nested family can still hide a label or formula, which the plan cannot see. Revit removes a shared parameter element that nothing in a family uses when it loads the family and keeps one that a nested family or a label still uses, so Migrate opens each reloaded family and refuses, rolling every family back, when the old GUID remains. In a direct-use path, it refuses if any non-editable nested family could hide a label, formula or other use, even when its symbols and instances do not expose the GUID. A family parameter with the name and another GUID becomes a SharedParameterFamilyChange. Every other use refuses, with the family named: a shared parameter element with the name that no family parameter carries (a label that uses it directly, added through Edit Label in a tag or title block family, or a nested family; Revit removes a shared parameter element that nothing in the family uses when the family is loaded); a loaded editable nested family that contains a shared parameter element with the old GUID, even when it has no instance in the host family; a family nested as a shared family in another loaded family; another data type; a type parameter in a category of InstanceCategoryIds (the family's type parameter would hide the instance values of its elements); an element or type whose value for the old GUID differs from its value for the target; a carrier whose target value is on the other scope (a type value of any type of an instance carrier's family, placed or not, or an instance value of a type carrier's type, from a binding with the other scope); an in-place or non-editable top-level family that defines the parameter or may define it; and a family that Revit does not open. Revit does not open an in-place or non-editable top-level family, so its elements decide: a parameter that shows where no project binding explains it refuses; where a binding could explain it, the plan rebinds the project parameter without the family's category in a transaction that always rolls back (a rolled-back rebind leaves the binding map intact) and reads the elements again, and a family that still shows the parameter, or a check that cannot run, refuses; a rollback that does not complete throws SharedParameterRollbackException. In Revit 2027 builds (REVIT2027_OR_GREATER), SharedParameterLabels reads each annotation label and the refusal lists one SharedParameterLabelUse line per label that shows the parameter: the label ID, its detail group, the position of the parameter in the label, and its prefix, suffix, sample text, spaces before, line break before and the label's non-breaking-spaces setting; when no label shows the parameter, no nested family shows it, and no non-editable nested family remains uninspected, the element is unused and does not refuse. If a non-editable nested family remains uninspected, the refusal names it and says that DB Tools cannot prove the parameter is unused because Revit does not let DB Tools edit it. In Revit 2026, DB Tools cannot read annotation labels and therefore refuses every direct shared-parameter element. An annotation-family refusal says the labels could not be read; a model-family refusal names the direct use without calling it an annotation label. Every refusal tells the user to reload the edited family into the project. No supported Revit lets an add-in change a label: the Revit 2027 reference assembly does not make AnnotationLabel.SetParameterFormatting or AnnotationLabel.Create public.
  • Migrate(document, plan) throws the plan's refusals before any change. Otherwise one transaction group holds every family. For each family it records, for each type (type parameter) or placed element (instance parameter), the value to keep: the old parameter's, or the target's when the old one is empty. Project target-only values in categories added to a binding are handled by SharedParameterMigration.Migrate, not by this family migration. It opens the family, replaces the family parameter with a temporary family parameter and then with the target (FamilyManager.ReplaceParameter, which cannot replace a shared parameter with another shared parameter directly), with the same group and instance or type kind, and checks in the family document that the group, kind, reporting setting, formula, every type value of every parameter, the formula of every other parameter, each dimension labeled with it, each associated element parameter and, in Revit 2027, each label kept their state with the target in place of the old GUID. Plan has already inspected loaded nested families recursively. After replacement, Migrate re-scans nested families and refuses if a family parameter, nested-family type or instance, or readable label still uses the old GUID. Project view-filter rules are listed by FindFilterRules; when the project parameter is deleted, Revit removes every rule of each rule set that uses it and keeps the filter's other rule sets and its AND/OR logic. In Revit 2026 it refuses an annotation-family replacement if the old shared-parameter element remains, because a label may use it; the refusal tells the user to edit the labels and reload the family. An unused SharedParameterElement may remain after replacement. It reloads the family (IFamilyLoadOptions overwrites the family and its type values; a nested shared family stays as the project has it); a Revit warning is dismissed and a Revit error rolls the load back and refuses. It opens the reloaded family and refuses if the old GUID is still there (a hidden use, see Plan). It then writes each recorded value that the reload did not keep, clears a value that was empty, regenerates the project (Revit shows an instance value written after a family reload only then) and reads every value back. A changed value on a read-only parameter (a formula) or on a member of a group placed more than once refuses. Any refusal or failure rolls the group back. It returns one SharedParameterFamilyReport per replaced parameter with the kept type and element value counts.

When the project binds the target, Revit shows the project binding's parameter group for that parameter in every loaded family that defines it, so the family editor shows that group after the migration. Family files on disk do not change; a family loaded again from such a file brings the old GUID back. Plan opens each family, so it takes longer in a project with many families; it logs the count and the time.

Hosted tests in Tests/Integration/Revit/Revit/SharedParameters/ cover text, integer, length and material values on two categories, type values, a failure after values are written, an incompatible spec, definition differences, and the main, combined and embedded schedule fields that FindScheduleFields lists. Elements in design options and elements owned by another user in a workshared model are not tested; a write that Revit blocks there takes the rollback path above.

Safe execution

ISafeExecutor

Every tool entry point runs inside ISafeExecutor.

public interface ISafeExecutor
{
    Task RunAsync(Func<Task> action, ILogger logger, IBannerNotifier? notifier,
        SafeExecutionOptions opts, CancellationToken ct = default);
    Task<SafeExecutionResult> RunWithoutThrowingAsync(Func<Task> action, ILogger logger,
        IBannerNotifier? notifier, SafeExecutionOptions opts, CancellationToken ct = default);
}

SafeExecutor:

  • gives each execution a GUID correlation ID and logs the elapsed milliseconds. A start or completion log write that fails goes through ContainedDiagnostic and does not change the outcome;
  • checks the token immediately before it invokes the action inside the protected boundary, so pre-canceled work returns a canceled result without running;
  • logs full exception details, including inner exceptions and XAML parse context. ExceptionDiagnosticsLogger owns the formatting of exception, cancellation, XAML and notifier-failure logs;
  • shows success and error banners through IBannerNotifier and logs notifier failures. The error banner shows the exception message, or The operation failed. for a blank message;
  • shows each failure once (Failure/FailureReport). When it shows a failure or refusal banner, it records that with the exception. The banner system keeps every request it accepts (see Notification banners), so the record means the banner will be seen. An outer layer that receives a recorded exception (or a wrapper or aggregate whose causes are all recorded) logs it and shows no banner and no failure surface. Records belong to the report scope that the outermost run of an asynchronous flow opens (an AsyncLocal). The outermost RunAsync, which rethrows, hands its record on to the window error boundary, which takes it once. A later run ignores and removes a record that another run handed on, so a failure that its caller cached and throws again in a later run is shown again. A cached failure that reaches the boundary without a run is still taken as shown once. Code that shows its own failure banner and rethrows calls FailureReport.ShowBanner; a last handler calls FailureReport.TakeShown;
  • calls ISafeExecutionFailureSurface on fatal errors. App composition adapts the logger window's show action to this interface (SafeExecutionFailureSurface), so Logging does not depend on SafeExecution;
  • reports, then rethrows, refusals, cancellations and failures from RunAsync(...). The rethrown exception keeps its instance and stack trace, unless a reporting failure wraps it in an AggregateException with the operation's exception first. RunWithoutThrowingAsync(...) returns the same outcome as a SafeExecutionResult, for event and UI callers that log and notify, then stop propagation. A null argument faults the task of either method. The XML documentation of ISafeExecutor gives the full contract.

An expected refusal throws SafeExecutionRefusedException; the result status is SafeExecutionStatus.Refused and SafeExecutionRefusalReporter reports it once: the first layer with a notifier shows the warning banner, and outer layers only log it.

Commands

ToolCommand

The abstract base class of Revit commands.

public abstract class ToolCommand : IExternalCommand, IExternalCommandAvailability
{
    public Result Execute(ExternalCommandData commandData, ref string message, ElementSet elements);
    internal Result ExecuteCore(UIApplication uiApplication, ref string message);
    protected abstract Task RunAsync(ICommandContext context);
}

Execute validates the Autodesk arguments, takes the non-null UIApplication and calls ExecuteCore. ExecuteCore resolves ISafeExecutor, ILogger and IBannerNotifier from the live IAppRuntime, runs CommandPreflight, and creates one CommandContext that owns its IAppRunScope before it calls RunAsync. CommandContext.RunThenDisposeAsync(...) owns action execution and disposal for both ribbon commands and contextual edits. It disposes once after success, failure or cancellation. A single failure keeps its stack. Combined failures place the action failure first. Command resolution, policy choice, setup-failure routing, executor admission and context creation remain in the entry points. ToolCommand has no service-resolution, call-gate or tool-window helpers. A command that owns a window composes its ToolWindowFactory and uses the returned IToolWindowSession.

public class MyToolCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        var transactionRunner = context.Resolve<ITransactionRunner>();
        await transactionRunner.RunInActiveDocumentAsync("My Operation", tx =>
        {
            var doc = tx.Document;
            // Modify the document.
        });
    }

Logging runtime

The logging runtime owns the Serilog setup, the UI sink, the active log-file path and manual file rollover.

internal sealed class LoggingRuntime :
    ILoggingRuntime, ILoggingDebugLevelController, ILoggingSinkSource,
    ILoggingFileSession, ILoggingInstanceMetadata

ILoggingRuntime combines ILoggerFactory, lifecycle, the current log path and console mirroring. Debug-level control is the internal ILoggingDebugLevelController, which LoggingRuntime implements explicitly. App composition uses the internal LoggingRuntime, which implements every narrow capability, and registers it through its interfaces, not as a concrete service. The sink, file-session and instance-metadata contracts are internal to Core. LoggingRuntime.CreateLogger(...) after disposal throws ObjectDisposedException.

  • File sink: LogFileSink keeps the active file writer and its path. A file cutover publishes the new writer and path before it retires the previous writer. A retirement failure is logged as diagnostic data and does not roll back the new path.
  • File line format: LogFileLineFormat writes each event as one line in Eastern time, such as [2026-07-04 2:05:06.789pm] [WRN] [17] Source.Context: message, and parses the same layout when the logger window reloads the file. Verbose and Debug are written as DBG, Information as INF, Warning as WRN, Error as ERR, Fatal as FTL and any other level as UNK. The reader shows DBG as DEBUG, INF as INFO, WRN as WARN, ERR and FTL as ERROR, and any other token as INFO. Exception text follows its event on separate lines; a line that does not parse keeps the time, level and source of the line before it.
  • Manual rollover: the logger window can switch file logging to a new file on demand.
  • Enrichment: every entry carries the thread ID, the instance ID and, when set, the Revit year. The instance ID comes from RevitInstance/Identity (RevitInstanceIdentity, RevitInstanceIdGenerator). The Revit year comes from LoggingOptions.RevitYear, which App sets from the year that its bootstrap receives.
  • Retention: old log files are deleted by age, count and total size.
  • Static owners: Core types that log from static members and receive no injected logger (AvailabilityFailurePolicy, RevitCallGateApiContext, SettingsChangePublisher) hold one static ILogger from the internal SerilogStaticLogger.Create(typeof(Owner).FullName!). Each call writes the message template, its named values, the exception and SourceContext to the current global Serilog logger, which is the most recently started runtime that is still active. With no active runtime the global logger is Logger.None and the event is dropped.
  • Banners: user-visible banners are logged through the WindowDiagnostics category: error banners at Error, warning banners at Warning, info and success banners at Information.

AppPaths.LogsDir is the only log-directory path: %APPDATA%/DBTools/Logs. Reading it does not create the directory; lifecycle owners call AppPaths.EnsureCreated() before they construct a logging runtime.

Logger window

LoggerWindowHost, LoggerWindowSurfaceSession and LoggerWindowViewModel depend only on the narrow internal capability contracts registered by Core logging composition. Nothing outside Core references the concrete host.

  • The view model keeps one bounded sequence of raw entries and derives the grouped Items collection from it. Display filters change only that projection; Copy All and Export enumerate the retained raw entries once, in arrival order.
  • LogEntry keeps the rendered message (Message, and RawText with the exception) for Copy, Export and search. LogMessageParts splits that text for display: a leading [Tag], a safe-execution phase (LoggingConstants.ExecutionPhase), a (CorrelationId=…) suffix and the elapsed time of a result: an outcome word (completed, complete, finished, ended, failed, canceled, stopped), then in or after and a time in milliseconds or seconds, such as completed in 460ms or finished in 12.5 ms. The row shows the remaining text, DurationText and a tag chip; DetailFields feeds the details pane and Copy details. Reload from file applies the same split to the file text.
  • Without a search, the filter hides a start row whose correlation ID belongs to a retained finish row, unless ShowStartRows is set. A group row shows its Lead: the first entry that the filters keep. The details pane shows DetailsEntry: the first selected row, or that group's lead. A double-click on a row opens the pane, and opening it scrolls the selected row into view (ListViewRevealSelectionBehavior).
  • The Source column uses MarqueeText (Presentation). Text that does not fit is still and shortened in the middle, keeping its start and as much of its last word as fits. While IsActive (bound to row hover and selection), it runs as a looping ticker; deactivation returns it to its start. AnimationsEnabled follows SystemParameters.ClientAreaAnimationKey; without animations the text never scrolls. The ticker runs only while the element is loaded, visible and inside its scroll viewport; scrolling re-checks the viewport, and unloading (a row that scrolls out, is recycled or rolls off) stops the ticker and removes its clock.
  • Buffering, filtering and file operations are in LoggerWindowViewModel.Buffering.cs, .Filtering.cs and .FileOperations.cs under Logging/LoggerWindow/ViewModels.

  • File reload reads the active log through LogFileSession.ReadCurrentLogTail while the writer is open. The bounded UTF-8 reader drops only an incomplete first line when the byte window starts inside a line. Continuation lines are separate entries; they take metadata from a parsed header only when that header is inside the selected window.

LoggerWindowHost registers the logger-window error relay through ILoggingSinkSource at host startup and toggles the debug level through ILoggingDebugLevelController. ILoggerWindowHost.ApplyUserToggle controls the logger-window debug switch. The Settings editor uses the public DebugModeState.SetEnabled to update the same session state; the host reacts to the change by setting the Serilog minimum level and showing or closing the logger window. It implements the UI-owned IWindowErrorLogSurface. It passes the UI-owned IFilePicker to LoggerWindowSurfaceSession, which selects the save path with the owner window; the view model raises an internal export-path request and stores no Window or picker. The host supplies ILogger<LoggerWindowViewModel> to the view model directly.

Posted logger-window operations go through one router, which observes rejection, abortion and callback failure exactly once. Host and session cleanup attempts every owned resource in order and keeps one original failure or an ordered aggregate.

LoggerWindowDispatcherRouter runs inline work on the owning dispatcher and propagates its failure to the caller. For posted work, it reports an action, posting or cancellation failure to the supplied handler at most once. If the handler throws, the router writes both failures through Serilog SelfLog (which writes nothing when disabled). If that write also throws, one AggregateException holds the reported failure, the handler failure and the diagnostic failure, in that order. The aggregate escapes in the reporting context: the target dispatcher for a queued action, the posting caller for a rejected or already-aborted operation, or the thread that raises Aborted (including dispatcher shutdown). The router does not guarantee that a WPF error handler exists or that shutdown continues.

The public ContainedDiagnostic.TryWrite(write, context) runs a diagnostic write, such as a log call, whose failure must not replace the caller's outcome. It returns null after a successful write. After a write failure it reports through Serilog SelfLog with the context. If SelfLog returns (also when disabled), it returns the original exception. If SelfLog throws, it returns an AggregateException with the write failure first and the SelfLog failure second. It throws only ArgumentNullException for a null write. Callers can ignore the result; WindowErrorPresenter keeps it as secondary presentation-failure data.

Notification banners

Notifications/Composition constructs IBannerNotifier, the banner service for success, info, warning and error banners.

IWindowErrorBanner (UI/Windows/ErrorBoundary) lets window error boundaries request error and refusal banners without a dependency on the notification implementation. The notification contract is in Notifications/Domain; owner-handle contracts are in UI/Windows/Ownership.

NotificationBannerService holds the public banner API and logging policy and the surfacing of action failures. ShowError, ShowWarning, ShowSuccess and ShowInfo show one kind each. ShowPrompt shows an instruction, such as a pick prompt, that has no automatic deadline and stays until its handle is disposed. ShowToast shows an action-free tool summary of a given kind; its optional autoCloseDelay replaces the lifetime of the kind. ShowToastActions shows a row with buttons and the lifetime of its kind. A banner action is one cancellation-aware asynchronous callback. The action command awaits it, closes the banner after success when CloseOnSuccess is true (the default), and does not close it because of failure or cancellation. A running action defers both automatic expiry and requested dismissal until it finishes. The service logs the full message of every banner. The host logs each row it closes (kind, automatic or user, title) and, when it is disposed, the rows still open, so a log shows which banners were open at shutdown.

Banner rules (NotificationBannerRequest, NotificationBannerWindowViewModel, NotificationBannerSchedule):

Info Blue bar and information icon (#76C3FA) 5 s
Warning (warnings and refusals) Yellow bar and tint (#FFEB3B, #19FFEB3B) 8 s
Error Red bar and tint (#FF5C5C, #26B00000) 10 s

  • Each row shows its title on line one and its message on line two, with the message lines joined by a middle dot. The tooltip has the full text. A message with more than two lines or more than 160 characters has a Details button that shows the log surface (WindowErrorBoundaryRegistry.ShowLogSurface). The dark-theme row surface is #3B4453, with #2E3440 dividers and #222933 edges. The banner uses local text colors so other windows keep the shared palette. Primary text is #E6E6E6; secondary text is #C7CDD7. Warning rows add a 10% yellow tint; error rows add a 15% dark-red tint. Success and information rows have no tint. All banner text stays above 4.5:1 contrast on the row and its tints.
  • A request with a key updates the open row with that key in place. A request without a key merges into an open key-less row with the same kind, title and message and the same presence of actions. Equal content counts a repeat (×2); other content replaces the text. Either way the row keeps its place and, once seen, its lifetime starts again. A closing row or a row with a user dismissal waiting for its action takes no merges. Each request holds its row: disposing a handle closes the row only when no other request holds it. If the last handle is disposed while an action runs, that release waits for the action to finish. A new matching request during that time takes a new holder and keeps the row open. A tool run with a correlation id can pass it as the key to keep one row per run.
  • Rows that need action (actions or Prompt) come first, then other rows, newest first. A collapsed strip shows three rows, or more when more need action, and a separate +N more row below them.
  • A row's lifetime runs only while it can be seen: it starts when the row first becomes visible in a shown strip, stops when the row moves behind the +N more row, and starts again when the row comes back. A row that waits under the pointer does not age. While the strip is hidden because its owner is minimized, every lifetime pauses; when the strip shows again, each continues with at least 2 s.
  • The visible list changes in place: one insert, move or removal per row, never a rebuild. A new row grows in over 160 ms; a closing row shrinks and fades over 200 ms. NotificationBannerHeightController sizes the window to the rows on every layout change, so the window follows each frame. An expanded strip is capped at 45% of the owner height (160 to 420 DIP) and scrolls.
  • While the pointer is over the strip, NotificationBannerSchedule pauses every lifetime and the view model freezes: new rows wait, repeats update in place, and no row moves. A new prompt does not wait, because it is the instruction for the pick in progress: it appears at once below the rows, and a keyed request that makes a waiting row a prompt shows that row the same way. A row already closing on its own (its lifetime ended, or its handle was disposed) stops closing and grows back. A handle disposed in that time closes its row after the pointer leaves, or drops it at once if it never appeared. If an action is running, the last-handle release waits for it to finish, then follows the same pointer-leave rule. When the pointer leaves, waiting rows appear and each row keeps its remaining time, but at least 2 s. Deadlines use the monotonic timestamp. The user's own clicks act at once: the close button, +N more, and the failure row of an action button. That failure row stays visible like a row that needs action, and a repeat of it brings a hidden or waiting row into view. A strip hidden under the pointer counts as the pointer leaving.

NotificationBannerHostRegistry owns dispatcher resolution, owner HWND selection, host creation, dismissal and cleanup of all hosts. NotificationBannerAnchor places the strip at the owner's top edge and width, inside the monitor work area.

  • The banner system keeps every request it accepts. When the requested owner has no HWND or no usable anchor position, the request shows on the registered default owner (Revit's main window). When a strip closes because its owner window closed, its unseen rows with an automatic deadline move to the default owner with their repeat counts. Prompts have no automatic deadline and close with their window. A request that no window can hold (no default owner, or the default owner itself closed) is logged as not shown at Error level. The service logged the request when it was made. Dispatcher retirement at App shutdown drops queued requests; nothing waits on them.
  • WindowOwnerHandleProvider resolves a closing or closed window to the registered default owner (Revit's main window), so a banner from a tool whose window closed before delivery still shows. Dialog and file-picker owners resolve the same way.
  • ModalWindow and ModelessWindow start lifecycle tracking in their constructors. A raw WPF window first seen after it closes uses the default owner only when it was not tracked from construction and has no HWND after EnsureHandle fails; other failures propagate. The lifecycle record (WindowOwnerHandleLifecycle) is in Presentation, so a retained shell never keeps a retired Core instance reachable.
  • A call on the UI thread resolves the owner and shows the banner synchronously. A worker-thread request queues owner resolution and banner creation together and does not wait. Its handle can cancel delivery before it starts or dismiss the banner after it shows. Worker requests use normal dispatcher priority, so a UI-thread request made while one is queued can appear first.
  • Queue and callback failures are logged with the request title and kind; a disposed, reset or retired request logs why it was dropped.
  • Host construction and showing run outside the registry lock; generation and registration are checked again before presentation. Each host checks its disposed state around the final AddBanner steps.
  • Default-owner registration captures the existing UI dispatcher without calling the HWND supplier, refreshes stale entries and never creates a dispatcher.
  • A registry reset invalidates pending requests. It takes and clears the registrations first, attempts each host on its own dispatcher and reports cleanup failures after all attempts.
  • Synchronous owner resolution, banner addition and new-host cleanup failures propagate; an add failure is ordered before a cleanup failure. Later timer and window-close cleanup callbacks are logged and do not propagate.

NotificationBannerWindowViewModel owns banner item state, merging, the frozen state, the visible-item projection, overflow state, action commands and expanded state. NotificationBannerTimingController keeps the row lifetimes in one NotificationBannerSchedule with one wake-up, runs every delayed callback under one window-lifetime cancellation source with TimeProvider.System, keeps only in-flight operations, dispatches callbacks to the owning dispatcher and logs callback failures. Disposal cancels the lifetime before the window can receive late callbacks. Tests use FakeTimeProvider.

WpfDispatcher.Invoke is synchronous and can wait for its dispatcher; so do the file-picker and alert APIs that return a value. WpfDispatcher.Post always queues and returns a completion task. A callback failure faults that task with the original exception and is not rethrown to the dispatcher error boundary; an aborted operation cancels the task. Direct dispatcher callbacks use the dispatcher error boundary. Banner dismissal observes and logs its completion task.

Manifest loading

ManifestResourceParser.Parse (project DBTools.Manifest) owns the YAML shape and the semantic checks of each document. Build tooling references that project; Core merges it privately. YAML is deserialized only into parser-private nullable DTOs, and the parser's mappers convert admitted values without a second validation policy.

Core promotes each resource into immutable, constructor-validated public manifest values; a partly populated public manifest is not a valid state. Core constructors keep their guards for direct callers. The parser, the ToolManifest and SandboxWindowManifest constructors and ToolAssemblyResolver apply one simple-assembly-name rule, ManifestResourceParser.IsSimpleAssemblyName: the name does not end with .dll in any case and contains no /, \, , or :. Each caller rejects a blank name first. ToolManifestValidationPolicy then applies ManifestResourceValidationPolicy over all promoted entries: duplicate manifest IDs and module types, and every warning-disable target against the complete set of declared ribbon-tool names. Parse, promotion and cross-resource errors keep the declaring resource and the original cause.

ToolModuleCatalog.Discover(...) calls the internal manifest loader once and returns one result with all promoted manifest entries, all created modules and every load, promotion and discovery error. App and the Sandbox's SandboxCatalog use that result in the load context that owns the product assembly. ThrowIfErrors() throws one AggregateException whose inner exceptions are the original causes in source order. App logs each error with its manifest and resource before it calls ThrowIfErrors().

ToolModuleCatalog.LoadManifestEntries(...) validates and promotes manifest values but never resolves or constructs moduleType. The Sandbox uses it for later metadata checks, so its compile-time Core cannot discover modules again against a different ToolModule type identity.

Type resolution and availability

ToolTypeResolver resolves a manifest type only from the assemblies the caller supplies; it never scans all loaded assemblies. Command types resolve against the manifest's tool assembly. Availability types resolve against the tool assembly, Core and the App runtime assembly, so startup cannot bind to a stale or unrelated assembly.

Generic availability predicates (active document, active view, selection) are in Tools/Availability. A tool-specific predicate stays with the tool feature that owns the rule. ToolCommand implements IExternalCommandAvailability through IsCommandAvailableCore and RequiresActiveDocument. When a manifest omits availabilityType, ToolRegistration.FromManifest(...) infers the command type if it implements that interface. An explicit separate availability type uses the existing resolver and validation route. An explicit type equal to the command type is rejected with tool and command context. The direct registration constructor retains nullable availability metadata.

CommandAvailabilityValidator.Validate(...) reuses the executing instance when its exact type and the registered availability type equal the command type. Contextual edits have no executing command instance, so the validator constructs the declared availability type once. It also constructs separate availability classes once. Null availability metadata skips the check. Both paths create the Revit category set and use the same refusal messages.

ToolRegistry

The registry of tool registrations and lifecycle hooks. Command execution reads registration metadata through CommandPreflight; HookCatalog resolves the lifecycle hooks in registration order.

public sealed class ToolRegistry
{
    public ReadOnlyCollection<ToolRegistration> Tools { get; }
    public IReadOnlyList<Type> LifecycleHookTypes { get; }
    public bool HasHookRegistrations { get; }
    public void RegisterTool(ToolRegistration registration);
    public ToolRegistration ResolveCommandRegistration(Type commandType);
    public void RegisterLifecycleHook<T>() where T : class, IHookLifecycle;
    public void MergeFrom(ToolRegistry source);
}

RegisterLifecycleHook<T>() rejects a type that is already registered. MergeFrom checks every incoming tool and lifecycle hook against the target before it changes the target, then appends the source registrations after the target's. The registry has no view-activation entry: Core's AddDbtHookRuntimeServices registers the one ViewActivationHook service.

App owns assembly loading and the validation of command and availability types. With the concrete types resolved, ToolRegistration.FromManifest(...) builds the registration and the registry accepts it.

Hooks

Supported hook types:

  • ViewActivationHook: the Core dispatcher for view-activated work. AddDbtHookRuntimeServices registers it; IViewActivationTask services supply its work.
  • IHookLifecycle: module-owned lifecycle work, such as contextual ribbon setup or dialog-showing event subscriptions, registered through ToolRegistry.RegisterLifecycleHook<T>().
internal sealed class HookHost
{
    internal Task AttachAsync(UIControlledApplication application, CancellationToken ct);
    internal Task RollbackAttachAsync(CancellationToken ct);
    internal void Detach();
}
  • IHookLifecycle defines asynchronous initialization, asynchronous rollback after an attach failure and synchronous shutdown at the application boundary. Shutdown has no cancellation token or task; HookShutdownAction holds a plain Action.
  • HookCatalog resolves the required ViewActivationHook service and the registered lifecycle implementations, in registration order, from DI. A missing service fails attachment.
  • HookHost adds its own ViewActivated subscription as the last HookAttachAction, queues subscription and the unsubscription after an attach failure through the call gate, and publishes the attached state only after the whole attach succeeds.
  • HookLifecycleCoordinator keeps the attach actions that initialized successfully, rolls them back in reverse order after a later attach failure and runs their shutdown actions in reverse initialization order. Normal detach clears that ownership only after every action succeeds; after a failure the complete, idempotent action set stays available for retry.
  • Each lifecycle implementation cleans up its own resources when its initialization fails after it acquired them.
  • ViewActivationHookDispatcher owns the safe-executor dispatch policy for this high-frequency event. ViewActivationHook keeps a runtime-failure gate per task and per document. The gate keys on DocumentSessionKey (title, path and instance hash): a reopened model starts clean, and after Save As or the first save of a new model the task can run once more under the new key.
  • Dialog Suppression records ownership immediately after its adapter subscribes and calls its unsubscribe path if later initialization fails.

Contextual ribbon:

  • Initialization cleanup runs in the queued initialization context. It attempts the selection detach, every contextual UI removal and the edit-event disposal, and keeps both the initialization and the cleanup failures.
  • Each registration keeps its tab, panel and button, and whether the injection created the panel or only the button. Cleanup removes a panel only when it owns it; a reused panel loses only the created button. A foreign button with the same ID, and its handler, are kept.
  • The injection registry removes only registrations that cleaned up successfully, keeps failed ones for retry and throws one aggregate after it attempts them all. Injection and button-state sweeps attempt every target, keep the original causes with their tab, panel and button, and throw one aggregate after the sweep.
  • The selection controller keeps the exact detach action captured at subscription, so shutdown needs no new UIApplication. The selection refresh completion callback runs only after all injection, toggle or cleanup changes succeed.
  • OnEvaluateAndToggleCompleted is an extension point of ContextualRibbonInjector; the Extreme Roof Framing Tool (ERFT) overrides it.

Windows

Presentation (DBTools.Presentation.Windows) owns the stable window surface: WPF Window inheritance, owner-handle support through IWindowOwnerHandleTarget and the IThemeOptOut contract.

ToolWindowHost constructs the stable shell. Core's ToolWindowFactory installs the owner, theme, icon, error boundary and progress lifecycle before the raw view loads; for a modeless window the session's shell initializer selects the modeless owner policy. Retiring the session releases all of it.

Settings, Alert, Logger and notification banners are raw views hosted by ToolWindowSession. ToolWindowFactory registers modal Settings and Alert sessions and modeless Logger sessions in the window registry. The banner host registry retires its modeless sessions when banners close or reset. Sandbox previews load the same raw resources with manifest-declared design-time view models.

ToolWindowRegistry.RetireAll retires child sessions first, then each session's registered cleanups, then closes the shell. App shutdown calls it before other runtime owners reset.

Window error boundary

DBTools.Core.UI.Windows.ErrorBoundary holds the window error workflow.

  • WindowStaticRuntime.Configure(...) is the one composition point where App startup supplies the banner notifier. The runtime receives IWindowErrorLogSurface and IWindowErrorBanner, so boundaries can surface the logger window and show handled-error banners without depending on the concrete shells.
  • WindowErrorBoundaryRegistry owns one exception subscription per dispatcher. It routes each failure to the most recently activated attached window, then through activation history, then the attached list, skipping windows that have closed.
  • WindowErrorBoundary classifies the original exception and every nested branch, including every aggregate branch. A branch is a DB Tools failure when its throwing method or a frame on its stack belongs to an assembly named exactly DBTools or starting with DBTools. (ordinal). Vendor code qualifies only as DBTools.HandyControl (the renamed HandyControl build) or DBTools.Presentation (which merges Helix). A raw HandyControl or HelixToolkit* assembly belongs to another add-in and never qualifies. A framework or Revit API failure raised from DB Tools code is therefore handled; another add-in's vendor failure is not.
  • A bare DB Tools OperationCanceledException whose token was canceled is marked handled with a Warning log only: no banner and no handled-failure signal.
  • The boundary presents and publishes the original outer exception, with its wrappers and causes, and returns the handled decision to the registry. An exception tree with no DB Tools branch stays unhandled and gets no notification.
  • A window seen as closed keeps a weak tombstone and cannot be attached again. A closed WPF window that was never attached or seen is outside this registry; classifying it would need reflection or a new HWND.
  • A lifecycle owner can subscribe through WindowErrorBoundaryRegistry to the handled-failure signal of its window. The subscription requires the attached per-window host and throws if it is missing. The notification carries the original failure and any presentation failure. Detaching clears the window's observers.
  • WindowErrorPresenter owns the banner and logger-window show policy. A failure whose record a run or tool handed on (see FailureReport) is only logged, and the record is taken. A SafeExecutionRefusedException shows its reason in a warning banner, without the logger window and never as Unhandled UI exception. Any other failure shows an error banner and the logger window.

WindowStaticRuntime configures and resets Core UI for App and Sandbox.

  • It serializes the whole lifecycle and reports ready only after diagnostics, window error boundaries and progress overlays are all configured. It rejects duplicate or partial existing configuration before it changes anything.
  • A failed configuration rolls back only what that attempt installed, in reverse order, so it can be retried; cleanup failures are kept with the primary failure.
  • Configure opens the dispatcher operation registry last, just before it reports ready. Reset retires that registry first, then resets error boundaries, progress overlays and diagnostics. It attempts every step, clears readiness even when a step fails and reports cleanup failures in one aggregate. The progress-overlay capability owns its host registry and visual attachment, so this reset disposes every registered host.
  • App shutdown calls Reset after runtime host teardown. The Sandbox calls it when its window-runtime registration is disposed.
  • The progress capability exposes only a getter for the attached overlay-visibility state, so tool XAML can collapse airspace content.

WindowRuntimeCapabilities.CreateSandbox(writeLog, defaultOwnerMode) builds the Sandbox logger factory, logger, error-log surface, notification surface and a no-op progress capability inside the Core that owns the window interfaces. App startup configures its own notification, logging and progress capabilities with WindowOwnerMode.DefaultOwner. Sandbox installs WindowOwnerMode.Unowned. This required policy controls default-owner binding; explicit per-window owner providers retain their existing behavior.

Alerts

public interface IAlertService
{
    AlertResult Show(AlertRequest request);
}

public static class AlertServiceExtensions
{
    public static bool Confirm(this IAlertService alerts, string message, IWindowOwnerHandleProvider ownerHandleProvider, string title = "DB Tools");
    public static T? SelectSingle<T>(this IAlertService alerts, AlertSelectionRequest<T> request) where T : class;
    public static IReadOnlyList<T> SelectMultiple<T>(this IAlertService alerts, AlertSelectionRequest<T> request) where T : class;
}

AlertServiceFactory, IAlertService and AlertServiceExtensions are public. Show is the only presentation call, so a substitute implements Show alone. AlertServiceExtensions owns the confirmation request (buttons yes and no) and, through the internal AlertSelectionPolicy, the selection requests (buttons ok and cancel) and their typed results. An empty selection returns null or an empty list without calling Show. The internal AlertService, AlertBodyBuilder, AlertWindowPresenter and AlertWindowViewModel own presentation, body composition, modal display and shell state. Confirm takes an IWindowOwnerHandleProvider; other alerts take owner and size policy in AlertWindowOptions. Implement IAlertBody for custom alert content. Core's container bodies (composite, banner table and message selection) return their immediate children through the internal IAlertBodyChildren; AlertWindowPresenter walks them root first, and each IAlertBodyTemplateProvider that owns a body adds its templates once. AlertCompositeBodySpec rejects an undefined CompositeBodyLayout.

Alerts open with WindowStartupLocation.CenterScreen, which WPF centers on the work area of the owner's monitor in device pixels. An alert therefore opens on its owner's monitor (Revit or the DB Tools window that raised it) at any display scaling. WPF does not clamp the position, so an alert larger than the work area extends past it.

Structural preview

DBTools.Presentation.StructuralPreview.IStructuralPreview3D owns structural preview navigation and rendering. ERFT and the Super Girt Tool (SGT) pass immutable scene and emphasis snapshots and consume stable pointer events. Core compiles against Presentation; the Helix and SharpDX assets are private to Presentation.

Each tool registers the viewport's synchronous disposal as a session cleanup. ToolWindowRegistry.RetireAll releases the viewport handlers, timers, camera, material and device state and payload subscriptions before it closes the shell. See Structural Preview.

  1. Call gates: implement IRevitCallGate for another execution mode.
