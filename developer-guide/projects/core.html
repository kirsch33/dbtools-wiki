DBTools.Core

DBTools.Core is the foundational library providing shared infrastructure for all DBTools components. It contains Revit execution abstractions, transaction management, safe execution patterns, logging infrastructure, settings management, tool module system, and shared UI components.

Overview

DBTools.Core serves as the central infrastructure layer, abstracting away Revit API complexities while providing consistent patterns for error handling, logging, and dependency injection across all tools.

Test ownership

DBTools.Core.Portable.Pure.Tests is the Linux-runnable net10.0 suite for portable Core behavior. It owns the Guard, strict JSON enum, safe-execution name, and monotonic-progress cases and references Core directly.

DBTools.Core.Pure.Tests is the desktop net10.0-windows suite for normal Core and merged-owner behavior, including collectible composition activation. DBTools.Core.Local.Tests owns Revit-local fixtures, including the physical Progress Overlay fixture; it has a test-only direct reference to DBTools.Presentation because that control remains Presentation-owned.

LoggerWindowDispatcherRouterSmokeTests runs real WPF dispatcher routing against desktop Core in the separate Windows VSTest Pure process, not inside Revit. Its nonparallel fixture checks recorded SelfLog fallback, ordered triple-failure propagation, and the posting-caller rejection path without replacing the Revit process's diagnostic writer. The Local logger-window fixture remains responsible for actual window ownership and session behavior.

Manifest validation

Embedded YAML is deserialized only into parser-private nullable DTOs. The parser immediately promotes each resource into immutable, constructor-validated public manifest values; partially populated public manifests are not a supported state. ToolManifestValidationPolicy then validates cross-resource rules over all successfully promoted entries: duplicate manifest and module identities, plus every warning-disable target against the complete ordinal set of declared ribbon-tool names. Parse, promotion, and cross-resource errors retain the declaring resource and original cause.

IRevitCallGate

The unified entry point for executing Revit API callbacks, supporting both inline (modal) and queued (modeless) execution modes.

public interface IRevitCallGate
{
    bool InGate { get; }
    Task<T> RunAsync<T>(Func<UIApplication, T> work, CancellationToken ct = default,
        RevitCallGateMode mode = RevitCallGateMode.Auto);
    Task RunAsync(Action<UIApplication> work, CancellationToken ct = default,
        RevitCallGateMode mode = RevitCallGateMode.Auto);
}

Call-gate admission is synchronous by construction. Async-state-machine Action<UIApplication> delegates and generic Task, Task<T>, ValueTask, and ValueTask<T> result shapes are rejected before context resolution or queue scheduling. Nullable ValueTask result types are rejected as well. Reference-typed multicast result delegates are rejected before invocation, and all reference-typed results receive a runtime awaitable check after invocation to catch interface-erased Task and boxed ValueTask values. Custom awaiter structs are outside this check.

QueuedRevitCallGate and the host's RevitCallGateTask each require an ILogger from their composition owner (App passes its runtime logger to AppLocalRevitTaskLifecycle.Start). A missing logger is a construction error; production does not substitute a null logger for queued Revit work.

RevitCallGateTask runs every queued call that was waiting when a native Execute turn starts, in order, within a 50 ms budget after the first call; calls queued during the turn wait for the next one. A call that leaves a transaction open, or that creates a transaction group through RevitTransactionGroups.Begin, is the last call of its turn. The factory ends the current turn before it starts the group. Every raise is posted to the Revit dispatcher, also from the dispatcher thread, so the raise for leftover work runs after Execute returns. The task logs a throttled Debug [CallGate/Turns] summary of turn count, queue depth, Raise-to-Execute gap and Execute duration. A queued gate call costs one Revit round trip when it waits alone. A caller that needs several reads for one user action makes them in one RunAsync body, or starts independent calls together so one turn runs them all. See Revit execution for the scheduler contract.

IRevitRunScope

Represents a single Revit run scope (command, modeless session, or test). Owns UIApplication, call-gate, document access, and disposal. Transaction services are scoped registrations resolved through IAppRunScope or ICommandContext with Resolve<T>().

public interface IRevitRunScope : IDisposable
{
    UIApplication UIApplication { get; }
    IRevitCallGate CallGate { get; }
    UIDocument GetActiveUiDocument();
    Document GetActiveDocument();
    Document GetVerifiedActiveDocument(Document expectedDocument, string? context = null);
}

IAppRunScopeFactory is the App-composed construction boundary for the concrete AppRunScope, which owns scoped service resolution, its IRevitRunScope, and disposal. Scope construction and disposal preserve the primary failure, attempt every owned cleanup step, and report any additional cleanup failures in order. IAppRunScope exposes Resolve<T>() and RevitRunScope directly; there is no separate command-runtime interface. AppRunScopeProfile selects the inline or queued call gate while preserving the manifest InlineUi and QueuedModeless values. GetVerifiedActiveDocument(...) rejects invalid expected or active documents and verifies matching DocumentSessionKey values before returning the active document.

Core logging keeps the active file writer and its path in LogFileSink. A file cutover publishes the replacement writer and path before retiring the previous writer; a retirement failure is contextual diagnostic data and does not roll back the committed path.

Transaction Management

ITransactionRunner

Provides a unified API for executing Revit model modifications with automatic transaction management.

public interface ITransactionRunner
{
    Task RunInActiveDocumentAsync(string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInActiveDocumentAsync<T>(string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
    Task RunInDocumentAsync(Document doc, string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInDocumentAsync<T>(Document doc, string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
}

Transaction-runner entrypoints apply the same synchronous admission before entering the call gate or starting a transaction. Reference-typed results also receive a runtime awaitable check inside the transaction body, including interface-erased Task values, so failure rolls the transaction back before commit.

TransactionFailureException is the public diagnostic contract for a transaction that did not reach Committed. Its constructors remain Core-internal; callers read the transaction name, terminal status, warnings, blocking failure text and failure-definition identities from the public properties. Tool write boundaries map this exception and Revit refusal exceptions to their tool-specific typed failure while preserving the original exception as the inner cause.

TransactionRunner

The primary implementation that wraps all Revit API calls in properly managed transactions:

  • Auto-selects transaction type: Uses SubTransaction if doc.IsModifiable (already in transaction), otherwise creates new Transaction
  • Cross-document protection: Prevents starting transactions on Document B while Document A is modifiable
  • Failure handling: Attaches TransactionFailurePreprocessor from Revit/Transactions to suppress non-critical Revit warnings

TransactionFailurePreprocessor.AttachToTransaction sets clear-after-rollback before failure processing starts. A warning is reported as suppressed only after Revit deletes it; a blocking failure or failure-accessor fault records a blocking diagnostic and requests rollback. An accessor fault also keeps the caught exception, which becomes the InnerException of the TransactionFailureException (an AggregateException when several accessors failed). Attachment faults propagate before commit instead of attempting to change rollback options inside the failure callback. The preprocessor also keeps one TransactionFailureRecord per message it reads: severity, description, failure definition GUID, failing element ids and whether the message rolled the transaction back. A fault while reading the failing element ids joins AccessorFaults but never changes how the message resolves. A runner built with new TransactionRunner(gate, logger) logs every record (and every accessor fault) at WARN after the commit, so a log names what Revit objected to; the one-argument constructor logs nothing. GM's apply runners opt in.

TransactionFailureProcessingTests keeps the raw Revit failure-preprocessor checks and exercises the runner boundary in a RevitLocal host: a posted blocking failure rolls back a runner-managed transaction and raises TransactionFailureException with the transaction name and blocking diagnostic. The transient document is nonmodifiable afterward and is closed by the fixture.

ITransactionGroupService

Manages transaction groups for operations requiring multiple undoable transactions to appear as a single undo item.

public interface ITransactionGroupService
{
    bool IsActive { get; }
    Task BeginAsync(string name, CancellationToken ct = default);
    Task FinalizeAsync(TransactionGroupFinalization finalization, CancellationToken ct = default);

    Task<bool> IsGroupHealthyAsync(CancellationToken ct = default);
}

Note: The transaction-group surface is intentionally manual and active-document scoped. Finalization accepts only the explicit Commit and Rollback enum values; unsupported values fail before inactive-session handling. RunAtomicAsync*, BeginAsync(Document, ...), RunAsync(string, Document, ...), and the later RunAsync(Document, string, ...) convenience wrapper were removed as dead or Revit-type-leaking public contract. Callers that need guaranteed cleanup must pair BeginAsync(...) with FinalizeAsync(...) in their own workflow.

Revit rolls back a transaction group that is still open when the Revit API callback that started it returns. A modeless GM apply on Revit 2027 showed this on 2026-11-05: under QueuedModeless every call-gate call is its own callback, so a group begun by one call was already closed for the next, and the apply committed outside it. BeginAsync and FinalizeAsync in separate calls therefore keep one group only on an InlineUi gate inside one callback, as SGT's and TDV's modal commands do. Queued modeless work uses IAtomicTransactionGroup.RunAsync, which TransactionGroupService also implements: it begins the group, runs the work, then assimilates the group when keep accepts the result or rolls it back otherwise, all in one gate call. An exception, or cancellation seen at any point before finalization (including after the work returns), rolls the group back and propagates. A document that already has an open transaction is refused before any work, because the group would own nothing to roll back. The work must complete inside that callback, where its gate calls run inline; work that is still pending when the callback returns is cancelled and the group is rolled back. Every outcome is classified by the group status Revit reports after the attempt, not by how many failures were thrown: only a confirmed RolledBack status counts as discarded and only Committed as kept. Anything else throws TransactionGroupOutcomeUnknownException, and the caller must not report the work as discarded.

Finalization always clears the active group state and attempts owned disposal. When the requested operation and cleanup both fail, the operation failure stays primary and cleanup failures follow it in an ordered aggregate.

ISafeExecutor

The central error handling service. All tool entrypoints must execute within ISafeExecutor.

public interface ISafeExecutor
{
    Task RunAsync(Func<Task> action, ILogger logger, IErrorNotifier? notifier,
        SafeExecutionOptions opts, CancellationToken ct = default);
    Task<SafeExecutionResult> RunWithoutThrowingAsync(Func<Task> action, ILogger logger,

SafeExecutor Implementation

Provides comprehensive error handling:

  • Correlation IDs: Each execution gets a unique GUID for log correlation
  • Timing: Tracks elapsed milliseconds for performance analysis
  • Exception logging: Logs full exception details including inner exceptions and XAML parse context
  • Cancellation admission: Checks the supplied token immediately before invoking the caller action inside the protected execution boundary, so pre-cancelled work returns a canceled result without admitting the action
  • Diagnostic ownership: SafeExecution/Runtime/ExceptionDiagnosticsLogger owns exception, cancellation, XAML, and notifier-failure log formatting; SafeExecutor retains execution policy and failure presentation
  • User notification: Shows error banners via IErrorNotifier
  • Failure surfacing boundary: Calls the execution-owned ISafeExecutionFailureSurface on fatal errors; App composition adapts the UI-owned log surface's show action without a Logging-to-SafeExecution dependency
  • Notification presentation: Owns safe-execution banner success/error presentation and notifier-failure logging inside the retained execution boundary
  • Explicit failure policy: RunAsync(...) is fail-fast, while RunWithoutThrowingAsync(...) is the opt-in path for event/UI callers that intentionally suppress propagation after logging/notifying
  • Delayed-hide ownership: ProgressOverlayDelayedHideScheduler retains the dispatcher operation it posts, observes every terminal outcome, and clears pending state only when the completing operation owns the current cancellation token; an aborted or faulted stale operation cannot retire a replacement hide.

Logging Infrastructure

Logging runtime

The logging runtime owns Serilog setup, the UI sink, active log-file path, and manual in-session file rollover.

LoggingRuntimeFactory.Create(LoggingOptions) remains the public construction boundary for general consumers and returns ILoggingRuntime. That contract combines ILoggerFactory, lifecycle, current log-path access, debug-level control, and console mirroring. App composition requires the existing internal LoggingRuntime, which implements every required narrow capability. Registration exposes that same host through its interfaces, not as a concrete DI service. The sink, file-session, and instance-metadata capability contracts remain internal to Core.

// Public surface (Core):
public static class LoggingRuntimeFactory
{
    public static ILoggingRuntime Create(LoggingOptions options);
}

// Internal implementation:
internal sealed class LoggingRuntime :
    ILoggingRuntime,
    ILoggingDebugLevelController,
    ILoggingSinkSource,
    ILoggingFileSession,
    ILoggingInstanceMetadata
{ /* Serilog setup, UI sink, file rollover, metadata */ }

The logger window (LoggerWindowHost, LoggerWindowSurfaceSession, LoggerWindowViewModel) depends only on the narrow internal capability contracts, registered inside Core logging composition; nothing outside Core references the concrete host. The view model owns one bounded raw-entry sequence as its retention authority and derives the grouped/expanded Items collection as a presentation projection. Display filters affect only that projection; Copy All and Export enumerate retained raw entries once in arrival order.

Logger export treats path selection, retained-entry formatting, and file writing as one operation: a canceled picker is silent; a picker or write failure records the diagnostic without losing a visible export-specific Error entry. File reload reads the active log through LogFileSession.ReadCurrentLogTail while its writer is open. The bounded UTF-8 reader drops only an incomplete first physical line when the byte window starts inside a line; an exactly aligned final line remains. Continuation lines are separate entries. They inherit metadata from a parsed header only when that header remains inside the selected physical-line window.

LoggingRuntime.CreateLogger(...) is valid only while the runtime is live. Calling it after disposal throws ObjectDisposedException; it never returns a silent null logger.

Logging runtime implementation

Features:

  • Serilog integration: Uses Serilog with structured logging
  • UI sink: Feeds log entries to the Logger Window
  • File sink: Custom TextFileSink avoids version conflicts with Serilog.Sinks.File
  • Notification banner logging: User-visible banners are written through the currently configured WindowDiagnostics category logger; error banners are Error, warning banners are Warning, and info/success banners are Information.
  • Notification banner boundaries: Notifications/Composition owns IErrorNotifier construction. NotificationBannerService keeps the public banner API, logging policy, explicit ShowError error route, action-free ShowToast route, sole action-bearing ShowToastActions route, and action-failure surfacing. Banner actions expose one cancellation-aware asynchronous callback; the action command awaits completion, closes only after successful completion when requested, and keeps the banner open on failure or cancellation. NotificationBannerHostRegistry owns dispatcher resolution, owner HWND selection, host creation, top-warning replacement, dismissal, and terminal all-host cleanup. Only an explicit zero owner HWND or the absence of a usable anchor position suppresses a banner. WindowOwnerHandleProvider resolves a closing or closed window to the registered default owner (Revit's main window), so a banner queued by a tool whose window closes before delivery still shows; dialog and file-picker owners resolve the same way. ModalWindow and ModelessWindow start lifecycle tracking in their constructors, before callers can register close handlers. A raw WPF window first seen after it closes uses the default owner only when it was not tracked from construction and has no HWND after EnsureHandle fails; other failures propagate. The window lifecycle record lives in stable Presentation (WindowOwnerHandleLifecycle), so a retained shell never keeps a retired Core generation reachable. Calls already on the UI thread resolve the owner and show synchronously. Worker-thread requests queue owner resolution and banner creation together without waiting for the dispatcher. Their returned handle can cancel delivery before it starts or dismiss the banner after it binds. Queue and callback failures are logged with the request title and kind, and disposed, reset, or retired requests identify the reason they were dropped. Host construction and showing occur outside the registry lock; generation validation and registration are rechecked before presentation. A worker request uses normal dispatcher priority, so a UI-thread request made while it is queued may be presented first; this ordering is intentional. Default-owner registration captures the actual existing UI dispatcher without invoking the HWND supplier, refreshes stale entries, and never creates a dispatcher implicitly. A registry reset invalidates pending requests. Synchronous owner resolution, banner addition, and new-host cleanup failures propagate, with an add failure ordered before a cleanup failure when both occur; later timer and window-close cleanup callbacks remain logged best-effort. Terminal reset snapshots and clears registrations first, attempts each host, and reports cleanup failures after all attempts. WpfDispatcher.Invoke is synchronous; WpfDispatcher.Post always queues and returns an owned completion task. A callback failure faults that task with the original exception without rethrowing to the dispatcher error boundary. An aborted dispatcher operation cancels the task. Direct dispatcher callbacks still use the existing dispatcher error boundary. Banner dismissal explicitly observes/logs the completion task. NotificationBannerWindowViewModel owns banner item state, visible-item projection, overflow state, action commands, expanded/collapsed state, and per-item auto-close cancellation. NotificationBannerTimingController owns every delayed close/auto-close task under one window-lifetime cancellation source, uses required TimeProvider.System at the sole production construction site, retains only in-flight operations, retires each operation when observation completes, dispatches callbacks to the owning dispatcher, and observes/logs callback failures; virtual-time tests use the official FakeTimeProvider and disposal cancels the lifetime before the window can receive late callbacks.
  • Notification host lifecycle: Host construction remains outside the registry lock. Each host rechecks its disposed state around the final AddBanner presentation steps, while reset closes hosts on their owning dispatchers. WpfDispatcher.Invoke and file-picker/alert return-value APIs are synchronous and may wait for their owning dispatcher; worker notification delivery uses WpfDispatcher.Post and does not wait.
  • Manual in-session rollover: Logger UI can force file logging to switch to a new file path on demand
  • Thread enrichment: Adds thread ID to all log entries
  • Instance identification: Uses the runtime-owned RevitInstanceIdentifier for the current process identity and Revit year
  • Log rotation: Automatic cleanup of old log files by age, count, and total size

Logger Window Composition

LoggerWindowHost owns the logger-window error relay and registers it through the narrow ILoggingSinkSource contract (not the concrete logging runtime) during host startup, and toggles debug level through ILoggingDebugLevelController. It implements the UI-owned IWindowErrorLogSurface, not the SafeExecution contract. At the App composition root, SafeExecutionFailureSurface adapts that surface's Show action to ISafeExecutionFailureSurface, so SafeExecution owns failure policy while Logging remains unaware of it. Error-boundary banners depend on IWindowErrorBanner; App composition supplies that surface through the concrete notification package, so DBTools.Core.UI.Windows does not import logging composition or notification packages. The host receives the UI-owned IFilePicker and passes it to LoggerWindowSurfaceSession; the session owns owner-window-aware save-path selection and LoggerWindowViewModel raises an internal export-path request instead of storing a WPF Window or file-picker service. The host still supplies ILogger<LoggerWindowViewModel> to the view model, so the logger window does not use lazy service-location or static runtime logging to build its view model and low-level path ownership stays separate from WPF file dialogs. LoggerWindowViewModel keeps buffered log ingestion in Logging/ViewModels/LoggerWindowViewModel.Buffering.cs, filtering in Logging/ViewModels/LoggerWindowViewModel.Filtering.cs, and file reload/export operations in Logging/ViewModels/LoggerWindowViewModel.FileOperations.cs. Posted logger-window operations have one router that observes rejection, abortion, and callback failure exactly once. Terminal host/session cleanup attempts every owned resource in order and preserves one original failure or an ordered aggregate. Core primary-failure boundaries use the internal contained-diagnostic helper so a failed ILogger write falls back to Serilog SelfLog without replacing the primary exception or skipping later cleanup.

ContainedDiagnostic.TryWrite(...) returns null after a successful requested write. After a write failure, it attempts contextual Serilog SelfLog reporting. If SelfLog returns (including when disabled), it returns the original diagnostic exception. If SelfLog also throws, it returns an AggregateException whose inner exceptions are ordered as the requested-write failure, then the SelfLog failure. It never throws that aggregate. Callers may ignore the returned diagnostic. WindowErrorPresenter retains it as secondary presentation-failure data.

LoggerWindowDispatcherRouter runs inline work on the owning dispatcher and propagates its action failure to that caller. For posted work, it reports an action, posting, or cancellation failure to the supplied handler at most once. If that handler throws, the router attempts to write both failures through Serilog SelfLog (which writes nothing when disabled). If the diagnostic write also throws, one AggregateException preserves the reported failure, handler failure, and diagnostic failure in that order. The aggregate escapes the reporting context: the target dispatcher for a queued action, the posting caller for a rejected or already-aborted operation, or the thread raising Aborted (including dispatcher shutdown). This preserves causes at the router boundary; it does not guarantee a WPF error handler is registered or that shutdown continues. LoggerWindowSurfaceSession retains its existing contained-diagnostic policy for synchronous failures.

Core file picking exposes cardinality-specific contracts: FilePickerPathRequest owns single-file, folder, and save-file requests, while FilePickerPathsRequest owns multi-file requests. IFilePicker accepts the corresponding request type for each result cardinality, so cross-cardinality dispatch is unrepresentable. The concrete FilePicker keeps path admission and file-type mapping private, and uses WPF's built-in OpenFolderDialog for owner-aware folder selection. Workflow-specific text and defaults stay with their owners: the logger window owns export-log naming, TDV settings owns library/fallback RVT picker titles, and RecordSet owns target-folder, host-file, and DWG picker titles. HookHost

Coordinates application-level hook attach/detach state. IHookLifecycle defines asynchronous initialization, asynchronous attach-failure rollback, and synchronous application-boundary shutdown. Synchronous Shutdown has no cancellation token or task surface, and HookShutdownAction owns only a plain Action. HookCatalog owns supported-hook policy and DI handler resolution solely through that contract; it has no concrete hook type checks or task-completion adapter. HookHost adds its direct ViewActivated subscription as the final HookAttachAction, queues both subscription and attach-failure unsubscription through the Revit call gate, and publishes attached host state only after the whole transaction succeeds. HookLifecycleCoordinator retains successfully initialized attach actions, rolls them back in reverse order after a later attach failure, and runs their synchronous shutdown actions in reverse initialization order. Normal detach clears that ownership only after every action succeeds; if any action fails, the complete idempotent action set remains available for retry. Each lifecycle implementation owns cleanup if its own initialization fails after acquiring resources. Contextual Ribbon performs that cleanup transactionally in its queued initialization context, attempting selection detach, every contextual UI removal, and edit-event disposal while preserving both initialization and cleanup failures. Its injection registry removes only successful registrations, retains failed registrations for retry, and throws one aggregate after attempting them all. Its selection controller retains the exact detach action captured during subscription, so synchronous shutdown needs no new UIApplication. The unused OnSubscribed and OnUnsubscribed extension hooks were deleted; OnEvaluateAndToggleCompleted remains because ERFT implements it. Dialog Suppression likewise records ownership immediately after adapter subscription and invokes the existing unsubscribe path if later initialization work fails. ViewActivationHookDispatcher owns the high-frequency safe-executor dispatch policy, and ViewActivationHook owns the per-task, per-document runtime-failure gate. The gate keys on DocumentSessionKey (title, path and instance hash): a reopened model starts clean, and after Save As or a new model's first save the task may run once more under the new key.

Contextual ribbon ownership is artifact-specific: each registration retains the actual tab, panel, and button plus whether that injection created the panel or only the button. Cleanup removes a whole panel only when it owns that panel; a reused panel loses only the created button, and a foreign same-ID button and handler are preserved. Injection and button-state sweeps attempt every target, preserve original causes under exact tab/panel/button context, and throw one aggregate after the sweep. The selection refresh completion callback runs only after injection, toggle, or cleanup mutations all succeed.

Concrete banner notifier construction is supplied by App startup through the single WindowStaticRuntime.Configure(...) composition boundary. WindowErrorBoundaryRegistry owns one exception subscription per dispatcher and routes each failure to the most recently activated attached active window, falling back through activation history and then the attached list while excluding windows that have already closed. The selected WindowErrorBoundary classifies the original exception and every nested branch, including every aggregate branch, for DBTools provenance: a branch qualifies when its throwing method or a frame on its stack belongs to an assembly whose name is exactly DBTools or starts with DBTools. (ordinal match). Shipped vendor code qualifies only through DBTools.HandyControl (the renamed HandyControl build) or DBTools.Presentation (which merges Helix). A raw HandyControl or HelixToolkit* assembly is always another add-in's copy and never qualifies, whether it throws directly or only appears on the stack. So a framework or Revit API failure raised from DBTools code is handled while a foreign add-in's vendor failure is not. A bare DBTools-owned OperationCanceledException whose token was cancelled is marked handled with a Warning log only: no banner and no handled-failure signal. It presents and publishes the exact original outer exception, preserving contextual wrappers and their causes, and returns the handled-state decision to the registry. Entirely foreign exception trees remain unhandled and produce no boundary notification. A window observed as closed retains a weak lifecycle tombstone and cannot be reattached. A never-attached, never-observed closed WPF window is outside this registry lifecycle contract; classifying it would require reflection or creating an HWND. A lifecycle owner may subscribe through WindowErrorBoundaryRegistry to the handled-failure signal for its exact window. Registering a Tool Module

public class MyToolModule : ToolModule
{
    public override void RegisterServices(IServiceCollection services, ToolManifest manifest)
    {
        services.AddSingleton<IMyService, MyService>();
        services.AddSingleton<IViewActivationTask, MyViewActivatedTask>();
    }
    
    public override void RegisterHooks(ToolRegistry registry, ToolManifest manifest)
    {
        registry.RegisterHook<IHookLifecycle, MyContextualRibbonInjector>();
    }
}

Extension Points

  1. Custom Call Gates - Implement IRevitCallGate for specialized execution modes
  2. Hook Handlers - Register IHookLifecycle implementations or IViewActivationTask services for view-activated work
  3. Settings Packs - Register ISettingsPackDefinition instances for tool-specific settings UI
  4. Alert Bodies - Implement IAlertBody for custom alert dialog content

Build Considerations

Conditional Compilation

  • Desktop builds always compile the complete Core for one Revit year; Pure tests and Sandbox use that same image. Revit references stay compile-only.
  • Portable builds ($(DBT_PortableTargetFramework)): only the bounded positive source list compiles, without WPF, Revit, merging or content identity.
  • Designer builds (DBT_IsDesignerBuild): Revit sources excluded for XAML designer
  • wpftmp builds: Special handling for temporary projects during BAML compilation
