DBTools.Core

DBTools.Core is the shared infrastructure library of DB Tools. It contains the Revit execution layer (call gates and run scopes), transaction management, safe execution, logging, settings, the tool module system and shared UI components.

Property Value
Assembly DBTools.Core.dll
Targets Desktop net10.0-windows (Revit 2026 (2026.5 or later) and Revit 2027); portable net10.0
WPF Desktop target only (UseWPF=true)
Nullable Enabled

Responsibilities

  1. Revit execution: thread-safe Revit API access through call gates and run scopes.
  2. Transactions: transaction and sub-transaction handling with rollback on failure.
  3. Safe execution: central error handling with user notification and logging.
  4. Logging: Serilog-based structured logging with a UI sink.
  5. Settings: typed settings sections with persistence and validation.
  6. Tool modules: discovery, registration and lifecycle of tools.
  7. Shared UI: window support, alert dialogs, progress overlays and behaviors.

Build

  • Desktop builds compile the complete Core for one Revit year. Pure tests and the Sandbox use that same image. Revit references are compile-only.
  • Portable builds ($(DBT_PortableTargetFramework)) compile only the explicit source list in DBTools.Core.csproj, without WPF, Revit, merging or content identity.
  • Designer builds (DBT_IsDesignerBuild=true) exclude Revit sources so the XAML designer can load without the Revit SDK.
  • _wpftmp builds (temporary projects during BAML compilation) exclude Revit-dependent sources and re-include the runtime files that XAML resolution needs.

A default desktop build writes its assembly to the artifact locations that the shared build props select. Revit-hosted test projects reference the evaluated Core TargetPath, not the product staging tree.

Shared parameter migration

SharedParameterMigration.Migrate(document, source, target, requiredCategories) replaces the project parameter source with the shared parameter target that has another GUID, for example a parameter that a project received from an older shared parameter file. target is an ExternalDefinition from the open shared parameter file; the file stays open until Migrate returns, and the project must not contain the target GUID. The caller supplies its own definitions and categories.

Migrate changes the project only when it can carry over every value. Before any change it:

  1. Refuses a global parameter, and refuses unless the source spec NameEquals the target spec. The message names both specs, for example 'Associated Pier Elevation' exists as Area; expected Length; nothing changed.
  2. Refuses when a rebar container overrides the source; the override cannot be carried to the target.
  3. Plans one write per value, read by storage type (String, Double, Integer, ElementId); unset values are skipped. An instance-bound source keeps each element value. A type-bound source copies each type value to every instance of that type in the bound categories; it refuses when a type has a value and no instance.
  4. Compares the source definition with the target: name, visibility, hide-when-no-value, and, through an element that has the parameter, description and user-modifiable. The target is canonical; each difference is reported and logged.

One transaction group then holds these transactions:

  1. Delete the source. Bind the target as an instance parameter of the source categories and requiredCategories, in the source parameter group. Set its variance between group instances to the source's and verify it.
  2. Write every planned value to its element, then read each one back.

Revit refuses a changed value on a member of a group placed more than once (directly or through a nested group) when the parameter does not vary between group instances ("Changes to groups are allowed only in group edit mode"), and the API has no group edit mode. When the source does not vary and a planned write changes such a value, step 1 also turns the variance on. A third transaction turns it off after the writes; Revit reports every element whose value it aligned with another instance of its group, and any such element, or any value read back afterwards that differs, rolls the group back. A source that does not vary holds one value per group member, so its values come back unchanged. Revit does not let every spec vary: in Revit 2026 and 2027 Text, Area, Material and URL can vary, and Integer, Number, Length and Yes/No cannot. For a spec that cannot vary, such a value is refused in the plan, before any change, and the message lists the grouped elements. Revit tells whether a parameter can vary only when the variance is set, so the plan sets it on the source in a transaction (a subtransaction inside an open transaction) that always rolls back, and only when such a value would be written; CheckMigrate and CheckRebind therefore find this refusal too. Hosted tests cover one group type with several instances, a group type with a standalone instance and copies nested in other groups, nested groups, a detail group, type values copied to grouped instances, a Length value in a group placed once, the Length refusal in the plan, an aligned value that rolls back, and a failure while the variance is on that restores the values and the variance. The API cannot create attached detail groups or design options, so those are not tested.

If any write or read-back fails (read-only, rejected by Revit, a Revit exception, a grouped value that Revit aligned), or any step throws, the group rolls back and the project keeps the source with its binding and values. A write that Revit blocks for any other reason takes the same path. A refusal, or a rollback after failed writes, throws SharedParameterMigrationException; its Failures list each value that could not be carried over as a SharedParameterValueFailure with the element ID and reason, and each is logged as a warning. Any other failure propagates its own exception after the rollback. A caller with more repair steps runs Migrate inside its own transaction group, which then rolls the migration back with the rest.

Rebind(document, parameter, requiredCategories) uses the same plan and transaction group to bind a shared parameter as an instance parameter of its categories and requiredCategories, for a type-bound parameter or one that lacks a category. Revit's BindingMap.ReInsert resets the variance between group instances and aligns grouped values, so Rebind records every value first, restores the variance, writes the values back and reads them back, with the same group handling as Migrate. It keeps the GUID and parameter group, copies each type value of a type-bound parameter to every instance of that type, refuses when a valued type has no instance or a rebar container overrides the parameter, and returns SharedParameterRebindReport.

CheckMigrate(document, source, target) and CheckRebind(document, parameter) run the same checks and plan without a change, and throw the same refusals, so a caller can find every refusal before it changes the project. Only the group variance check opens a transaction, and it always rolls back.

HoldsAnyValue(document, parameter) is true when an element or type in the bound categories has a value, or a rebar container overrides the parameter, so a caller can delete a parameter only when that loses no value. Revit keeps no element values for an unbound shared parameter: after the binding is removed, elements no longer have the parameter, and binding it again shows no value.

Deleting a parameter also removes every schedule field that uses it, with the field's sorting, grouping and filter entries; Revit removes a combined parameter field whole. GetDependentElements does not list those schedules. Migrate deletes the source and a caller that deletes a valueless parameter loses such fields as well. BindingMap.ReInsert, and so Rebind, keeps them. The API cannot recreate every field (calculated and percentage fields, for example), so Core does not try. FindScheduleFields(document, parameter) lists, without a change, each field that a delete would remove as a SharedParameterScheduleField: the schedule ID and name, the field heading, and whether the field is a combined parameter field or belongs to an embedded schedule. It reads the main and embedded definition of every schedule. The API does not expose the formula of a calculated field, so a calculated field that uses the parameter is not listed. A caller shows the list and lets the user decide before it deletes the parameter.

A successful Migrate returns SharedParameterMigrationReport: the kept value count, the number of copied type values, and the definition differences. TagFamilyNote tells the user to reload tag families, because a tag label keeps the source GUID and a project cannot change a loaded family. Combined Foundation Tags uses CheckMigrate, CheckRebind, FindScheduleFields, Migrate, Rebind and HoldsAnyValue in Install/Repair.

Hosted tests in Tests/Integration/Revit/Revit/SharedParameters/ cover text, integer, length and material values on two categories, type values, a failure after values are written, an incompatible spec, definition differences, and the main, combined and embedded schedule fields that FindScheduleFields lists. Elements in design options and elements owned by another user in a workshared model are not tested; a write that Revit blocks there takes the rollback path above.

Safe execution

ISafeExecutor

Every tool entry point runs inside ISafeExecutor.

public interface ISafeExecutor
{
    Task RunAsync(Func<Task> action, ILogger logger, IErrorNotifier? notifier,
        SafeExecutionOptions opts, CancellationToken ct = default);
    Task<SafeExecutionResult> RunWithoutThrowingAsync(Func<Task> action, ILogger logger,
        IErrorNotifier? notifier, SafeExecutionOptions opts, CancellationToken ct = default);
}

SafeExecutor:

  • gives each execution a GUID correlation ID and logs the elapsed milliseconds;
  • checks the token immediately before it invokes the action inside the protected boundary, so pre-canceled work returns a canceled result without running;
  • logs full exception details, including inner exceptions and XAML parse context. ExceptionDiagnosticsLogger owns the formatting of exception, cancellation, XAML and notifier-failure logs;
  • shows success and error banners through IErrorNotifier and logs notifier failures;
  • shows each failure once (Failure/FailureReport). When it shows a failure or refusal banner, it records that with the exception. The banner system keeps every request it accepts (see Notification banners), so the record means the banner will be seen. An outer layer that receives a recorded exception (or a wrapper or aggregate whose causes are all recorded) logs it and shows no banner and no failure surface. Records belong to the report scope that the outermost run of an asynchronous flow opens (an AsyncLocal). The outermost RunAsync, which rethrows, hands its record on to the window error boundary, which takes it once. A later run ignores and removes a record that another run handed on, so a failure that its caller cached and throws again in a later run is shown again. A cached failure that reaches the boundary without a run is still taken as shown once. Code that shows its own failure banner and rethrows calls FailureReport.ShowBanner; a last handler calls FailureReport.TakeShown;
  • calls ISafeExecutionFailureSurface on fatal errors. App composition adapts the logger window's show action to this interface (SafeExecutionFailureSurface), so Logging does not depend on SafeExecution;
  • propagates failures from RunAsync(...). RunWithoutThrowingAsync(...) is for event and UI callers that log and notify, then stop propagation.

An expected refusal throws SafeExecutionRefusedException; the result status is SafeExecutionStatus.Refused and SafeExecutionRefusalReporter reports it once: the first layer with a notifier shows the warning banner, and outer layers only log it.

Commands

ToolCommand

The abstract base class of Revit commands.

public abstract class ToolCommand : IExternalCommand, IExternalCommandAvailability
{
    public Result Execute(ExternalCommandData commandData, ref string message, ElementSet elements);
    internal Result ExecuteCore(UIApplication uiApplication, ref string message);
    protected abstract Task RunAsync(ICommandContext context);
}

Execute validates the Autodesk arguments, takes the non-null UIApplication and calls ExecuteCore. ExecuteCore resolves ISafeExecutor, ILogger and IErrorNotifier from the live IAppRuntime, runs CommandPreflight, and creates one CommandContext that owns its IAppRunScope before it calls RunAsync. ToolCommand has no service-resolution, call-gate or tool-window helpers. A command that owns a window composes its ToolWindowFactory and uses the returned IToolWindowSession.

public class MyToolCommand : ToolCommand
{
    protected override async Task RunAsync(ICommandContext context)
    {
        var transactionRunner = context.Resolve<ITransactionRunner>();
        await transactionRunner.RunInActiveDocumentAsync("My Operation", tx =>
        {
            var doc = tx.Document;
            // Modify the document.
        });
    }
}

Logging

Logging runtime

The logging runtime owns the Serilog setup, the UI sink, the active log-file path and manual file rollover.

public static class LoggingRuntimeFactory
{
    public static ILoggingRuntime Create(LoggingOptions options);
}

internal sealed class LoggingRuntime :
    ILoggingRuntime, ILoggingDebugLevelController, ILoggingSinkSource,
    ILoggingFileSession, ILoggingInstanceMetadata
{ }

ILoggingRuntime combines ILoggerFactory, lifecycle, the current log path, debug-level control and console mirroring. App composition uses the internal LoggingRuntime, which implements every narrow capability, and registers it through its interfaces, not as a concrete service. The sink, file-session and instance-metadata contracts are internal to Core. LoggingRuntime.CreateLogger(...) after disposal throws ObjectDisposedException.

  • File sink: LogFileSink keeps the active file writer and its path. A file cutover publishes the new writer and path before it retires the previous writer. A retirement failure is logged as diagnostic data and does not roll back the new path.
  • Manual rollover: the logger window can switch file logging to a new file on demand.
  • Enrichment: every entry carries the thread ID. The process identity and Revit year come from RevitInstance/Identity (RevitInstanceIdentity, RevitInstanceIdGenerator).
  • Retention: old log files are deleted by age, count and total size.
  • Banners: user-visible banners are logged through the WindowDiagnostics category: error banners at Error, warning banners at Warning, info and success banners at Information.

AppPaths.LogsDir is the only log-directory path: %APPDATA%/DBTools/Logs. Reading it does not create the directory; lifecycle owners call AppPaths.EnsureCreated() before they construct a logging runtime.

Logger window

LoggerWindowHost, LoggerWindowSurfaceSession and LoggerWindowViewModel depend only on the narrow internal capability contracts registered by Core logging composition. Nothing outside Core references the concrete host.

  • The view model keeps one bounded sequence of raw entries and derives the grouped Items collection from it. Display filters change only that projection; Copy All and Export enumerate the retained raw entries once, in arrival order.
  • LogEntry keeps the rendered message (Message, and RawText with the exception) for Copy, Export and search. LogMessageParts splits that text for display: a leading [Tag], a safe-execution phase (LoggingConstants.ExecutionPhase), a (CorrelationId=…) suffix and the elapsed time of a result: an outcome word (completed, complete, finished, ended, failed, canceled, stopped), then in or after and a time in milliseconds or seconds, such as completed in 460ms or finished in 12.5 ms. The row shows the remaining text, DurationText and a tag chip; DetailFields feeds the details pane and Copy details. Reload from file applies the same split to the file text.
  • Without a search, the filter hides a start row whose correlation ID belongs to a retained finish row, unless ShowStartRows is set. A group row shows its Lead: the first entry that the filters keep. The details pane shows DetailsEntry: the first selected row, or that group's lead. A double-click on a row opens the pane, and opening it scrolls the selected row into view (ListViewRevealSelectionBehavior).
  • The Source column uses MarqueeText (Presentation). Text that does not fit is still and shortened in the middle, keeping its start and as much of its last word as fits. While IsActive (bound to row hover and selection), it runs as a looping ticker; deactivation returns it to its start. AnimationsEnabled follows SystemParameters.ClientAreaAnimationKey; without animations the text never scrolls. The ticker runs only while the element is loaded, visible and inside its scroll viewport; scrolling re-checks the viewport, and unloading (a row that scrolls out, is recycled or rolls off) stops the ticker and removes its clock.
  • Buffering, filtering and file operations are in LoggerWindowViewModel.Buffering.cs, .Filtering.cs and .FileOperations.cs under Logging/LoggerWindow/ViewModels.
  • Export is one operation: path selection, formatting and writing. A canceled picker does nothing. A picker or write failure records the diagnostic and keeps a visible export Error entry.
  • File reload reads the active log through LogFileSession.ReadCurrentLogTail while the writer is open. The bounded UTF-8 reader drops only an incomplete first line when the byte window starts inside a line. Continuation lines are separate entries; they take metadata from a parsed header only when that header is inside the selected window.

LoggerWindowHost registers the logger-window error relay through ILoggingSinkSource at host startup and toggles the debug level through ILoggingDebugLevelController. It implements the UI-owned IWindowErrorLogSurface. It passes the UI-owned IFilePicker to LoggerWindowSurfaceSession, which selects the save path with the owner window; the view model raises an internal export-path request and stores no Window or picker. The host supplies ILogger<LoggerWindowViewModel> to the view model directly.

Posted logger-window operations go through one router, which observes rejection, abortion and callback failure exactly once. Host and session cleanup attempts every owned resource in order and keeps one original failure or an ordered aggregate.

LoggerWindowDispatcherRouter runs inline work on the owning dispatcher and propagates its failure to the caller. For posted work, it reports an action, posting or cancellation failure to the supplied handler at most once. If the handler throws, the router writes both failures through Serilog SelfLog (which writes nothing when disabled). If that write also throws, one AggregateException holds the reported failure, the handler failure and the diagnostic failure, in that order. The aggregate escapes in the reporting context: the target dispatcher for a queued action, the posting caller for a rejected or already-aborted operation, or the thread that raises Aborted (including dispatcher shutdown). The router does not guarantee that a WPF error handler exists or that shutdown continues.

ContainedDiagnostic.TryWrite(...) returns null after a successful write. After a write failure it reports through Serilog SelfLog. If SelfLog returns (also when disabled), it returns the original exception. If SelfLog throws, it returns an AggregateException with the write failure first and the SelfLog failure second. It never throws. Callers can ignore the result; WindowErrorPresenter keeps it as secondary presentation-failure data.

Notification banners

Notifications/Composition constructs IErrorNotifier.

public interface IWindowErrorBanner
{
    void ShowBanner(string title, string message);
    void ShowWarningBanner(string title, string message);
}

public interface IErrorNotifier : IWindowErrorBanner
{
    void ShowSuccessBanner(string title, string message);
    void ShowInfoBanner(string title, string message);
}

IWindowErrorBanner (UI/Windows/ErrorBoundary) lets window error boundaries request error and refusal banners without a dependency on the notification implementation. The notification contract is in Notifications/Domain; owner-handle contracts are in UI/Windows/Ownership.

NotificationBannerService holds the public banner API and logging policy and the surfacing of action failures. ShowError, ShowWarning, ShowSuccess and ShowInfo show one kind each. ShowPrompt shows an instruction, such as a pick prompt, that stays until its handle is disposed. ShowToast shows an action-free tool summary of a given kind; its optional autoCloseDelay replaces the lifetime of the kind. ShowToastActions shows a row with buttons. A banner action is one cancellation-aware asynchronous callback. The action command awaits it, closes the banner after success when requested, and keeps the banner open on failure or cancellation. The service logs the full message of every banner.

Banner rules (NotificationBannerRequest, NotificationBannerWindowViewModel, NotificationBannerSchedule):

Kind Style Lifetime
Success Neutral row, green check 3 s
Info Neutral row, blue icon 5 s
Warning (warnings and refusals) Amber bar and tint 8 s
Error Red bar and tint 10 s
Prompt Neutral row, gray bar Until its handle is disposed
Any kind with actions Its kind Until closed or an action closes it
  • Each row shows its title on line one and its message on line two, with the message lines joined by a middle dot. The tooltip has the full text. A message with more than two lines or more than 160 characters has a Details button that shows the log surface (WindowErrorBoundaryRegistry.ShowLogSurface). Text uses Body and TextSecondary on CardSurfaceElevated; warning and error rows add a 15% tint of their color. All banner text stays above 4.5:1 contrast.
  • A request with a key updates the open row with that key in place. A request without a key merges into an open key-less row with the same kind, title and message and the same presence of actions. Equal content counts a repeat (×2); other content replaces the text. Either way the row keeps its place and, once seen, its lifetime starts again. A closing row takes no merges. Each request holds its row: disposing a handle closes the row only when no other request holds it. A tool run with a correlation id can pass it as the key to keep one row per run.
  • Rows that need action (actions or Prompt) come first, then other rows, newest first. A collapsed strip shows three rows, or more when more need action, and a separate +N more row below them.
  • A row's lifetime runs only while it can be seen: it starts when the row first becomes visible in a shown strip, stops when the row moves behind the +N more row, and starts again when the row comes back. A row that waits under the pointer does not age. While the strip is hidden because its owner is minimized, every lifetime pauses; when the strip shows again, each continues with at least 2 s.
  • The visible list changes in place: one insert, move or removal per row, never a rebuild. A new row grows in over 160 ms; a closing row shrinks and fades over 200 ms. NotificationBannerHeightController sizes the window to the rows on every layout change, so the window follows each frame. An expanded strip is capped at 45% of the owner height (160 to 420 DIP) and scrolls.
  • While the pointer is over the strip, NotificationBannerSchedule pauses every lifetime and the view model freezes: new rows wait, repeats update in place, and no row moves. A row already closing on its own (its lifetime ended, or its handle was disposed) stops closing and grows back. A handle disposed in that time closes its row after the pointer leaves, or drops it at once if it never appeared. When the pointer leaves, waiting rows appear and each row keeps its remaining time, but at least 2 s. Deadlines use the monotonic timestamp. The user's own clicks act at once: the close button, +N more, and the failure row of an action button. That failure row stays visible like a row that needs action, and a repeat of it brings a hidden or waiting row into view. A strip hidden under the pointer counts as the pointer leaving.

NotificationBannerHostRegistry owns dispatcher resolution, owner HWND selection, host creation, dismissal and cleanup of all hosts. NotificationBannerAnchor places the strip at the owner's top edge and width, inside the monitor work area.

  • The banner system keeps every request it accepts. When the requested owner has no HWND or no usable anchor position, the request shows on the registered default owner (Revit's main window). When a strip closes because its owner window closed, its rows that nobody saw and that close on their own move to the default owner with their repeat counts; prompts and rows with buttons close with their window. A request that no window can hold (no default owner, or the default owner itself closed) is logged as not shown at Error level. The service logged the request when it was made. Dispatcher retirement at App shutdown drops queued requests; nothing waits on them.
  • WindowOwnerHandleProvider resolves a closing or closed window to the registered default owner (Revit's main window), so a banner from a tool whose window closed before delivery still shows. Dialog and file-picker owners resolve the same way.
  • ModalWindow and ModelessWindow start lifecycle tracking in their constructors. A raw WPF window first seen after it closes uses the default owner only when it was not tracked from construction and has no HWND after EnsureHandle fails; other failures propagate. The lifecycle record (WindowOwnerHandleLifecycle) is in Presentation, so a retained shell never keeps a retired Core instance reachable.
  • A call on the UI thread resolves the owner and shows the banner synchronously. A worker-thread request queues owner resolution and banner creation together and does not wait. Its handle can cancel delivery before it starts or dismiss the banner after it shows. Worker requests use normal dispatcher priority, so a UI-thread request made while one is queued can appear first.
  • Queue and callback failures are logged with the request title and kind; a disposed, reset or retired request logs why it was dropped.
  • Host construction and showing run outside the registry lock; generation and registration are checked again before presentation. Each host checks its disposed state around the final AddBanner steps.
  • Default-owner registration captures the existing UI dispatcher without calling the HWND supplier, refreshes stale entries and never creates a dispatcher.
  • A registry reset invalidates pending requests. It takes and clears the registrations first, attempts each host on its own dispatcher and reports cleanup failures after all attempts.
  • Synchronous owner resolution, banner addition and new-host cleanup failures propagate; an add failure is ordered before a cleanup failure. Later timer and window-close cleanup callbacks are logged and do not propagate.

NotificationBannerWindowViewModel owns banner item state, merging, the frozen state, the visible-item projection, overflow state, action commands and expanded state. NotificationBannerTimingController keeps the row lifetimes in one NotificationBannerSchedule with one wake-up, runs every delayed callback under one window-lifetime cancellation source with TimeProvider.System, keeps only in-flight operations, dispatches callbacks to the owning dispatcher and logs callback failures. Disposal cancels the lifetime before the window can receive late callbacks. Tests use FakeTimeProvider.

WpfDispatcher.Invoke is synchronous and can wait for its dispatcher; so do the file-picker and alert APIs that return a value. WpfDispatcher.Post always queues and returns a completion task. A callback failure faults that task with the original exception and is not rethrown to the dispatcher error boundary; an aborted operation cancels the task. Direct dispatcher callbacks use the dispatcher error boundary. Banner dismissal observes and logs its completion task.

Settings window

Settings/ViewModels owns SettingsPanelBlock, SettingsPackCollection, SettingsPackViewModel, SettingsWarningViewModel and the settings-window partials. Regex rows are in Settings/RegexPattern. Save state, save validation, pending changes and owner-aware pack contracts are in Settings/SettingsPack. Settings/Feedback and Settings/Reset hold the feedback and reset workflows; Settings/DesignTime holds the designer sample pack graph. The Settings window XAML is in Presentation (src/DBTools.Presentation/Settings/Views/SettingsWindow.xaml).

SettingsWindowFactory loads the embedded Settings view through ToolWindowFactory and returns a registered modal IToolWindowSession with the owner, title, size, initializer and view model applied. SettingsCommand calls session.ShowDialog(). The session owns teardown on close and retirement. The view model owns Save, Reset All, cancel and close, validation, warnings and the success banner, and is the session's close gate: it refuses to close while Save Settings, Reset All Settings, a pack Reset or the load-problem Reset Settings runs. Save requests its close through the gate, so a running reset keeps Settings open.

Construction cleanup:

  • From the first pack runtime it acquires, construction owns cleanup. If warning or row construction fails, the row disposes its warnings and runtime. If a later pack fails, the collection removes cleanly disposed rows and keeps failed cleanup owners for retry. The construction failure stays primary when cleanup also fails.
  • The window factory keeps the view model until window setup completes. Failed setup detaches handlers, clears owner bindings, closes the incomplete window and disposes the view model. Each cleanup step runs independently; the aggregate reports the construction error first.

Validation and persistence:

  • SettingsWarningValidator takes pack runtimes, not presentation rows. It checks warning ownership, updates the bound flags and publishes warning state. Its result fixes the counters, the ordered state transitions and every evaluated (PackKey, WarningId, IsActive) decision; the persistence workflow and the window apply those decisions to their rows, also for unchanged states. Startup has its own activation-only workflow with error logging and runtime cleanup.
  • The validator wraps each validation failure with its pack key and title and does not log or show it. Validate Library logs and shows feedback; silent initialization passes the same wrapper to SettingsWindowFactory.
  • For a blocked save, the outer message of the pack validation exception contains the pack title, key and validation text; the original exception is the inner cause. Save feedback shows the outer message.
  • SettingsPersistenceWorkflow owns pre-commit validation, post-commit failure wrapping and baseline ordering. Settings/Persistence owns provider-based storage. Catalog and warning validation do not depend on Settings/ViewModels.

Change publication:

SettingsChangePublisher delivers events synchronously to ordinary consumers and has a SettingsChangeDelivery.BestEffort path for immediate ribbon UI changes. App's ribbon composition (RibbonSettingsObserver) registers one callback for flag, warning-set and single-warning updates. Awaited publication delivers the ordinary events, then calls that callback with SettingsChangeDelivery.Required, which must apply on the ribbon dispatcher; it adds no second best-effort post. A skipped, retired or failed ribbon application propagates as SettingsPostCommitException after persistence commits, so the UI keeps the committed baseline and shows no success feedback. Core-only and Sandbox use without a ribbon observer publishes the ordinary events only.

Manifest loading

ManifestResourceParser.Parse (project DBTools.Manifest) owns the YAML shape and the semantic checks of each document. Build tooling references that project; Core merges it privately. YAML is deserialized only into parser-private nullable DTOs, and the parser's mappers convert admitted values without a second validation policy.

Core promotes each resource into immutable, constructor-validated public manifest values; a partly populated public manifest is not a valid state. Core constructors keep their guards for direct callers. ToolManifestValidationPolicy then applies ManifestResourceValidationPolicy over all promoted entries: duplicate manifest IDs and module types, and every warning-disable target against the complete set of declared ribbon-tool names. Parse, promotion and cross-resource errors keep the declaring resource and the original cause.

ToolModuleCatalog.Discover(...) calls the internal manifest loader once and returns one result with all promoted manifest entries, all created modules and every load, promotion and discovery error. App and the Sandbox's SandboxCatalog use that result in the load context that owns the product assembly. ThrowIfErrors() throws one AggregateException whose inner exceptions are the original causes in source order. App logs each error with its manifest and resource before it calls ThrowIfErrors().

ToolModuleCatalog.LoadManifestEntries(...) validates and promotes manifest values but never resolves or constructs moduleType. The Sandbox uses it for later metadata checks, so its compile-time Core cannot discover modules again against a different ToolModule type identity.

Type resolution and availability

ToolTypeResolver resolves a manifest type only from the assemblies the caller supplies; it never scans all loaded assemblies. Command types resolve against the manifest's tool assembly. Availability types resolve against the tool assembly, Core and the App runtime assembly, so startup cannot bind to a stale or unrelated assembly.

Generic availability predicates (active document, active view, selection) are in Tools/Availability. Manifests reference them for common requirements; a tool-specific predicate stays with the tool feature that owns the rule.

Hooks

Supported hook types:

  • ViewActivationHook: the Core dispatcher for view-activated work, run by IViewActivationTask services.
  • IHookLifecycle: module-owned lifecycle work, such as contextual ribbon setup or dialog-showing event subscriptions.
internal sealed class HookHost
{
    internal Task AttachAsync(UIControlledApplication application, CancellationToken ct);
    internal Task RollbackAttachAsync(CancellationToken ct);
    internal void Detach();
}
  • IHookLifecycle defines asynchronous initialization, asynchronous rollback after an attach failure and synchronous shutdown at the application boundary. Shutdown has no cancellation token or task; HookShutdownAction holds a plain Action.
  • HookCatalog owns the supported-hook policy and resolves handlers from DI through that contract only.
  • HookHost adds its own ViewActivated subscription as the last HookAttachAction, queues subscription and the unsubscription after an attach failure through the call gate, and publishes the attached state only after the whole attach succeeds.
  • HookLifecycleCoordinator keeps the attach actions that initialized successfully, rolls them back in reverse order after a later attach failure and runs their shutdown actions in reverse initialization order. Normal detach clears that ownership only after every action succeeds; after a failure the complete, idempotent action set stays available for retry.
  • Each lifecycle implementation cleans up its own resources when its initialization fails after it acquired them.
  • ViewActivationHookDispatcher owns the safe-executor dispatch policy for this high-frequency event. ViewActivationHook keeps a runtime-failure gate per task and per document. The gate keys on DocumentSessionKey (title, path and instance hash): a reopened model starts clean, and after Save As or the first save of a new model the task can run once more under the new key.
  • Dialog Suppression records ownership immediately after its adapter subscribes and calls its unsubscribe path if later initialization fails.

Contextual ribbon:

  • Initialization cleanup runs in the queued initialization context. It attempts the selection detach, every contextual UI removal and the edit-event disposal, and keeps both the initialization and the cleanup failures.
  • Each registration keeps its tab, panel and button, and whether the injection created the panel or only the button. Cleanup removes a panel only when it owns it; a reused panel loses only the created button. A foreign button with the same ID, and its handler, are kept.
  • The injection registry removes only registrations that cleaned up successfully, keeps failed ones for retry and throws one aggregate after it attempts them all. Injection and button-state sweeps attempt every target, keep the original causes with their tab, panel and button, and throw one aggregate after the sweep.
  • The selection controller keeps the exact detach action captured at subscription, so shutdown needs no new UIApplication. The selection refresh completion callback runs only after all injection, toggle or cleanup changes succeed.
  • OnEvaluateAndToggleCompleted is an extension point of ContextualRibbonInjector; the Extreme Roof Framing Tool (ERFT) overrides it.

Window error boundary

DBTools.Core.UI.Windows.ErrorBoundary holds the window error workflow.

  • WindowStaticRuntime.Configure(...) is the one composition point where App startup supplies the banner notifier. The runtime receives IWindowErrorLogSurface and IWindowErrorBanner, so boundaries can surface the logger window and show handled-error banners without depending on the concrete shells.
  • WindowErrorBoundaryRegistry owns one exception subscription per dispatcher. It routes each failure to the most recently activated attached window, then through activation history, then the attached list, skipping windows that have closed.
  • WindowErrorBoundary classifies the original exception and every nested branch, including every aggregate branch. A branch is a DB Tools failure when its throwing method or a frame on its stack belongs to an assembly named exactly DBTools or starting with DBTools. (ordinal). Vendor code qualifies only as DBTools.HandyControl (the renamed HandyControl build) or DBTools.Presentation (which merges Helix). A raw HandyControl or HelixToolkit* assembly belongs to another add-in and never qualifies. A framework or Revit API failure raised from DB Tools code is therefore handled; another add-in's vendor failure is not.
  • A bare DB Tools OperationCanceledException whose token was canceled is marked handled with a Warning log only: no banner and no handled-failure signal.
  • The boundary presents and publishes the original outer exception, with its wrappers and causes, and returns the handled decision to the registry. An exception tree with no DB Tools branch stays unhandled and gets no notification.
  • A window seen as closed keeps a weak tombstone and cannot be attached again. A closed WPF window that was never attached or seen is outside this registry; classifying it would need reflection or a new HWND.
  • A lifecycle owner can subscribe through WindowErrorBoundaryRegistry to the handled-failure signal of its window. The subscription requires the attached per-window host and throws if it is missing. The notification carries the original failure and any presentation failure. Detaching clears the window's observers.
  • WindowErrorPresenter owns the banner and logger-window show policy. A failure whose record a run or tool handed on (see FailureReport) is only logged, and the record is taken. A SafeExecutionRefusedException shows its reason in a warning banner, without the logger window and never as Unhandled UI exception. Any other failure shows an error banner and the logger window.

WindowStaticRuntime configures and resets Core UI for App and Sandbox.

  • It serializes the whole lifecycle and reports ready only after diagnostics, window error boundaries and progress overlays are all configured. It rejects duplicate or partial existing configuration before it changes anything.
  • A failed configuration rolls back only what that attempt installed, in reverse order, so it can be retried; cleanup failures are kept with the primary failure.
  • Reset attempts every Core UI cleanup step, clears readiness even when a step fails and reports cleanup failures in one aggregate. The progress-overlay capability owns its host registry and visual attachment, so this reset disposes every registered host.
  • The progress capability exposes only a getter for the attached overlay-visibility state, so tool XAML can collapse airspace content.

WindowRuntimeCapabilities.CreateSandbox(...) builds the Sandbox logger factory, logger, error-log surface, notification surface and a no-op progress capability inside the Core that owns the window interfaces. App startup configures its own notification, logging and progress capabilities.
