DBTools.App

DBTools.App builds DBTools.dll, the Revit add-in entry and the App runtime. It targets net10.0-windows (DBT_RevitTargetFramework) for desktop Revit 2026 (2026.5 or later) and Revit 2027.

Revit API references are compile-only and are never staged as product runtime files. DBT_RemoveForbiddenHostAssemblies removes RevitAPI, RevitAPIUI, AdWindows, UIFramework, System.Runtime and System.ObjectModel DLLs after copying. Deletion errors fail the build. The App project must not add a loose-copy target for the merged ricaun.Revit.UI files. Product output stages App at the year root and the tool assemblies below Tools/.

Responsibilities

App owns:

  • the public parameterless Revit entry (AddinEntry) and the daemon idle acknowledgement;
  • the non-inlined startup and shutdown boundary, and the startup fallback diagnostics;
  • lifecycle, Core hook composition, ribbon composition, the settings host and shutdown;
  • the embedded tool manifests.

The fourteen tool projects under src/Tools/ own their tool assemblies, including the Super Girt Tool (SGT), Settings and DialogSuppression. Each tool owner embeds its icons, raw views and manifest-declared design-time view models. Presentation owns the stable themes and compiled WPF controls.

Startup

AddinEntry has a public parameterless constructor for Revit. The first action of OnStartup checks DBTOOLS_DAEMON_REVIT_ROLE and the load context of the entry assembly.

  • Idle copy: only a file-backed entry in AssemblyLoadContext.Default acknowledges the installed idle copy. It records the key DBToolsDaemon.IdleAddin:<simple-name> (for App, DBToolsDaemon.IdleAddin:DBTools) with the entry location as its value, and returns success without touching the ribbon, events or other startup work.
  • Normal startup: every other context (ProductLoadContext, DevModeLoadContext, a null context and any other context) enters ToolWindowCallbackScope and the non-inlined AppStartupBoundary. Startup initializes the App runtime, validates themes, composes the ribbon, starts the Revit call gate and publishes deferred startup work.

Startup parses the Revit year from ControlledApplication.VersionNumber. AppRuntimeInitializer passes it to AppRuntimeHostLifecycle.InitializeHost(ribbonTarget, revitYear). InitializeHost publishes the year to RevitInstanceIdentity before it creates logging or services; RevitInstanceIdentity accepts the same year again and rejects a different one. Logging, the per-year settings file and the container take the year from the InitializeHost argument, not from RevitInstanceIdentity.

AppRuntimeInitializer then resolves the startup services, configures WindowStaticRuntime and builds the AppStartupContext. If initialization fails, it shuts down the runtime that it created and then resets the window runtime, but only when this attempt configured it. A rejected duplicate configuration leaves the incumbent window runtime in place. The report puts the initiating failure first.

Preparation runs these phases in order: ValidateTheme, CreateDeferredStartupRunner, ComposeRibbon, PublishInitialStartupEffects and StartBackgroundStartup. A failed phase is logged as Startup phase {Phase} failed with the original exception, is presented with the theme, ribbon, startup effects, background startup or preparation message, and returns the captured handles for cleanup. A failure outside the phases is reported as phase TransferStartupOwnership with the preparation message. Startup state publication failures use the publication message whether registration fails before publication or observation registration fails after publication. Publication cleanup finishes before one presentation attempt. A rejected candidate is cleaned directly without publishing it over the incumbent lifecycle state. Deferred UI failures use the Deferred UI Startup safe-execution path.

The lifecycle cleanup subscription and the deferred startup subscription each register their own Idling handler through a separate AppLifecycleIdlingRegistration. The optional Idling subscribe and unsubscribe pair of AppStartupConfiguration reaches both. Cleanup registers first, so a pending failed-startup cleanup gets the first Idling callback. The cleanup subscription attempts its handler removal once. Startup ownership captures the deferred subscription before it registers, so a deferred handler removal that fails, also during a failed registration, keeps the handler for the next cleanup to retry.

Startup failure dialogs are suppressed while DBT_TEST_RUN_ID is active. A failed dialog callback is contained and recorded in the fallback log with the initiating failure first. App log templates identify their emitting owner with [EmittingType]; tool-module registration uses the AppToolModuleRegistrar bootstrap logger category. A registration failure names the tool, the manifest resource, the registration stage and the module type, or manifest-only for a manifest without a module.

Failure cleanup runs synchronously at the Revit API boundary and combines the primary and cleanup failures. A startup, shutdown or ribbon-runtime failure that cannot reach the normal log is written by a BCL-only writer to %APPDATA%\DBTools\Logs\DBTools.Fallback.log, so a missing Core or UI dependency does not hide the diagnostic.

Shutdown

OnShutdown uses the same boundary and returns only after the lifecycle cleanup result is complete. An idle installed entry has no runtime and returns success directly. Without a published lifecycle state, shutdown succeeds. While cleanup that another owner started is unfinished, shutdown fails and leaves the state published. Completed cleanup returns its recorded result, and shutdown clears only the publication that it cleaned.

Each generation keeps the handles it acquired. AppStartupOwnership holds the background startup task state, the ribbon composition, the AppDeferredStartupSubscription, the lifecycle cleanup subscription and the RevitCallGateTask that AppLocalRevitTaskLifecycle.Start published; AppRuntimeResources holds the AppRuntime. Shutdown releases these captured handles, not whatever the process slots hold:

  • AppLocalRevitTaskLifecycle.Shutdown(task, cancelPending) retires and disposes the captured task, and resets RevitCallGateTaskHost only while it still publishes that task. Cleanup after a published background startup fails, replacement cleanup and an abandoned builder cancel queued work so callers in the running process observe cancellation; other cleanup drops it.
  • AppRuntimeHostLifecycle.ShutdownHost(runtime) detaches the captured runtime from AppRuntimeAccessor only while it is current, then disposes it.
  • Replacement cleanup and an abandoned startup builder release only their own handles. A replacement task or runtime stays published.

A lifecycle cleanup subscription that still holds a queued startup failure when it is disposed records that failure in the fallback log and throws only a handler-removal failure, so a replacement is not rejected for a stale fault.

The App runtime host lifecycle (ShutdownHost) step runs before the Window static runtime contract step (WindowStaticRuntime.Reset, which also retires dispatcher operations). These steps and the cleanup summary are written to the fallback log after logging is disposed. The Revit task host step logs failures through the live logger.

Composition

AppRuntimeFactory builds the service root once from the ribbon target and the Revit year. AppServiceProviderFactory registers the Revit year once as an int singleton, then logging, settings (AppPaths.GetSettingsFile(revitYear)), UI ownership, Revit call gates, safe execution, command preflight, hooks, alerts and ribbon composition. It returns the concrete ServiceProvider. AppServiceRoot owns the provider: disposal stops the logger window host, disposes the provider and its singletons, then disposes logging.

AppHostedComposition is the public composition entry for hosted tests. EnsureRuntime(version) parses an unset Revit year and initializes the runtime once with an isolated ribbon target. The host owns the call-gate task. CreateLoggingRuntime() uses the initialized year. BuildServiceProvider(logging, isolationName, configure) requires Core's concrete logging runtime, gives each provider a distinct ribbon prefix and applies configure after App registrations. The caller disposes the provider and logging runtime. The entry also installs and resets the Revit main-window owner through App's window-owner lifecycle. Tool test assemblies use this entry without access to App internals.

AppToolModuleRegistrar asks Core's ToolModuleCatalog to discover the embedded manifest resources once. It instantiates the module owners, collects their settings, services and hooks in temporary registration state, validates module responsibilities and merges the state into the App container.

Core's ToolAssemblyResolver loads the module, command, availability and icon owner of each manifest by explicit path from the product year's Tools/ directory, in the active owning load context. It checks the declared PE identity, rejects a loaded image with the same name from another path or identity, and probes no other directory.

Manifest registration infers command-owned availability when availabilityType is omitted and rejects a redundant explicit command type. An explicit separate availability class keeps the existing resolution route. Synchronous command preflight reuses the executing command for its own availability check. Contextual edits and separate availability classes create one instance at validation. Settings uses its inferred command availability and remains available without an active document. ToolCommand.Execute and IsCommandAvailable enter the Presentation callback scope of the owning assembly. ExecutionContext flow is suppressed across callbacks, so host dispatchers and timers cannot keep a reference to an owning load context.

Ribbon

Ribbon planning builds each PushButtonData directly from a ToolRegistration: the file-backed Location of the command assembly, the command full name and the optional availability class full name. A button definition carries the logical tool internal name. RibbonTarget.GetItemName adds the target prefix for Revit. Grouped controls keep manifest order and use the same definitions. Settings, SGT and DialogSuppression use the same registration path as every other tool.

RibbonControlPlanBuilder.Create turns the tool registrations into one RibbonPlan. Its panels follow the order Common, Structural, Testing, Services and Settings, then other panel names in ordinal order. Each RibbonPanelPlan lists its controls by order. At equal order, split buttons come first, then pulldown buttons, stacks and push buttons; push buttons with equal order keep their registry order. RibbonComposition creates the plan once from the registry's tool snapshot and passes the same plan to retained-panel discovery, retained-control validation, panel creation and control execution. RibbonCompositionState keeps the native PushButton of each registered tool for enabled-state changes.

RibbonComposition owns ribbon creation, settings subscriptions and disposal. Compose returns that same owner after successful initialization. A duplicate composition throws InvalidOperationException: Ribbon controls are already composed for this process. App startup cannot continue. The rejected attempt preserves the incumbent ribbon state and subscriptions. A failed initialization rolls back its own panels and subscriptions and permits a retry before disposal.

On a reload (Dev Mode), RibbonComposition finds the retained panels without changing them and validates every requested panel and button before it removes, creates or restores anything. A refused reload leaves the ribbon unchanged and throws InvalidOperationException with a message that ends Restart Revit to load this ribbon definition.

Retained ribbon change Result

Changed availability class on a retained button Applied.
Cleared availability class Refused; restart Revit.

Tests

  • Pure tests cover the idle gate (role and load-context decisions), ribbon planning, settings and startup state. They compile only the source needed for platform-neutral behavior, must not run Revit startup and must not load Revit-typed members.
  • Local (Revit-hosted) tests reference the real App project and cover entry behavior, real ribbon composition, command availability, lifecycle cleanup and Revit window ownership. A Revit-hosted test parses the Revit year from its live UIApplication, passes it to the App bootstrap methods and uses the shared call gate.

Revit-hosted tests take runtime ownership from the staged product tree. Tool project references stay compile references and do not add separate product images to the test dependency closure. Hosted inputs include the complete year root with Tools/ preserved; test assemblies, NUnit files and companions are separate inputs. The daemon's ProductLoadContext forwards product references to the same product instances that App uses.

Release checks validate App's entry identity, embedded manifest ownership, command and availability owners, the stable Presentation resources, source-map freshness and the placement in the year tree.
