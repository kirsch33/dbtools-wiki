DBTools.App

DBTools.App builds DBTools.dll, the direct Revit add-in entry and App runtime. It targets net10.0-windows for Revit 2026.5+ and 2027.

Ownership

App owns the public parameterless Revit entry, daemon idle acknowledgement, non-inlined startup/shutdown boundary, startup fallback diagnostics, lifecycle, hooks, ribbon composition, settings host, shutdown, and centrally embedded manifests. Tool assemblies own SGT, Settings, and DialogSuppression.

The first startup branch checks DBTOOLS_DAEMON_REVIT_ROLE and the exact AssemblyLoadContext.Default owner. The idle copy records DBToolsDaemon.IdleAddin:DBTools with its actual location and returns before normal App startup. Active startup enters ToolWindowCallbackScope and starts the App lifecycle. The BCL-only fallback writer records DBTools.Fallback.log under %APPDATA%\DBTools\Logs.

Tool registration and ribbon

AppToolModuleRegistrar asks Core's ToolModuleCatalog to discover embedded manifests. Each tool manifest names its owner, loaded by explicit path from the product year's Tools/ directory in the active owning context.

Ribbon planning builds PushButtonData directly from each ToolRegistration: the command assembly's file-backed Location, command full name, and optional concrete command availability full name. There is no App command lifecycle registry, generated bridge, or command fallback resolver. ToolCommand.Execute and IsCommandAvailable enter the stable Presentation callback scope so command callbacks cannot capture an owning context through ExecutionContext.

Startup and shutdown phases

AddinEntry has a public parameterless constructor for Revit. Its first OnStartup action checks the daemon role and the entry assembly's actual load context. Only a file-backed entry in AssemblyLoadContext.Default acknowledges the installed idle copy; the acknowledgement key is DBToolsDaemon.IdleAddin:<simple-name> and its value is the entry location. The idle branch returns success without touching ribbon, events, or other startup work. ProductLoadContext, DevModeLoadContext, null contexts, and all other contexts take normal startup.

Normal startup enters the non-inlined AppStartupBoundary, initializes the App runtime, validates themes, composes the ribbon, starts the Revit call gate, and publishes deferred startup work. Failure cleanup is synchronous at the owning Revit API boundary and combines primary and cleanup failures. Startup, shutdown and ribbon-runtime failures that cannot reach the normal log use the BCL-only %APPDATA%/DBTools/Logs/DBTools.Fallback.log path so a missing Core/UI dependency does not suppress the diagnostic.

OnShutdown follows the same boundary and returns only after the lifecycle cleanup result is complete. An idle installed entry has no owned runtime and returns success directly. The App runtime host lifecycle (ShutdownHost) sub-step, dispatcher-registry retirement, and cleanup summary are recorded to the fallback file after logging is disposed. The Revit task host sub-step still records failures through the live logger.

Runtime and composition details

AppRuntimeFactory builds the service root once. AppServiceProviderFactory registers logging, settings, UI ownership, Revit call gates, safe execution, command preflight, hooks, alerts, and ribbon composition. AppToolModuleRegistrar discovers embedded manifest resources once, instantiates module owners, captures settings/services/hooks in temporary registration state, validates module responsibilities, and merges the state into the App container.

Tool manifests resolve their module, command, availability, and icon owner from the product year's Tools/ image through Core's ToolAssemblyResolver; AppHooks stays in App. It uses the active owning load context, checks the declared PE identity, rejects a loaded same-name image from another path or identity, and does not probe a fallback directory.

The command preflight creates the concrete command availability type before execution. ToolCommand.Execute and IsCommandAvailable enter the Presentation callback scope for the owning App/tool assembly, while ExecutionContext flow is suppressed across callbacks so host dispatchers and timers cannot retain a generation context.

Ribbon contract

Ribbon planning builds controls directly from ToolRegistration. A button's PushButtonData contains the command assembly's file-backed location, command full name, and optional concrete availability full name. Grouped controls preserve manifest order and use the same direct definitions. Existing buttons are reused only when their assembly path and class binding still match; a stale owner fails loudly rather than silently routing to a different generation. On a Dev Mode reload, a retained button can receive a changed availability class. Clearing an existing class requires a Revit restart. Removing, reordering or retyping retained items, or adding to a retained stack, fails and asks for a restart. A change to retained stack placement, membership, or boundaries also fails and asks for a restart. New panel items and grouped-button children can be appended after the retained items.

Settings, SGT, and DialogSuppression follow the same registration path as every other manifest-declared tool, and their module/command assembly is the corresponding Tools/ image.

Resources

App embeds central tool manifests. Each tool owner embeds its icons, raw views, and manifest-declared design-time ViewModels. Presentation owns stable themes and compiled WPF controls. App has one desktop compilation; Pure tests reference that same image.

The coordinator runs both supported years and separately proves installed Default-context idle and Dev Mode reload behavior. Documentation and source-level tests do not claim those native results.

Build and source maps

DBTools.App.csproj emits DBTools.dll and references Core and Presentation. The generic assembly merge folds ricaun.Revit.UI into App; the App project must not add a loose-copy target for that merged implementation. ProductOutput stages App at the year root and standalone tools under Tools/.

src/DBTools.App/MAP.md is generated from the current live tree and manifest fields. When an owner directory or test path changes, run python3 .agents/work/canon_source_maps.py; do not hand edit the generated map.

Hosted test boundary

Local App and tool tests compile against the APIs they exercise, but runtime ownership comes from the staged product tree. Tool project references remain compile references and do not create competing flat product images in the test dependency closure. Hosted inputs include the complete year root with Tools/ preserved, while test assemblies, NUnit files, and companions remain separate inputs. The daemon's ProductLoadContext forwards product references to the same declared product instances used by the App.

The App test marker and Revit host support live at the test owner boundary. A hosted test must initialize the selected Revit year and use the shared call gate; a pure test references the normal App and must not run Revit startup or load Revit-typed members. The two lanes share behavior fixtures only when their runtime dependencies are genuinely the same.

Project references and release checks

App references Core and Presentation directly. Tool projects own all fourteen tool assemblies, including SGT, Settings, and DialogSuppression. Revit API references are compile-only for product output and are never staged as product runtime files. The declared merge props own ricaun.Revit.UI folding and its determinism evidence.

Release checks validate App's direct entry identity, embedded manifest ownership, command and availability owners, stable Presentation resources, source-map freshness, and exact year-tree placement. They do not prove installed Revit startup, daemon ProductLoadContext sharing, or Dev Mode reload; those remain coordinator-owned runtime proofs.
