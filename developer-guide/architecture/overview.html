Architecture overview

NAME

architecture - the dbtools assemblies, how they start and how they run a command

SYNOPSIS

entry     dbtools.addin -> dbtools.dll, dbtools.App.Addin.AddinEntry
source    src/dbtools.{App,Core,Manifest,Presentation,Sandbox}
tools     src/Tools/{Common,Structural,Experimental,Services}/<Tool>/  (manifest.yml)
years     Revit 2026 (2026.5+), 2027: net10.0-windows  (build/Distribution/RevitYearContract.cs)
placement .agents/canon/CANON.md  (where each kind of code belongs)

DESCRIPTION

Revit loads dbtools.dll through dbtools.addin. Its App code builds the services and the ribbon, and loads the tools from Tools/. Tools from the Experimental folder appear on the dbtools Testing panel.

The daemon (dbtools-daemon) starts Revit for hosted tests. In Dev Mode, it reloads each new build into a running Revit.

Desktop projects target net10.0-windows ($(DBT_RevitTargetFramework)), and $(RevitYear) selects the Revit API references and output folder. Core and SGT also build for net10.0, without WPF or the Revit API, for portable pure tests. The Revit 2026 Design Automation appbundle targets net8.0-windows. Directory.Build.targets defines the compilation symbol REVIT2027_OR_GREATER for every project built with RevitYear 2027 or later; code that uses API new in Revit 2027 compiles only under that symbol.

CONTRACTS

Each rule names its check, if any.

  1. References. App references Core and Presentation. Core (net10.0-windows) references Presentation, dbtools.Manifest and the Revit API. Tools reference Core and Presentation.
  2. Presentation. Presentation uses WPF. It owns the merged HelixToolkit, Serilog and Microsoft.Extensions libraries in AssemblyMerges.props. It never references App, Core, a tool or the Revit API. BuildPolicyBehaviorTests and HelixMergeArtifactContractTests check parts of rules 1 and 2.
  3. Sandbox. The Sandbox compiles against Core and Presentation with Private="false", and loads them from the year folder that it validates.
  4. No third-party DLLs. build/Merging/AssemblyMerges.props merges each third-party runtime library into the assembly that owns it. The build checks its output against DistributionContract.ProductFiles.
  5. Tool assemblies. Tool projects set DBT_IsToolAssembly=true. The build stages them in Tools/ with a content-derived version, which ContentVersionTests checks.
  6. One tool folder. ToolAssemblyResolver.LoadAssembly loads only <folder of dbtools.dll>/Tools/<name>.dll, into the load context of dbtools.dll. ToolAssemblyResolverTests checks this.
  7. No load context of its own. dbtools creates no AssemblyLoadContext. Installed, it runs in the default context of Revit. The daemon uses ProductLoadContext for hosted tests and DevModeLoadContext for Dev Mode (Assembly Loading Contract).
  8. Themes per view. Each view merges the theme itself and leaves Application.Resources unchanged (Theme System).
  9. Fallback log. AppFallbackFailureLog.RecordFailure uses only the BCL, so it works before Core loads.

FLOW

Startup

AddinEntry.OnStartup runs these steps:

  1. Idle check (AddinIdle). When DBTOOLS_DAEMON_REVIT_ROLE is set, the copy of dbtools.dll in the default context stays idle. It stores its path in the AppContext data dbtools-daemon.IdleAddin:dbtools and returns Succeeded, so the daemon can test its own copy.
  2. User data directory (AddinUserData). OnStartup reads DBT_USER_DATA_DIR once. An unset or empty value leaves AppPaths.BaseDir unchanged: %APPDATA%\dbtools, or the dbtools.AppPaths.BaseDir AppContext value when one is set. Any other value must be an absolute path to an existing directory that the process can write; its full path becomes that AppContext value. A value that fails these checks returns Failed before any runtime work, and OnShutdown then returns Succeeded at once. The failure names the variable, the value and the reason. It goes to Trace and to the startup failure dialog, which DBT_TEST_RUN_ID suppresses, and to no file. A set value never falls back to %APPDATA%\dbtools.
  3. Callback scope. AppStartupBoundary.Start enters ToolWindowCallbackScope, which suppresses ExecutionContext flow and sets contextual reflection to the dbtools.dll context. Start is not inlined, so no other product assembly loads before the idle check.
  4. Pending cleanup. AppLifecycleCoordinator.Start returns Failed while an earlier failed start still cleans up.
  5. Runtime. Startup reads the Revit year from VersionNumber. AppRuntimeFactory builds logging, services and the tool registrations, and AppRuntimeAccessor publishes them.
  6. Preparation. AppStartupPreparationWorkflow runs ValidateTheme, CreateDeferredStartupRunner, ComposeRibbon, PublishInitialStartupEffects and StartBackgroundStartup. The background task installs the main-window owner provider and attaches the hooks.
  7. Publication. Startup registers the failed-startup cleanup handler first, then the deferred handlers, and publishes the started state. The deferred handlers apply the deferred StartupContribution effects once the main window exists.

A failure in steps 5 to 7 cleans up and returns Failed. A later background-task failure cleans up at the next Idling event.

Tool registration

  1. ToolModuleCatalog.Discover reads the embedded manifests. For each moduleType, it loads the assembly with ToolAssemblyResolver and creates the ToolModule through its public parameterless constructor. It sorts the modules by order, then by type name. Any error stops startup.
  2. AppToolModuleRegistrar stages the settings, services, packs, hooks and ribbon tools of each module, and checks them. A manifest without moduleType adds ribbon tools only, through ToolModuleRibbonRegistrar.
  3. ToolRegistry.MergeFrom checks every internal name and lifecycle hook first, and changes nothing on a conflict.
  4. A ribbon button names its command by assembly path and class name. Without availabilityType, a command that implements IExternalCommandAvailability is its own availability class. ToolCommand does, and requires an active document by default.

Command run

  1. ToolCommand.Execute enters ToolWindowCallbackScope and runs through ISafeExecutor.
  2. CommandContextFactory.CreateContext calls CommandPreflight.Validate before it opens a run scope. Preflight refuses the command if its panel is off, availability refuses it, or an active warning disables it.
  3. IAppRunScopeFactory opens a run scope with the command's profile. InlineUi runs on the Revit UI thread, and QueuedModeless queues work to it from a modeless window.
  4. The command returns Succeeded, or Cancelled after a refusal or a failure, so Revit shows no error dialog. See Revit Execution.

DATA

Item Holds
App service provider Logging, settings, hooks, ISafeExecutor, the tool registry and the ribbon state
Run scope IRevitRunScope, IRevitCallGate, ITransactionRunner and ITransactionGroupService (RevitServiceCollectionExtensions), opened through IAppRunScopeFactory
AppPaths.BaseDir: %APPDATA%\dbtools\, or the DBT_USER_DATA_DIR directory settings.<year>.json, Logs\ and Cache\
System temporary directory (Path.GetTempPath()) Transient files with unique names that ElevationTags, FoundationTags and RecordSet try to delete after use. TMP and TEMP relocate it.

DIAGNOSTICS

Logs\dbtools.Fallback.log below AppPaths.BaseDir holds failures from before logging starts, such as a bad Revit year, and failures that the logger cannot record. The log names a failed startup phase. After a refused DBT_USER_DATA_DIR, records go to Trace only. AppStartupFailurePresenter shows a dialog unless DBT_TEST_RUN_ID is set.
