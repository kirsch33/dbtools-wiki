Architecture Overview

DBTools is a suite of Revit add-in tools. Revit loads one entry assembly, DBTools.dll, built from src/DBTools.App. App loads shared infrastructure from DBTools.Core.dll, stable WPF types from DBTools.Presentation.dll, and each tool from its own assembly in the Tools/ directory.

    Revit[Revit Host] -->|DBTools.addin| App[DBTools.dll / App]
    App --> Core[DBTools.Core.dll]
    App --> Presentation[DBTools.Presentation.dll]
    Presentation --> Handy[DBTools.HandyControl.dll]
    App -->|explicit path: Tools/| Tools[Tool assemblies]
    Core --> RevitAPI[Revit API]

Components

Project Assembly Responsibility
src/DBTools.App DBTools.dll Revit entry point, startup and shutdown, service composition, ribbon, embedded tool manifests
src/DBTools.Core DBTools.Core.dll Shared execution (call gate, transactions, safe execution), settings, logging, tool registry, manifest loading, tool assembly resolution
src/DBTools.Presentation DBTools.Presentation.dll WPF resources, themes, controls and window shells that live for the whole Revit process
build/HandyControl DBTools.HandyControl.dll Renamed build of the vendored HandyControl library
src/Tools/<Category>/<Tool> DBTools.<Tool>.dll One tool: its module, commands, features and views
src/DBTools.Sandbox Sandbox executable Candidate validator and UI development host that runs without Revit

Presentation references only WPF and HandyControl. App, Core and the tools may reference Presentation. See Project References.

Product tree

Each supported Revit year has one directory:

<year>/
├── DBTools.addin
├── DBTools.dll
├── DBTools.Core.dll
├── DBTools.Presentation.dll
├── DBTools.HandyControl.dll
└── Tools/
    └── DBTools.<Tool>.dll        (14 tool assemblies)

The build merges every third-party runtime library into one owner assembly, so the directory contains no other DLLs. The same tree is used by the installer, hosted test staging, Sandbox and Dev Mode. See Assembly Loading Contract and Build Pipeline.

Load contexts

The installed add-in runs in Revit's default AssemblyLoadContext. For hosted tests and Dev Mode, the dbtools-daemon loads the product into its own context (ProductLoadContext or DevModeLoadContext). DBTools creates no load context of its own. App loads each tool assembly into the context that already holds DBTools.dll.

Startup

DBTools.App.Addin.AddinEntry implements IExternalApplication. OnStartup runs these steps in order:

  1. Idle check. If DBTOOLS_DAEMON_REVIT_ROLE is set and the entry assembly is in the default load context, the add-in sets the AppContext key DBToolsDaemon.IdleAddin:DBTools to the entry assembly's location and returns Succeeded without further work. OnShutdown then also returns immediately. This lets the daemon run a Revit that has the installed add-in while it tests its own copy.
  2. Callback scope. AppStartupBoundary (not inlined) enters ToolWindowCallbackScope, which suppresses ExecutionContext flow and sets contextual reflection to the entry assembly's load context.
  3. Runtime. App reads the Revit year from VersionNumber, creates the logging host and the service provider, and publishes them through AppRuntimeAccessor.
  4. Theme validation. ThemeValidator.ValidateOrThrow loads and freezes the theme dictionaries and lays out a probe control tree.
  5. Ribbon. App composes the ribbon from the embedded manifests.
  6. Background startup. App starts the local Revit task host and an asynchronous startup task that installs the Revit main-window owner provider and attaches tool hooks.
  7. Publication. App registers an Idling handler for failed-startup cleanup, then the deferred startup handlers (ApplicationInitialized and Idling), and publishes the started state.

A failure in steps 3 to 6 cleans up what was created and returns Failed. A failure of the background task is cleaned up on the next Idling event. Failures that cannot reach the normal log are written to %APPDATA%\DBTools\Logs\DBTools.Fallback.log with BCL APIs only, so this log works before Core loads.

Tools and commands

Each tool has a manifest.yml that names its assembly, module type, commands and availability types. App embeds all manifests. At startup:

  1. ToolModuleCatalog loads and validates the embedded manifests once.
  2. The App registrar loads each declared assembly with ToolAssemblyResolver.LoadAssembly, which loads only <entry directory>/Tools/<name>.dll.
  3. The registrar creates each module, collects its settings, services, settings packs and hooks, checks ownership, and merges them into the App service collection. Manifests without a module register only ribbon items.
  4. ToolRegistry.MergeFrom validates every incoming tool and hook against the existing registrations before it changes anything, so a conflict leaves the registry unchanged. Duplicate internal names are rejected.
  5. The ribbon refers to each command by its assembly location and full type name.

When a command runs, CommandPreflight checks, before any run scope exists, that its ribbon panel is enabled in Settings, that its availability type allows it, and that no active feature warning disables it. Only then does CommandContextFactory create the run scope with the command's execution profile.

Settings-only and hook-only tools still have a manifest and a module.

Services and scopes

The App service provider holds application-lifetime services: logging, settings, hooks, ISafeExecutor, the tool registry and ribbon state. Each command run, modeless session or test opens a scope that holds the Revit run scope (IRevitRunScope), its IRevitCallGate, ITransactionRunner and ITransactionGroupService. Command, availability and window callbacks enter ToolWindowCallbackScope.

Source layout

Tool source is under src/Tools/<Category>/<Tool>/ with namespace root DBTools.<Tool>. Folders are named for what they own, for example App/, Features/, Domain/, Revit/, Settings/, Assets/ and Tests/. A tool has only the folders it needs. Generic folders such as Helpers, Models or Infrastructure are not used for production code.

Supported years

Desktop Revit 2026.5 and later, and Revit 2027, both target net10.0-windows. build/Distribution/RevitYearContract.cs defines the supported years. APS Design Automation tests use a separate Revit 2026 net8.0-windows profile.

Build and validation

build.sh (Linux, WSL) and build.ps1 (Windows) run build/Build.proj. BuildAll builds, validates and publishes the complete two-year distribution. BuildApp, BuildTests and test.sh build smaller graphs. See Build Pipeline and Test Pipeline.

Distribution validation records the length and SHA-256 of every file in the candidate. These hashes identify what was built and tested. They do not authenticate assemblies at load time.
