Build Pipeline

build.sh (Linux, WSL) and build.ps1 (Windows, PowerShell 7) are the build entry points. Both run dotnet build build/Build.proj -t:<Target> with the pinned SDK; a plain dotnet build build/Build.proj -t:<Target> runs the same graph. The default target is BuildAll, which builds, validates and publishes the complete distribution for Revit 2026 and 2027. BuildAll compiles no test projects.

Synopsis

./build.sh [Target] [parameters]
pwsh -NoProfile -File build.ps1 [Target] [parameters]

Both entries print build/Usage.txt for --help. Option names ignore dashes and case.

Option Short form Description
--Configuration <Release\|Debug> -d, --debug Build configuration; -d selects Debug
--Years <years> -y, --year Revit years, for example 2026 or "2026 2027"
--SkipClean <true\|false> --clean --clean sets SkipClean to false and deletes build output first
--Verbose [true\|false] -v, --verbose; -q, --quiet Terminal verbosity; quiet is the default
--DryRun [true\|false] BuildBundle and BuildInstaller skip the bundle and print the ISCC command instead of running it
--CandidateDistributionPath <dir> --candidate-dist Package an existing promoted tree
--InnoSetupExe <path> Inno Setup compiler for BuildInstaller
--Revit2026Dir <dir>, --Revit2027Dir <dir> Installed Revit, used only for validation
--TestProjects <a,b> Projects for the selected-test targets

An unknown option exits with status 2 before any SDK work. This includes the former NUKE options --target, --skip and --verbosity. build.sh exits with status 3 in a Windows shell (Git Bash, Cygwin) and names build.ps1. Build.proj validates the option values in its Initialize step: a boolean other than true or false fails before any target runs.

Targets

Target Result

BuildAll, StagePortableAcceptanceInput, ValidateDistributionCandidate, PackageSandboxValidationInput, PromoteToDist, BuildBundle and BuildInstaller build the complete distribution. They require the Release configuration and the complete supported year set, which is the default; a -y that omits a supported year fails. ValidateDistributionCandidate and PromoteToDist also require a clean Git worktree. BuildBundle and BuildInstaller with --candidate-dist PATH package an existing promoted tree without building. --clean deletes build output; without it, an incremental BuildAll reuses the existing artifacts. No target switches to another SDK or output root.

BuildAll depends on PromoteToDist, so it runs, in order: Restore, BuildValidationRunner (the Dev Mode policy runner), BuildApp for each year with ValidateProductVersions, VerifyArtifacts, StageDistributionCandidate, WriteCandidateMetadata, StagePortableAcceptanceInput, ValidateDistributionCandidate, ValidateManifestTypes and PromoteToDist.

Examples

./build.sh BuildAll
./build.sh BuildAll --clean
./build.sh BuildApp --Configuration Debug --Years 2026
./build.sh BuildTests
./build.sh BuildSelectedLocalTests --TestProjects DBTools.App.Local.Tests -y 2026
pwsh -NoProfile -File build.ps1 BuildAll

Individual projects also build with plain dotnet build. Their MSBuild graph computes content versions and stages runtime prerequisites, but does not validate or publish a distribution.

Implementation

Each entry maps its options to MSBuild properties, acquires the pinned SDK, initializes the HandyControl submodule when needed, and runs Build.proj. A BUILD test checks that both entries produce the same dotnet build command line. No Build.proj target runs bash or Python, so BuildAll and BuildTests behave the same on Windows. Test execution is done by test.sh.

Build.proj owns the target graph and starts each child dotnet build with its own binary log. The C# code of each target is a BuildPipelineStep in build/Tasks (DBTools.Build.Tasks, net8.0, loaded by the SDK's MSBuild on .NET 10). It owns option validation, Revit reference checks, Inno Setup discovery and the distribution steps. The task assembly is written to .artifacts/build-tasks/<Configuration>/ and recompiles only when its inputs change.

Compilation on every operating system uses the centrally pinned Nice3point Revit API metadata packages with runtime assets excluded. An installed Revit is never a build prerequisite. --Revit2026Dir and --Revit2027Dir name an installation, native or mounted under WSL, for validation only. The staged Revit API files are reference metadata, not an executable runtime. APS Design Automation builds the separate Revit 2026 net8.0 Sentinel test project with its own API provider.

Product output

build/MSBuild/ProductOutput.proj and ProductOutput.targets stage this tree for each year in .artifacts/bin/Release/<year>/net10.0-windows/:

<year>/
├── DBTools.addin
├── DBTools.dll
├── DBTools.Core.dll
├── DBTools.Presentation.dll
├── DBTools.HandyControl.dll
└── Tools/
    └── DBTools.<Tool>.dll

StageProductOutputTask keeps the Tools/ directory and validates each declared owner image. DBTools.addin names DBTools.dll and the class DBTools.App.Addin.AddinEntry. Intermediate runtime inputs can be year-keyed under .artifacts/bin/Release/<year>-runtime-input/. Local test staging copies the year tree recursively into the test output and removes stale top-level tool images. The installer receives the file list from DistributionContract.ProductFiles as the ISCC define ProductFiles and checks each year against it.

Assembly merges

build/Merging/AssemblyMerges.props declares one owner for each merged library; AssemblyMerge.targets runs the merge. Every merged library is private to its owner and absent from the year tree, including Tools/. Each owner is merged once per build; MSBuild Inputs and Outputs skip the merge when nothing changed. The merger writes a deterministic MVID and PDB, and version validation requires each stable assembly (Presentation, HandyControl) to have the same version and SHA-256 in every year.

Owner Merged libraries
DBTools.dll (App) ricaun.Revit.UI
DBTools.Core DBTools.Manifest, YamlDotNet, CommunityToolkit.Mvvm, CSharpFunctionalExtensions, LibTessDotNet, Microsoft.Extensions.DependencyInjection, .Logging, .Options, .Primitives, Serilog.Extensions.Logging
DBTools.Presentation HelixToolkit and SharpDX assemblies, Cyotek.Drawing.BitmapFont, CommunityToolkit.Diagnostics, Serilog, Microsoft.Extensions.Logging.Abstractions, Microsoft.Extensions.DependencyInjection.Abstractions

Serilog is in Presentation, which is never reloaded, because its thread-static state must not enter a collectible load context (dotnet/runtime#134928). The merge details are in Assembly Loading Contract.

Content versions

WPF resolves compiled resource URIs by assembly name and version, and Dev Mode identifies Presentation and HandyControl by full identity and SHA-256 hash. A content version therefore changes exactly when an assembly image can change. build/MSBuild/ContentVersion.targets computes it inside each ordinary compilation from these inputs:

  • source, XAML and resource bytes, with the metadata that names, types and exposes each resource (Link, LogicalName, ManifestResourceName, Access, culture and generator metadata);
  • resolved references: a package by its immutable coordinates, a project or local reference by its bytes, resolved before WPF markup compilation;
  • source generators and the properties visible to them;
  • the emitted assembly attributes, rendered as the SDK generates them, and the framework attribute;
  • the signing key, Win32 manifest and resources, and the effective PathMap;
  • the compiler options that change emitted code or metadata;
  • for a merge owner, the merged project images and the merger code and binaries;
  • for HandyControl, its vendor URI rewrite rules and the rewrite task's source (DBT_ContentVersionRule and DBT_ContentVersionInput). The content hash keys the rewrite, and a missing rewritten file reruns it.

These are not inputs: build scripts and targets, .editorconfig and other analyzer configuration, diagnostic-only analyzers and warning options. Editing them changes no version. No Git commit or tree enters assembly attributes, content inputs or debug metadata. The computation runs inside the project's own compilation: it starts no second MSBuild evaluation and loads no other project. Because the inputs are hashed, resetting a source timestamp cannot hide changed bytes.

A referenced content version is part of the referencing image, so consumers change version with it. An implementation-only change behind an unchanged version does not propagate through compiler references.

The input list is written one entry per line to:

.artifacts/obj/content-version/<Configuration>/<year|shared>-<flavor>/<project>/<framework>/inputs.txt

The SHA-256 of the list is the input hash. Its first six bytes give the four-part assembly version:

4.<u16(bytes 0..1) % 65535>.<u16(bytes 2..3) % 65535>.<u16(bytes 4..5) % 65535>

AssemblyInformationalVersion is <version>+inputs.<hash>. Compare two input lists to see why a version changed. Identical inputs keep the same identity and output timestamps. Content versions apply to Presentation, HandyControl, Core, App and projects that set DBT_IsToolAssembly=true. Other product metadata uses the release version from Version.props.

Checked-in files are named relative to the repository root and artifacts relative to a relocatable root, so a fresh clone gives the same versions. Repository source and intermediate PDB documents use the path prefix /_/dbtools/; transformed vendor documents use /_/dbtools/vendor-build/. SourceLink revision stamping is off. A WPF temporary project hashes its parent's input list, so local-type identities in BAML carry the final version.

The staged year trees carry the version evidence: each first-party image has its content version and input hash, the version must derive from that hash, and a stable image must be byte-identical in every year. The staging step reads them before it validates the compiled resource URIs.

Candidate validation and promotion

Distribution validation walks each year tree recursively. It requires the exact relative file set with Tools/ as the only directory, and checks PE identities, source-derived versions, first-party reference identities, framework references, and the length and SHA-256 of every file. It also checks the add-in entry, commands, availability types, manifests, resources and ownership. A missing, extra, misnamed, misplaced or stale file fails the candidate.

Manifest validation scans every manifest.yml under src/ and resolves module, command, availability and design-time ViewModel type names against the compiled images of each year. Every declared owner must resolve to Tools/<owner>.dll. BuildAll and ValidatePrePush run it.

ValidateDistributionCandidate prints one Dev Mode preflight line per year:

Revit <year> Dev Mode preflight: <n> failures, <m> warnings; outcome=<x>

Promotion requires a clean Git worktree (tracked and untracked files) with a resolved HEAD. Three records describe a distribution:

  • The build metadata (build.json) records the years, frameworks, the distribution fingerprint, the Git commit and tree IDs, the source versions, the hash of each product file and the Protocol package pin.
  • The portable acceptance receipt, written by ValidateDistributionCandidate, records for each year the validated files, the Revit reference descriptors and the Dev Mode preflight result.
  • The promotion receipt, .artifacts/dist/Release/promotion-receipt.json, embeds the acceptance receipt with the source snapshot and the distribution fingerprint. It contains no temporary staging paths; consumers validate it against the published tree.

Promotion validates the staged candidate, its fingerprint, the exact year trees and the receipt. It then deletes the published .artifacts/build.json, replaces .artifacts/dist/Release with the validated tree, and writes build.json last. Read the distribution only after the build command exits successfully.

When promotion prepares the new tree, each declared file whose SHA-256 equals the file at the same path in the current .artifacts/dist/Release becomes a hard link to that file; new and changed files are copied. An unchanged file therefore stays the same file across promotions, and a virus scanner that has scanned it (Windows Defender on a Dev Mode host) does not scan it again. If the platform refuses a link (different file system, no hard-link support, permission error), promotion logs the reason once at low importance and copies that file and all remaining files. No step writes into a published file. Point Dev Mode at .artifacts/dist/Release/<year> directly; a copy is a set of new files that the scanner scans again.

Hosted test inputs

Hosted staging builds one complete product tree for the selected year and includes it with relative paths unchanged, including the 14 tool assemblies in Tools/. Test assemblies, NUnit and adapter files, and companions are separate inputs. The input cache checks relative path, identity, length and hash before the daemon request is written.

Test restore roots are per year: Local years restore separately, and Design Automation shares the 2026 root. The Pure root restores every Pure project against $(DBT_PureRevitYear) owners through static graph restore. NuGet keys package specifications by project path, so one root never mixes owner variants. See Test Pipeline.

Pinned SDK

build/DotNet/sdk.sh selects the SDK version from global.json. If no installed dotnet has that SDK, it uses the private root ~/.dotnet/pinned-sdk-<version>. A system dotnet with the pinned SDK is used as is.

A build needs only the SDK. A net8.0 test host (the APS Design Automation Sentinel) also needs the .NET 8 runtime. sdk.sh pins that runtime version, because global.json cannot, and installs it only when such a host runs: test.sh requests it, or run bash build/DotNet/sdk.sh --test-host-runtime. On a system dotnet without the .NET 8 runtime, a net8.0 test host uses the private root.

A package in the private root is valid only when its marker file, .dbt-complete-<package>-<version>, names its archive. To install a package, sdk.sh:

  1. checks the archive against the SHA-512 in Microsoft's release metadata;
  2. extracts it into a staging directory beside the root;
  3. renames the version directories into place;
  4. writes the marker.

A version directory without a valid marker is replaced from the verified archive; one that already matches stays. The lock <root>.lock serializes installs across builds and worktrees, and a build that waited for the lock checks the markers again before it installs anything. The Linux installer requires Python 3.10 or later.

build.ps1 uses the same root, SHA-512 check, marker and lock for the SDK without Python. It downloads the release metadata's dotnet-sdk-win-<arch>.zip and replaces a root without a valid marker as a whole. It installs no test-host runtime.

Build servers

DBT_BUILD_SERVERS sets the server mode for every wrapper invocation (build.sh, test.sh, the lane helpers and their child builds). DBT_MSBUILD_MAX_CPU_COUNT sets the graph build parallelism (default 2); the wrappers validate it and Build.proj passes it to its child builds. build.sh runs Build.proj itself without the MSBuild server; each child dotnet build uses the selected mode.

  • 1 (default): the invocation owns one compiler server and one MSBuild server. Its scope ID, dbtools-scope-<owner pid>-<run id>, is the compiler pipe name, and <scope id>-msbuild is the MSBuild handshake salt. On every trapped exit, each server gets a shutdown request with a 30 s timeout; then every process the invocation still owns is terminated, the compiler by its exact -pipename: argument and MSBuild nodes by the exact salt in their environment. No process is matched by name. A starting invocation stops dbtools-scope servers whose owner process no longer exists; servers of a live owner are never touched. In one measurement on an 8 GB host, a clean two-year BuildApp took 229 s with the servers and 547 s without them, and used about 1.4 GB more peak memory.

  • 0: no compiler server and no MSBuild server (UseSharedCompilation=false). Use this on hosts that admit builds by free memory.

build.ps1 always uses mode 0, because the ownership checks read Linux /proc. Node reuse is off in both modes. Outside a wrapper, Directory.Build.props keeps the compiler server off. UseSharedCompilation is not a content-version input.

build/Testing/check-build-server-lifecycle.sh <second-checkout> is a manual test with the real SDK. It covers a normal exit, a failed build, SIGTERM, SIGKILL followed by the next build's sweep, and a concurrent owner in another checkout.

Logs

Each run writes to .artifacts/build/<YYYYMMDD-HHmmssfff>-<pid>/, named by build.sh or build.ps1 (by Build.proj for a plain dotnet build). The folder holds the full plain-text console.log at detailed verbosity and one binary log per child build. When the build ends, successfully or not, the entry writes a completed marker and copies the log to .artifacts/build/console.log.

Each run first prunes old folders. It keeps the ten newest completed folders, deletes folders that contain only a marker, deletes unmarked folders after 24 hours without activity, and skips folders whose process is still running. Test builds write .artifacts/build/test-matrix.binlog, replacing the previous one.

The terminal shows per-step progress, errors, warnings, the Dev Mode preflight lines and the MSBuild summary. --verbose adds the child build output. The file log is always detailed.

HandyControl

HandyControl is built from the vendor/HandyControl submodule through build/HandyControl/DBTools.HandyControl.csproj. The project imports the four upstream shared .projitems files and the upstream resources, writes transformed intermediate copies that use the DBTools assembly name and versioned pack URIs, and compiles Shared/Themes/Theme.xaml as the theme. The upstream project-root Theme.xaml generated by its PreBuild step is not an input. A missing submodule, resource or transform input fails with its path.

Concurrency

Run one build or test command per worktree at a time. Concurrent builds need separate BaseArtifactsDir roots; sharing compiler or WPF output between roots is not supported. A nested test command reuses the build-server scope of its parent. build.sh, build.ps1 and test.sh take no lock and do not check free memory.

Continuous integration

The CI and Documentation workflows run only on manual dispatch, not on pushes or pull requests. CI mode build runs BuildAll; mode build-test also builds and runs the selected tests. The release workflow, triggered by a published release, builds and promotes the distribution and bundle on Linux, then runs only the Inno Setup compiler on Windows. The self-hosted Windows test runner consumes compiled test artifacts through test.sh and does not build the product.

Source maps and CANON

These checks are run by the pre-push hook and CI, not by any build target:

  • python3 .agents/work/canon_source_maps.py writes one MAP.md beside each manifest. A map lists the current source tree, including untracked files that are not ignored, and labels test folders as test mirrors. --check recomputes the maps byte for byte (UTF-8, LF) and fails if one is stale.
  • python3 .agents/work/canon_source_fidelity.py --gate checks folder and namespace agreement, type and file identity, repeated declarations, vocabulary and unresolved rulings for the declared source roots.

Troubleshooting

Problem Action
dotnet or the pinned SDK is missing Run bash build/DotNet/sdk.sh.
The .NET 8 runtime for the Design Automation Sentinel is missing Run bash build/DotNet/sdk.sh --test-host-runtime.
HandyControl output is missing Run the build from a Git checkout with network access, so the entry can initialize the submodule.
WPF designer output collides Build through the repository targets, so _wpftmp gets its own intermediate path.
MSBuild task DLLs stay locked A wrapper killed past its exit trap leaves its servers running until the next wrapper invocation stops them. Run the command again.
A focused build is slow Build the project or use BuildApp; keep BuildAll for the full distribution.
