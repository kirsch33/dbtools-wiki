Theme System

DBTools.Presentation.dll holds every compiled WPF resource of the product: the theme dictionaries, stable controls and window shells. It stays loaded for the life of the Revit process. Tool views are raw XAML that Presentation parses at run time, so App, Core and the tool assemblies contain no BAML and no .g.resources. Each window merges the theme into its own resources, never into Application.Resources, so DB Tools does not change the appearance of other add-ins.

Assembly roles

Assembly Compiled WPF content
DBTools.Presentation Theme dictionaries, stable windows and controls, tool behaviors and converters under Tools/<TOOL>/, the merged Helix theme, and the settings views of DialogSuppression, ElevationTags, FoundationTags and JoistGirderWeight (linked from those tool folders)
DBTools.HandyControl The HandyControl skins and themes
DBTools.Core None. Window lifecycle, error boundaries, registry, commands and runtime hosts can be reloaded
Tool assemblies None. Tool views are embedded as raw XAML

Presentation keeps explicit Page, Compile and EmbeddedResource items (EnableDefaultPageItems=false). The linked tool settings views keep their tool namespaces, for example DBTools.DialogSuppression.Settings.Views; the tool projects remove them from their own Page items.

Tool views

A tool embeds each view as an EmbeddedResource with the logical name DBTools.ToolViews.<TOOL>.<View>.xaml. ToolWindowFactory.Create (Core) opens a view in these steps:

  1. ToolWindowHost.Create (Presentation) creates a stable shell, ToolWindowModalShell or ToolWindowModelessShell.
  2. The shell initializer runs before the view is parsed. The default is WindowInitializer.Initialize or InitializeModeless, which applies the theme, binds the owner window, registers the progress overlay and installs the error boundary and logging.
  3. ToolWindowXaml.LoadElement parses the raw view inside ToolWindowReflectionScope, and the view and shell receive the tool's view model as DataContext.
  4. The factory registers the session in ToolWindowRegistry.

The caller shows the window with session.ShowDialog() or session.Show() and gets named controls with session.Require<T>(name). The Settings, Alert, Logger and notification banner windows are raw resources in Presentation and use the same loader; so do tool template dictionaries such as the VTC diff templates and the SGT opening view. For these windows Core keeps the state, commands and lifecycle and event handling; the controls need no typed constructor from a reloadable assembly and do no type discovery at run time.

Retirement tears down bindings, automation roots, resources and callbacks. Core lifecycle handlers are released through BehaviorState and session cleanup before the shell closes. A custom shell initializer releases its own handles.

Raw views name only framework types or public stable Presentation types and merge the theme through Presentation's ResourceUri markup extension before they use static theme keys. Tool content uses explicit keyed templates. SGT's opening and girt grids use stable behaviors over tool row state. ERFT and SGT pass immutable scene data to the stable 3D viewport, which owns camera, material, picking and device state (see Structural Preview).

Theme dictionaries

The root dictionary is:

/DBTools.Presentation;V<PresentationVersion>;component/Resources/Theme.xaml

<PresentationVersion> is the content version of the Presentation assembly (see Build Pipeline). The root merges, in this order:

  1. /DBTools.HandyControl;V<HandyControlVersion>;component/Themes/SkinDark.xaml
  2. /DBTools.HandyControl;V<HandyControlVersion>;component/Themes/Theme.xaml
  3. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Tokens.xaml
  4. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Brushes.xaml
  5. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Converters.xaml
  6. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Controls.xaml
  7. /DBTools.Presentation;V<PresentationVersion>;component/Resources/DataGrid.xaml
  8. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Menus.xaml
  9. /DBTools.Presentation;V<PresentationVersion>;component/Resources/Components.xaml

ThemeResourceLoader (Core) checks this order. At startup ThemeValidator.ValidateOrThrow registers the pack URI scheme, loads each dictionary separately and freezes its freezables, loads the root and checks its merged dictionaries, and then measures and arranges a probe tree of standard controls. A failure stops startup; see Troubleshooting.

Resource URIs

Every compiled resource URI contains the assembly's version. A changed stable assembly therefore has a new identity, and WPF cannot select an older copy of Presentation or HandyControl that an earlier DB Tools version has already loaded. Presentation URIs use the Presentation version, and HandyControl URIs use the HandyControl version.

The component URI is relative, so Application.LoadComponent does not need the pack scheme to be registered.

  • Use ResourceUri.CreateResourceUri for Application.LoadComponent, dictionary sources and the dictionary markup extensions.
  • Use ResourceUri.CreateAbsoluteResourceUri for images and icons created in code without a WPF base URI. It registers the pack scheme and returns pack://application:,,,/<assembly>;V<version>;component/<path>.

WindowInitializer loads the window icon with BitmapCacheOption.OnLoad inside its warning boundary; otherwise WPF can defer the file lookup until it creates the window handle.

XAML namespaces

XAML outside Presentation refers to stable types with clr-namespace:...;assembly=DBTools.Presentation. XAML compiled by Presentation uses the namespace form without assembly=. This keeps the BAML compiler from resolving Presentation types through a reloadable assembly.

BAML assembly versions

The BAML assembly table must contain the final assembly version, because WPF resolves local markup extensions through that table separately from the outer pack URI. Keep SDK assembly-info generation on in WPF temporary projects. With it off, BAML references Version=0.0.0.0; if an older Presentation is already loaded in the default context, the CLR can satisfy that request with the older copy. That copy lacks HandyControlResourceUriExtension, and WPF throws NotImplementedException before it opens the HandyControl dictionaries. WPF's local-assembly fallback runs only when loading throws, so a successful bind to the older copy bypasses it. See .NET 10 WPF assembly and type resolution and CoreCLR version compatibility.
