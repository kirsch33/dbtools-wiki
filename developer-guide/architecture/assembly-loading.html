Assembly Loading Contract

The product is a tree of ordinary files: one entry assembly, two top-level libraries and one assembly per tool. The installed add-in loads in Revit's default AssemblyLoadContext. Revit-hosted tests and Dev Mode load the product into a context that the dbtools-daemon creates. In every host, App loads each tool assembly by explicit path into the context that holds dbtools.dll, and Revit calls each command by its assembly path and class name.

Installed layout

Each supported year has one directory of ordinary files. This is the product tree that the installer, Revit-hosted test staging, Sandbox and Dev Mode use:

dbtools.addin names dbtools.dll and the class dbtools.App.Addin.AddinEntry. dbtools.dll contains the entry point and host infrastructure and no tool code. WPF needs the physical location of Presentation, so it stays at the top level. Settings reads the product version from dbtools.version in its own Revit year directory.

Merged libraries

Every third-party runtime library is merged into one owner assembly; no third-party DLL is staged. build/Merging/AssemblyMerges.props declares the merges:

  • Core owns the manifest parser, YamlDotNet, CommunityToolkit.Mvvm and CSharpFunctionalExtensions.
  • SGT owns LibTessDotNet privately. The double-precision assembly is not merged.
  • Presentation owns the Helix and SharpDX closure, Serilog, its logging provider and the Microsoft.Extensions logging, dependency injection, options and primitives libraries.

SGT and ERFT declare CSharpFunctionalExtensions directly. Desktop builds share its public types through Core. Portable dependencies retain their NuGet identities.

Installed Revit loads Presentation in the default AssemblyLoadContext. In Dev Mode, the daemon loads it in a non-collectible stable context and shares it across generations.

LoggerFactoryScopeProvider and SerilogLoggerProvider keep their scopes in AsyncLocal fields in Presentation. Serilog's thread-static state also lives there. SerilogStack coordinates the process-wide logger across Core generations. App and Core bind to the merged logging types through dbtools.Presentation. Standalone package copies used by other add-ins have different assembly identities.

Presentation owns the ambient Revit application slot (RevitApplicationContextSlot) and the asynchronous call timing state (RevitCallGateActionTiming). Their slots hold stable types across Core generations.

A declaration's Include is the assembly name. A NuGet package that supplies that assembly uses the same name as its package ID.

MSBuild passes each merge its inputs as items: the resolved runtime asset of a package, or the output of a project. The merge copies its evaluated reference files into a temporary reference directory. ILRepack searches only that directory and resolves framework identities only from those files, so other package or compiler-output files and the runtimes installed on the build host cannot change the result. MSBuild Inputs and Outputs, including the owner's project.assets.json, decide when a merge reruns. The task deletes its temporary files afterwards.

MergeReferenceGuard checks merged images against the evaluated references. It rejects unresolved types or members, newer reference versions and references to assemblies that the merge removed.

App host references

App compiles against the selected Revit year's API references. RibbonNativeAccess reads the native Autodesk.Windows ribbon panel and item from their Revit API wrappers.

Entry and idle acknowledgement

AddinEntry has a public parameterless constructor for Revit. OnStartup first calls AddinIdle.TryAcknowledge. If DBTOOLS_DAEMON_REVIT_ROLE is set to any nonempty value and the entry assembly is in exactly AssemblyLoadContext.Default, it sets the AppContext data dbtools-daemon.IdleAddin:dbtools to the entry assembly's file location and returns Succeeded before any runtime, ribbon, logging or tool work. OnShutdown returns Succeeded immediately for that instance.

Otherwise startup applies DBT_USER_DATA_DIR with AddinUserData, which uses BCL APIs and constants only. If the directory is refused, the entry formats and reports the reason before loading product dependencies, then returns Failed. A validated directory allows AppStartupBoundary.Start, a non-inlined method, to start the App lifecycle inside ToolWindowCallbackScope. Startup, shutdown and ribbon failures that cannot reach the normal log are written to Logs\dbtools.Fallback.log below AppPaths.BaseDir with BCL APIs only.

Tool resolution

ToolAssemblyResolver.LoadAssembly(rootAssembly, assemblyName) loads a manifest-declared assembly. The name must be a simple assembly name: it does not end with .dll in any case and contains no /, \, , or :. Other names throw ArgumentException before any file lookup. If the name equals the root assembly's name, the root is returned. Otherwise the resolver:

  1. requires a file-backed root assembly;
  2. resolves <root directory>/Tools/<assemblyName>.dll and requires the file;
  3. reads the file's assembly name and requires the declared simple name;
  4. returns an assembly of that name already loaded in the root's context, if its full identity and location match the file; a different identity or location is an error;
  5. otherwise loads the file with that context's LoadFromAssemblyPath.

The resolver does not search other contexts, install an AppDomain resolver or create a load context.

The ribbon registers each command by its assembly location, full class name and availability type name. Availability is implemented by the command's own assembly. Command and availability callbacks enter ToolWindowCallbackScope, which suppresses ExecutionContext flow and sets contextual reflection to the command's load context.

Hosted tests and Dev Mode

The daemon creates ProductLoadContext for hosted tests and DevModeLoadContext for Dev Mode. App loads each declared tool from Tools/ into that context; Dev Mode does not probe other subfolders. Presentation stays loaded for the life of the process. App, Core and the tool assemblies can be reloaded, as the host decides. DevModeCollectibleUnloadTests composes such a generation on Linux and requires it to unload; see Testing Tools.

A Dev Mode fleet job loads the Dev Mode scenario into a separate test context in the Revit process for each generation. The scenario references the testing bridge and exercises the product through Revit, verified ribbon proxies, windows and the log in the private data directory. The scenario references no dbtools product assembly and holds no type or object from a product generation.

Linux lifetime checks

The BUILD lane checks reloadable product code for common Dev Mode lifetime failures against both supported Revit years.

  • The resolver fixture inventories AssemblyResolve and AssemblyLoadContext.Resolving registrations, plus AssemblyLoadContext.Load overrides, across product source under src. Each inventoried resolver has a named safety exercise. The exercises use missing names, unusual versions (including 1.0.0 and 0.0.0.0), culture and public-key differences, and dbtools-owned names. A resolver returns a matching assembly or null; it does not throw.
  • The raw XAML audit scans product XAML under src, including Presentation. It checks each binding path segment against a dependency property or a property on a type that implements INotifyPropertyChanged. A OneTime binding does not require change notifications. The audit resolves sources from code-behind data contexts, d:DataContext, DataTemplate.DataType, RelativeSource, and ElementName when their types are known. It reports unresolved counts by source group and sample file locations. An unresolved binding remains unverified and does not count as a pass.
  • Reloadable code cannot call Window.Show or Window.ShowDialog directly. Registered tool windows go through ToolWindowRegistry.
  • Revit application event subscriptions go through Core's hook lifecycle. The contextual ribbon selection controller is part of that lifecycle. A suppression for DBTDEV002, DBTDEV003, or RS0030 must name its rule, include a non-empty reason, and apply to one member. Assembly, module, namespace, and pragma suppressions fail the BUILD check. A diagnostic severity override or NoWarn entry that disables or downgrades these rules also fails.
  • Reloadable code cannot call Dispatcher.BeginInvoke, Dispatcher.InvokeAsync, or Dispatcher.Invoke directly. It also cannot call the matching DispatcherExtensions.BeginInvoke or DispatcherExtensions.Invoke methods. It uses Core's WpfDispatcher registry. The rule does not cover DispatcherTimer.
  • See the dispatcher operation retirement contract.

Sandbox

Sandbox runs one new process in the default context for each candidate year. Its entry point uses only BCL types. It validates the candidate and loads its root assemblies before starting WPF through a non-inlined method. Sandbox loads tool assemblies from Tools/ on demand and exits after headless validation. See Sandbox Validator.

Distribution hashes

Distribution validation checks the exact relative file set, PE identities, source-derived versions, first-party reference identities, file lengths and SHA-256 hashes. The hashes identify the staged candidate. Nothing checks them when an assembly loads.
