Assembly Loading Contract

The product is a tree of ordinary files: one entry assembly, three top-level libraries and one assembly per tool. The installed add-in loads in Revit's default AssemblyLoadContext. Revit-hosted tests and Dev Mode load the product into a context that the dbtools-daemon creates. In every host, App loads each tool assembly by explicit path into the context that holds DBTools.dll, and Revit calls each command by its assembly path and class name.

DBTools.addin names DBTools.dll and the class DBTools.App.Addin.AddinEntry. DBTools.dll contains the entry point and host infrastructure and no tool code. WPF needs the physical location of Presentation and HandyControl, so they stay at the top level.

Merged libraries

Every third-party runtime library is merged into one owner assembly; no third-party DLL is staged. build/Merging/AssemblyMerges.props declares the merges:

  • App owns ricaun.Revit.UI.0.9.0.
  • Core owns the manifest and YAML parser, MVVM, functional, dependency injection, logging, options and primitives libraries, and Serilog.Extensions.Logging.
  • SGT owns LibTessDotNet privately. The double-precision assembly is not merged.
  • Presentation owns the Helix and SharpDX closure, Serilog, and the public dependency injection and logging abstractions.

SGT and ERFT declare CSharpFunctionalExtensions directly. Desktop builds share its public types through Core. Portable dependencies retain their NuGet identities.

Serilog is in Presentation, which is never reloaded, because its thread-static state must not enter a collectible load context (dotnet/runtime#134928).

A declaration's Include is the assembly name. The optional PackageId names a NuGet package whose name differs; ricaun uses PackageId="ricaun.Revit.UI" because its assembly name contains a version.

MSBuild passes each merge its inputs as items: the resolved runtime asset of a package, or the output of a project. The merge copies its evaluated reference files into a temporary reference directory. ILRepack searches only that directory and resolves framework identities only from those files, so other package or compiler-output files and the runtimes installed on the build host cannot change the result. MSBuild Inputs and Outputs, including the owner's project.assets.json, decide when a merge reruns. The task deletes its temporary files afterwards.

App host references

The pinned ricaun.Revit.UI.0.9.0 assembly references Revit 27.0.4, also when App is compiled for Revit 2026. The App merge therefore binds these host references to the exact identities of the selected year during the final Cecil normalization:

RevitAPI;RevitAPIUI;AdWindows;UIFramework

Only App does this. MergeReferenceGuard then resolves every TypeRef, MemberRef and attribute type name with Cecil against the selected year's evaluated references. It rejects a missing type or member, a referenced version higher than the evaluated one, and any reference to an assembly that a merge removed. The Nice3point UIFramework reference is part of the Revit reference metadata used for this check; it is not shipped.

Entry and idle acknowledgement

AddinEntry has a public parameterless constructor for Revit. OnStartup first calls AddinIdle.TryAcknowledge. If DBTOOLS_DAEMON_REVIT_ROLE is set to any nonempty value and the entry assembly is in exactly AssemblyLoadContext.Default, it sets the AppContext data DBToolsDaemon.IdleAddin:DBTools to the entry assembly's file location and returns Succeeded before any runtime, ribbon, logging or tool work. OnShutdown returns Succeeded immediately for that instance.

Otherwise startup enters AppStartupBoundary, a non-inlined method, which starts the App lifecycle inside ToolWindowCallbackScope. Startup, shutdown and ribbon failures that cannot reach the normal log are written to %APPDATA%\DBTools\Logs\DBTools.Fallback.log with BCL APIs only.

Tool resolution

ToolAssemblyResolver.LoadAssembly(rootAssembly, assemblyName) loads a manifest-declared assembly. The name must be a simple assembly name: it does not end with .dll in any case and contains no /, \, , or :. Other names throw ArgumentException before any file lookup. If the name equals the root assembly's name, the root is returned. Otherwise the resolver:

  1. requires a file-backed root assembly;
  2. resolves <root directory>/Tools/<assemblyName>.dll and requires the file;
  3. reads the file's assembly name and requires the declared simple name;
  4. returns an assembly of that name already loaded in the root's context, if its full identity and location match the file; a different identity or location is an error;
  5. otherwise loads the file with that context's LoadFromAssemblyPath.

The resolver does not search other contexts, install an AppDomain resolver or create a load context.

The ribbon registers each command by its assembly location, full class name and availability type name. Availability is implemented by the command's own assembly. Command and availability callbacks enter ToolWindowCallbackScope, which suppresses ExecutionContext flow and sets contextual reflection to the command's load context.

Hosted tests and Dev Mode

The daemon creates ProductLoadContext for hosted tests and DevModeLoadContext for Dev Mode. App loads each declared tool from Tools/ into that context; Dev Mode does not probe other subfolders. Presentation and HandyControl stay loaded for the life of the process. App, Core and the tool assemblies can be reloaded, as the host decides.

Sandbox

Sandbox runs one new process in the default context for each candidate year. Its entry point uses only BCL types: it validates the candidate, loads the top-level product files and the Tools/ assemblies from their paths, and then starts WPF through a non-inlined method. The process exits after validation, so no candidate assembly remains loaded for the next year. See Sandbox Validator.

Distribution hashes

Distribution validation checks the exact relative file set, PE identities, source-derived versions, first-party reference identities, file lengths and SHA-256 hashes. The hashes identify the staged candidate. Nothing checks them when an assembly loads.
