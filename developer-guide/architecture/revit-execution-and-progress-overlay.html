Revit Execution and Progress Overlay

DB Tools runs all Revit API work through a call gate, inside a run scope that each command, modeless session or test owns. Tool windows report long operations through the progress overlay. This page owns the design of run scopes, call gates, transaction services and the progress overlay. DBTools.Core describes the rest of the Core library and its source folders.

Command entry

ToolCommand (src/DBTools.Core/Tools/Commands/ToolCommand.cs) is the base class of every Revit command. Its public Execute runs the command body inside ISafeExecutor and gives the protected RunAsync hook one owning CommandContext; see ToolCommand for the API. Command subclasses resolve services from ICommandContext. Its base interface IAppRunScope exposes the scope's RevitRunScope and Resolve<T>(). A feature that owns a window composes ToolWindowFactory and calls CreateModal for an IModalToolWindowSession with ShowDialog/HideForPick, or CreateModeless for an IModelessToolWindowSession with Show. The session owns the reflection scope and the window's retirement.

An expected refusal throws SafeExecutionRefusedException with a reason for the user. SafeExecutor then returns SafeExecutionStatus.Refused, with no failure surface and no exception diagnostics. SafeExecutionRefusalReporter shows a Warning banner, which writes the one Warning log entry; an execution without a banner logs [Refused] {Name}: {Message}. ToolCommand returns Revit Result.Cancelled for a refusal and for a failure. An unexpected exception writes Error diagnostics and shows an Error banner.

Run scopes

App composition (AppServiceProviderFactory) registers IAppRunScopeFactory with the Core implementation AppRunScopeFactory. CommandContextFactory calls Create(UIApplication, AppRunScopeProfile). The factory selects the call gate for the profile, constructs RevitRunScope, and returns the concrete AppRunScope, which owns scoped service resolution, its IRevitRunScope and disposal. Construction and disposal keep the primary failure, attempt every owned cleanup step and report further cleanup failures in order.

Profile Call gate Use
InlineUi (default) InlineRevitCallGate Modal commands and daemon-hosted Revit automation that already run on the Revit UI thread.
QueuedModeless QueuedRevitCallGate Modeless tool windows and long workflows that must queue Revit API work to the UI thread through the service root's RevitCallGateTask.

A tool selects its profile through RunProfile in its manifest; ToolRegistration uses InlineUi when none is given.

IRevitRunScope owns the UIApplication, the call gate, document access and disposal. Transaction services are scoped registrations, resolved with Resolve<T>() on IAppRunScope or ICommandContext.

public interface IRevitRunScope : IDisposable
{
    UIApplication UIApplication { get; }
    IRevitCallGate CallGate { get; }
    UIDocument GetActiveUiDocument();
    Document GetActiveDocument();
    Document GetVerifiedActiveDocument(Document expectedDocument, string? context = null);
}

A consumer that keeps its launch document calls GetVerifiedActiveDocument(...). The run scope rejects an invalid expected or active document and requires matching DocumentSessionKey values before it returns the active document.

RevitServiceCollectionExtensions registers only the Revit-scoped run-scope access, the call gate and the transaction services. The App composition root registers the Revit task, IAppRunScopeFactory, safe execution, command preflight and the command context services.

Revit task

Each App service root owns one RevitCallGateTask, the ExternalEvent host that queued gates schedule through. AppServiceProviderFactory registers it as a singleton that is created on first request, with ILogger<RevitCallGateTask>, and registers Func<IRevitCallGateTask>, which returns the task of the same root. Registration creates no ExternalEvent.

  • Startup resolves the task on the Revit main thread after the synchronous preparation steps and passes it to AppLocalRevitTaskLifecycle.Start, which publishes it in RevitCallGateTaskHost. Startup keeps the returned task in its AppStartupOwnership. Shutdown retires and disposes that task before the service root and resets RevitCallGateTaskHost only while it still publishes that task.
  • AppRunScopeFactory, HookHost, ContextualRibbonRuntime and the Foundation Tags update workflow receive the provider. They call it only when they build a QueuedRevitCallGate: a QueuedModeless run scope, a ViewActivated hook attachment or rollback, a contextual ribbon UI call, or the selection actions of an update result. An InlineUi run scope does not resolve the task.
  • A gate keeps the task it was built with. After that generation retires, a new queued call completes canceled and does not reach a replacement task. A provider called after its root is disposed throws ObjectDisposedException.
  • RevitCallGateTaskHost holds the published task for RevitCallGateApiContext, which reads its known application. Call gates do not read it.

Call gates

IRevitCallGate is the single entry point for Revit API access. It runs synchronous callbacks on the Revit UI thread. Revit API calls outside the call gate can raise invalid-context exceptions or break UI-thread rules.

public interface IRevitCallGate
{
    bool InGate { get; }
    bool RunsInline { get; }
    Task<T> RunAsync<T>(Func<UIApplication, T> work, CancellationToken ct = default,
        RevitCallGateMode mode = RevitCallGateMode.Auto);
    Task RunAsync(Action<UIApplication> work, CancellationToken ct = default,
        RevitCallGateMode mode = RevitCallGateMode.Auto);
}
Mode Behavior
Auto Run inline when the caller already has a gate context; otherwise queue through the owned ExternalEvent host.
ForceQueue Always queue through the owned ExternalEvent, in a later turn. The inline gate rejects it with ContextUnavailableException.
  • InlineRevitCallGate(UIApplication) runs delegates immediately on the Revit UI thread with the supplied application. Modal commands use it.
  • QueuedRevitCallGate(IRevitCallGateTask, ILogger) schedules the callback through the Revit task it receives.
  • RunsInline is true when every accepted callback runs synchronously inside the calling API turn: true for InlineRevitCallGate, false for QueuedRevitCallGate, also while a nested Auto call runs inline. A decorator forwards the value of its inner gate. It grants no API authority and does not describe the current InGate state. SGT's modal session and GM's Commit Review modal session read it instead of the concrete gate type.
  • QueuedRevitCallGate requires a Revit task and an ILogger; RevitCallGateTask requires an ILogger. A missing argument is a construction error.
  • The active UIApplication, the queued-gate depth and the Revit-test depth are internal scoped state. QueuedRevitCallGate owns the queued and test scopes; RevitRunScope owns its application context token. Every scope restores the exact previous value, and a repeated disposal does nothing.

Delegate admission

Admission is synchronous and runs before the gate validates the API context or schedules anything. Keep asynchronous workflows outside the gate and make in-gate delegates synchronous:

await _gate.RunAsync(app =>
{
    // Revit API work here (synchronous only)
    return true;
});
  • Every member of an Action invocation list is checked for an async state machine, so an async void action is rejected.
  • A delegate whose result type is Task, Task<T>, ValueTask or ValueTask<T>, including nullable ValueTask, is rejected.
  • A multicast result delegate with a reference result type is rejected, because ordinary multicast dispatch exposes only the last return value.
  • After invocation, a reference-typed result gets a runtime Task/ValueTask check, which also finds interface-typed Task and boxed ValueTask values.
  • Custom awaiter structs are not detected.

Sources: src/DBTools.Core/Revit/Execution/CallGate/{CallGateDelegateValidator,InlineRevitCallGate,QueuedRevitCallGate,RevitCallGateTask,RevitCallGateTaskQueue}.cs.

API-context admission

RevitCallGateApiContext.IsActive decides whether the current code has Revit API context.

  • Known native entry points use the internal synchronous Enter scope.
  • An untracked call first checks the Revit dispatcher thread, then creates and immediately disposes an unraised ExternalEvent with a stateless no-op handler. Worker threads return false before the probe.
  • Every untracked call probes again. No result is cached across turns.
  • Current exposes a known UIApplication only while the context is active. An ambient application reference does not grant API context.

The public UIApplication constructor requires ApplicationServices.Application; there is no public conversion from UIControlledApplication.ControlledApplication. If startup has not received a UIApplication, queued work gets one from the real ExternalEvent callback. No private-field reflection is used.

The probe creates a new event instead of adding and removing a handler on a Revit event. It does not change the subscriber collection of the current event and does not write a document, so it is legal in Idling, ViewActivated, DocumentChanged and updater callbacks. Admission does not permit an API that a particular callback forbids; callers must obey read-only and dynamic-update restrictions.

The 2026 and 2027 API references list the Create signature and the null-handler exception, but not the outside-context exception. An Autodesk forum thread describes that runtime check and the difference between UI-thread access and API context.

The probe does not identify which add-in owns a callback. Inside another add-in's main-thread API callback it returns true, and DB Tools runs inline without its own scope. Callbacks that DB Tools owns enter an explicit synchronous UIApplication scope; later continuations must probe or queue again.

The scope is a ref struct, so a caller cannot hold it across an await. Its shared lifetime lets a wrong-thread disposal revoke the context before the misuse is reported. Enter is internal. The build contract suite (RevitCallGateApiContextEntryContractTests) inspects the compiled production assemblies and allows Enter only in ToolCommand.ExecuteCore, the explicit IExternalEventHandler.Execute of RevitCallGateTask, the contextual ribbon SelectionChanged and edit-event callbacks, the ViewActivated dispatcher, the FoundationTags Idling retry tick and InlineRevitCallGate after its own thread and IsActive check. Only Enter constructs the scope. The suite checks call sites in the build; it does not authenticate callers at run time. Global Mapper (GM) has access for synchronous-delegate validation only and does not enter scopes.

Queued turns

Each native Execute turn of the queued gate runs, in FIFO order, every item that was waiting when the turn started. N waiting calls cost one Revit round trip.

  • Items queued during a turn wait for the next turn.
  • After the first item, a turn starts no new item once its 50 ms budget (RevitCallGateTask.DrainBudget) is used.
  • A failed or canceled item completes its own task; the turn continues with the next item.
  • An item that leaves a transaction open in any document ends the turn. Revit discards what a callback leaves open only when the callback returns, so the next item must run in a later turn.
  • An item that creates a transaction group through RevitTransactionGroups.Begin also ends the turn.
  • Nested Auto calls run inline. ForceQueue defers to a later turn.

A caller that needs several reads for one user action makes them in one RunAsync body, or starts independent calls together so that one turn runs them all.

A transaction group without an open transaction is not visible to the open-transaction check. Production code therefore creates every TransactionGroup through RevitTransactionGroups.Begin(document, name, validateStart). The factory calls RevitCallGateTurnBoundary.EndAfterCurrentCall(), so the current turn ends when the running call returns, then constructs and starts the group and disposes it if the start fails. The build contract suite (TransactionGroupTurnBoundaryContractTests) inspects the compiled production assemblies and rejects TransactionGroup construction outside that factory.

The scheduler posts every raise to the Revit dispatcher at Normal priority, also from the dispatcher thread. A caller never waits on native Raise, a burst of calls shares one raise, and the raise for work left after a turn runs after Execute returns.

Denied and TimedOut raise results keep the queue and retry with a backoff from 50 ms, doubling to at most 500 ms, for at most 5 seconds (RevitCallGateRaiseRetry). When that time expires, the waiting batch faults; the scheduler still accepts new work.

Each turn feeds a Debug summary with the prefix [CallGate/Turns]: turns and calls, maximum queue depth, the Raise-to-Execute gap, Execute duration, native Raise duration and results, and refused-raise retries. The summary is written when a turn leaves the queue empty, at most once per second, or after 10 s of a queue that stays busy. Turns inside the one-second interval are reported with the next activity.

Retirement cancels the posted raise, stops and detaches the retry timer, releases queued delegates and disposes the native event. Dropped tasks never complete, so a worker that waits synchronously on one hangs. Cleanup after a failed startup cancels the tasks instead, because Revit and its callers are still running.

Transactions

Resolve transaction services from the command scope: context.Resolve<ITransactionRunner>() and context.Resolve<ITransactionGroupService>(). RevitServiceCollectionExtensions registers both as scoped services on the scope's IRevitCallGate.

ITransactionRunner

public interface ITransactionRunner
{
    Task RunInActiveDocumentAsync(string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInActiveDocumentAsync<T>(string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
    Task RunInDocumentAsync(Document doc, string name, Action<RevitTransactionContext> action, CancellationToken ct = default);
    Task<T> RunInDocumentAsync<T>(Document doc, string name, Func<RevitTransactionContext, T> action, CancellationToken ct = default);
}

Delegates receive RevitTransactionContext, which carries the UIApplication and the Document. TransactionRunner runs on IRevitCallGate and applies the synchronous delegate admission before it enters the gate or starts a transaction. The runtime awaitable check for a reference-typed result runs inside the transaction body, so an awaitable result rolls the transaction back before commit.

  • If doc.IsModifiable (a transaction is already open), it uses a SubTransaction; otherwise it starts a Transaction.
  • It refuses to start a transaction on one document while another document is modifiable.
  • It attaches TransactionFailurePreprocessor, which suppresses non-critical Revit warnings.

TransactionRunner enters the call gate and resolves the target document through TransactionBoundary (RunAsync, GetActiveDocument and EnsureNoCrossDocNesting). TransactionExecutor owns the Transaction or SubTransaction lifecycle and names an unnamed transaction DBTools Transaction. The static status validators of TransactionBoundary turn an unexpected start, commit or group-finalization status into TransactionFailureException; TransactionExecutor and TransactionGroupSession call them, and TransactionGroupSession names an unnamed group DBTools Apply Group.

await _transactionRunner.RunInActiveDocumentAsync("Create Wall", context =>
{
    Wall.Create(context.Document, curve, levelId, false);
});

var wallId = await _transactionRunner.RunInActiveDocumentAsync("Create Wall", context =>
    Wall.Create(context.Document, curve, levelId, false).Id);

Failure handling

TransactionRunner collects failures through transaction or subtransaction disposal before returning a result. The first operation failure stops further work. Existing work/rollback aggregates precede any disposal failure. A single failure keeps its identity, type and original stack. Multiple failures propagate in an ordered aggregate. A disposal failure after commit propagates without undoing the committed write.

TransactionFailurePreprocessor.AttachToTransaction sets clear-after-rollback before failure processing starts. Revit holds a stable RevitCallbackRelay (Presentation) that forwards to the preprocessor. After a transaction ends, Revit can keep native copies of the failure handling options until it next pumps, and a Dev Mode reload proves the old generation unreachable before that. Production code therefore declares the preprocessor before its transaction and attaches it with AttachTo after Start, so the transaction is disposed, and rolled back if needed, before Dispose drops the preprocessor from the relay; its records stay readable. For the same reason, copy-paste options get a constant relay (RevitCallbackRelay.Constant) as the duplicate type names handler. Hand Revit a relay, not a reloadable object, for any callback that Revit can keep after the call.

  • A warning is reported as suppressed only after Revit deletes it.
  • A blocking failure, or a fault in a failure accessor, records a blocking diagnostic and requests rollback. An accessor fault keeps the caught exception, which becomes the InnerException of the TransactionFailureException (an AggregateException when several accessors failed).
  • An attachment fault propagates before commit; the preprocessor does not change rollback options inside the failure callback.
  • The preprocessor keeps one TransactionFailureRecord per message it reads: severity, description, failure definition GUID, failing element IDs and whether the message rolled the transaction back. A fault while reading the failing element IDs is added to AccessorFaults and does not change how the message resolves.

A runner built with new TransactionRunner(gate, logger) logs every record and every accessor fault at Warning after the commit; the one-argument constructor logs nothing. GM's apply runners use the logging form.

TransactionFailureException is the public diagnostic for a transaction that did not reach Committed. Its constructors are internal to Core. Callers read the transaction name, final status, warnings, blocking failure text and failure-definition identities from its properties. BlockingFailureDefinitionIds keeps the IDs in the order Revit reported them, duplicates included, and BlockingFailureDefinitionGuids holds their GUIDs in the same order. The exception implements ITransactionFailureDefinitionSource, which exposes only the GUID list, so code without the Revit API can read it. Core does not classify the GUIDs; GM's GroupEditErrorMatcher matches Revit's four group-edit failures. A posted blocking failure rolls back a runner-managed transaction and raises this exception with the transaction name and the blocking diagnostic. Tool write boundaries map this exception and Revit refusal exceptions to their own typed failures and keep the original exception as the inner cause.

Sources: src/DBTools.Core/Revit/Transactions/{TransactionRunner,TransactionExecutor,TransactionBoundary,TransactionFailurePreprocessor}.cs.

Transaction groups

ITransactionGroupService makes several transactions on the active document one Revit undo entry. It is the manual lifecycle; the caller owns the try/finally around FinalizeAsync, in the workflow that knows whether to commit or roll back.

public interface ITransactionGroupService
{
    bool IsActive { get; }
    Task BeginAsync(string name, CancellationToken ct = default);
    Task FinalizeAsync(TransactionGroupFinalization finalization, CancellationToken ct = default);
    Task<bool> IsGroupHealthyAsync(CancellationToken ct = default);
}
  • If the document is already modifiable, BeginAsync creates no group, IsActive becomes true, and FinalizeAsync only resets state.
  • FinalizeAsync accepts only TransactionGroupFinalization.Commit (assimilate) and Rollback; another value fails before the inactive-session check. Finalization always clears the active group state and attempts disposal of the owned group. If the operation and the cleanup both fail, the operation failure comes first in an ordered aggregate.
  • Revit rolls back a group that is still open when the API callback that started it returns, and RevitTransactionGroups.Begin ends the queued turn after the current call. Separate BeginAsync and FinalizeAsync calls therefore keep one group only on an InlineUi gate inside one callback, as the modal Super Girt Tool (SGT) and Transfer Drafting Views (TDV) commands use them.

Queued modeless work uses IAtomicTransactionGroup.RunAsync(name, work, keep, ct), which TransactionGroupService also implements; GM commit review constructs it directly for its gate. In one gate call it begins the group, runs the work, then assimilates the group when keep(result) is true and rolls it back otherwise. The group is one Revit undo entry also under the queued gate.

  • An exception, or a cancellation seen at any point before finalization (also after the work returns), rolls the group back and propagates.
  • A document that already has an open transaction is refused before any work, because the group would own nothing to roll back.
  • The work must complete inside the callback, where its gate calls run inline. Work still pending when the callback returns is canceled and the group is rolled back.
  • The outcome is classified by the group status Revit reports: only RolledBack counts as discarded and only Committed as kept. Any other status throws TransactionGroupOutcomeUnknownException, and the caller must not report the work as discarded.

Progress overlay

Hosts

  • Host tool views through ToolWindowFactory.CreateModal or CreateModeless. The typed sessions share the IToolWindowSession lifecycle. The modal and modeless shells expose the WPF owner. Core installs WindowInitializer before the XAML loads and retires its state with the session.
  • Bind an overlay to its window with ProgressOverlay.For(window, logger), on the owner's UI thread. State, dispatcher affinity and diagnostics stay tied to that window. The logger is required.
  • WindowProgressOverlayCapability (WindowProgressOverlayCapability.Hosts.cs) is the only registry from Window to overlay state and visual host. There is no ambient or process-global host.
  • ProgressOverlay.Operations.cs holds the public lifecycle API. ProgressOverlayRunWorkflow.cs owns RunAsync(...): the show policy, the linked cancellation source, cancel observation and hide sequencing.
  • ProgressOverlayDelayedHideScheduler keeps the dispatcher operation it posts and observes every outcome. It clears the pending hide only when the completing operation owns the current cancellation source, so an aborted or faulted stale operation cannot clear a replacement hide.

IProgressOverlay

Member Behavior
Show(title, cancelable) Shows the overlay and resets the cancellation state.
Update(status, progress01) Sets status text and progress in [0,1]. A null argument leaves that value unchanged. A non-finite progress value throws ArgumentOutOfRangeException before status or progress changes. Finite values are clamped to [0,1].
UpdateStep(current, total, description, progress01) Sets the status to Step X/Y: {description}.
Scope(title, cancelable) Returns a disposable scope. Nested scopes restore the parent state in LIFO order.
CancelRequested Thread-safe snapshot of the Cancel button state.
RequestCancel() Sets CancelRequested.
Hide() Hides the overlay and clears transient state.
RunAsync(title, work, cancelable, options, ct) Runs work with an overlay lifecycle and cancellation bridge. A second run on the same window while one is active throws InvalidOperationException.

ProgressOverlay marshals public calls to its owner's WPF dispatcher. Do not change overlay state directly from a background thread. Pure and view-model tests can use a simple IProgressOverlay double.

Rendering

  • A status change forces a render (RequestRender(force: true)); a progress-only update is throttled. Phase changes stay visible when Revit starves the dispatcher.
  • ProgressOverlayRenderScheduler throttles render requests to one per 30 ms and pumps one dispatcher frame (DispatcherFramePump.TryPumpSingleFrame) with a 20 ms budget and a depth guard.
  • A forced render bypasses the pending-render guard. A pending render older than 250 ms is treated as stuck and replaced.
  • Do not add other dispatcher pump loops or dispatcher-frame code outside that helper while Revit work is active.

Cancellation

Use RunAsync(...) for long operations. ProgressOverlayRunWorkflow observes CancelRequested, cancels a linked token source and passes the work delegate a token that fires on cancel. After Show(...) resets the cancellation state, the cancel watcher starts before the work begins. SGT analysis (AnalysisSessionWorkflow), SGT placement (PlacementWorkflow) and GM commit review (CommitReviewApplyOverlayWorkflow) use RunAsync.

A workflow that drives its own Scope(...) reads CancelRequested and bridges it to its own cancellation. TDV transfer does this: its reporter returns Overlay.CancelRequested as IsCancellationRequested.

using (Overlay.Scope("Transferring Drafting Views", cancelable: true))
{
    result = await _session.ApplySelectionAsync(items, reporter, CancellationToken.None);
}

Progress values

Tools report IProgress<(string message, double? progress01)>: a status message and an optional fraction in [0,1].

MonotonicProgressAdapter (src/DBTools.Core/Progress/Aggregation) wraps such a reporter and forwards non-decreasing values clamped to [0,1]. A null fraction forwards the status and does not change the tracked value. A non-finite fraction throws ArgumentOutOfRangeException and does not change the tracked value. Create one adapter per operation.

TDV The transfer executor reports per-view stage percentages (0, 10, 25, 35, 60, 85, 100). TdvWindowViewModel.UpdateTransferOverlayProgress maps them through six weighted stages and never decreases.

Common failures

  • Dispatcher errors or missing state: an overlay call on a window that Core WindowInitializer did not initialize, or a change that bypasses the overlay API.
  • Invalid Revit API context: Revit API calls outside IRevitCallGate, or async delegates inside the gate.
