Revit Execution and Progress Overlay

This guide captures the required execution flow for Revit API access and the progress overlay system used by DBTools tools. It summarizes the current contracts in code and shows practical do/don’t examples.

Centralized runner responsibilities

ToolCommand

  • Owns the top-level Revit command entrypoint: public Execute validates Autodesk inputs and passes the non-null UIApplication to the package-visible ExecuteCore seam. ExecuteCore runs through ISafeExecutor, resolves CommandContextFactory from the live runtime, and invokes the protected RunAsync implementation hook with the one owning CommandContext.
  • Keeps command helpers narrow: command subclasses resolve services from ICommandContext, whose inherited IAppRunScope exposes the scope's RevitRunScope and Resolve<T>() directly. Window-owning features compose ToolWindowFactory and invoke IToolWindowSession.ShowDialog() or Show() so the session owns reflection scope and retirement.

Expected refusals throw Core's SafeExecutionRefusedException with a user-facing reason. SafeExecutor returns SafeExecutionStatus.Refused without failure surfacing or exception diagnostics. The Warning banner owns the single Warning log; executions without a banner log [Refused] {Name}: {Message}. ToolCommand still returns Revit Result.Cancelled. Unexpected exceptions retain the existing Error diagnostics and Error banner.

IAppRunScopeFactory

  • Composes the concrete App scope: App composition registers IAppRunScopeFactory after Core Revit services. CommandContextFactory consumes it and calls Create(...); the factory selects the profile-specific call gate, constructs RevitRunScope, and returns IAppRunScope, which owns scoped resolution and disposal.
  • Profiles are the switch: InlineUi uses InlineRevitCallGate; QueuedModeless uses QueuedRevitCallGate. The profile determines whether Revit API calls run inline (modal) or are queued through the App-owned ExternalEvent host (modeless).

Active-document verification

Consumers that retain a launch document call GetVerifiedActiveDocument(...). The run scope rejects invalid expected or active documents and requires matching DocumentSessionKey values before it returns the active document.

IRevitCallGate profiles

  • Modal inline (InlineUi): InlineRevitCallGate checks every Action invocation-list member for an async state machine and rejects statically awaitable result types before validating context, then runs admitted callbacks immediately on the Revit UI thread. Use for modal commands and daemon-hosted Revit automation where Revit already owns the thread.
  • Queued modeless (QueuedModeless): QueuedRevitCallGate applies the same admission before scheduling through the owned ExternalEvent host. Use for modeless windows or long-running flows that must be queued to the UI thread.
  • Reference-typed results: Reference-typed multicast result delegates are rejected before invocation because ordinary multicast dispatch exposes only the final return value. After invocation, reference-typed results receive a runtime Task/ValueTask guard, including values erased behind interfaces. Nullable ValueTask result types are rejected statically; custom awaiter structs are not detected.

When to use InlineUi vs QueuedModeless

  • InlineUi: modal Revit commands or daemon-hosted Revit automation contexts that already run on the UI thread and do not require ExternalEvent/Idling pumping.
  • QueuedModeless: modeless tool windows or long-running workflows that must marshal Revit API work onto the UI thread via the queued host.

ITransactionRunner / ITransactionGroupService

  • Resolve scoped transaction services from the App/command scope (context.Resolve<ITransactionRunner>() / context.Resolve<ITransactionGroupService>()) to ensure Revit API access is routed through the call gate and wrapped in proper transactions. IRevitRunScope owns only UIApplication, the call gate, document access, and disposal.
  • TransactionRunner is explicitly built on top of IRevitCallGate and applies synchronous delegate/result-type admission before entering the gate or opening a transaction. Its reference-result awaitable guard executes inside the transaction body, before commit. This keeps transactions and UI-thread access consistent with Revit’s rules.
  • ITransactionRunner exposes named active-document and explicit-document methods. Delegates receive RevitTransactionContext, which carries both UIApplication and Document without multiplying overloads by delegate shape.
  • ITransactionGroupService exposes only the manual active-document lifecycle: BeginAsync(...), FinalizeAsync(...), IsActive, and IsGroupHealthyAsync(...). Callers that need guaranteed cleanup must own the try/catch/finally around FinalizeAsync(...) in the workflow that knows whether the group should commit or roll back.
  • Trimmed surface: The old no-context RunAsync(...), UIApplication-specific transaction overloads, RunAtomicAsync*, BeginAsync(Document, ...), RunAsync(string, Document, ...), and RunAsync(Document, string, ...) overloads were removed as dead public contract or avoidable Revit API type exposure.

Prohibition: Revit API outside IRevitCallGate

  • IRevitCallGate is the unified entry point for all Revit API access and enforces synchronous callbacks on the UI thread. Any direct Revit API usage outside the call gate risks invalid context exceptions or UI-thread violations.

Execution context best practices (external refs)

These are contextual practices aligned with Revit’s external API requirements and the current call-gate implementation.

  • Modeless UI uses the owned ExternalEvent host. The queued gate marshals work to the Revit UI thread through one generation-owned native event and enters an explicit main-thread API scope inside its Execute callback.
  • Use task-based wrappers to schedule synchronous Revit work (e.g., Revit.Async-style wrappers). The call gate rejects async-state-machine Actions and Task/ValueTask result shapes before scheduling, so keep asynchronous workflows outside the gate and in-gate delegates synchronous.
  • Validate API context before inline execution. Inline execution uses the same API authority as queued execution. RevitHost supplies application data; the product determines authority, including after an awaited continuation in the driver callback.

API-context admission and ExternalEvent probes

RevitCallGateApiContext.IsActive is the product's API-context authority. Known native entry points use its internal synchronous Enter scope as a fast path. Untracked calls first check the Revit dispatcher, then create and immediately dispose an unraised ExternalEvent with a stateless no-op handler. Workers return false before the probe. Every untracked call probes again; no success or failure is cached across turns. Current exposes a known UIApplication only while the context is active. An ambient application reference is data, not authority.

The public UIApplication constructor requires ApplicationServices.Application. There is no public conversion from UIControlledApplication.ControlledApplication. If startup has not received any UIApplication, queued work obtains it from the real ExternalEvent callback. No private-field reflection is used.

The probe uses a fresh event rather than adding/removing a handler on a Revit event. It neither modifies the current event's subscriber collection nor writes a document, so it avoids the same-event subscription restriction and document-write restrictions in Idling, ViewActivated, DocumentChanged and updater callbacks. API admission still does not grant permission to use an API forbidden in a particular callback; callers must respect read-only and dynamic-update restrictions.

The 2026 and 2027 API references list the Create signature and null-handler exception, but omit its outside-context exception. An Autodesk support discussion records that runtime check and distinguishes UI-thread access from API authority. The choice of allocation over subscription follows these API boundaries; the references do not separately certify every callback combination. The probe does not distinguish add-in ownership. When it succeeds inside another add-in's main-thread API callback, it returns true and DBTools runs inline without an explicit DBTools scope, matching ricaun's routing. DBTools-owned callback entries use an explicit synchronous UIApplication scope, and later continuations must probe or queue again.

The scope is a ref struct, so a caller cannot hold it across an await. Its shared lifetime lets even an unsafe wrong-thread disposal revoke the original authority before reporting the misuse. Enter stays internal: App's linked native callbacks and FoundationTags' standalone Idling owner need access. GM's existing friendship supports synchronous-delegate validation, and GM does not enter scopes.

The hosted certification fixture (RevitCallGateApiContextHostedCertificationTests) exercises real ViewActivated, DocumentChanged, FailuresProcessing, and IUpdater.Execute callbacks through real transactions and view activation. It always opens and activates the staged GM model, restores the original view, and rolls back the temporary view. The host retains the staged active document until Revit closes. It cannot certify OnShutdown while the daemon keeps the whole NUnit run inside one Revit callback; the RevitHostedTurns lane certifies modeless false results (RevitCallGateModelessHostedTurnCertificationTests) and native Idling delivery to App's deferred-startup subscription (AppDeferredStartupSubscriptionHostedTurnTests). Only an untracked main-thread admission allocates and disposes an unraised ExternalEvent per authority check; explicit scopes avoid that probe cost, and workers return false before probing. Each native Execute turn runs, in FIFO order, every queued item that was waiting when the turn started, so N waiting calls cost one Revit round trip instead of N. Items queued during the turn wait for the next turn, and after the first item a turn starts no new item once its 50 ms budget is used, so an expanding queue cannot monopolize that turn. A failed or canceled item completes its own task and the turn continues with the next item. An item that leaves a transaction open in any document ends the turn: Revit discards what a callback leaves open only when the callback returns, so the next item waits for a later turn instead of running inside it. A transaction group without an open transaction is invisible to that check, so production code creates transaction groups through RevitTransactionGroups.Begin. The factory ends the current turn before it constructs and starts the group. TransactionGroupTurnBoundaryContractTests (Build tests) scans compiled production assemblies and permits construction only inside that factory. Nested Auto calls stay inline while ForceQueue explicitly defers to a future turn. The probe never raises its event and therefore does not claim that Revit dispatched a later native turn.

The owned scheduler posts every raise to the Revit dispatcher at Normal priority, also when the caller is already on the dispatcher thread. A caller therefore never waits on native Raise, a burst of calls shares one raise, and the raise for work left after a turn runs after Execute returns instead of inside Revit's own handler. Denied and TimedOut responses retain the queue and retry with 50–500 ms backoff for at most five seconds. Expiry faults that waiting batch; the scheduler accepts new work. Each turn feeds a throttled Debug summary ([CallGate/Turns]): turns and calls, maximum queue depth, the Raise-to-Execute gap, Execute duration, native Raise duration and results, and refused-raise retries. It is written when a turn leaves the queue empty, at most once per second, or after 10 s of a queue that stays busy; turns inside the one-second interval are reported with the next activity. Retirement aborts its posted raise, stops and detaches its retry timer, releases queued delegates, and disposes its native event. Dropped tasks never complete; a worker synchronously waiting on one would hang. Failed-startup cleanup uses cancellation instead because Revit and its callers remain alive.

Progress overlay usage

Host requirements

  • Host tool views through ToolWindowFactory and IToolWindowSession. The stable modal/modeless shells expose the WPF owner contract. Core installs WindowInitializer before raw XAML loads and retires its lifecycle state with the session.
  • For tool-specific windows, bind overlay ownership explicitly with ProgressOverlay.For(this, logger) so state, dispatcher affinity, and diagnostics remain tied to that host window. The logger is required at this runtime boundary; composition supplies the owner logger rather than routing through a fallback.

Scope and dispatcher rules

  • Always use Scope(...) for long operations. Nested scopes are state-local to the owner-bound overlay and clean up in LIFO order.
  • Show/Update/Hide are UI-dispatched. ProgressOverlay marshals public calls to its owner's WPF dispatcher, so callers should use the overlay API and avoid touching overlay state directly from background threads.
  • Status transitions force a render pump. Update(...) delegates state mutation to OverlayState.ApplyUpdate(...), where status-string changes call RequestRender(force: true) and progress-only updates remain throttled (force: false). This keeps short phase changes visible under Revit dispatcher starvation without removing global throttles.
  • Overlay render flushing is guarded and throttled. RequestRender still schedules a render callback, and uses a single-frame pump helper (TryPumpSingleFrame) with a depth guard and short time budget to restore incremental visual updates without unbounded re-entrancy. Under Revit-hosted dispatcher starvation, the queued callback that clears the pending-render flag can be delayed; forced renders (step transitions) bypass the pending guard, and a stuck-pending timeout allows recovery when the dispatcher is slow.
  • Overlay responsibilities are owner-bound. ProgressOverlay.Hosts.cs is the single Window-to-OverlayState lifecycle and visual-host registry; ProgressOverlay.Operations.cs exposes the public lifecycle API; Runtime/ProgressOverlayRunWorkflow.cs owns RunAsync(...) show policy, linked CTS lifecycle, cancel polling, watcher observation, and hide sequencing. There is no ambient or process-global host selection.
  • Coverage expectation: cheap IProgressOverlay doubles can stay in pure/view-model tests, but production overlay behavior belongs in a local WPF/Revit-hosted lane. GM's local shell fixture directly exercises ProgressOverlay.For(...) visual-host injection and RunAsync(...) cancellation bridging with a real WPF dispatcher instead of RecordingOverlay.

Cancel handling

  • Prefer RunAsync(...) so the overlay owns cancellation bridging. ProgressOverlayRunWorkflow polls CancelRequested, cancels a linked CTS, and hands the work delegate a token that fires on cancel — so long-running operations should run their work through RunAsync(...) rather than hand-rolling a watcher. SGT placement (PlacementCommandService) and GM commit-review both use this API.
  • Poll CancelRequested and bridge to your CTS only when not using RunAsync(...). The overlay exposes a thread-safe CancelRequested property; workflows that still drive their own Scope(...) (for example SGT analysis) bridge it into operation cancellation manually.

Do/Don’t examples (from current code)

Call gate usage

Do: queue modeless work with synchronous delegates.

await _gate.RunAsync(app =>
{
    // Revit API work here (sync only)
    return true;
});

This aligns with QueuedRevitCallGate.RunAsync(...), which admits only synchronous result shapes before marshalling to the Revit UI thread.

Don’t: use an async-void Action or return Task, Task<T>, ValueTask, or ValueTask<T> from a call-gate delegate. These shapes are rejected before the delegate can start.

Progress overlay scope

Do (SGT): create a scope and poll cancel status.

using var scope = _overlay.Scope(ProgressScopeAnalyze, cancelable: true);
_overlay.Update(ProgressCalibratingFamilies, 0.0);
if (_overlay.CancelRequested)
{
    linkedCts.Cancel();
}

SGT’s analysis workflow creates a scope, updates it, and bridges cancel requests into the analysis CTS.

Do (GM): use Scope(...) and CancelRequested while applying mappings.

using var scope = _overlay.Scope("Applying mappings...", true);
if (_overlay.CancelRequested)
{
    _cts.Cancel();
}

GM's commit review view model follows this pattern to keep UI cancel actions responsive during long operations.

Don’t: manipulate overlay state directly or bypass the dispatcher. Use Show/Update/Hide/Scope so the overlay stays UI-thread safe.

Nested Scope(...) calls restore the parent state held by the same owner-bound overlay in LIFO order when the inner scope ends. After Show(...) resets the previous cancellation state, the cancel watcher starts its delay before the operation body begins, so normal cleanup observes one already-started watcher rather than a scheduling race.

Phase 2: Granular progress primitives

Tuple progress payload

Phase 2 migrated tool-level progress from IProgress<string> to IProgress<(string message, double? progress01)>. This allows tools to emit both a status message and a numeric 0..1 progress fraction in a single report, enabling smoother overlay bar updates.

Affected interfaces:

  • IMappingService.ApplyPlanAsync — GM mapping engine
  • IOrchestrator.PlaceAsync / UpdateAsync — SGT orchestrator
  • IPlacementWriter.PlaceAsync / UpdateAsync — SGT domain writer

MonotonicProgressAdapter

Wraps an IProgress<(string, double?)> and enforces monotonic non-decreasing progress01 values. Status-only updates (null progress01) are forwarded without affecting tracking. Create one instance per logical run.

Both the adapter and overlay reject NaN and infinities before publishing an update. Finite values still clamp to [0,1]. A rejected adapter report does not change its monotonic tracking. Overlay admission occurs before either status or progress changes.

var adapter = new MonotonicProgressAdapter(
    new Progress<(string message, double? progress01)>(update =>
        _overlay.Update(update.message, update.progress01)));
await _mapping.ApplyPlanAsync(plan, adapter, ct);

MappingChangeContext helper updates (GM)

MappingChangeContext.ReportProgress(message) now accepts an optional double? progress01 parameter. The 3-arg ReportProgress(stageName, current, total) overload has been renamed to ReportProgressStage(stageName, current, total, progress01?) for clarity.

Note: RecordSet intentionally uses IProgress<int> (percentage) rather than the tuple pattern. This is because RecordSet's PlanExecutor uses a weight-based percentage calculation internally, and the VM combines the separate status log stream with the integer percentage for overlay updates. This approach avoids additional refactoring of the executor's internal progress model while still achieving the same overlay UX.

Common failure modes

  • Dispatcher errors or missing host: calling overlay APIs without a window initialized by Core WindowInitializer, or bypassing the overlay API, can lead to dispatcher errors or missing state. Always use Scope/Show/Update/Hide on a supported Presentation window host.
  • Revit context leaks: direct Revit API access outside IRevitCallGate or attempting async delegates inside the gate can lead to invalid context errors. Stick to the call gate + transaction runner, and keep delegates synchronous.
  • Re-entrant UI pumping risk during active Revit execution: progress overlay updates now use a bounded single-frame pump with depth guards; avoid introducing additional custom pump loops or unguarded dispatcher-frame usage outside this shared helper.
