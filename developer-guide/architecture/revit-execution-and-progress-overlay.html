Revit Execution and Progress Overlay

This page describes how DBTools runs Revit API work and how tools report progress through the progress overlay.

Command entry

ToolCommand

ToolCommand (src/DBTools.Core/Tools/Commands/ToolCommand.cs) is the base class of every Revit command.

  • The public Execute validates the Autodesk inputs and passes the non-null UIApplication to the internal ExecuteCore.
  • ExecuteCore runs through ISafeExecutor, resolves CommandContextFactory from the live runtime, and calls the protected RunAsync hook with one owning CommandContext.
  • Command subclasses resolve services from ICommandContext. Its base interface IAppRunScope exposes the scope's RevitRunScope and Resolve<T>().
  • A feature that owns a window composes ToolWindowFactory and calls IToolWindowSession.ShowDialog() or Show(). The session owns the reflection scope and the window's retirement.

An expected refusal throws SafeExecutionRefusedException with a reason for the user. SafeExecutor then returns SafeExecutionStatus.Refused, with no failure surface and no exception diagnostics. SafeExecutionRefusalReporter shows a Warning banner, which writes the one Warning log entry; an execution without a banner logs [Refused] {Name}: {Message}. ToolCommand returns Revit Result.Cancelled for a refusal and for a failure. An unexpected exception writes Error diagnostics and shows an Error banner.

IAppRunScopeFactory

App composition (AppServiceProviderFactory) registers IAppRunScopeFactory with the Core implementation AppRunScopeFactory. CommandContextFactory calls Create(UIApplication, AppRunScopeProfile). The factory selects the call gate for the profile, constructs RevitRunScope, and returns an IAppRunScope, which owns scoped resolution and disposal.

Profile Call gate Use
InlineUi (default) InlineRevitCallGate Modal commands and daemon-hosted Revit automation that already run on the Revit UI thread.
QueuedModeless QueuedRevitCallGate Modeless tool windows and long workflows that must queue Revit API work to the UI thread through the App-owned ExternalEvent host.

A tool selects its profile through RunProfile in its registration; ToolRegistration uses InlineUi when none is given.

Active-document verification

A consumer that keeps its launch document calls GetVerifiedActiveDocument(...). The run scope rejects an invalid expected or active document and requires matching DocumentSessionKey values before it returns the active document.

Call gates

IRevitCallGate is the single entry point for Revit API access. It runs synchronous callbacks on the Revit UI thread. Revit API calls outside the call gate can raise invalid-context exceptions or break UI-thread rules.

  • InlineRevitCallGate checks every member of an Action invocation list for an async state machine and rejects awaitable result types before it validates the API context. It then runs the callback immediately. ForceQueue on the inline gate throws ContextUnavailableException.
  • QueuedRevitCallGate applies the same admission, then schedules the callback through its ExternalEvent host.
  • A multicast result delegate with a reference result type is rejected before invocation, because ordinary multicast dispatch exposes only the last return value. After invocation, a reference-typed result gets a runtime Task/ValueTask check, which also finds values behind interfaces. Nullable ValueTask result types are rejected statically. Custom awaiter structs are not detected.

Keep asynchronous workflows outside the gate and make in-gate delegates synchronous:

await _gate.RunAsync(app =>
{
    // Revit API work here (synchronous only)
    return true;
});

An async void action, or a delegate that returns Task, Task<T>, ValueTask or ValueTask<T>, is rejected before it starts.

Sources: src/DBTools.Core/Revit/Execution/CallGate/CallGateDelegateValidator.cs, InlineRevitCallGate.cs, QueuedRevitCallGate.cs.

API-context admission

RevitCallGateApiContext.IsActive decides whether the current code has Revit API context.

  • Known native entry points use the internal synchronous Enter scope.
  • An untracked call first checks the Revit dispatcher thread, then creates and immediately disposes an unraised ExternalEvent with a stateless no-op handler. Worker threads return false before the probe.
  • Every untracked call probes again. No result is cached across turns.
  • Current exposes a known UIApplication only while the context is active. An ambient application reference does not grant API context.

The public UIApplication constructor requires ApplicationServices.Application; there is no public conversion from UIControlledApplication.ControlledApplication. If startup has not received a UIApplication, queued work gets one from the real ExternalEvent callback. No private-field reflection is used.

The probe creates a new event instead of adding and removing a handler on a Revit event. It does not change the subscriber collection of the current event and does not write a document, so it is legal in Idling, ViewActivated, DocumentChanged and updater callbacks. Admission does not permit an API that a particular callback forbids; callers must obey read-only and dynamic-update restrictions.

The 2026 and 2027 API references list the Create signature and the null-handler exception, but not the outside-context exception. An Autodesk forum thread describes that runtime check and the difference between UI-thread access and API context.

The probe does not identify which add-in owns a callback. Inside another add-in's main-thread API callback it returns true, and DBTools runs inline without its own scope. Callbacks that DBTools owns enter an explicit synchronous UIApplication scope; later continuations must probe or queue again.

The scope is a ref struct, so a caller cannot hold it across an await. Its shared lifetime lets a wrong-thread disposal revoke the context before the misuse is reported. Enter is internal; App's native callbacks and FoundationTags' Idling owner use it. GM has access for synchronous-delegate validation only and does not enter scopes.

RevitCallGateApiContextHostedCertificationTests runs real ViewActivated, DocumentChanged, FailuresProcessing and IUpdater.Execute callbacks through real transactions and view activation. It opens and activates the staged GM model, restores the original view and rolls back the temporary view. The host keeps the staged document open until Revit closes. The fixture cannot test OnShutdown, because the daemon runs the whole NUnit run inside one Revit callback. The RevitHostedTurns category tests modeless false results (RevitCallGateModelessHostedTurnCertificationTests) and native Idling delivery to App's deferred-startup subscription (AppDeferredStartupSubscriptionHostedTurnTests).

Queued turns

Each native Execute turn of the queued gate runs, in FIFO order, every item that was waiting when the turn started. N waiting calls cost one Revit round trip.

  • Items queued during a turn wait for the next turn.
  • After the first item, a turn starts no new item once its 50 ms budget (RevitCallGateTask.DrainBudget) is used.
  • A failed or canceled item completes its own task; the turn continues with the next item.
  • An item that leaves a transaction open in any document ends the turn. Revit discards what a callback leaves open only when the callback returns, so the next item must run in a later turn.
  • Nested Auto calls run inline. ForceQueue defers to a later turn.

A transaction group without an open transaction is not visible to the open-transaction check. Production code therefore creates every TransactionGroup through RevitTransactionGroups.Begin(document, name, validateStart). The factory calls RevitCallGateTurnBoundary.EndAfterCurrentCall(), so the current turn ends when the running call returns, then constructs and starts the group and disposes it if the start fails. TransactionGroupTurnBoundaryContractTests (testing/DBTools.Build.Tests) inspects the compiled production assemblies and permits TransactionGroup construction only inside that factory.

The scheduler posts every raise to the Revit dispatcher at Normal priority, also from the dispatcher thread. A caller never waits on native Raise, a burst of calls shares one raise, and the raise for work left after a turn runs after Execute returns.

Denied and TimedOut raise results keep the queue and retry with a backoff from 50 ms, doubling to at most 500 ms, for at most 5 seconds (RevitCallGateRaiseRetry). When that time expires, the waiting batch faults; the scheduler still accepts new work.

Each turn feeds a Debug summary with the prefix [CallGate/Turns]: turns and calls, maximum queue depth, the Raise-to-Execute gap, Execute duration, native Raise duration and results, and refused-raise retries. The summary is written when a turn leaves the queue empty, at most once per second, or after 10 s of a queue that stays busy. Turns inside the one-second interval are reported with the next activity.

Retirement cancels the posted raise, stops and detaches the retry timer, releases queued delegates and disposes the native event. Dropped tasks never complete, so a worker that waits synchronously on one hangs. Cleanup after a failed startup cancels the tasks instead, because Revit and its callers are still running.

Transactions

Resolve transaction services from the command scope: context.Resolve<ITransactionRunner>() and context.Resolve<ITransactionGroupService>(). RevitServiceCollectionExtensions registers both as scoped services on the scope's IRevitCallGate. IRevitRunScope owns only the UIApplication, the call gate, document access and disposal.

  • TransactionRunner runs on IRevitCallGate. It applies the synchronous delegate and result-type admission before it enters the gate or opens a transaction. Its awaitable check for reference results runs inside the transaction body, before commit.
  • ITransactionRunner has named active-document and explicit-document methods. Delegates receive RevitTransactionContext, which carries the UIApplication and the Document.
  • ITransactionGroupService is the manual active-document lifecycle: BeginAsync(name), FinalizeAsync(TransactionGroupFinalization), IsActive and IsGroupHealthyAsync(). The caller owns the try/finally around FinalizeAsync, in the workflow that knows whether to commit or roll back. If the document is already modifiable, BeginAsync creates no group, IsActive becomes true, and FinalizeAsync only resets state.
  • Revit rolls back a group that is still open when the callback that started it returns. Separate BeginAsync and FinalizeAsync calls therefore keep one group only under the inline gate, inside one callback (a modal command).
  • TransactionGroupService also implements IAtomicTransactionGroup; GM commit review constructs it directly for its gate. IAtomicTransactionGroup.RunAsync(name, work, keep, ct) runs the whole group inside one callback, so it is one Revit undo entry also under the queued gate. It refuses a document with an open transaction, assimilates the group when keep(result) is true and rolls it back otherwise. An exception or a cancellation before finalization rolls the group back and propagates. If Revit does not confirm the rollback, the call throws TransactionGroupOutcomeUnknownException; the caller must not report the work as discarded.

Progress overlay

Hosts

  • Host tool views through ToolWindowFactory and IToolWindowSession. The modal and modeless shells expose the WPF owner. Core installs WindowInitializer before the XAML loads and retires its state with the session.
  • Bind an overlay to its window with ProgressOverlay.For(window, logger), on the owner's UI thread. State, dispatcher affinity and diagnostics stay tied to that window. The logger is required.
  • ProgressOverlayWindowCapability (ProgressOverlayWindowCapability.Hosts.cs) is the only registry from Window to overlay state and visual host. There is no ambient or process-global host.
  • ProgressOverlay.Operations.cs holds the public lifecycle API. ProgressOverlayRunWorkflow.cs owns RunAsync(...): the show policy, the linked cancellation source, cancel observation and hide sequencing.

IProgressOverlay

Member Behavior
Show(title, cancelable) Shows the overlay and resets the cancellation state.
Update(status, progress01) Sets status text and progress in [0,1]. A null argument leaves that value unchanged. A non-finite progress value throws ArgumentOutOfRangeException before status or progress changes. Finite values are clamped to [0,1].
UpdateStep(current, total, description, progress01) Sets the status to Step X/Y: {description}.
Scope(title, cancelable) Returns a disposable scope. Nested scopes restore the parent state in LIFO order.
CancelRequested Thread-safe snapshot of the Cancel button state.
RequestCancel() Sets CancelRequested.
Hide() Hides the overlay and clears transient state.
RunAsync(title, work, cancelable, options, ct) Runs work with an overlay lifecycle and cancellation bridge. A second run on the same window while one is active throws InvalidOperationException.

ProgressOverlay marshals public calls to its owner's WPF dispatcher. Do not change overlay state directly from a background thread.

Rendering

  • A status change forces a render (RequestRender(force: true)); a progress-only update is throttled. Phase changes stay visible when Revit starves the dispatcher.
  • ProgressOverlayRenderScheduler throttles render requests to one per 30 ms and pumps one dispatcher frame (DispatcherFramePump.TryPumpSingleFrame) with a 20 ms budget and a depth guard.
  • A forced render bypasses the pending-render guard. A pending render older than 250 ms is treated as stuck and replaced.
  • Do not add other dispatcher pump loops or dispatcher-frame code outside that helper while Revit work is active.

Cancellation

Use RunAsync(...) for long operations. ProgressOverlayRunWorkflow observes CancelRequested, cancels a linked token source and passes the work delegate a token that fires on cancel. After Show(...) resets the cancellation state, the cancel watcher starts before the work begins. SGT analysis (AnalysisSessionWorkflow), SGT placement (PlacementWorkflow) and GM commit review (CommitReviewApplyOverlayWorkflow) use RunAsync.

A workflow that drives its own Scope(...) reads CancelRequested and bridges it to its own cancellation. TDV transfer does this: its reporter returns Overlay.CancelRequested as IsCancellationRequested.

using (Overlay.Scope("Transferring Drafting Views", cancelable: true))
{
    result = await _session.ApplySelectionAsync(items, reporter, CancellationToken.None);
}

Progress values

Tools report IProgress<(string message, double? progress01)>: a status message and an optional fraction in [0,1].

MonotonicProgressAdapter (src/DBTools.Core/Progress/Aggregation) wraps such a reporter and forwards non-decreasing values clamped to [0,1]. A null fraction forwards the status and does not change the tracked value. A non-finite fraction throws ArgumentOutOfRangeException and does not change the tracked value. Create one adapter per operation.

Tool Progress source Overlay mapping
GM MappingPlanExecutor reports per-writer progress (writerIndex / writerCount); MappingApplyState.ReportProgress(message, progress01) reports within a writer. CommitReviewApplyWorkflow wraps the reporter in MonotonicProgressAdapter; CommitReviewApplyOverlayWorkflow updates the overlay.
TDV The transfer executor reports per-view stage percentages (0, 10, 25, 35, 60, 85, 100). TdvWindowViewModel.UpdateTransferOverlayProgress maps them through six weighted stages and never decreases.

Tests

Pure and view-model tests can use simple IProgressOverlay doubles. Production overlay behavior is tested with a real WPF dispatcher: GM's local shell fixture exercises ProgressOverlay.For(...) visual-host injection and RunAsync(...) cancellation.

Common failures

  • Dispatcher errors or missing state: an overlay call on a window that Core WindowInitializer did not initialize, or a change that bypasses the overlay API.
  • Invalid Revit API context: Revit API calls outside IRevitCallGate, or async delegates inside the gate.
