Project References

Desktop Revit 2026.5 and later, and Revit 2027, use one target framework, net10.0-windows. build/Distribution/RevitYearContract.cs and build/MSBuild/RevitTargetFrameworks.props define the supported years and their framework. Projects use $(DBT_RevitTargetFramework) and contain no year-specific framework conditions.

Assemblies

Project Assembly Role
src/DBTools.App DBTools.dll Revit entry point, App lifecycle and host infrastructure, embedded tool manifests
src/DBTools.Core DBTools.Core.dll Shared execution, settings, logging, tool registry, manifest loading, tool assembly resolution
src/DBTools.Presentation DBTools.Presentation.dll Stable WPF resources, controls and window shells

src/DBTools.Manifest merged into Core Portable manifest.yml parser (net8.0) for build tooling and validation
src/Tools/<Category>/<Tool> DBTools.<Tool>.dll One tool: commands, features and tool services
src/DBTools.Sandbox Sandbox executable Candidate validation and UI development without Revit

Reference direction

  • App references Core and Presentation. It embeds every src/Tools/**/manifest.yml as a resource and compiles no tool source.
  • Core references Presentation and DBTools.Manifest. It references the Revit API where a shared capability needs it.
  • Tools reference Core, and Presentation for their UI.
  • Presentation references only WPF and HandyControl. It does not reference App, Core, tool types or the Revit API.
  • Sandbox compiles against Core, Presentation and HandyControl without copying their runtime files, and loads them from the candidate year directory at run time.

App owns the ricaun.Revit.UI compile reference; the merge folds its runtime into DBTools.dll. Add a third-party runtime dependency through a declared merge in build/Merging/AssemblyMerges.props, not through a copy step. See Assembly Loading Contract.

Tool assemblies

Set DBT_IsToolAssembly=true in a project that produces a shipped tool assembly. The build stages its output in the year's Tools/ directory and gives it a content-derived version. At run time App resolves the tool through ToolAssemblyResolver, which loads into the context of the App and Core root assembly. The same rule applies in the default context, in the daemon's ProductLoadContext and in DevModeLoadContext.

Every manifest under src/Tools/ has its own assembly, including Settings, SGT and DialogSuppression. A tool assembly must not contain a copy of Core or of Presentation.

Test references

Pure projects use the ordinary compile and runtime graph of their lane. Revit-hosted Local projects receive the selected year's host references and the staged product tree with Tools/ intact. Hosted input generation keeps the product root separate from test assemblies and adapter dependencies. A project reference must not place product assemblies flat beside a test assembly: the product requires the year root and its Tools/ subdirectory.

Keep a dependency's host or resource constraint in the project that owns it, and validate the resulting candidate tree. Do not add projects for unsupported frameworks or a second DBTools load context.

See Assembly Loading Contract, Build Pipeline and Test Pipeline.
