Sandbox Validator

DBTools.Sandbox validates one staged product year outside a running Revit session. It checks the candidate files, metadata and manifests, then builds the real tool windows and checks themes, layout, bindings and Dispatcher cleanup. It is also a host for developing tool UI with design-time view models.

Sandbox is a Windows WPF executable (DBTools.Sandbox.exe, win-x64). Both modes need the matching Revit year installed: Sandbox resolves AdWindows.dll, RevitAPI.dll, RevitAPIUI.dll and UIFramework.dll from the Revit installation directory.

Synopsis

DBTools.Sandbox [--headless] [--dist-dir DIR] [--revit-reference-dir DIR]
Option Description
--headless Run the full validation sequence, close every window and exit with the result. Without it, Sandbox opens the window catalog for interactive use. Requires --revit-reference-dir.
--dist-dir DIR A year directory (for example .artifacts/dist/Release/2026) or a distribution root that contains year directories. Default: .artifacts/dist/Release of the repository that contains the executable, else of the current directory.
--revit-reference-dir DIR A directory with the four Revit reference files for the year. Their metadata must be compatible with the installed runtime. Valid only with --headless.

Both --option VALUE and --option=VALUE are accepted. An empty value, an unknown argument or a missing value is an error. Without --headless, Sandbox uses the installed Revit runtime as the reference. A --dist-dir of the form /mnt/<drive>/... is converted to a Windows path.

Examples, in PowerShell on Windows after ./build.sh BuildAll. Validate the 2026 candidate against the installed Revit 2026 files:

.\.artifacts\sandbox\Release\2026\net10.0-windows\DBTools.Sandbox.exe --headless `
  --dist-dir .artifacts\dist\Release\2026 `
  --revit-reference-dir 'C:\Program Files\Autodesk\Revit 2026'

Open the window catalog for the 2026 candidate:

.\.artifacts\sandbox\Release\2026\net10.0-windows\DBTools.Sandbox.exe `
  --dist-dir .artifacts\dist\Release\2026

The exit status is 0 when headless validation passes and 1 when it fails. A failure before WPF starts is written to standard error.

Process model

Each year runs in a new process in the default load context:

  1. SandboxEntry uses only BCL types. It parses the options, resolves the year directory and runs SandboxCandidate.Validate.
  2. A non-inlined method prepares the Revit runtime resolver and loads HandyControl, Presentation, Core, App and the manifest-declared tools from their candidate paths.
  3. A second non-inlined method starts the WPF application. The JIT compiles this call only after the candidate assemblies are loaded, so Core and WPF cannot resolve from anywhere else first.

The process exits after validation, so no assembly of one candidate stays loaded for another year. Sandbox creates no load context, does not run App's Revit startup, does not load Revit reference files as product assemblies and does not probe subfolders other than Tools/.

Candidate contract

A candidate is one year directory of the product tree. SandboxCandidate checks the add-in file, the top-level files, the flat Tools/ directory, the PE simple names, and conflicts with assemblies already loaded in the process. No third-party DLL may be present.

Validation sequence

  1. Resolve the year directory and the optional Revit reference directory.
  2. Check DBTools.addin, the exact top-level files, the recursive Tools/ files, the supported year and framework, and the PE simple names.
  3. Read the App, Core, Presentation, HandyControl and tool references and their source-derived versions from PE metadata, without loading Revit API assemblies.
  4. Discover the embedded manifests and validate module, command, availability, icon, raw XAML and design-time view model ownership.
  5. Load the resources and themes, build the window catalog and each tool window, run layout and interaction checks, capture binding errors, close every window and verify Dispatcher cleanup.
  6. Fail if any Revit API assembly is loaded at the end.

Portable validation of a distribution archive checks the same file set and also file lengths and SHA-256 hashes.

Tool window registration

A tool lists its Sandbox windows in manifest.yml:

sandboxWindows:
  - id: DBTools.MyTool.Main
    displayName: "My Tool"
    group: "Common"
    xamlResource: "DBTools.ToolViews.MyTool.MyToolView.xaml"
    windowKind: Modal
    designTimeViewModelType: "DBTools.MyTool.App.DesignTime.MyToolDesignTimeViewModel"
    designTimeViewModelAssembly: "DBTools.MyTool"
    designTimeViewModelVisibility: Public

windowKind is Modal or Modeless. SandboxCatalog (Core) reads these entries into window specifications, and Sandbox hosts each raw view in the stable Presentation ToolWindowHost. No candidate Window type crosses between assemblies.

Validation requires, for each entry:

  • a nonempty id, displayName, group, xamlResource, designTimeViewModelType and designTimeViewModelAssembly;
  • an EmbeddedResource in the owning project with exactly that LogicalName;
  • a root element that derives from FrameworkElement and is not a Window; the host supplies the window shell;
  • no x:Class, x:ClassModifier or x:FieldModifier, no code-behind event attributes, no CLR namespaces of the tool assembly, no implicit templates for tool types, no inferred DataGrid columns and no pack URIs into the tool assembly;
  • a concrete design-time view model whose visibility matches designTimeViewModelVisibility (Public or Internal) and that has a parameterless constructor (public for Public); Sandbox invokes it. Give it fixed display data and no Revit, network or settings services. Design-time view models supply their own unavailable-feature state.

Every manifest command type must implement IExternalCommand and every availability type IExternalCommandAvailability, in the declared owner assembly under Tools/.

Window checks

ToolWindowValidator opens each raw view through ToolWindowHost with its design-time view model and then:

  • measures and arranges the window at a fixed size and at infinite size;
  • selects every tab of each TabControl and restores the original tab;
  • shows the row details of the first three rows of each nonempty DataGrid, except grids whose details are VisibleWhenSelected;
  • records WPF binding errors;
  • closes the window and waits for a bounded ApplicationIdle Dispatcher barrier.

It fails when the Dispatcher is missing, shutting down or aborted, or when a cleanup operation is still pending after the barrier.

Build output and archives

Sandbox is built once per year, although both years use the same framework:

.artifacts/sandbox/<Configuration>/<year>/<TFM>/   build output
sandbox/<year>/<sanitized-tfm>/                    path inside the validation archive

./build.sh PackageSandboxValidationInput writes a content-addressed validate-dist-<sha256>.zip with the candidate and Sandbox. The DIST suite consumes that archive and writes a structured result JSON (see Distribution acceptance). The archive and the result keep normalized relative paths. The portable validation of the archive runs on any host and checks files and metadata only. The Windows acceptance suite runs DBTools.Sandbox.exe --headless for each year, with the reference files the archive carries under revit-refs/<year>/, so the window checks run there.

Troubleshooting

Failure Where to look
Candidate file missing or extra ProductOutput staging and DistributionContract
.addin entry mismatch build/Installer/DBTools.addin and the App output
Tool assembly missing The manifest assembly name and Tools/ staging
Raw XAML resource missing EmbeddedResource LogicalName in the owning project
Design-time view model cannot be created Its visibility, designTimeViewModelVisibility and parameterless constructor
Binding errors Explicit bindings and the stable Presentation templates
Layout failure ToolWindowValidator measure and arrange messages
Cleanup timeout Dispatcher and window owner lifetime

A window failure reports both the primary exception and any cleanup exception.
