Wiki Server

wiki/server-config/ holds the configuration of the web server that serves this documentation site at https://dbtools.greatwhitelab.net. The server runs Caddy for the static files and a webhook container that updates them. A push to the main branch of the kirsch33/dbtools-wiki repository makes the server pull the new site.

Publishing flow

  1. The Documentation workflow (.github/workflows/documentation.yml, manual dispatch) builds the site with .github/scripts/build-docs.sh and pushes wiki/_site to the main branch of kirsch33/dbtools-wiki. It authenticates with the deploy key in the WIKI_DEPLOY_KEY secret.
  2. GitHub sends the push event of kirsch33/dbtools-wiki to https://dbtools.greatwhitelab.net/hooks/dbtools-wiki, signed with the shared secret in the X-Hub-Signature-256 header.
  3. Caddy proxies /hooks/* to the webhook container on port 9000.
  4. The dbtools-wiki hook runs only when the HMAC-SHA256 signature is valid, repository.full_name is kirsch33/dbtools-wiki and ref is refs/heads/main. It then runs /scripts/pull-site.sh dbtools-wiki.
  5. pull-site.sh reads the site entry from sites.json. On first use it clones the branch with depth 1 into the web directory; after that it fetches the branch and runs git reset --hard origin/<branch>.
  6. Caddy serves /web/dbtools-wiki as static files. A path that matches no file or directory returns /index.html.

Files

File Content
Dockerfile The webhook image: almir/webhook, pinned by digest, plus bash, git and jq. It runs as the base image's unprivileged webhook user.
docker-compose.yml The webhook service: builds the image, runs webhook -verbose -template -hooks=/etc/webhook/hooks.json -hotreload, mounts config/ and scripts/ read-only and /web read-write, reads webhook.env, and joins the external caddy_default network.
webhook.env.example Template for webhook.env, which sets WEBHOOK_SECRET.
config/hooks.json The hook definitions. -template lets each hook read WEBHOOK_SECRET with getenv.
config/sites.json Maps a site name to repo (GitHub owner/name), web_dir and branch (default main).
scripts/pull-site.sh pull-site.sh <site-name>: clones or updates one site from sites.json. It exits with status 1 when the name is missing or unknown, or sites.json is absent.
caddy-snippet.txt The Caddy site block for dbtools.greatwhitelab.net.

hooks.json and sites.json also define a blog site (kirsch33/blog, served from /web/blog) that uses the same script.

Requirements

  • Docker with Compose, and a Caddy container on the external Docker network caddy_default.
  • The image needs bash, git and jq, because pull-site.sh uses all three. The base image has only the webhook binary and /bin/sh; the Dockerfile adds them with apk.
  • The host directory /web must be writable by the UID:GID in the user field of docker-compose.yml (1001:1001). Set it to the server user that owns the bind mounts.
  • The site repository must be readable over anonymous HTTPS, because pull-site.sh clones https://github.com/<repo>.git without credentials.
  • The GitHub webhook and webhook.env must use the same secret.

Setup

  1. Copy webhook.env.example to webhook.env and set WEBHOOK_SECRET, for example from openssl rand -hex 32.

  2. Check and start the service:

    docker compose config --quiet
docker compose up -d --build

  3. Add the block from caddy-snippet.txt to the Caddyfile and reload Caddy.

  4. On kirsch33/dbtools-wiki, add a webhook for push events with the payload URL https://dbtools.greatwhitelab.net/hooks/dbtools-wiki, the content type application/json and the same secret.

-hotreload makes the webhook reload hooks.json when the file changes. A change to the Dockerfile needs docker compose up -d --build. To move to another base image, resolve its digest and rebuild on the wiki host.
