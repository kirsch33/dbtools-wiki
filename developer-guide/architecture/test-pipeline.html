Test Pipeline

Select a project with dotnet test. Portable projects execute under VSTest on the invoking host. Entry projects under testing/Daemon/ use the pinned dbtools-daemon.RevitTest.TestAdapter. For commands and filters, see Testing Tools.

Execution

Tests Marker Host
Pure [Test] Local VSTest for portable projects and daemon Windows VSTest for Pure Entry projects
Revit-hosted [RevitLocal] Revit on a daemon worker
Design Automation [RevitDA] APS Revit 2027 engine, submitted through dbtools-daemon
BUILD [Test] Local VSTest for build and distribution contracts

Revit-hosted tests exercise the ribbon, WPF and add-in lifecycle in Revit. Design Automation tests run DB-only in the APS Revit 2027 engine. See APS Design Automation engine tests.

Selection

The selected Entry project determines the owner and lane. MSBuild evaluates each test project's compile items. VSTest --filter narrows the selection by test name or category. --list-tests lists available tests from the built project. Pure requests have no year. Hosted builds supply both years and the adapter submits one job for each year selected by DBTOOLS_DAEMON_REVIT_YEARS.

User interface input

By default, a daemon job, Pure or Revit-hosted, runs on the daemon's private desktop, which receives no keyboard or mouse input and never becomes the foreground, whether the Windows session is locked or not. Tests drive the user interface in-process: through view-model commands, WPF automation peer providers, RaiseEvent, Keyboard.Focus or FocusManager in the test's own windows, and the calling thread's own Win32 state (SetActiveWindow, SetKeyboardState, messages to its own windows); or through UI Automation patterns in another process. A test project fails to build when it uses an API listed in testing/BannedSymbols.txt (error RS0030) or when its source names an OS input or foreground function such as SendInput or SetForegroundWindow (error DBT0003, DBT_RejectOsInputInterop in Directory.Build.targets).

Artifact tests

The --filter 'TestCategory=ProductArtifacts' selection reads both staged Release years, compiler PDBs, merge inputs, hosted test assemblies and the Dev Mode scenario manifest. Run dotnet build build/Build.proj and dotnet build build/Build.proj -t:BuildTests before running the selection.

The Presentation ToolWindowXamlTests fixture, compiled by Presentation Pure, parses raw XAML from every tool in DistributionContract.ToolAssemblyFiles and Core. Its project references supply the complete tool set to the test consumer.

Daemon adapter entry projects

testing/Daemon/Hosted/<Tool>.Hosted.Entry.csproj builds dbtools.<Tool>.Local.Tests for both years (Hosted2026.proj, Hosted2027.proj). <Tool> is a tool key or App, Core or Presentation. Use <Tool>.HostedTurns.Hosted.Entry.csproj to run the dbtools.<Tool>.HostedTurns.Local.Tests project for App, Core or GM. testing/Daemon/Pure/<Tool>.Pure.Entry.csproj selects the corresponding dbtools.<Tool>.Pure.Tests.csproj. The Core and SGT portable projects run directly with dotnet test. RecordSet.Cad.Pure.Entry.csproj selects the AutoCAD test project. Distribution.Pure.Entry.csproj builds dbtools.Distribution.Windows.Tests and attaches the validation archive to the request. A request selects one year by its exact test name. testing/Daemon/DesignAutomation/Engine.DesignAutomation.Entry.csproj selects the DB-only Revit 2027 example (DesignAutomation2027.proj). Run this Entry explicitly to submit a WorkItem.

The Entry supplies one test assembly per daemon request. Separate Entry projects keep different dependency closures in separate bundles. Hosted jobs for different years also have separate bundles.

MSBuild restores and builds each lane with the Entry configuration and artifact paths. Each Hosted graph validates its runtime closure before returning its inputs. The Entry writes dbtools-daemon.runsettings with the literal sources, models and includes. Hosted settings default to years 2026,2027, isolated execution and a 30-minute timeout. Every Entry template sets TreatNoTestsAsError. Portable test projects use testing/Portable.runsettings for the same VSTest setting.

Before VSTest runs, Entry.targets checks that the restored and vendored adapter packages match the SHA-256 pin in testing/Daemon/Directory.Build.props. IDE runners and vstest.console do not run that check. The adapter waits for the terminal result of each accepted job and reports retrieval errors and failed jobs to VSTest. The command's verdict comes from that invocation.

Product staging

The Local graph uses one product stage per configuration and Revit year. Test selection and DBT_TestOutputYear apply to the test graph. Direct and NuGet-added references to product projects use the same build properties. Presentation is shared across the Revit years in a configuration. Core uses the desktop build for the selected year.

Each Revit-hosted test for a year receives the product tree that the installer uses, under product/<year>/. The tree keeps its relative paths. Test assemblies and NUnit and adapter dependencies are separate inputs. App loads tools from Tools/ by explicit path into the context that holds it, so ProductLoadContext and DevModeLoadContext receive the same identities as the staged tree. Test support installs no resolver for product assemblies.

Test projects

Test projects are next to their production owners:

src/dbtools.App/Tests/dbtools.App.{Pure,Local}.Tests.csproj
src/dbtools.Core/Tests/dbtools.Core.{Pure,Local}.Tests.csproj

testing/dbtools.Distribution.Windows.Tests/   Windows distribution acceptance
testing/RevitTestModels/                      test models by Revit year

An owner has both a .Pure.Tests and a .Local.Tests project only when both kinds of test exist.

  • Pure projects list their source files explicitly and reference their normal production owners. Shared props give every Pure project $(DBT_PureRevitYear) (2026) and static graph restore, and pass that year on owner references, so a plain dotnet build or dotnet test of one project needs no properties. Windows Pure projects compile against the pinned desktop Revit references. Their runtime output contains IL-only copies of RevitAPI, RevitAPIUI, AdWindows, and UIFramework. These stubs preserve Revit type definitions, constants, and enum values. A stub method throws NotSupportedException with the message <assembly> is a test stub. Its API calls require the host. This applies during type initialization and when GetCustomAttribute<TransactionAttribute>() constructs a Revit attribute. An NUnit action records the exception when it is thrown and fails the case even if a catch block handles it. Mark a test with [AllowRevitStubCalls] when it checks the stub failure itself. Sandbox Pure leaves assembly resolution to the Sandbox Revit runtime resolver.
  • .Local.Tests projects disable default compile items and include only Revit-hosted fixtures.
  • Presentation tests are under Presentation and belong to the Presentation projects, also when they test a tool's Presentation types. Presentation Pure links the Core test support it shares and references Core for the tool window, window runtime and logger window integration fixtures. Tests that need a real WPF window run where Windows is available.

Portable Pure projects

Core and the Super Girt Tool (SGT) define an optional $(DBT_PortableTargetFramework). Their *.Portable.Pure.Tests projects build against that framework and run on Linux. Run these projects with dotnet test. To make a project portable:

  1. declare desktop and portable TargetFrameworks;
  2. condition DBT_RevitHostIdentity, UseWPF and the Presentation ProjectReference on the desktop framework, and keep Revit references under the desktop host identity condition;
  3. set DBT_UsesMergedAssemblies=false in portable consumers.

build/MSBuild/Portable.targets excludes App, Revit, Views, DesignTime and XAML inputs. Portable images use ordinary NuGet dependencies, have no content version and add no staged runtime files. Core uses an explicit list of source files for its portable build.

Test models

Revit-hosted projects declare RevitTestModel items relative to testing/RevitTestModels:

testing/RevitTestModels/
├── 2026/dbtools_test_model.rvt
├── 2026/_LinkedModels/sgt_test_linked_model.rvt
├── 2026/families/
├── 2026/test-model-build.json
├── 2027/...                                  (same layout)
├── GM/SharedParameters/shared_parameters.txt
└── VTC/vtc_import_layers.dxf

Revit-hosted projects share dbtools_test_model.rvt for each year. They stage the host and its relative link together. A fixture that needs a family file declares it as an additional input. Revit-hosted fixtures find the inputs under DBTOOLS_DAEMON_REVIT_MODELS_DIR with their relative paths intact. Pure fixtures that read repository files use the dbtools.RepoRoot metadata that Directory.Build.props embeds in the test assembly. TestPathResolver reads the root on every call, so a job never sees the model root of a previous job. A fixture may open a temporary copy of a model, but the daemon owns the active document and the worker lifecycle. Models resolve only from these roots, not from a worker checkout or an %APPDATA% cache.

The Dev Mode scenario takes the same host and link through the per-year model directory. The daemon stages every file in that directory at its relative path.

Test support

testing/TestSupport holds shared test infrastructure and doubles for true externals. Tool-specific doubles are under testing/TestSupport/<Tool> and are linked as source by the matching test projects; they are not a separate assembly.

  • Revit/RevitHost.cs starts the App lifecycle and opens an explicit API scope with the UIApplication for the synchronous prefix of the test body. The scope closes when the body returns its task. Hosted tool fixtures borrow the App service root's task, which also serves App QueuedModeless run scopes. A fixture that constructs its own Revit task owns its disposal. Hosted startup advances queued hook attachment through the real event handler and completes deferred UI startup. While no Revit calls are pending, AppHostedComposition advances the dispatcher with a bounded Background operation. The startup wait preserves the caller's API scope and leaves input to WPF.
  • One daemon callback has no second native Revit turn. A forced-queue test can call the real event handler synchronously to exercise queue dispatch. Use a RevitHostedTurns fixture to test work across native turns. RevitCallGateModelessHostedTurnCertificationTests uses it to verify that Revit delivers work queued during a progress frame in a later native turn.
  • Wpf/WpfTestRuntimeBootstrap.cs registers pack URI support, installs the shared window owner, validates themes in the runtime assembly's contextual reflection scope, and releases only its own provider at teardown. It adds no Resolving handlers and does not force Presentation into the default context.
  • Logging/TestLoggingBridge.cs uses production logging when Revit provides it and a console and file host otherwise.

Each opted-in test assembly uses one App lifecycle, one Revit task and one main-window owner. Assembly teardown shuts them down before the next assembly starts in the same Revit process. A hosted sandbox WindowStaticRuntimeTestScope releases its window configuration, retires dispatcher work, and restores the incoming dispatcher registry state at teardown. Profile setup disables view-activated model updates for Elevation Tags, Combined Foundation Tags and Joist Girder Weights. The production hooks attach. A fixture that tests automatic updates enables its tool through the settings provider. Fixtures release their windows, document leases and other owned resources. The shared after-test action checks the App registry for retained tool windows. Cleanup reports both the primary failure and any cleanup failure.
