Test Pipeline

This page describes how DB Tools tests are selected, staged and run. For the test.sh options, examples and the rules for writing tests, see Testing Tools.

DB Tools tests run through one of two routes:

  • ./test.sh resolves the selected projects, builds them, freezes their inputs and runs them locally or submits them to the dbtools-daemon fleet. It writes the receipts that --no-build and CI consume. See the test.sh command reference.
  • Plain dotnet test on an entry project in testing/Daemon/ uses the pinned daemon VSTest adapter (DbToolsDaemon.RevitTest.TestAdapter). MSBuild builds the selected assemblies, models, includes and per-year sources, and the adapter submits them in one request. See Daemon adapter entry projects.

Use one route per invocation. Both read the relay URL from DBTOOLS_DAEMON_RELAY_URL; the daemon owns relay credentials, and neither route accepts or stores them.

Scopes and suites

Scope or suite Marker Where it runs
Pure tests (pure) plain [Test] Without Revit. Locally when possible; otherwise as a daemon PureSuite job on a hidden Windows desktop
Revit-hosted tests (local) [RevitLocal] Inside Revit on a daemon worker, for one selected year
Design Automation tests (da) [RevitDA] On the invoking host, as an HTTP client of APS Design Automation; never through the daemon
DIST The Windows distribution acceptance suite, always a daemon PureSuite job
BUILD Linux-native build and distribution contract suites

Revit-hosted tests exercise the real ribbon, WPF and add-in lifecycle in Revit. Design Automation tests build the Revit 2026 Sentinel WorkItem test project and run it with dotnet test; see APS Design Automation Sentinel.

Pure requests have no year. A Revit-hosted request for two years makes one daemon request per year, each with its own product tree and report. Design Automation tests always build Revit 2026.

Selection

test.sh list --projects prints the sorted scope<TAB>project rows and is the source of truth for what a request selects. It evaluates project membership, explicit Compile Include, Exclude and Remove items, disabled default items, NUnit fixture attributes and the selected tool, scope and year. The same index resolves fixtures and exact FQNs. A fixture must resolve to one compiled owner class. An unknown fixture or project, an unreadable project or source file, a project the selected tool and scope cannot reach, or an explicit scope with no resolved project exits with status 2 before any build or submission.

An exact FullyQualifiedName=<FQN> filter becomes an exact daemon selector, and a prefix filter becomes a prefix selector. A Revit-hosted filter that cannot be mapped exits with status 2 instead of selecting the whole assembly.

Pure routing

test.sh checks each selected Pure assembly for its .deps.json, .runtimeconfig.json and the output-local NUnit3.TestAdapter.dll, then routes it:

  • to the daemon if it is the DIST suite or a machine is pinned;
  • to the daemon if it targets Windows and the host is not Windows;
  • to the daemon if the host lacks Microsoft.WindowsDesktop.App; a missing other framework is an error;
  • otherwise to local VSTest.

Projects that run locally, including the Linux BUILD and Distribution suites, run one after another; daemon submissions run concurrently, at most DBT_PURE_CONCURRENCY (default 2) at a time. A local project that runs zero tests fails. With a filter expression, the run fails only when no selected project runs a test. Linux-native BUILD projects and *.Portable.Pure.Tests projects are skipped on Windows with a notice.

Inputs and receipts

For a selected scope and year, the MSBuild graph returns the test assembly, target framework, model items and product-tree includes in one pass. Before any submission, test.sh freezes the assemblies, runtime closure, product-tree includes, models and companions into the content-addressed test input cache (DBT_TEST_INPUT_CACHE_ROOT), so a later build cannot change the submitted files. A normal exit removes the per-run directory.

--compile-only writes a receipt bound to the source identity, the selected projects, the graph inputs and the output hashes. --no-build verifies all of these and refuses stale or missing files. CI resolves the selectors once with ./test.sh list --projects, compiles each selected scope with --compile-only, transfers the receipt and the recorded input closure, and runs them with --no-build. The consumer never rebuilds. Linux BUILD and DIST jobs do not depend on the Windows transfer.

The portable BUILD project selection requires no prebuilt product or candidate output:

./test.sh test --tool BUILD --project testing/DBTools.Build.Tests/DBTools.Build.Tests.csproj --scope pure --filter 'TestCategory!=ProductArtifacts'

--tool BUILD also selects the Distribution and Sandbox projects. Their setup requirements remain separate. Ordinary test compilation creates test artifacts under .artifacts.

The complete --filter 'TestCategory=ProductArtifacts' selection requires a source-current ./build.sh BuildAll and compiled hosted test outputs. It checks promoted distributions, compiler PDBs, merge inputs and hosted test outputs. AssembleDistributionCandidate alone does not supply all of these inputs.

Artifact admission inspects every staged build.json and the final record. It selects the newest parsed builtAtUtc whose sourceCommit and sourceTree match HEAD and its tree. Admission requires clean tracked and untracked source, including root build configuration and documentation. Distributed bytes must match the declared distributionFingerprint before tests read them. Compiler PDBs, merge inputs and dependency files require current BuildAll outputs as setup; the distribution fingerprint does not authenticate those intermediate files.

The Presentation ToolWindowXamlTests fixture, compiled by Presentation Pure, parses raw XAML from every tool in DistributionContract.ToolAssemblyFiles and Core. Its project references supply the complete tool set to the test consumer.

Results

Daemon summary and full-report JSON require a command envelope with the report under result.report. A document without the envelope fails validation. After a zero submit exit, the summary must report result_status=passed, a positive passed count, and zero failed, errored, and aborted counts. Skipped tests can accompany passed tests. Zero executed tests, including an all-skipped run, fail admission. A nonzero submit exit is kept even when the terminal JSON is missing or malformed. When retrieval succeeds, failed runs keep their reports and original exit status. A refused submit (ok: false, a null result and an error) ran nothing: the wrapper prints the error code, summary, causes and next step, fetches no report, and keeps the CLI's nonzero exit, or returns 2 after a zero exit. Other rejected terminal summaries are saved as *.invalid-summary.json.

Full report retrieval accepts a report exit of zero or the submit exit. The report file must be nonempty, and its JSON request identity, status, and counts must match the accepted summary. Retrieval makes three report attempts, stopping after the first accepted report. Two one-second delays separate three failed attempts. It never resubmits tests. Only an accepted report is published to the result path. After exhaustion, nonempty rejected output is saved as PATH.invalid-report.json, where PATH is the full report path. A refused report command prints its error code, summary, causes and next step whatever its exit; only a refusal with exit 3 is fetched again, and a refused report is not saved. The wrapper keeps a nonzero submit exit or returns 2 after a zero submit exit. Independent scopes in one request continue after a failure, but test.sh returns the first nonzero status.

Daemon adapter entry projects

testing/Daemon/Hosted/<Tool>.Hosted.Entry.csproj builds DBTools.<Tool>.Local.Tests for both years (Hosted2026.proj, Hosted2027.proj). <Tool> is a tool key or App, Core or Presentation. The App and Core entries also build DBTools.<Tool>.HostedTurns.Local.Tests. testing/Daemon/Pure/<Tool>.Pure.Entry.csproj selects every DBTools.<Tool>.*Pure.Tests.csproj beside its owner. After the build, the entry writes dbtools-daemon.runsettings from Hosted.runsettings or Pure.runsettings with the literal sources, models and includes. The hosted settings default to years 2026,2027, isolated execution and a 30-minute timeout, and treat a run with no tests as an error.

Product staging

Each Revit-hosted test for a year receives the product tree that the installer uses, under product/<year>/. The tree keeps its relative paths. Test assemblies and NUnit and adapter dependencies are separate inputs. App loads tools from Tools/ by explicit path into the context that holds it, so ProductLoadContext and DevModeLoadContext receive the same identities as the staged tree. Test support installs no resolver for product assemblies.

Test projects

Test projects are next to their production owners:

src/DBTools.App/Tests/DBTools.App.{Pure,Local}.Tests.csproj
src/DBTools.Core/Tests/DBTools.Core.{Pure,Local}.Tests.csproj
src/DBTools.Presentation/Tests/DBTools.Presentation.{Pure,Local}.Tests.csproj
src/DBTools.Sandbox/Tests/DBTools.Sandbox.Pure.Tests.csproj
src/Tools/<Category>/<Tool>/Tests/DBTools.<Tool>.{Pure,Local}.Tests.csproj
testing/DBTools.Build.Tests/                  build and distribution contracts (Linux)
testing/DBTools.Distribution.Tests/           portable archive contracts (Linux)
testing/DBTools.Distribution.Windows.Tests/   DIST suite
testing/RevitTestModels/                      test models by year and tool

An owner has both a .Pure.Tests and a .Local.Tests project only when both kinds of test exist.

  • Pure projects list their source files explicitly and reference their normal production owners. Shared props give every Pure project $(DBT_PureRevitYear) (2026) and static graph restore, and pass that year on owner references, so a plain dotnet build or dotnet test of one project needs no properties. Revit is compile-only in Pure tests: a test must not load Revit-typed members or scan owner types outside the loadable set.
  • .Local.Tests projects disable default compile items and include only Revit-hosted fixtures.
  • Presentation tests are under Presentation and belong to the Presentation projects, also when they test a tool's Presentation types. Presentation Pure links the Core test support it shares and references Core for the tool window, window runtime and logger window integration fixtures. Tests that need a real WPF window run where Windows is available.

Portable Pure projects

Core and the Super Girt Tool (SGT) define an optional $(DBT_PortableTargetFramework). Their *.Portable.Pure.Tests projects build against that framework and run on Linux; CI and Windows test.sh route them to Linux. To make a project portable:

  1. declare desktop and portable TargetFrameworks;
  2. condition DBT_RevitHostIdentity, UseWPF and the Presentation ProjectReference on the desktop framework, and keep Revit references under the desktop host identity condition;
  3. set DBT_UsesMergedAssemblies=false in portable consumers.

build/MSBuild/Portable.targets excludes App, Revit, Views, DesignTime and XAML inputs. Portable images use ordinary NuGet dependencies, have no content version and add no staged runtime files. Core uses an explicit list of source files for its portable build.

Test models

Revit-hosted projects declare RevitTestModel items relative to testing/RevitTestModels:

testing/RevitTestModels/
├── 2026/GM/gm_test_model.rvt
├── 2026/SGT/sgt_test_model.rvt
├── 2026/SGT/_LinkedModels/sgt_test_linked_model.rvt
├── 2026/Regression/realtest_model.rvt
├── 2027/...                                  (same layout)
├── GM/SharedParameters/shared_parameters.txt
└── VTC/vtc_import_layers.dxf

Model files and explicit non-RVT inputs keep their relative paths in the daemon stage. Revit-hosted fixtures find them under DBTOOLS_DAEMON_REVIT_MODELS_DIR; Pure fixtures use the repository root in DBT_TEST_REPO_ROOT. TestPathResolver reads the root on every call, so a job never sees the model root of a previous job. A fixture may open a temporary copy of a model, but the daemon owns the active document and the worker lifecycle. Models resolve only from these roots, not from a worker checkout or an %APPDATA% cache.

Test support

testing/TestSupport holds shared test infrastructure and doubles for true externals. Tool-specific doubles are under testing/TestSupport/<Tool> and are linked as source by the matching test projects; they are not a separate assembly.

  • Revit/RevitHost.cs initializes the year, the App runtime and the product Revit call gate before the test body, and supplies the real UIApplication through an ambient scope that does not carry API access across an await. It owns the scheduler unless a fixture holds a longer lease. A test that builds a QueuedRevitCallGate passes the fixture's Revit task; a borrowed task stays with its publisher. A QueuedModeless run scope from the App runtime schedules through that runtime's own task. Forced-queue tests call the real external-event handler synchronously to model a later API turn; one daemon NUnit callback contains no second native turn.
  • Wpf/WpfTestRuntimeBootstrap.cs registers pack URI support, installs the shared window owner, validates themes in the runtime assembly's contextual reflection scope, and releases only its own provider at teardown. It adds no Resolving handlers and does not force Presentation or HandyControl into the default context.
  • Logging/TestLoggingBridge.cs uses production logging when Revit provides it and a console and file host otherwise.

Revit-hosted fixtures release only their own runtime, Revit task, owner handle and window resources. Cleanup reports both the primary failure and any cleanup failure.
