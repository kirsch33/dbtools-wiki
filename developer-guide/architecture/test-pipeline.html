Test Pipeline

DBTools tests run through one of two routes:

  • ./test.sh resolves the selected projects, builds them, freezes their inputs and runs them locally or submits them to the dbtools-daemon fleet. It accepts the shared --tool, --scope, --year, --fixture and filter options and writes the receipts that --no-build and CI consume.
  • Plain dotnet test on an entry project in testing/Daemon/ uses the pinned daemon VSTest adapter (DbToolsDaemon.RevitTest.TestAdapter). MSBuild builds the selected assemblies, models, includes and per-year sources, and the adapter submits them in one request.

Use one route per invocation. Both read the relay URL from DBTOOLS_DAEMON_RELAY_URL; the daemon owns relay credentials, and neither route accepts or stores them.

Lanes

Lane Marker Where it runs
Pure plain [Test] Without Revit. Locally when possible; otherwise as a daemon PureSuite job on a hidden Windows desktop
Local [RevitLocal] Inside Revit on a daemon worker, for one selected year
DA [RevitDA] On the invoking host, as an HTTP client of APS Design Automation; never through the daemon
DIST The Windows distribution acceptance suite, always a daemon PureSuite job
BUILD Linux-native build and distribution contract suites

Local tests exercise the real ribbon, WPF and add-in lifecycle in Revit.

The DA lane builds the Revit 2026 Sentinel WorkItem test project and runs it with dotnet test. A run takes 5 to 12 minutes and spends APS cloud credits. It requires APS_CLIENT_ID and APS_CLIENT_SECRET and fails, rather than skips, when either is missing. APS_BUCKET selects the OSS bucket (default dbtools-tests). Run the network-free tests of that project with -f 'TestCategory!=RevitDA'. See APS Design Automation Sentinel.

test.sh

Synopsis

./test.sh <verb> [options]
Verb Action
test Build the selected tests and run or submit them
list List the statically discovered tests for the selection
validate-request Resolve selectors and projects without building or submitting
submit Build and submit a Local daemon job; rejects the pure and da scopes
rerun --request <id> Rerun the failures of an accepted daemon request from its submitted bytes, without building
build Run build.sh

Without --scope, the scope is pure. rerun replays the recorded request and rejects --scope. test.sh passes nothing through to dotnet: -- is rejected; use --filter, --fqn, --fixture or --compile-only. An unknown option is an error. Run ./test.sh --help for the complete option list.

Selection

Option Description
--tool TOOL[,TOOL] BUILD, APP, CORE, DA-SENTINEL, DIST, or a tool key such as GM
--scope SCOPE[,SCOPE] pure, local, da or all
-y, --year YEAR; --years 2026,2027 Revit years for hosted execution
--project PATH[,PATH] Repository-relative .csproj paths with forward slashes; narrows the tool and scope selection and cannot bypass it
--fixture NAME Fixture class; repeatable
-f, --filter FILTER VSTest filter for Pure tests; exact or prefix FQN form for daemon jobs
--fqn FQN Exact test name; repeatable; exclusive with --filter and --fixture
--changed-since REV Select test owners affected since a revision; unknown inputs select all

test.sh list --projects prints the sorted scope<TAB>project rows and is the source of truth for what a request selects. It evaluates project membership, explicit Compile Include, Exclude and Remove items, disabled default items, NUnit fixture attributes and the selected tool, scope and year. The same index resolves fixtures and exact FQNs. A fixture must resolve to one compiled owner class. An unknown fixture or project, an unreadable project or source file, a project the selected tool and scope cannot reach, or an explicit scope with no resolved project exits with status 2 before any build or submission.

An exact FullyQualifiedName=<FQN> filter becomes an exact daemon selector, and a prefix filter becomes a prefix selector. A hosted filter that cannot be mapped exits with status 2 instead of selecting the whole assembly.

Years

Pure requests have no year. They reject --year, --years, --keep-open and --isolation. Local requests take -y or --year; --scope all applies the year only to the hosted part. DA always builds Revit 2026: a DA-only request rejects other years, and a combined request must include 2026. A two-year Local selection makes one daemon request per year, each with its own product tree and report.

Execution

Pure routing

test.sh checks each selected Pure assembly for its .deps.json, .runtimeconfig.json and the output-local NUnit3.TestAdapter.dll, then routes it:

  • to the daemon if it is the DIST suite or a machine is pinned;
  • to the daemon if it targets Windows and the host is not Windows;
  • to the daemon if the host lacks Microsoft.WindowsDesktop.App; a missing other framework is an error;
  • otherwise to local VSTest.

Local projects, including the Linux BUILD and Distribution suites, run one after another; daemon submissions run concurrently. A local project that runs zero tests fails. With a filter expression, the run fails only when no selected project runs a test. Linux-native BUILD projects and *.Portable.Pure.Tests projects are skipped on Windows with a notice.

Inputs and receipts

For a selected lane and year, the MSBuild graph returns the test assembly, target framework, model items and product-tree includes in one pass. Before any submission, test.sh freezes the assemblies, runtime closure, product-tree includes, models and companions into the content-addressed test input cache, so a later build cannot change the submitted files. A normal exit removes the per-run directory.

--compile-only writes a receipt bound to the source identity, the selected projects, the graph inputs and the output hashes. --no-build verifies all of these and refuses stale or missing files. CI resolves the selectors once with ./test.sh list --projects, compiles each selected scope with --compile-only, transfers the receipt and the recorded input closure, and runs them with --no-build. The consumer never rebuilds. Linux BUILD and DIST jobs do not depend on the Windows transfer.

Results

The daemon terminal JSON is the result. A successful run must report a positive executed count; a report of zero tests fails. A distinctive nonzero daemon exit status is kept even when the terminal JSON is missing or malformed. Independent scopes in one request continue after a failure, but test.sh returns the first nonzero status and never reports a failed run as passed.

DIST

DIST is a closed surface. It requires --tool DIST alone, --scope pure, --filter FullyQualifiedName=DBTools.Distribution.Windows.Tests.WindowsAcceptanceTests.ValidatesTheStagedCandidate, --result-json PATH, and exactly one --include that names a validate-dist-<sha256>.zip archive (see PackageSandboxValidationInput in Build Pipeline). It rejects --fixture and --machine.

dotnet test with the daemon adapter

: "${DBTOOLS_DAEMON_RELAY_URL:?Set the daemon relay URL}"

# One hosted test for Revit 2026; the entry builds the per-year sources.
DBTOOLS_DAEMON_REVIT_YEARS=2026 dotnet test testing/Daemon/Hosted/GM.Hosted.Entry.csproj \
  --filter "FullyQualifiedName~FamilyDeepScanTests.GM_DeepScan_Smoke"

# Pure tests on a hidden daemon desktop.
dotnet test testing/Daemon/Pure/GM.Pure.Entry.csproj \
  --filter "FullyQualifiedName~UIStateCacheTests.SetAsync_WritesTheStableCamelCaseGoldenFormat"

testing/Daemon/Hosted/<Tool>.Hosted.Entry.csproj builds the Local tests of that owner for both years (Hosted2026.proj, Hosted2027.proj). testing/Daemon/Pure/<Tool>.Pure.Entry.csproj selects every DBTools.<Tool>.*Pure.Tests.csproj beside its owner. After the build, the entry writes dbtools-daemon.runsettings from Hosted.runsettings or Pure.runsettings with the literal sources, models and includes. The hosted settings default to years 2026,2027, isolated execution and a 30-minute timeout, and treat a run with no tests as an error.

Product staging

Each Local or hosted test for a year receives the same product tree that the installer uses:

product/<year>/
├── DBTools.addin
├── DBTools.dll
├── DBTools.Core.dll
├── DBTools.Presentation.dll
├── DBTools.HandyControl.dll
└── Tools/DBTools.<Tool>.dll

The tree keeps its relative paths. Test assemblies and NUnit and adapter dependencies are separate inputs. App loads tools from Tools/ by explicit path into the context that holds it, so ProductLoadContext and DevModeLoadContext receive the same identities as the staged tree. Test support installs no resolver for product assemblies.

Test projects

Test projects are next to their production owners:

src/DBTools.App/Tests/DBTools.App.{Pure,Local}.Tests.csproj
src/DBTools.Core/Tests/DBTools.Core.{Pure,Local}.Tests.csproj
src/DBTools.Sandbox/Tests/DBTools.Sandbox.Pure.Tests.csproj
src/Tools/<Category>/<Tool>/Tests/DBTools.<Tool>.{Pure,Local}.Tests.csproj
testing/DBTools.Build.Tests/                  build and distribution contracts (Linux)
testing/DBTools.Distribution.Tests/           portable archive contracts (Linux)
testing/DBTools.Distribution.Windows.Tests/   DIST suite
testing/RevitTestModels/                      test models by year and tool

A project has both a .Pure.Tests and a .Local.Tests project only when both kinds of test exist.

  • Pure projects list their source files explicitly and reference their normal production owners. Shared props give every Pure project $(DBT_PureRevitYear) (2026) and static graph restore, and pass that year on owner references, so a plain dotnet build or dotnet test of one project needs no properties. Revit is compile-only in Pure tests: a test must not load Revit-typed members or scan owner types outside the loadable set.
  • Local projects disable default compile items and include only hosted fixtures.
  • Presentation behavior tests are under Presentation; the Core Pure projects link the fixtures they can run without Revit. Tests that need a real WPF window run in a Windows-capable lane.

Portable Pure projects

Core and SGT define an optional $(DBT_PortableTargetFramework). Their *.Portable.Pure.Tests projects build against that framework and run on Linux; CI and Windows test.sh route them to Linux. To make a project portable:

  1. declare desktop and portable TargetFrameworks;
  2. condition DBT_RevitHostIdentity, UseWPF and the Presentation ProjectReference on the desktop framework, and keep Revit references under the desktop host identity condition;
  3. set DBT_UsesMergedAssemblies=false in portable consumers.

build/MSBuild/Portable.targets excludes App, Revit, Views, DesignTime and XAML inputs. Portable images use ordinary NuGet dependencies, have no content version and add no staged runtime files. Core uses an explicit list of source files for its portable build.

Test models

Hosted projects declare RevitTestModel items relative to testing/RevitTestModels:

testing/RevitTestModels/
├── 2026/GM/gm_test_model.rvt
├── 2026/SGT/sgt_test_model.rvt
├── 2026/SGT/_LinkedModels/sgt_test_linked_model.rvt
├── 2026/Regression/realtest_model.rvt
├── 2027/...                                  (same layout)
├── GM/SharedParameters/shared_parameters.txt
└── VTC/vtc_import_layers.dxf

Model files and explicit non-RVT inputs keep their relative paths in the daemon stage. Hosted fixtures find them under DBTOOLS_DAEMON_REVIT_MODELS_DIR; Pure fixtures use the repository root in DBT_TEST_REPO_ROOT. TestPathResolver reads the root on every call, so a hosted job never sees the model root of a previous job. A fixture may open a temporary copy of a model, but the daemon owns the active document and the worker lifecycle. Do not resolve models from a worker checkout or an %APPDATA% cache; there is no dbtools.testparams.json.

Test support

testing/TestSupport holds shared test infrastructure and doubles for true externals. Tool-specific doubles are under testing/TestSupport/<Tool> and are linked as source by the matching test projects; they are not a separate assembly.

  • Revit/RevitHost.cs initializes the year, the App runtime and the product Revit call gate before the test body, and supplies the real UIApplication through an ambient scope that does not carry API access across an await. It owns the scheduler unless a fixture holds a longer lease. Forced-queue tests call the real external-event handler synchronously to model a later API turn; one daemon NUnit callback contains no second native turn.
  • Wpf/WpfTestRuntimeBootstrap.cs registers pack URI support, installs the shared window owner, validates themes in the runtime assembly's contextual reflection scope, and releases only its own provider at teardown. It adds no Resolving handlers and does not force Presentation or HandyControl into the default context.
  • Logging/TestLoggingBridge.cs uses production logging when Revit provides it and a console and file host otherwise.

Hosted fixtures release only their own runtime, Revit task, owner handle and window resources. Cleanup reports both the primary failure and any cleanup failure.

Writing tests

When a test fails, investigate the production code first. Use test doubles only for true external boundaries such as Revit, the file system, the network and the clock; do not replace DBTools services or orchestration to make an assertion pass. Each behavior test asserts a real outcome. Keep a fixture in its owner project and lane. A fixture with several independent checks records each failure, attempts safe cleanup and reports them together.

The build and distribution suites read already-built product metadata and reject a stale source snapshot. Source, build and test changes alter the snapshot; documentation and transient artifacts do not.
