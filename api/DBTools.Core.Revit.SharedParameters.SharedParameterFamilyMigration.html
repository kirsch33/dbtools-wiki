Remarks

A loaded family keeps its own definition of a shared parameter. Its formulas, dimension labels and annotation labels refer to the parameter by GUID, so a project that replaces its own parameter leaves them on the old GUID. Deleting that parameter from the project also removes it from the labels of loaded families. Callers therefore run this migration before Migrate(Document, ParameterElement, ExternalDefinition, IReadOnlyCollection<Category>, SharedParameterUseHandling) or any delete of the old parameter.

Plan(Document, IReadOnlyList<SharedParameterFamilyTarget>) changes nothing. When the project has a parameter with the name of a target and another GUID, it opens every editable loadable family (Autodesk.Revit.DB.Document.EditFamily(Autodesk.Revit.DB.Family)) and closes it unsaved. It opens editable nested families recursively. It does not open a non-editable nested family; it checks its symbols and instances for the GUID. A carrier parameter can proceed when those elements do not show the GUID. A direct-use path refuses when any non-editable nested family could hide a label, formula or other use. A family parameter with the name and another GUID becomes a change. A use that is not a family parameter is refused: a label that shows the parameter directly (added through Edit Label in a tag or title block family) or a nested family that defines it. Revit 2027 names each such label with its detail group and formatting. Revit 2026 refuses every direct shared-parameter element because it cannot read labels. It describes an annotation-family element as an unread label, and does not call a model-family element an annotation label. Other refusals: a nested shared family, another data type, a type parameter in a category that the target binds as an instance parameter, an element whose old and new values differ, and an in-place or non-editable top-level family that defines the parameter or may define it. Revit does not open such a family; when its elements show the parameter and a project binding could explain that, the plan rebinds the project parameter without the family's category in a transaction that always rolls back and reads the elements again.

Migrate(Document, SharedParameterFamilyPlan) runs in one transaction group. For each family it records the old values of its types or elements, opens the family, replaces the parameter through a temporary family parameter (FamilyManager.ReplaceParameter(FamilyParameter, string, ForgeTypeId, bool), then the target definition) with the same group and instance or type kind, and checks in the family that every formula, value, dimension label, associated element parameter and, in Revit 2027, label follows. It also checks for a remaining family parameter, nested-family symbol or instance, or readable label that uses the old GUID. Project view-filter rules are handled by FindFilterRules(Document, ParameterElement) when the project parameter is deleted. An unused Autodesk.Revit.DB.SharedParameterElement may remain after replacement. In Revit 2026 it refuses an annotation family when that element remains because the family may use the GUID in a label that DB Tools cannot read. It reloads the family over the loaded one, writes each recorded value that the reload did not keep and reads every value back. Any refusal or failure rolls the group back; the project keeps its families and values.

Family files on disk do not change. A family loaded again from such a file brings the old GUID back.

The project must not be modifiable: Revit opens and reloads families only between transactions. Every target definition of the plan must come from the shared parameter file that is still open.
